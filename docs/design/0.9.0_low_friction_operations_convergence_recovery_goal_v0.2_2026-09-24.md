## 4. Publisher-specific GitHub HTTPS boundary

### 4.1 Positive trusted transport

The bounded helper supports only effective GitHub HTTPS fetch/push URLs:

```text
https://github.com/<owner>/<repo>.git
```

Both effective fetch and push URLs must:

- be GitHub HTTPS;
- resolve to the same owner/repo;
- equal the `--expected-repo` assertion;
- satisfy all existing single-destination, branch, ref, upstream, mirror, follow-tags, submodule, push-option, signing, hook, credential, askpass and final-recheck fences.

### 4.2 Effective URL, not literal config

Transport classification must use the **effective** fetch and push URLs after Git URL rewriting.

A literal HTTPS remote that Git rewrites via `insteadOf` or `pushInsteadOf` to SSH/custom transport is not a supported HTTPS positive.

Required behavior examples:

```text
literal HTTPS -> effective HTTPS
    => eligible for trusted publisher

literal HTTPS -> effective SSH through rewrite
    => fail closed before first remote/network Git operation

fetch effective HTTPS / push effective SSH
    => fail closed before first remote/network Git operation
```

### 4.3 SSH/custom fail-closed

These are not trusted-positive transports:

```text
git@github.com:<owner>/<repo>.git
ssh://git@github.com/<owner>/<repo>.git
other SSH/scp-style URL
custom remote helper/transport
```

The bounded publisher must reject them **before `ls-remote`, fetch, push, or any other remote/network Git command**.

The rejection may use a stable result such as:

```text
SSH_REMOTE_REQUIRES_ORDINARY_APPROVAL
UNSUPPORTED_TRANSPORT_REQUIRES_ORDINARY_APPROVAL
```

Exact wording is implementation detail. Semantics are fixed:

```text
no network publication through trusted helper
no injected executable execution
ordinary raw git push approval remains available
```

Do not rewrite the remote to HTTPS or configure SSH as fallback.
