## 5. C2 — execution context + mandatory source exact truth

### 5.1 唯一执行顺序

实现必须严格按下列顺序，任何一步失败均在 spawn 前终止：

```text
exact repo/worktree/branch/expected_commit
→ current HEAD exact match
→ exact mandatory source path
→ local exact blob read with lazy fetch disabled
→ only-if-missing isolated object fallback
→ content/digest binding
→ only then spawn model/Executor
```

task locator 至少冻结 exact repo identity、exact worktree path、exact branch、40-hex expected commit、mandatory repo-relative paths。

### 5.2 上下文检查

只检查与本 task 有关的身份，不要求整个 worktree clean：

```text
git rev-parse --show-toplevel
git rev-parse --git-common-dir
git branch --show-current
git rev-parse --verify HEAD
git worktree list --porcelain
git remote get-url origin
```

当前 root/worktree/branch/HEAD 必须与冻结 locator 一致。发现别的合法 worktree 或 unrelated dirty files 不阻断，也不自动切换/搬迁。

### 5.3 mandatory path 与 worktree 一致性

每个 mandatory path：

- 必须是 repo-relative、无 `..`、非绝对路径；
- worktree 中若存在，应是 regular file；
- 使用 `git --literal-pathspecs ls-files -v -z -- <path>` 拒绝 `assume-unchanged` / `skip-worktree`；
- 使用 `git check-attr -z filter ident working-tree-encoding -- <path>` 拒绝会改变 truth 的自定义 transform；
- 使用 `git diff --no-ext-diff --no-textconv --quiet <expected_commit> -- <path>` 判断 worktree 是否与 frozen commit 等价；
- mismatch 返回 `MANDATORY_SOURCE_WORKTREE_MISMATCH`。

这项检查只作用于 mandatory paths。source authority 永远是 exact commit blob；即使 worktree copy 合法，传给 Executor 的文本也从 commit object 取得。

### 5.4 local exact blob first

为避免 partial clone 的隐式 hydration，local path 使用隔离后的 Git 环境，并至少设置：

```text
GIT_NO_LAZY_FETCH=1
GIT_NO_REPLACE_OBJECTS=1
GIT_CONFIG_GLOBAL=<os.devnull>
GIT_CONFIG_NOSYSTEM=1
GIT_TERMINAL_PROMPT=0
```

其中 `GIT_CONFIG_GLOBAL` 的实际值必须使用当前平台的 `os.devnull`，不得把 Linux 的 `/dev/null` 硬编码到跨平台实现。继续拒绝危险进程 Git 环境、replace refs/grafts、危险 repo transport/config。

读取步骤：

```text
git cat-file -e <expected_commit>^{commit}
git ls-tree -z <expected_commit> -- <path>
git cat-file -e <blob_oid>
git cat-file -t <blob_oid>
git cat-file -s <blob_oid>
git cat-file -p <blob_oid>
```

只有 `cat-file -e <blob_oid>` 在 `GIT_NO_LAZY_FETCH=1` 下确认 object 缺失，才允许进入 fallback。其他错误不降级成 fallback。

### 5.5 isolated-object fallback

fallback 输入只接受：

```text
exact canonical repo identity
exact 40-hex expected_commit
exact repo-relative path
```

还必须：

- configured origin identity 与 expected repo 一致；
- 若存在多个 promisor remote，或 promisor owner 不能唯一证明为该 origin，直接失败；
- 临时 `GIT_OBJECT_DIRECTORY` 位于 `${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/readiness/objects/`；
- 原 object dir 只通过 `GIT_ALTERNATE_OBJECT_DIRECTORIES` 读取；
- 保持 `GIT_NO_REPLACE_OBJECTS=1`、global/system config isolation 和 non-interactive auth；
- fallback 内允许 promisor hydration，但 caller 不能提供 URL/refspec；
- 只读取前面已经解析出的 exact blob；
- fallback 前后比较 `FETCH_HEAD`、index、config、refs 与原 object store 内容摘要，必须完全不变；
- 临时 object directory 可在读取完成后删除。

最终 binding 对每个 source 至少保存：

```text
repo
expected_commit
path
blob_oid
size_bytes
sha256
text
read_mode=local|isolated_fallback
```

所有 mandatory source 都完成 binding 后才能调用 launcher 的 spawn 函数。负例必须直接观察 `codex/model child count=0` 与 `Executor child count=0`。

C2 不再承担 Host install/identity、authorization continuity、通用 instruction audit、branch recovery、worktree exchange 或 workflow state transition。

## 6. C3 — Bridge-managed instruction 写入前预算

实现只提供 writer-facing projected-byte helper。

每个真实 writer 在**任何该次调用的项目文件 mutation 前**：

1. 在内存生成更新后的 root `AGENTS.md`；
2. 读取当前支持的 `project_doc_max_bytes` 与 native instruction discovery 所需最小配置；
3. 计算 projected effective UTF-8 bytes；
4. 检查 Bridge-owned block cap；
5. PASS 后才允许写 templates/AGENTS 等文件；
6. overflow 或 config 无法证明时零 mutation。

消费者固定：

```text
Lite/core writer
Persistent Run writer
Overleaf writer
```

继续使用已批准 block caps：

```text
core <= 2048 UTF-8 bytes
persistent_run <= 4096 UTF-8 bytes
overleaf <= 2048 UTF-8 bytes
```

用户自有 instructions 超限只报告 limit、projected total、first risk source、需要释放的 bytes；不得自动删除、摘要、改写或提高 limit。

删除 `readiness.py` 中与 writer/source 两个窄能力无关的通用 instruction/runtime controller 语义。

## 7. C4 — Persistent local lifecycle/status

### 7.1 唯一运行对象

每个 run 最多：

```text
one exact tmux session
one run-scoped supervisor
one machine-local binding JSON
one child process
existing progress/report/latest
```

没有 app-server、Codex thread、Notifier、Clear Writing、daemon、watcher 或 database 前置条件。

### 7.2 launch identity 与 exact tmux identity

完整 `launch_id` 为下列 immutable fields 的 canonical JSON SHA-256：

```text
repo_realpath
run_key
goal_repo_relative_path
goal_sha256
working_directory_repo_relative_path
launch_argv
backend="tmux"
```

binding path 继续按 exact `repo_realpath + NUL + run_key` 确定性派生，因此 terminal/stale binding 不会因 launch 参数变化而被绕开。

session name 直接编码完整 64-hex identity：

```text
ai-bridge-pr-<full-64-hex-launch_id>
```

完整 `launch_id` 同时写入 binding JSON 与 supervisor argv `--launch-id <64-hex>`。不再额外创建 tmux user option 或第二份 session metadata。

session 检查只使用 exact target：

```text
tmux has-session -t =<session_name>
```

因此 session name、binding `launch_id` 与 supervisor argv 三者必须机械一致；session name 不等于由 binding full launch_id 确定性派生的 exact name 即 conflict，不接管。

### 7.3 原子启动顺序

1. 验证 Goal 与 launch_id；
2. 检查 binding/session truth table；
3. 原子写 binding，记录 immutable identity 与 `start_requested_at`；
4. `tmux new-session -d -s <session_name> -c <working_directory> <supervisor --launch-id <full-id> ...>`；
5. 若 `tmux new-session` 本身失败且 exact session 未创建，记录 create failure；不重试；
6. supervisor 启动后再次核对 binding full launch_id 与由它派生的 exact session name；
7. supervisor `Popen(child)` 成功后原子写 `child_started_at`、`child_pid`；
8. supervisor 仅在真实 `child.wait()` 返回后写 `child_exit_observed_at`、`exit_code`；
9. supervisor 退出。

任一步中断都不自动执行第二次 launch。

### 7.4 start/status truth table

| binding | exact session | `start` | `status` |
|---|---|---|---|
| none | none | NEW_START | `NOT_STARTED` |
| compatible nonterminal | exact full-hash session active | RETURN_EXISTING | `STARTING` 或 `RUNNING` |
| nonterminal | missing | NO_RELAUNCH | `UNKNOWN/UNAVAILABLE` |
| none/mismatch | session exists | NO_TAKEOVER | `CONFLICT` |
| terminal | session missing | `ALREADY_TERMINAL` | 只读 terminal facts |
| terminal | session exists | NO_START | `CONFLICT` |

同一 run key 不自动再跑。再次运行需要新的明确 run identity / run key 和新的任务决定。

partial start、supervisor loss、PID 是否存在、tmux 是否消失都不能生成 terminal fact。exit code 只来自 supervisor 的 `child.wait()` observation。

项目原生 progress file 缺失或不可读时 status 显示 `UNKNOWN`，不影响 child。

## 8. C5 — one-shot Clear Writing automatic notification expression

### 8.1 调用位置

只有 existing automatic notification owner 已经决定“这一封应发送”之后，才进入 expression adapter：

```text
existing automatic owner
→ immutable facts / validated 0.10 brief
→ one fresh codex exec --ephemeral
→ mechanical fidelity
→ normal text or deterministic fallback
→ existing Notifier transport
```

manual `ai-bridge notifier send` 与 `send-test` 不经过 adapter，保持 0.10 兼容。

### 8.2 production plugin identity

每次 normal path 在模型启动前，用当前 selected `CODEX_HOME` 的正式 CLI 查询 installed plugin identity（优先 `codex plugin list --json`）。必须唯一确认：

```text
pluginId=writing-style@yuukias-ai-skills
installed=true
enabled=true
version=<actual>
installedPath/source=<actual>
```

同时必须实际验证 installed root、其 `.codex-plugin/plugin.json` 与 inventory 的 plugin/version 一致，且 payload 真实存在；仅有 inventory 的 `installed/enabled` 标记不足以证明 skill 可消费。随后从该 installed root 解析两个 skill：

```text
writing-fidelity
chinese-prose
```

missing、disabled、ambiguous 或路径无法绑定时，不启动模型，直接 fallback。

### 8.3 唯一模型进程

neutral cwd 位于 Bridge state，不在 target repo instruction tree。唯一允许的模型命令形状为：

```text
codex exec --ephemeral --json --sandbox read-only --skip-git-repo-check -C <neutral-dir> -
```

prompt 通过 stdin，包含：

- immutable reader-facing facts；
- 明确要求 `$writing-fidelity` 与 `$chinese-prose`；
- 只允许改写表达，不得改变事实/结论强度；
- 不要求访问业务 repo、网络、MCP 或其他工具。

不得 `resume`，不得第二次 `codex exec`，不得在模型结果失败后“修一次”。

单次 adapter 设置 bounded timeout；Execution 实现默认 180 秒，可通过代码常量调整但不能由任务任意扩成长期 reader。timeout 后终止该进程并 fallback。

### 8.4 JSONL 与真实 skill 消费证明

只解析 `stdout` 的 JSONL；`stderr` 仅作诊断，不能冒充 event stream。

normal success 必须同时满足：

- process exit code = 0；
- exactly one `thread.started`；
- exactly one `turn.started`（产品上限仍为 `<=1`，正常成功要求 1）；
- exactly one matching `turn.completed`；
- 没有 `turn.failed` / terminal `error`；
- 有一个 final agent message；
- 两个 installed production skill 均有 runtime consumption evidence。

skill consumption evidence 只接受当前 Codex 正式可观察面之一：

1. first-party structured skill invocation event，能够绑定 skill name/path/plugin identity；或
2. JSONL `command_execution` 明确读取两个 exact installed `SKILL.md`，解析后的真实路径均位于前一步绑定的 installed `writing-style` root。

历史 055 smoke 已证明第二种 observable shape 可出现；本候选仍必须在 C5 重新证明。模型自述“我用了 skill”、源码文件存在、fake app-server fixture 均不算证据。

若当前 final runtime 不再暴露上述任一可验证消费证据，normal expression 视为不可证明，立即 fallback；不得恢复 app-server discovery。

### 8.5 机械保真

模型无权修改 recipient/provider/dedupe/task routing；这些 transport/identity 字段从原 immutable facts/validated brief 直接传给现有 Notifier，不从模型输出反解析。

reader text 发送前至少检查：

- required exact literals 全部仍在；
- protected 数字/比例/日期/时间没有增删改；
- `UNKNOWN` 不得被替换为估计；
- blocked/failed/pending/terminal 等极性不被升级；
- runtime-only facts 不得出现 Goal PASS / READY / RELEASE_READY 等语义完成主张；
- 路径、版本、task/run identity 等标为 reader-required 的 token 保持 exact。

可采用 adapter-local protected-values 结构，但不得升级成跨 workflow event schema。检查失败直接 fallback。

### 8.6 fallback 与 transport

以下任一失败都 0 模型重试：

```text
plugin/skill identity unavailable
codex exec spawn/timeout/nonzero
JSONL invalid
turn count invalid
skill consumption unproven
final message absent
fidelity failure
```

fallback 是确定性短中文，只使用 immutable facts；仍调用现有 Notifier transport。

真实 Gmail send 若失败，只记录 transport failure；不改变业务任务/运行状态、不杀 primary、不再次调用模型。

## 9. Capability Gate Matrix

所有 release-critical Gate 必须由同一 final candidate SHA 直接通过。测试、schema 或 helper 单测只作开发回归，不替代下列 normal entry。

## 10. Gate 顺序、候选身份与预算

固定顺序：

```text
cheap deterministic regression
→ C1
→ C2
→ C3
→ C4
→ freeze one final candidate SHA
→ C5 one real writing-style run
→ full tests / hosted CI / docs / installed identity
```

开发期可以反复使用确定性回归，但 final Gate 证据不跨 SHA 拼接。C5 开始后若生产代码、模板、Host rules、CLI、version 或 Gate 标准变化，旧 C5 失效并必须重新进入 pre-final Critic；不得自行再消费第二次模型/Gmail预算。

C1–C4 不需要付费模型或真实 Gmail。C5 final normal path预算固定为：

```text
real codex exec model invocations: max 1, retry 0
real Gmail sends: max 1, retry 0
recipient/account/provider/purpose: must be explicitly user-authorized before run
Codex executable/version/CODEX_HOME and the model identity used for this one run: record before execution and include in the authorization/evidence boundary
private data: none by default; use only public-safe/minimal canonical facts unless user separately authorizes otherwise
```

本 Plan 不授予上述 C5 external effects。Execution implementation 可以在未获授权时完成 C5 deterministic/fallback tests，但必须在真实 C5 Gate 前停下并报告所需 exact authorization。

## 12. 权限、外部效果与恢复

### 12.1 future approved handoff 可覆盖的普通实现范围

execution-ready Critic PASS 后，只有用户实际发送其生成的短 handoff，才可授权：

- 从 approved package commit 创建 exact branch `work/bridge-core--product-scope-reset`；
- 在该 branch 修改本仓库已冻结 scope 的产品代码、templates、rules、tests、docs；
- 普通 build/test/lint/本地 fixture；
- C1–C4 的无破坏 normal-entry Gate；
- task-owned `git add/commit`；
- 若 handoff 明确包含，向同一 GitHub repo 的 exact implementation branch 做 ordinary non-force push，并运行 ordinary CI；
- 只读公共依赖/官方文档/同一 repo 网络读取。

这不授权任何 `release` ref movement 或 force/destructive 操作。

### 12.2 必须在发生前另获用户明确授权

本 package、Planner、Critic 均不能代签：

- C5 的真实 `codex exec` 模型消费；
- C5 的真实 Gmail provider/account/App Password/recipient/purpose；
- 任何 private data 进入模型或邮件；
- 新 provider、付费 API、额外模型调用；
- 超出 max 1 model + max 1 Gmail 的重试；
- formal `release` movement；
- force/destructive Git、remote/upstream 改写；
- deployment、scheduler allocation 或其他 frozen Gate 外 external mutation。

App Password 只能由已有安全配置读取，不打印、不提交、不进入模型 prompt。

如果这些授权未到，执行停在对应边界并保留已完成代码/测试；不得把 mock/dry-run 冒充 C5 PASS。
