## 1. 核心判断

当前 `69fe058...` **不能直接进入 G01–G14 最终批次和发布**。原因不是已有 A–D 四个能力包失效，而是 0.11.0 的 TODO 处置承诺与实际实现之间仍存在三个未收口区域：

1. **Persistent Run 主动进度/ETA 仍是 PARTIAL。** 当前代码已经有真实进度归一化、`latest/history`、ETA/UNKNOWN、停滞判断和可选邮件投影，但 `report_progress_file()` 只有被调用时才工作，没有任何保证约 60 分钟主动报告的周期调用 owner，也没有把进度主动投递到原 Codex thread。更严重的是当前 `_delivery_decision()` 对任何 fraction 变化立即投递，会绕过普通限频；同时 cadence 与 `latest.json` 的上一观察时刻比较，如果生产者频繁调用 reporter，反而可能一直达不到 60 分钟间隔，造成周期投递饥饿。
2. **低打扰只读 Git 与 wrapper audit 仍是 PARTIAL。** 当前 Host Policy 已有安全 GitHub CLI 列表、Slurm、`ps`、tmux、fetch 和 bounded publisher/sync 等入口，但 0.11 Proposal v0.2 明确保留的“剩余安全本地只读形状 + wrapper 价值审计”没有完整落地。当前全局规则仍没有正式直接放行一组已经证明不会触发可执行扩展的本地 Git 读取形状。
3. **Notifications 目前不是清晰的任务级产品合同。** SMTP transport、私密 rclone 同步和语义 owner 边界已经存在，但 SMTP 私密文件默认仍是项目局部 `.ai-bridge/private/notifier.env`；Persistent Run 只有单一 `delivery_mode=notifications`，没有把“运行中进度邮件”和“语义完成邮件”拆成两个独立任务选择；当前 operational-progress 邮件正文也没有直接承载完整 stage/count/fraction/ETA/basis/uncertainty/last-progress 字段。

因此，0.11.0 需要一次**小范围恢复实现**，然后重新冻结最终源码候选；不能把当前单元测试、CI 绿灯、本机 JSON 或邮件发送函数存在本身当作用户能力完成。

## 4. Persistent Run：当前实现到底缺什么

### 4.1 已经做对的部分

当前 `normalize_progress_evidence()` 已经做到：

- stage
- progress since previous
- completed / total / fraction（分母真实且合法时）
- ETA / expected finish
- ETA basis
- ETA uncertainty
- `UNKNOWN`
- normal / slow / stalled / blocked / complete / failed
- last real progress
- 不把 runtime 状态升级成 semantic completion

`report_progress_file()` 也已经持久化 `latest.json` 和有界 `history.jsonl`，reconnect 后不需要 attach tmux。

这些内容保留，不重写成另一套状态机。

### 4.2 当前实现的两个限频错误

当前 `_delivery_decision()` 有两项与原 0.9.0 设计冲突：

1. `fraction` 每次变化立即 `deliver/progress_changed`。如果训练每个 epoch、文件、样本都更新 fraction，普通进度会绕开 60 分钟 cadence，造成刷屏/刷邮件。
2. cadence 比较的是 `latest.json` 的上一**观察**时刻，而 `latest.json` 每次 reporter 调用都更新。若项目每 5 分钟调用一次 reporter，则每次都只看到 5 分钟差值，反而可能永远达不到 3600 秒，从而没有正常周期投递。

恢复方案不是降低 reporter 调用频率，而是把：

- **last observed snapshot**
- **last logically delivered snapshot/time**

分开。普通 count/fraction 变化只更新观察态；只有 start/resume、stage transition、stalled/blocked/failed/runtime completion、material ETA change 可以提前投递，其他活跃进展在距**上次实际逻辑投递**达到 report interval 时投递。

material ETA 继续严格使用 0.9.0 已冻结默认：

[
|Delta t_{	ext{finish}}| ge max(15	ext{ min}, 0.25	imes t_{	ext{prior remaining}})
]

known ↔ UNKNOWN 永远 material。默认 report interval 仍约 60 分钟；任务可给另一个有界值；没有任务特定理由不得默认低于 15 分钟。

## 5. Codex 原 thread 主动投递：现实研究结论

### 5.1 `thread/resume`

当前 0.160.1 协议明确：若 `threadId` 对应正在运行的 thread，app-server 会 **rejoin running thread**，可用 path 作一致性检查。这说明 8 月“只能把外部 thread 当冷历史恢复”的旧前提已经变化。

它解决的是**精确 thread 重新加入/读取**，不是单独的“插入一个用户可见进度消息”接口。

### 5.2 `thread/queue/add`：不采用为进度主路径

0.160.1 已有实验性 `thread/queue/add`，CLI 的 `codex queue` 也明确要求连接共享 app-server，避免另起 embedded server 对同一个 thread 写入。

但该接口的数据类型是 `UserInput`，并生成 queued user submission。因此把 Bridge 进度写进去会把系统进度伪装成用户输入，且之后启动 queue 项仍会产生 agent turn。它不符合本轮首选语义。

**结论：不作为 Persistent Run 进度投递主路径。**

### 5.3 `thread/inject_items`：最有价值的无模型候选，但目前不能直接宣称 PASS

0.160.1 与最新 main 都有非实验性 `thread/inject_items`，官方注释就是“在不启动 user turn 的情况下把 raw Responses API items 追加到 thread history”。核心实现：

- active turn 存在时，把注入项加入该 turn 的 input queue；
- 没有 active turn 时，把项写入持久 history；
- 官方测试证明可以注入 assistant/developer response item，且注入本身不会产生 Responses API 模型请求。

这非常接近所需的“无额外模型调用”路径。

但源码同时给出一个关键反证：当前 `ThreadHistoryBuilder::handle_response_item()` 对普通 raw response message 只处理特殊的 **user hook prompt**；普通 assistant/developer injected response item 不会自动物化成常规 `ThreadItem::AgentMessage`。TUI 对 raw response notification 也不是普通对话 transcript 的持久显示入口。官方测试证明的是“持久化/下一次模型可见”，**没有证明用户在原 Codex thread UI 中能立即看到该 assistant 注入项**。

因此本 Proposal 不把 `thread/inject_items` 当已验证产品能力。

### 5.4 `turn/start`：可行但有真实成本的 fallback

0.160.1 `turn/start` 可以：

- 在指定 thread 启动 turn；
- 也可能在已有 active turn 时进入 steering 语义；
- 接受 `toolOutput`，可避免把 Bridge 进度伪装成用户文字；
- 必然进入模型 turn，产生 token/费用、生成新的 assistant output，并把相应内容纳入 thread context。

因此如果无模型的 UI-visible 路径最终探针失败，唯一目前有现实把握的官方方向是：

- **只在 exact thread idle 时**启动一个受限“进度渲染 turn”；
- 输入使用固定 Bridge progress tool-output / context，不使用伪造 user message；
- 只让模型把已经冻结的 normalized snapshot 渲染成简短进度文本，不允许规划、改变任务、取消/重启/扩资源；
- active turn 时不 `turn/steer`，而是保留最新 pending snapshot，等 thread idle 后再送，避免与正在进行的 Codex turn 发生未定义并发；
- 记录每次额外 turn 的 token/耗时，作为用户可见成本；
- 不把这个 turn 视为第二个 Planner/Reviewer/Executor。

该 fallback **仍需真实 0.160.1 disposable-thread Gate**。若它不能稳定满足“进度可见且不引入任务行为”，则 0.11 的原 thread requirement 记 `UNSUPPORTED_WITH_EVIDENCE`，并阻止声称短期 TODO 已全部完成；邮件不得冒充替代。

### 5.5 生产选择规则

实现第一阶段只做两个有限探针，不跑最终 batch：

1. **P0-A 无模型探针**：对 disposable 0.160.1 thread 使用共享 app-server 的 `thread/inject_items` 注入一个 assistant-role progress snapshot。必须同时证明：
   - 原 thread UI 真实出现进度；
   - 没有模型网络请求/turn；
   - 不是 user message；
   - reconnect/resume 后仍一致；
   - active turn 边界没有多 writer/未定义行为。
2. 若 P0-A FAIL，才运行 **P0-B render-turn 探针**：idle thread 的 `turn/start` + bounded progress tool output；证明可见、只渲染、不做任务决策、成本可计量、active turn 时 fail/defer closed。

P0-A/P0-B 都在 Critic PASS + 用户另行执行授权之后才能运行。本 Proposal 本身不运行。

## 6. exact thread 身份与共享 app-server 边界

0.160.1 会向 Codex 启动的 shell/exec 命令注入 `CODEX_THREAD_ID`。这是比“按标题猜 thread”可靠得多的运行时身份。

0.11 恢复实现应：

1. 长任务从 Codex 原 thread 启动时，在任务启动边界捕获 `CODEX_THREAD_ID`；
2. 与 `task_key`、`run_locator`、repo/Goal source hash 一起写入**机器本地 Persistent Run observation binding**；repo 文本不能自行指定任意别的 thread；
3. reporter 后续只向这个 exact thread 投递；
4. reconnect 时仍从本地 run binding 恢复 exact thread；
5. 若 run 是从 Codex 外部启动、没有可信 thread identity，则不得按目录/标题模糊猜测；该 run 的 Codex-thread 投递能力明确不可用，除非用户/正常入口后来提供受信 exact binding。

连接目标必须是**拥有/共享该 thread 的官方 app-server 路径**。不能为了投递启动另一个 embedded app-server 并对同一 live rollout 竞争写入。官方 `codex queue` 自己也显式避免“本地 daemon 已存在却从 embedded server queue”的多 writer 形状；Bridge 应复用相同安全原则。

## 7. 谁拥有周期 tick

`report_interval=3600` 只是投递判定参数，绝不等于“每小时一定有人调用 reporter”。周期 tick 必须有明确 owner。

### 7.1 统一原则

**run/process lifetime owner 同时拥有 reporter tick lifetime。**

Bridge 只提供一个确定性的 Persistent Run reporter loop / tick primitive；它：

- 读取同一个 project-native progress source；
- 调用现有 normalization + delivery decision；
- 不决定任务下一步；
- 不启动新资源、不取消、不扩 scope；
- 不作为机器常驻 daemon；
- 与 exact run/task/thread binding 一起启动；
- run 终止或 owner lifecycle 结束时自然退出；
- 无法证明 owner 时 fail closed，不偷偷常驻。

### 7.2 三种拓扑

| 运行拓扑 | 周期 tick owner | 约束 |
|---|---|---|
| terminal/tmux-owned orchestrator | 同一个 canonical tmux run/orchestrator 内的轻量 reporter 子进程或项目已有 heartbeat hook | tmux/run 结束则 reporter 同时结束；不另建全局 watcher |
| scheduler-owned job | scheduler job script/已有调度器生命周期内启动 reporter，或项目 heartbeat/checkpoint 直接调用 one-shot reporter | Bridge 不为 scheduler 再套 tmux；job 完成/失败即停止 reporter |
| already-detached service/job | 现有 service/job owner 的生命周期 hook/sidecar 调用 reporter | 不创建新的 system service；若现有 owner 无法提供 tick，则 proactive reporting 不能报 PASS |

项目已有 heartbeat/checkpoint **可以**负责“事件触发的立即报告”，但若它不能保证在长阶段至少按 report interval 调 reporter，就还需要上述 lifecycle-bound reporter loop。

为了及时观察 stage/stall/ETA material change，loop 可以以轻量本地观察频率读取 progress source；**观察频率与用户报告频率分离**。正常进度仍只约 60 分钟投递，不因每次观察或每个 epoch/file/sample 改变而通知。

## 8. Notifications：恢复为清晰的可选能力

### 8.1 机器级私密 SMTP owner

当前已有的 `AI_BRIDGE_PRIVATE_RCLONE_SOURCE` + `ai-bridge private sync --profile notifier` 已经解决“用户无需在 Git 写 secret”和“同步时不回显 secret”，但默认 target 是每个项目各自的 `.ai-bridge/private/notifier.env`。

这只能算“一处远端 secret 来源，可复制到多个项目”，还不是“同一机器一处配置，多项目直接消费”。

最小恢复：

- 新增机器级 canonical private profile：`${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/private/notifier.env`
- `private sync --profile notifier` 默认/明确 machine scope 将同一个 rclone source 拉到机器级 0600 文件
- 保留项目 `.ai-bridge/private/notifier.env` 作为**可选项目覆盖/向后兼容**，不是每项目必填
- 合并优先级：机器级默认 < 项目局部覆盖 < 当前 process env
- SMTP user/password/from/default to/subject prefix 都可以来自机器级 profile
- 不新建云服务，不把 secret 写 Git，不回显 password

这使一台机器配置一次即可供多个 Bridge 项目使用。

### 8.2 两个完全独立的任务选择

现有 Goal / task / Persistent Run contract 增加两个显式枚举：

```text
Progress email: ENABLED | DISABLED
Semantic completion email: ENABLED | DISABLED
```

默认都为 `DISABLED`。缺字段也按 `DISABLED`，不能因为“Notifications 已安装”或 SMTP profile 存在而产生新外部邮件。

- `Progress email=ENABLED` 只授权运行中 operational progress 邮件。
- `Semantic completion email=ENABLED` 只允许有语义 completion authority 的当前 Planner/Reviewer/Critic/Final Critic 在真正满足 positive completion criteria 后发终态邮件。
- 两者互不推导。

应复用 0.11 已有 mandatory-source/task binding：reporter 消费**当前已绑定的 frozen Goal/contract**读取 task intent，不新建授权数据库或独立 task state machine。机器 SMTP profile 只是 transport readiness，不是任务授权。

### 8.3 运行中邮件正文

当且仅当 progress email 启用时，`operational_progress` brief 直接包含并渲染：

- current stage
- runtime status
- completed / total / fraction（真实分母时）
- ETA / expected finish
- ETA basis
- ETA uncertainty
- last real progress
- progress since previous report

无可靠 ETA 时正文必须直接写“预计完成时间未知”，而不是只给 `latest.json` 路径。

### 8.4 终态语义 owner 保持不变

runtime `complete`、PID 退出、tmux 消失、heartbeat/checkpoint 都只属于运行层。

Persistent Run reporter 可以立即发“runtime completion observed”进度/运行事件，但不能生成 `PASS`、`READY`、`RELEASE_READY` 或“Goal 完成”。

真正语义完成邮件仍只由现有具有 positive-completion 判定权的 Planner / Reviewer / Critic / Final Critic 产生；Notifier 只验证 schema、确定性渲染、去重和发送。

## 9. 剩余 Host Policy / wrapper 收口

### 9.1 只读 Git

当前 Host Policy 没有完成原 TODO 中所有候选 Git 读取形状。0.11 不应为了“关 TODO”新建 read wrapper。

实施时只把**真实命令形状可证明没有可执行扩展/跨 repo/secret 风险**的原生命令加入规则候选，例如：

- exact `git rev-parse` 身份读取
- `git branch --show-current`
- `git worktree list --porcelain`
- bounded `git ls-files`
- `git remote get-url origin`
- 经过真实当前 Codex `execpolicy check` 与恶意 repo config 反例验证的 canonical `git status` 形状

`diff/log/show` 只有在命令同时关闭 pager、external diff、textconv 等执行面，并且当前 execpolicy 能保证 suffix 不重新打开危险路径时才直接 allow；否则维持普通 approval。远端 `ls-remote` 仍涉及 transport/credential/helper，不能因为“读”就 generic allow。

关闭这个 TODO 的成功标准不是“所有候选字符串都 allow”，而是：

- 常用安全读取有稳定低打扰入口；
- 不能安全证明的邻近命令明确保持 gated；
- 没有新增每命令一个 wrapper。

### 9.2 `plugin-replay` wrapper 价值审计

本轮重新查到**当前真实消费者**，不是历史惯性：

- AI_Skills `automation/reviewed_handoff/prompts/CODEX_EXECUTOR.md` 仍明确消费 `ai-bridge plugin-replay`
- AI Skills maintainer skill 在需要 production evidence 时仍使用该入口
- 2026-10-02/03 的 workflow-core / clear-writing / HPC tracking evidence 有真实 `ai-bridge plugin-replay` receipts

它的独特边界仍是：

> 对当前已经安装的 production plugin，在 fresh unattended Codex child 中处理显式 local/private input，保持 Bridge 的 staging / write isolation / evidence 边界，并避免放宽 generic raw `codex exec`。

官方 Codex 的普通 plugin 安装/fresh session 不能单独替代这组 unattended + private-input + write-isolation + machine evidence 合同。

因此本 Proposal 的审计结果是 **KEEP_NARROW**，但同时继续禁止把它当通用“fresh Reviewer”或 Presentation/UI artifact review transport。若未来官方成熟入口完整覆盖上述独特边界，再另做兼容迁移；0.11 不为了 TODO 数量删除当前真实消费者。

## 12. Capability Gate 恢复策略

0.11 已批准的 G01–G14 不重编号。G01–G05、G07–G13 的能力定义不因本轮改变；本轮只恢复两个原本已经属于版本范围、但实现不足的 Gate 语义。

### G01–G05：保持不变

- G01 并行长期 worktree
- G02 受支持的双脏关联工作树恢复
- G03 partial clone mandatory blob 安全读取
- G04 mandatory control source 真消费
- G05 同名非 main 安全快进

### G06：恢复其原始“安全诊断低打扰”范围

G06 不再只看已有几条 Host Policy 是否存在，而要证明：

- 实际当前 Codex 下，最终选中的 safe native Git/GitHub inspection shapes 无多余审批；
- malicious pager/ext-diff/textconv/fsmonitor/transport/helper 邻近形状仍 gated/fail closed；
- 没有新增 read wrapper；
- `plugin-replay` KEEP_NARROW 有当前消费者证据，且不被误用于普通 artifact review。

这是原 0.9 low-friction + 0.11 residual wrapper audit 的恢复，不是新增产品方向。

### G07–G13：保持不变

有效规则预算、真实 fresh rule consumption、stale Host recovery、授权连续性、真实 refusal recovery、0.9/0.10 回归和 same-final-candidate identity 均照原合同执行。

### G14：恢复完整 Persistent Run 主动投递语义

G14 必须同时通过以下子项，不能只证明 `latest.json` 或 SMTP 函数存在：

**G14-A 周期 owner**  
一个真实长运行的 run owner 确实持续调用 reporter；在允许的加速验收 interval 内产生至少一个“无 stage/ETA 特殊事件、纯 cadence 到期”的主动报告。没有 caller = FAIL。

**G14-B truth/cadence**  
start/resume、meaningful stage transition、stalled/blocked/failed/runtime-complete、material ETA change 可提前；普通 fraction/count 变化不会每次投递；默认 60 分钟/15 分钟下限和 material ETA 公式由 deterministic regression 固定。

**G14-C 原 Codex thread**  
exact run 捕获 exact `CODEX_THREAD_ID`，报告主动出现在**原任务 thread**；不是新 thread、不是用户伪输入、不是 email 替代；reconnect 后一致。优先无模型 P0-A；若只能 P0-B，记录每个额外 model turn 的成本和 context effect，active turn 不 steer。

**G14-D Notifications 独立意图**  
四组合至少以 deterministic matrix 验证：
- progress email off / completion email off
- on / off
- off / on
- on / on

缺字段默认双 off。真实 SMTP 只需验证最小正面组合，不用发四组真实邮件。

**G14-E 邮件内容与 completion authority**  
progress 邮件直接含 stage/status/count/fraction/ETA/basis/uncertainty/last-progress，UNKNOWN 明写；runtime complete 不能伪造 semantic completion；真正终态邮件只接受现有 semantic owner。

任何一个子项缺失，`TODO_PERSISTENT_RUN_PROGRESS_ETA_REPORTING.md` 仍不得 CLOSED。

## 14. 最小最终验收预算

本节只是未来 Critic PASS 后的**上限设计**，本轮没有授权运行。

### Fresh Codex

目标：**最多 4 个 fresh Codex sessions** 完成最终正面/负面覆盖；只有 P0-A 无模型 route 失败且 P0-B 必须独立确认时，允许在 pre-final Critic 再批准后增加第 5 个，不得自动扩样本。

建议合并：

1. 一个 Persistent Run thread-delivery / reconnect / exact thread canary；
2. 两个并行 worktree task 可同时覆盖 G01 与相关 readiness；
3. 一个 authority/refusal/recovery normal-entry canary；
4. 必要的规则消费/Host recovery 与上述会话合并。

P0-A/P0-B 是实现前/开发期机制探针，不冒充 final unseen Gate；最终 C' 仍须有至少一个实际 thread-delivery 正例。

### 真实 GitHub

使用**一个明确授权的 disposable/测试仓库或测试分支集合**：

- read-only partial clone / HTTPS fetch/ls-remote 可重复；
- 最多 1 次普通 non-force positive publication effect；
- 不 force、不删 remote branch、不修改消费者仓库；
- G03/G05/G12 能合并就合并，不能为了“多证据”重复 push。

### 真实 SMTP

仅在用户明确授权 SMTP account/recipient 后：

- 最多 **2 封真实邮件**：1 封 operational progress，1 封 semantic completion；
- 其余 progress/completion intent 组合、UNKNOWN、dedupe、rate-limit 全用本地确定性 sender/fixture；
- 邮件内容必须用 C' 的最终 renderer；
- 不回显 SMTP 密码，不改变真实邮箱设置。

### 时间 cadence

live cadence canary 可使用任务合同明确允许的 **15 分钟**验收间隔来证明 ticker 与主动投递，不需要为了测试机械等待整整 60 分钟；默认 60 分钟及 15 分钟下限由确定性时钟回归证明。最终用户任务仍默认约 60 分钟。

## 15. 失败与恢复

- thread no-model 注入不在 UI 可见：P0-A FAIL，进入已预定义 P0-B；不改成邮件替代。
- P0-B model-turn 不能稳定保持纯渲染/idle-only：记录 `UNSUPPORTED_WITH_EVIDENCE`，0.11 不得声称 Persistent TODO closed，回 Planner/Critic。
- shared app-server / exact thread 不能安全连接：停止 thread delivery，不另启 embedded 多 writer。
- ticker owner 无法绑定 run lifecycle：对应 topology 不宣称 proactive reporting PASS。
- SMTP 不可用：记录 delivery failure，run 继续；除非当前任务把通知本身明确设为 required gate。
- progress source 不足：ETA=`UNKNOWN`，不生成假比例/ETA。
- semantic completion 未满足：即使 runtime complete，也不发 completion mail。
- Host safe-read shape 在当前 Codex execpolicy 或恶意 config probe 中不安全：保持 approval，不造 wrapper。
- 任一生产修改发生在 C' 冻结后：形成 C'' 并按影响重跑正式 Gate，不能跨 SHA 拼 PASS。

## 17. 为什么这不是过重设计

恢复实现不增加新 workflow、控制器或常驻服务。真正新增的只有三类原版本已经承诺的产品接缝：

1. **一个已有 Persistent Run reporter 的 lifecycle-bound tick + thread projection**，使“主动”真正发生；
2. **Notifier 的 task intent / machine private config / progress renderer**，使邮件可预测且不刷屏；
3. **原 Host Policy 的最后一轮安全 native read 审计**，不新增 read wrapper。

其余 0.11 已实现能力保持原样，0.9.x/0.10.0 能力只做回归。相比继续直接跑 G01–G14，这个恢复会增加一次有限开发轮次，但它阻止了更严重的错误：把“能手动查 JSON、能发邮件”冒充成用户已经确认的“原 Codex thread 主动周期进度/ETA”。

## 18. Critic 必须重点反证

独立 Critic 应至少攻击以下问题：

1. 当前官方 0.160.1 的 `thread/inject_items` 是否真的可能用户可见；本提案是否正确地没有把持久/model-visible 等同 UI-visible。

3. lifecycle-bound reporter loop 是否可以真正保证 cadence，而不变成常驻 daemon/controller。
4. last-observed / last-delivered 分离是否正确关闭当前 cadence starvation 与 fraction spam。
5. task-level progress/completion email 两开关 + machine private profile 是否足够，不需要授权数据库。
6. Host safe-read 候选是否仍可能通过 pager/ext-diff/textconv/fsmonitor/helper 执行代码；不安全形状应保持 gated，而不是为“关 TODO”强行 allow。
7. `plugin-replay KEEP_NARROW` 的当前 consumer evidence 是否足够；如果官方成熟能力已完全替代，应要求兼容迁移而不是历史保留。
8. Local Autonomous 的 Bridge closure 与 AI Skills `status: NEW` 是否被正确区分，没有虚报系统层 DONE。
9. 4 个 fresh Codex、1 个真实 GitHub 正面 push、2 封真实 SMTP 的上限是否足以覆盖真实不同失败模式且没有无限调优空间。
10. Program Run 是否始终完全排除。
