## 6. Phase 0：先确定 thread 投递机制

Phase 0 是开发机制探针，不是 final Gate，只能在 approved Kickoff 后运行。

### 6.1 当前运行身份

重新核 actual Codex version、CODEX_HOME、shared app-server daemon/remote endpoint、disposable thread exact id/status/path、实际 server version，以及 `thread/resume` / `thread/inject_items` / `turn/start` 支持。

官方 `send_message_to_user_async` 在 0.160.1 与研究时 current main 均为 `UnderDevelopment`、`default_enabled=false`、`DirectModelOnly`。只作研究参考；不启 feature flag，不冒充 Bridge 外部无模型 send API。

### 6.2 shared writer 只是必要条件，不是 atomic idle guarantee

只连接**拥有或共享 exact thread** 的官方 app-server 路径。优先复用当前 Codex local daemon / explicit remote session discovery；不得为 live thread 再启动 embedded app-server 与已有 owner 并发写 rollout。

若只能另起 embedded writer：`P0_WRITER_BINDING=UNSAFE_UNAVAILABLE`，停止 P0-A/P0-B，回 Planner/Critic。

但“所有请求经过同一个 app-server”**不等于**“delivery check + write 期间没有其他 client writer”。普通 `thread/read/status -> later inject/start` 只是一对分离请求，不能写成原子 idle-only 保证。

### 6.3 ER11-01：P0-A 必须先获得 atomic idle-only guard

已核 0.160.1 官方源码：

- `ThreadInjectItemsParams` 没有 expected-idle / fail-if-active 字段；
- `inject_client_response_items()` 请求真正执行时若已有 active turn，会把 item 加入 active turn input queue；
- `TurnStartParams` 没有 expected-idle 前置；
- `turn/start` 内部 `start_or_steer_turn()` 在已有 active turn 时可返回 `Steered`。

所以 v0.2 **禁止**使用“先 read idle，再发第二个 request”作为安全依据。P0-A 的 thread write 只有以下至少一项在**实际 target runtime**被证明时才允许：

**A. 官方原子接口**：当前实际 Codex/app-server 提供与同一 write request 绑定的 expected-idle / fail-if-active / compare-and-submit 语义；另一个 client 在并发窗口启动 turn 时，progress request 必须以“未写入”失败/DEFER，而不是排队进入 active input。

**B. 官方/现有运行时的排他 writer boundary**：exact thread 的**所有实际 writer**（TUI、remote/mobile/desktop client、queue/session command、Bridge client、其他 app-server client）在 check + delivery 整个临界区共同受一个可证明的排他 lease/lock/serialization primitive 约束；该 primitive 必须由这些 writer 都参与。仅有：
- 同一个 app-server；
- 同一个 Bridge connection；
- Bridge 进程自己的 mutex/file lock；
- “这个 disposable thread 理论上没人会操作”
都不构成 B。

Phase 0 先只读检查实际 protocol/server/runtime 是否具有 A 或 B。若都没有：

`P0_A=UNSUPPORTED_ATOMIC_IDLE_GUARD`

**不发送 inject request**，并且 P0-B 也不能运行，因为 P0-B 同样要求 atomic idle-only。

如果 A/B 有候选，必须先运行 **two-client race negative**：client 1 进入 delivery 的 idle-check/guard 临界过程，client 2 在人为放大的竞态窗口尝试启动 turn；随后 client 1 delivery 必须被原子拒绝/DEFER，且 progress 不进入 active context、不产生 steer。若 progress 进入 active turn、被模型消费或 client 2 不受该排他边界约束，route FAIL。

P0-A 的其他前置仍是 disposable exact thread、无真实任务/私有数据、shared writer 已核。只有 atomic guard 成立后，才向 exact idle thread 注入固定 assistant-role canonical progress item。

P0-A PASS 仍必须同时看到：

1. 原 task thread UI 自动出现 progress；
2. 无 `turn.started`、无 model network request、无新增 token usage；
3. 不是 user message；
4. exact thread/run/task binding 不变；
5. reconnect/resume 后仍可见且不重复；
6. two-client active-turn race 下只 fail/defer；
7. 无 second writer。

只有 atomic guard 已成立且 P0-A 仅因 method/UI/reconnect 不满足而失败，才可能进入 P0-B。

### 6.4 ER11-02：P0-B 同时需要 atomic idle guard + pre-model mechanical no-tool confinement

P0-B 不再因为“prompt 要求不要调用工具”而默认可运行。

独立核对 0.160.1 后，当前基线只证明 `turn/start` 有 sandbox/approval/environment/disabled-plugin 等部分字段；它**没有被本执行包证明**存在一个 same-existing-thread、仅对该 turn 生效、能在模型请求前清空全部 execution/external tool surface 的成熟机制。官方 `temporary_structured_request.rs` 之所以能安全做 structured request，是因为它创建**独立 ephemeral thread**，并显式关闭 shell/unified exec、web、plugins/apps、MCP、environment/dynamic tools 等；该模式不能直接替代“输出必须出现在原 exact thread”。

因此 Phase 0 对实际 runtime 的默认结论是：

`P0_B_ENABLED=NO_UNTIL_PROVEN`

只有以下条件**全部**成立才可以运行那个最多一次的 P0-B turn：

1. `6.3 的 atomic idle-only A/B 仍成立；不能 read-idle 后直接 `turn/start`。
2. actual runtime 有**受支持的 same-thread / exact-turn 机械隔离机制**，在请求进入模型前关闭所有执行型/外部能力。验证必须按实际工具表面 fail closed，至少覆盖 shell/unified exec/code execution、web/search、apps/plugins、MCP、environment/runtime workspace、dynamic tools、multi-agent/agent spawn、可产生外部 effect 的图像/连接器能力和权限升级工具；未知可执行工具存在即不满足。
3. 该隔离不能靠 prompt、`output_schema`、事后发现 tool call、只设 read-only sandbox 或“模型答应不调用”替代。
4. 不允许 `danger-full-access` 或 Host-wide `approval_policy=never`。如果机制需要临时 thread/turn settings，必须在请求前读取并保存 exact old settings，且变更要被证明只影响该 exact turn；若任何 setting 会 sticky 到 subsequent turns，必须有官方支持的精确 restore，并在模型 turn 后无论成功/失败都 restore + readback。restore 失败 -> 标记 thread unsafe、停止后续任务，不继续使用。
5. mechanical inspection 必须在模型请求前证明 effective tool surface 为空/仅含无副作用内部渲染所需能力；不能在 turn 完成后才推断“幸好没调用工具”。

若实际 runtime 仍是已核的 0.160.1 且没有额外官方 supported same-thread mechanism，则直接：

`P0_B=UNSUPPORTED_NO_SAME_THREAD_TOOL_CONFINEMENT`

**不启动 model turn**。

只有上述机械条件全部成立，且 P0-A 已按合法理由失败，才在同一 disposable exact idle thread最多一次 `turn/start`：使用固定 progress tool-output/application context，不伪 user input；model 只渲染 canonical snapshot，不估计 ETA/比例、不决定下一步；记录 token/耗时/context；reconnect 后 UI 一致。

### 6.5 `thread/queue/add` 不作主路

0.160.1 为实验性且输入是 `UserInput`。本包禁止用它把系统 progress 伪装成 user submission。

### 7.2 Bridge 启动 `codex exec`

当前 Lite/Reviewed child 需要 Persistent Run projection 时：

- 只从第一个唯一 `thread.started.thread_id` 取得 child thread；
- 不用 launcher ambient `CODEX_THREAD_ID` 冒充 child；
- raw JSONL 留机器本地 evidence；
- 非-Persistent task UX 不因抓 id 退化；
- missing/multiple/invalid event fail closed，不猜 thread。

### 7.3 machine-local binding

这是 observation binding，不是 auth DB。

## 8. observation 与 last logical delivery 分离

保留 `latest.json` / bounded history 作为 observation。另存最小 logical-delivery state：

- last delivered snapshot/time/reason
- last successful thread projection identity
- progress email result（若启用）

普通 count/fraction 只更新 observation。

Immediate：

- start/resume
- meaningful stage transition
- first stalled/blocked/failed/runtime completion
- material ETA

material ETA：

`abs(expected_finish_delta) >= max(15 minutes, 25% of prior remaining time)`

known ↔ UNKNOWN 永远 material。

普通 active progress 只有距**last delivered**达到 interval 才投递。默认 3600 秒；任务可给有理由的 bounded cadence；无任务理由不得低于 900 秒。

每 5 分钟 observation 不能把 60 分钟 cadence 永久饿死。

thread/email/local 使用同一个 canonical snapshot；email 失败不影响 thread/run，thread 失败不能自动用 email 冒充。

## 9. lifecycle-bound report loop

正常入口可为：

`ai-bridge persistent-run report-loop --target <repo> --goal <goal> --progress <source>`

语义固定：

- foreground；
- 不 daemonize；
- 不发现下一任务；
- 不改资源/scope；
- tick 只读 progress、normalize、decision、projection；
- runtime terminal 后最后报告并退出；
- SIGTERM/INT 正常清理。

### tmux owner

同一 canonical launch script 启 actual work + reporter child，记录 PID，trap 在 owner/work exit/failure/signal 时 kill/wait reporter。Reporter 不单独保持 tmux session。

### scheduler owner

job script/native orchestrator 持有 reporter child；job/cgroup + cleanup trap 收尾。已有 heartbeat 若保证 interval 调 one-shot reporter，可不用 loop。Bridge 不套 tmux。

### existing service owner

只有现有 supervisor 能管理 sidecar child 才支持；不为 Bridge 新建 system service。不能证明 cleanup -> 该 topology 不 claim proactive PASS。

Observation frequency 与用户 report cadence 分离。

## 10. ER11-03：Notification Intent、manual one-shot 与真实 semantic authority 分离

Frozen Goal/task 继续明确：

`Progress email: ENABLED | DISABLED`  
`Semantic completion email: ENABLED | DISABLED`

缺失/非法 -> automatic path DISABLED/no-send。SMTP profile存在绝不推导 task intent。

### 10.1 A — automatic / derived live send

以下属于 **automatic**：

- Persistent Run progress projection；
- `ai-bridge notifier once` / `run` 自动扫描；
- 当前或未来 workflow 在没有用户当场手敲 send 命令时触发的 semantic completion。

automatic path 必须走独立的内部 authorization mode（例如 `authorization_source=automatic`），不得 shell out 到 manual `notifier send` 来绕过检查。

映射：

- `operational_progress`、`operational_blocked`、现有 milestone/awaiting-human/非成功 terminal 等“不是成功语义完成”的自动邮件，要求当前 task frozen source 的 `Progress email=ENABLED`；
- 成功 semantic completion 自动邮件要求 `Semantic completion email=ENABLED` **并且** `10.3 的真实 semantic decision locator 验证通过。

`notifier once/run` 在 intent 缺失、source 无法 mandatory-bind、decision locator不合法时必须 no-send 并给明确 suppressed reason；不能仅验证 brief 中字符串。

Persistent Run progress JSON 中历史 `notification_authorized` / repo 自称 authorized 不再提供 live automatic authority。

### 10.2 B — current user explicit one-shot compatibility

保留现有人工正常入口：

`ai-bridge notifier send <brief>`  
`ai-bridge notifier send-test`

当前用户**亲自在终端执行**该 one-shot command，本身就是该次 SMTP effect 的 current authorization；不要求历史 Goal 为这一次人工 send 补 Progress/Semantic intent 字段。

为机械区分 automatic 与 manual：

- live CLI `send` / `send-test` 进入 `authorization_source=explicit_user_cli`；
- live manual path 必须确认是交互式当前用户终端调用，并拒绝已知 Bridge/Codex 自动执行上下文（包括 Bridge-managed executor guard / `CODEX_THREAD_ID` 等自动 agent 环境）；非交互/自动上下文返回 `EXPLICIT_USER_ONE_SHOT_REQUIRED`；
- dry-run/render 可非交互执行，因为没有外部 send effect；
- `once/run`、Persistent Run、Control/Reviewed automation 永远使用 automatic mode，不能借 manual flag/function；
- repo script/Codex Executor 调用 `ai-bridge notifier send` 不得因为命令名称叫 manual 就绕过 automatic contract。

该限制只区分 effect authority，不新增 auth DB/state machine，也不改变用户直接在普通终端输入原命令的语法。

### 10.3 C — automatic semantic completion 必须绑定真实 workflow decision artifact

`decision_authority: Critic/Reviewer/...` **只是展示字段，不是 authority**。Automatic semantic completion 必须先解析当前 task 的现有 workflow 类型，并验证真实、canonical decision locator。

**Reviewed Handoff**：只接受由 task_key 推导的既有 canonical paths，并复用当前 validators。最低同时要求：

- `automation/reviewed_handoff/tasks/<task_key>/CURRENT.json` task_key匹配；
- state=`AWAIT_HUMAN_DECISION`、`human_gate_reason=PASS`、`last_review_decision=PASS`；
- current `implementation_commit` 为非空精确 commit；
- latest `results/<task_key>/REVIEW_<round>.md` 通过现有 review validator，`decision=PASS`、task_key/round/implementation_commit 与 CURRENT一致；
- `results/<task_key>/FINAL_REPORT.md` 通过当前 final-report validator；
- 整个 Reviewed task validator没有 authority/state/binding错误。

**Control / Agent-Flow**：复用当前 `validate_task_state` / `validate_final_critic_artifact` 等既有 validator。最低同时要求：

- exact task_key / request_nonce / current review_target_id；
- terminal/human-gate state符合现有 Control contract；

**Lite 或未知 workflow**：没有现成 semantic owner decision artifact时，automatic “Goal complete” email **不支持**。用户仍可用 `10.2 explicit one-shot，或者先由已有合法 semantic owner/workflow产生其 canonical decision artifact；Notifier不得为 Lite 新造 Reviewer/state machine。

Automatic brief中的 `decision_authority` 必须与已验证 artifact的真实 owner一致，但单独改这个 JSON 字符串永远不能生成 authority。

Notifier只验证 locator与identity，然后 render/dedupe/send；不重新判断领域 positive completion。

## 14. Deterministic regression

### Persistent Run

- start/resume immediate
- stage immediate
- stalled/blocked/failed/runtime-complete immediate
- fraction 连续变化 < interval 全 suppress
- 每 5 分钟 observation，60 分钟基于 last-delivered 必须 cadence deliver
- denominator invalid 不造 fraction
- ETA known↔UNKNOWN immediate
- ETA 小变化 suppress / material threshold deliver
- 无理由 interval <900 fail/normalize；测试用 clock injection，不开放生产 escape
- no cancel/restart/resource expansion
- observation/history 与 delivery state 分离

### lifecycle

- owner start/tick/exit，reporter cleanup
- owner signal/failure cleanup
- runtime terminal loop自退
- no owner -> 不自建 daemon

### thread

- ambient ID 只用于 existing-thread launch；
- Bridge child 唯一 `thread.started`；
- ambient 与 child 冲突时 child event胜出；
- missing/multiple/invalid event fail；
- repo fake thread id无效；
- shared daemon存在时禁止 embedded second writer；
- reconnect same id；
- `send_message_to_user_async` 不进入 route；
- **atomic idle guard negative**：普通 status-read + later write 明确不被视为 guard；
- **two-client race**：client A 在 idle check/guard 临界点暂停，client B 启动 turn；A 的 inject/start 必须 fail/defer，且 active context无progress、无steer；
- 仅 Bridge-local mutex/file lock 不得让 two-client test假 PASS；
- P0-B mechanical confinement：在模型请求前证明 effective execution/external tool surface被清空；prompt/output_schema/read-only sandbox/事后 tool-call 检测都不能代替；
- 如临时 same-thread setting 会 sticky，保存/restore/readback 与 restore-failure stop 路径必须有 deterministic regression；
- 0.160.1 若无受支持 same-thread confinement，test 应得到 `UNSUPPORTED_NO_SAME_THREAD_TOOL_CONFINEMENT` 且 model request count=0。

### Notifications/private

- 四 intent 组合；
- missing fields -> automatic no-send；
- progress JSON self-auth无效；
- automatic `once/run` 在 intent缺失时no-send；
- fake repo brief只把 `decision_authority` 改成 Critic/Reviewer不能 automatic semantic completion；
- Reviewed genuine PASS locator与 stale/mismatched implementation negative；
- Control genuine Final Critic PASS locator与 stale request_nonce/review_target negative；

- **legacy explicit `notifier send`** 在真实交互式 current-user one-shot mode无需历史 intent；automation/non-TTY/Codex executor环境不能借该入口绕过；
- `send-test` 保持 explicit one-shot；
- existing milestone、blocked/awaiting-human renderer/dedupe仍兼容，但 automatic send要服从对应 progress intent；
