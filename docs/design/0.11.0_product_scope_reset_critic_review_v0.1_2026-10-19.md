## 1. 结论

`CRITIC_RESULT=REVISE`

方向判断基本正确：当前 0.11.0 确实已经从“补执行连续性缺口”演变成一个过度耦合的运行架构，不能再把 v0.8 当成接近完成的候选继续修。把 app-server reader、专用 Progress display thread、自动 reciprocal worktree exchange、第二套通用授权连续性协议、跨所有 workflow 的通知 intent/event ownership 从核心 release 中撤出，是正确的架构重置。

但 Proposal v0.1 还不能 PASS。原因不是“不够完善”，而是有四个会直接影响用户结果或安全恢复的设计缺口：

1. 它把用户已经明确提出的“一封自动通知邮件只调用一次 Clear Writing”从 0.11.0 静默延期了；这是删需求，不是简化实现。
2. 执行上下文/必读控制源的真值绑定仍没有冻结“精确提交内容 vs dirty worktree”的优先级，可能把当前 `require_clean=True` 的过重失败模式带进新实现，也可能反向信任未冻结的工作树字节。
3. 最小 Persistent Run 的 stale/partial-start/supervisor-loss 语义不足；按当前文字实现会存在重复启动或误报状态的空间。
4. 从 0.10 恢复到新候选的删减审计仍漏了几项真实生产改动，而且把“正好四个 Gate”写成复杂度硬边界；这会让 reset branch 留下旧通知扩张，或为了守 Gate 数量再次把不同能力硬塞到一起。

关闭这四项后，本提案不需要重新打开低摩擦、app-server 删除、自动 worktree exchange 删除或版本号等已经足够清楚的方向。

## 2. 当前 0.11.0 是否整体过度设计

结论：**是，且是产品范围、运行机制、故障面和发布耦合四层同时过度设计，不是只差最后一个 G14 修复。**

### 2.1 用户价值

正式 `0.10.0` 到 `da9f6d2b...` 共 47 个提交。实际新增/扩张的生产面包括：

- `readiness.py` 约 1200 行；
- 新 `reader_layer.py`；
- 新 `codex_progress_thread.py`；
- `persistent_run.py` 从约 500 行扩到约 1000 行；
- `notifier.py` 从约 500 行扩到约 900 行；
- Reviewed、Control、CLI、Host、Overleaf、private config 等多处同步扩张。

这些增量没有形成与复杂度同量级的独立用户能力。最明显的反证是：用户要的是“通知文本需要时自然中文化”，最终候选却需要证明 app-server thread topology、reader isolation、display injection、viewer concurrency、reconnect 等一整条内部机制。

### 2.2 运行机制

Final Scope Recovery 从较短的早期 Plan 演化到 v0.6–v0.8 接近两千行，并把工作树、授权、通知、Clear Writing、Persistent UI 和发布 Gate 绑到一个候选。当前 canary 没有证明“最后只差一个实现 bug”，而是证明 release-critical 设计依赖了当前 Codex 不提供的隔离/readback 前提。

OpenAI 当前官方文档明确把 `codex exec` 定位为脚本、管道和一次性非交互任务入口，并支持 `--ephemeral`、JSONL 和明确 sandbox/approval；而 app-server WebSocket transport 当前仍是实验能力，不支持生产 workload。对一次文本转换使用 `codex exec` 比自建 app-server reader 更接近平台自然边界。

### 2.3 故障面

旧路线增加了至少这些新的独立故障面：

- shared app-server 是否存在、版本是否匹配；
- WebSocket/JSON-RPC client transport；
- thread persistence / resume；
- reader thread instruction source；
- deprecated `multiAgentMode` readback；
- display injection / viewer concurrency；
- reader budget / plugin discovery；
- notification intent / emitter ownership；
- worktree exchange quiescence / transaction recovery。

其中任何一个失败都可能阻断整个 candidate freeze。这违反“表达层、显示层、通知层失败不得杀业务 run”的原始产品目标。

### 2.4 发布耦合

旧 G14 同时证明多个本应独立的能力。一个显示或表达表面的 failure 可以否掉低摩擦、上下文连续性和 managed writer budget 已经成立的 release。这种 Gate 耦合本身就是架构问题。

因此 Proposal 提出的“从产品能力重新切 scope，而不是继续 v0.8 recovery”是正确方向。

## 3. 四项核心能力的判断

### A. 低打扰 Host Policy：保留，方向正确

正式 0.10 已经有一批窄 allow；当前 main 新增的 safe Git reads 与 `sync-current-branch` 也有真实用户价值。

当前 `sync_current_branch` 已经具备：

- exact current branch assertion；
- clean worktree；
- exact same-name `origin` upstream；
- remote identity；
- transport/config/hook fence；
- local HEAD 必须是 remote HEAD ancestor；
- `--ff-only`；
- post-state OID equality。

这属于合适的“动态条件需要窄 helper”，而不是通用 Git controller。Codex rules 本身支持精确 prefix allow/prompt/forbidden 且更严格规则优先，因此继续优先使用 Host Policy 是正确选择。

### B. 执行上下文与必读控制源连续性：保留，但 Proposal 必须再冻结一层真值语义

这是 0.11.0 最有价值的能力之一，真实 incident 已经证明缺口。partial clone 下 isolated object reader 也确有必要，但它只能是 exact repo + exact commit + exact path 的 fallback。

当前 `read_control_file_isolated` 已经做了大量正确的安全工作：固定 40 位 commit、拒绝危险 Git env/config/replace refs/grafts、使用独立 `GIT_OBJECT_DIRECTORY`、校验 tree entry/blob/size、并验证受保护 Git state/object store 未改变。

问题在于当前 `preflight_reviewed_event` 仍要求整个 worktree clean，而且 `bind_repo_texts_isolated` 对所有源都走 isolated reader；Proposal 虽说“普通 clean worktree/HEAD-bound 内容优先”，但没有把 exact source truth 写死。这是本轮 blocker F02。

### C. Bridge-managed instruction 写入前预算：保留，方向正确

产品目标应收窄为：“Bridge 自己要写 root `AGENTS.md` 时，在写入前计算真实 projected chain；超限则原字节不动。”

这比当前 `readiness.py` 里的通用 instruction config/discovery/audit 产品轻得多。Proposal 已正确规定只服务 writer，不自动删改 user-owned instructions。应继续保留 Host/Persistent/Overleaf 三个真实 writer 的共同 preflight，而不是恢复成面向所有任务的 runtime subsystem。

### D. 本地 Persistent Run start/status：应留在 0.11.0，但必须补齐 stale-run 恢复边界

正式 0.10 已有 progress normalize/report/latest，但没有真正的 start/status lifecycle。补一个 run-scoped tmux supervisor 和 binding JSON 是独立用户能力：终端拥有的长任务可以断线存活并从 CLI 查状态。

这不是 daemon：supervisor 只与一条 run 同寿命，child 结束后退出；也不需要 watcher、数据库或 Codex thread。

因此 D 不应延期。但 Proposal 目前还没有定义“binding 与 tmux/child 不一致”的恢复语义，见 F03。

## 4. 删除旧机制的判断

以下删除决定 **PASS**：

- 删除 `reader_layer.py` 当前 app-server reader 实现；
- 删除 `codex_progress_thread.py`；
- 删除自建 WebSocket/JSON-RPC client；
- 删除 dedicated Progress display thread / shared app-server / viewer concurrency 作为 0.11 核心；
- 删除 `instructionSources=[]` 与 `multiAgentMode` readback 作为通知前提；
- 删除 production reciprocal worktree exchange；
- 删除通用 `bounded_effect_identity` / authorization continuity 第二层；
- 删除跨 Lite/Reviewed/Control/Persistent 强制三 intent/event owner 同步；
- 旧 G01–G14 与 18 journeys 不再作为新 release authority。

外部现实进一步支持这一路线：

- app-server WebSocket transport 当前官方仍标为实验且不支持生产 workload；
- 当前 Codex 源码已经把 `multiAgentMode` 标为 deprecated/ignored，实际 proactive multi-agent 与 reasoning effort 相关；
- Git 自身已有 worktree add/list/lock/move/remove/repair；`lock` 防 move/delete，但并不构成业务进程 quiescence lease，因此 Bridge 不应继续维护“看不到 active process 就自动 exchange”的伪安全路线。

这些删除不会削弱安全边界，反而减少 Bridge 自己承担的平台职责。

唯一例外是：**自动 Clear Writing 不能直接从 0.11.0 产品要求里删除，只能删除当前 app-server 实现。** 见 F01。

## 5. 通知与 Clear Writing

保留 0.10 notifier transport/dedupe/manual send 是正确的；把运行/语义 authority 留给各 workflow owner 也是正确的。

但是 Proposal v0.1 将 automatic Clear Writing 整体 `DEFER`，这一点不能接受。

当前用户已经把真实需求说得非常具体：自动邮件只需要“调用一次 Clear Writing”。这不是要求 app-server、Progress thread 或 event bus；恰恰相反，它要求把这项能力做薄。

AI_Skills 的既有 release evidence 已经证明正式 `writing-style@yuukias-ai-skills` 可以通过 fresh normal `codex exec` 加载 `writing-fidelity` 与 `chinese-prose` 并生成正常中文改写。OpenAI 当前官方文档也明确支持 `codex exec --ephemeral` 作为可管道的一次性非交互入口。

因此 0.11.0 应保留一个独立、很薄、业务非阻塞的 notification expression adapter：

```text
immutable canonical facts
→ 最多一次 fresh codex exec --ephemeral + writing-style
→ 机械保真检查
→ notifier 现有 transport
```

约束：

- 不创建 app-server client；
- 不创建 persistent reader/session；
- 不与 Persistent Run start/status 耦合；
- 不允许第二次模型重试；
- skill/model/transform/fidelity 失败立即 deterministic fallback；
- fallback 仍发送；
- expression/transport failure 不改变业务状态、不杀 primary process；
- 不跨 workflow 强制传播新 schema；只有实际需要自动通知的入口调用这个薄 adapter。

这是一项用户已经明确要求的 0.11 能力，不需要再次把产品偏好交回用户。

## 6. Persistent Run 最小模型

Proposal 的结构方向正确：

```text
run-scoped tmux
→ run-scoped supervisor
→ one child lifecycle
→ one binding JSON
→ existing progress/report/latest
→ start/status
```

它不构成 daemon/watcher/state machine，只要 supervisor 不拥有跨 run 调度、不自动复活任务、不轮询外部 workflow。

但必须冻结以下恢复规则，否则“幂等 start”会产生重复运行风险：

- binding 不存在 + tmux session 不存在：允许 new start；
- compatible binding + exact tmux session active：返回 existing run，不重新启动 child；
- binding 存在但 tmux session 不存在，且 binding 非 terminal：**不得自动 relaunch**；返回 typed stale/unavailable 状态，由显式新 run/resume 决策处理；
- tmux session 存在但 binding 不存在或 identity 不匹配：冲突，禁止接管；
- binding 已 terminal：status 只报告 terminal facts；同一 run key/Goal hash 的 `start` 不应静默创建第二次运行；
- start 在“写 binding / 建 tmux / supervisor 建 child”中途失败时，必须能区分未启动、启动状态未知和已启动，不能通过重试猜测；
- supervisor 意外退出而 child 生命周期无法证明时，status 返回 `UNKNOWN/UNAVAILABLE`，不得自动重启或把 tmux 缺失等同于 child 已终止；
- exit code 只有 supervisor 真实观察到 child terminal 才可写为 terminal fact。

这些规则不要求新增状态机；几个有限的 binding status 和 fail-closed 分支足够。

## 8. Capability Gate 判断

Proposal 的 C1–C4 都是不同真实能力，不是 schema 重复：

- C1 证明低摩擦和危险邻近边界；
- C2 证明正确位置与必读源真消费；
- C3 证明 managed write preflight；
- C4 证明本地长期运行/状态。

normal entry、正例、危险负例、should-not-change 和 same-candidate SHA 思路基本正确。旧 G14 reader canary 应只保留为旧路线反证，不迁移。

但 Proposal 把“release-critical capability gates = 4”写进复杂度硬边界不合理。Gate 数应由最终承诺的独立能力决定，Capability Gate Policy 明确反对机械固定数量。

由于 F01 要保留用户已要求的 one-shot Clear Writing 通知表达，v0.2 应增加一个独立而小的第五 Gate，而不是把它重新塞回 C4：

### 建议 C5

**Claim：** 当 writing-style 正常可用时，一份 immutable notification facts 只经一次 fresh `codex exec --ephemeral` 得到自然中文，机械检查保护事实；writing-style/model/fidelity 失败时同一 delivery 立即 fallback，业务不受影响。

必须证明：

- 正常路径确实实际加载正式 writing-style；
- 一次 logical delivery 最多一次模型调用；
- 数字、状态、`UNKNOWN`、路径、结论强度受机械检查；
- 模型/skill 不可用负例不会 suppress 通知或杀业务；
- 不创建 app-server/persistent reader；
- notifier 0.10 transport/manual compatibility 不回归。

这仍然比旧 G14 小一个数量级，而且没有跨能力耦合。

## 9. 复杂度预算

以下边界合理，应保留：

- 0 daemon；
- 0 database；
- 0 persistent Codex thread；
- 0 custom app-server client；
- 0 automatic worktree exchange；
- 每个 Persistent Run 最多一个 run-scoped supervisor 和一个 binding JSON。

代码 800–1200 行目标和 1500 行重新审查阈值也可以保留，但只能作为“过重触发器”，绝不能成为促使 Executor 压缩逻辑、隐藏 helper 或省掉错误处理的质量指标。

需要修改的是固定“4 个 release-critical Gate”：Gate 数跟随最终独立产品承诺，当前按本 review 应为五个。

总体路线正确：

- 保留历史 commits/docs/results；
- 新 implementation branch 从届时 current main 建立；

## 11. 版本号

保留 `0.11.0` 合理。

## 13. Blocking Findings

### BR11-RESET-R0-F01 — 明确的 Clear Writing 用户能力被静默延期

**对应问题：** Proposal §4、§8.5、§9 将 automatic Clear Writing 归入未来版本。

**证据：**

- 用户当前真实要求已经收敛为“自动邮件只调用一次 Clear Writing”；
- AI_Skills 已有 writing-style production smoke，fresh normal `codex exec` 能加载 `writing-fidelity` / `chinese-prose` 并产出自然中文；
- OpenAI 官方把 `codex exec --ephemeral` 定义为可用于脚本/管道的一次性非交互入口。

**为什么会失败：** 如果按 v0.1 发布，0.11 会通过“删掉复杂实现”同时删掉用户原本要求的结果，形成范围降级。

**最小关闭条件：**

- v0.2 将 one-shot Clear Writing notification expression 纳入 0.11；
- 明确与 Persistent/app-server 解耦；
- 最多一次 fresh `codex exec --ephemeral`；
- mechanical fidelity；
- immediate deterministic fallback；
- failure 不杀业务；
- 新增独立 C5 Gate；
- 不恢复旧 G14。

**Owner：** Planner / Bridge notification-expression adapter；writing-style 专业表达能力继续属于 AI_Skills writing-style。

### BR11-RESET-R0-F02 — 必读控制源的 exact source truth 未冻结

**对应问题：** Proposal §8.2/C2 的“clean worktree/HEAD-bound 内容优先”仍有歧义。

**证据：**

- 当前 `preflight_reviewed_event` 会要求整个 worktree clean；
- 当前 isolated reader 能绑定 exact 40 位 commit/path/blob；
- 原真实失败恰恰来自“必读源没读到内容却继续执行”。

**为什么会失败：** 新实现可能走两个错误极端之一：无关 dirty 文件导致整个任务被拒绝；或 dirty mandatory file 被当成 frozen source 消费。

**最小关闭条件：**

v0.2 明确：

1. task locator 绑定 exact expected commit/HEAD；
2. mandatory source 的 authority 是该 exact commit 的内容；
3. unrelated dirty worktree 不构成全局 blocker；
4. mandatory path 若工作树字节与 expected commit 不一致，不能静默当成 frozen source；
5. exact blob 本地存在时用普通 Git/object read；缺 blob 才进入 isolated object fallback；
6. fallback 固定 repo/commit/path，受保护 Git state/object store 零变化；
7. 任一必读源失败时 model/Executor child count = 0。

**Owner：** execution preflight。

### BR11-RESET-R0-F03 — Persistent Run 的 stale/partial-start 恢复语义不足

**对应问题：** Proposal §8.4/C4 只定义 happy-path idempotency。

**证据：**

当前 main 的 start/status/supervisor 已经出现 binding、tmux 和 child 三层事实；reset 后即使删除 app-server，这三层仍可能不一致。

**为什么会失败：** tmux 缺失、binding stale、supervisor 意外退出或启动中断时，如果 `start` 自动“恢复”，可能重复运行长任务；如果 `status` 推断 terminal，又可能报告假完成。

**最小关闭条件：**

v0.2 冻结一个无需新状态机的有限恢复表：

- no binding + no session → new start；
- compatible binding + exact active session → return existing；
- nonterminal binding + missing session → stale/unavailable，禁止自动 relaunch；
- session exists + missing/mismatched binding → conflict，禁止接管；
- terminal binding → status 只读 terminal facts，同 run key 不自动二次启动；
- partial start / unexpected supervisor loss → UNKNOWN/UNAVAILABLE，只有真实观察到 child exit 才写 exit code；
- C4 增加上述至少两个异常负例。

**Owner：** Persistent Run。

### BR11-RESET-R0-F04 — reset migration 审计仍有漏项，且 Gate 数被机械固定

**对应问题：** Proposal §7、§11、§12、§13。

**证据：**

release→audited main 除已列大模块外，还存在：

- `private.py` machine/project notifier profile 扩张；
- 新 `templates/notifier/DEFAULTS.json`；
- `overleaf.py` writer projection；
- root `AGENTS.md` 从约 538 行收敛到约 186 行；
- version / CI trigger / README / CHANGELOG surfaces。

**为什么会失败：**

- 未分类的通知配置可能在 reset 后残留旧三-intent 架构；
- 机械恢复 0.10 root AGENTS 会把已解决的 instruction budget 文档膨胀重新带回；
- 硬编码“4 Gates”会诱导把新增/恢复的独立能力再次塞进错误 Gate。

**最小关闭条件：**

- v0.2 在 KEEP/SIMPLIFY/REMOVE/DEFER 表中补齐上述 surfaces；
- `private.py` / notifier DEFAULTS 明确恢复 0.10 或给独立保留理由；
- `overleaf.py` writer projection 明确归 C3；
- root AGENTS 明确保留当前紧凑结构，不回滚为 0.10 长文；
- version/CI/README/CHANGELOG 定义为 final-scope 重建；
- 删除“Gate 数必须等于 4”的硬约束，按实际 capability 形成当前五个 Gate。

**Owner：** Planner reset migration design。
