# Bridge Kit 0.7.3 — Minimal Approval False-Positive Fix

Status: implementation contract for the next patch release. This document does not itself change installed Host Policy.

## Scope

0.7.3 is intentionally small. It addresses only approval false positives already reproduced in normal unattended work after 0.7.2:

1. host process inspection with `ps`;
2. repository synchronization with `git fetch --all --prune`.

Do not turn this patch into a general unattended-execution architecture. Do not add project-local Slurm job IDs, `srun` rules, `sbatch`/`salloc` policy, tmux orchestration wrappers, process-manager wrappers, new workflow state, or retry machinery unless a new reproduced blocker requires them.

`0.7.2` remains the Slurm read-only fix and must still be deployed to affected Codex identities.

## 1. Global Host Policy: allow `ps`

Direct `ps` is a process-reporting utility. It reads and displays process information; it does not signal, kill, renice, suspend, resume, or otherwise mutate processes.

For the trusted personal Codex development/HPC identities targeted by Bridge Kit, the usability benefit of avoiding repeated host-process inspection approvals outweighs the residual information-disclosure risk. Therefore 0.7.3 should preauthorize direct `ps` globally:

```starlark
prefix_rule(
    pattern = ["ps"],
    decision = "allow",
    justification = "Allows read-only host process inspection needed for unattended diagnostics; ps reports process state and does not mutate processes.",
)
```

This is an explicit tradeoff. Because an execpolicy `allow` rule auto-approves the matched command and may bypass the normal sandbox path, do not claim that unusual `ps` options will receive a second Auto-review decision. The accepted residual risk is broader process-information visibility, not process mutation.

Host AGENTS guidance should establish the normal form:

```text
ps -u "$USER" -o pid,ppid,stat,etime,cmd
```

and should say:

- prefer current-user inspection;
- use process listings to diagnose stale/background work;
- do not request environment-variable output or cross-user inspection unless the task explicitly requires it;
- `ps` evidence is diagnostic and must not become a mandatory blocker when stronger task state already exists (for example Slurm state, lock, heartbeat, stage-state, or tmux/session state).

Do not build `ai-bridge host processes` in 0.7.3. A wrapper is unnecessary unless later production evidence shows raw `ps` creates a real problem.

## 2. Global Host Policy: allow the reproduced Git synchronization form

The reproduced command is:

```text
git fetch --all --prune
```

It is a normal synchronization operation over already-configured remotes. It updates Git metadata/remote-tracking refs and prunes stale remote-tracking refs; it does not switch branches or rewrite the working tree.

0.7.3 should preauthorize this command shape:

```starlark
prefix_rule(
    pattern = ["git", "fetch", "--all", "--prune"],
    decision = "allow",
    justification = "Allows routine synchronization of configured remotes and pruning of stale remote-tracking refs for trusted development repositories.",
)
```

Keep the existing narrower `git fetch origin main` allow rule.

Do not replace these with blanket `pattern = ["git", "fetch"]` authorization. Generic fetch can accept arbitrary repositories/refspecs and is outside this patch.

The implementation must use real `codex execpolicy check` tests for the reproduced command and representative nearby Git forms. If current execpolicy prefix semantics cause an unacceptable concrete widening, report that evidence before inventing a wrapper; do not pre-emptively redesign the patch around hypothetical suffixes.

## 3. What stays on Auto-review

This patch does not change policy for:

- `sbatch`;
- `salloc`;
- `srun`;
- `scancel`;
- mutating `scontrol`;
- `kill`, `pkill`, `renice`;
- `setsid`;
- generic `bash` / `sh` / `zsh`;
- generic Python/script execution outside normal sandbox behavior;
- arbitrary `git fetch` URL/refspec forms;
- project-specific launchers or allocation ownership.

These remain under the existing sandbox/Auto-review behavior. Do not solve unreproduced problems in 0.7.3.

## 4. No project-local execpolicy in this round

Do not add a DII `.codex/rules` rule for a specific `srun --jobid=...` command. Interactive allocation IDs change between goals, and current production evidence did not show `srun` being wrongly blocked.

If a future command is repeatedly misclassified, handle that concrete failure then. Do not hard-code transient allocation IDs into reusable policy.

## 5. Repository AGENTS guidance

Project-local `AGENTS.md` remains useful for behavior routing even though it does not grant execpolicy permission.

For `Distributed_Imaging_Inference`, update AGENTS separately so unattended goals:

- use `ps -u "$USER" -o pid,ppid,stat,etime,cmd` as the normal host-process inspection form when needed;
- treat `ps` as diagnostic, not as a mandatory proof that no stale work exists;
- prefer stronger project state such as Slurm job state, persistent-session state, lock, heartbeat, stage-state and resume metadata;
- do not terminate an entire scientific goal merely because an optional process diagnostic is unavailable;
- do not invent a broader fallback such as `setsid`, `sudo`, new GPU allocation, or job cancellation merely because a diagnostic route failed;
- continue to obey the goal-specific resource contract in the current Goal/Plan.

Do not add project-local approval rules unless a concrete project-specific command is actually blocked and needs durable authorization.

## 6. Acceptance matrix

Must resolve to direct `allow` after installing 0.7.3:

- `ps -u testuser -o pid,ppid,stat,etime,cmd`;
- representative ordinary `ps` inspection forms;
- `git fetch --all --prune`;
- all existing 0.7.2 Slurm read-only cases;
- existing `git fetch origin main`.

Must remain gated / outside the new direct allow surface:

- `kill`, `pkill`, `renice`;
- `sbatch`, `salloc`, `srun`, `scancel` unless existing policy independently decides otherwise;
- mutating `scontrol`;
- arbitrary shell escalation;
- arbitrary Git fetch URL/refspec forms not matched by an existing explicit rule;
- destructive Git operations already gated by 0.7.2.

## 7. Production verification

Before release:

1. run repository tests;
2. run `ai-bridge host validate` with real Codex CLI;
3. install the candidate Host Policy on an affected remote Codex identity;
4. verify the previously rejected formatted `squeue` works after 0.7.2/0.7.3 deployment;
5. verify the previously rejected `ps -u ... -o ...` runs without Auto-review termination;
6. verify `git fetch --all --prune` runs without Auto-review termination;
7. use execpolicy checks, not live destructive actions, for negative mutation cases.

## 8. Release boundary

If the reproduced failures are fixed without regression, bump `0.7.2 -> 0.7.3` and update version constants, README, CHANGELOG, host validation and tests.

Success means exactly this: the known harmless `squeue`, `ps`, and routine Git synchronization operations that killed unattended work no longer do so after Bridge Kit is deployed, while unrelated resource allocation, process mutation, destructive Git and generic shell capabilities remain on the existing review path.
