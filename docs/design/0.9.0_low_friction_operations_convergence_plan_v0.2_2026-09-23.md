## 0. Planner response to the three Critic blockers

### Critic blocker 1 — GH read scope

**ACCEPT.**

v0.1 was too broad in proposing direct allow shapes for GitHub CLI commands whose positional arguments can target another repository, especially:

- `gh repo view [<repository>]`;
- `gh pr view [<number>|<url>|<branch>]`;
- `gh issue view {<number>|<url>}`;
- analogous direct `view` shapes whose positional selector can widen the read scope.

v0.2 removes all GitHub CLI `view` families from the global direct-allow proposal. No Bridge wrapper is added to replace them.

The retained GitHub CLI direct candidates are only no-positional status/list forms whose repository selector is a flag and is placed outside the allowed command shape by the explicit option terminator:

```text
gh auth status --
gh pr list --
gh pr status --
gh issue list --
gh issue status --
gh run list --
```

These remain **candidates pending real Phase-0 CLI + execpolicy checks**. If the installed `gh` does not accept the terminator in a no-positional invocation or any retained form can still select another repository after the matched prefix, that form stays on ordinary approval rather than receiving a wrapper.

### Critic blocker 2 — publish-current-branch exact effect

**ACCEPT.**

v0.2 keeps one bounded publisher and makes its pre-mutation contract materially stricter. It now requires:

- canonical current repository identity;
- exactly one effective fetch URL and one effective push destination;
- push and fetch identity equality with the current-user/task assertion;
- no multiple `pushurl`/URL fan-out;
- no `remote.origin.mirror=true`;
- no tag expansion from `push.followTags`;
- no recursive submodule push;
- no active effective pre-push hook through the trusted helper;
- equality assertions for the expected repo and branch that cannot choose the remote/refspec;
- a final current-branch/current-HEAD recheck before mutation;
- preservation of Reviewed watcher publication authority.

### Critic blocker 3 — Reviewed worktree frozen scope binding

**ACCEPT.**

v0.2 specifies exactly which existing task artifacts bind the effect:

- **exact worktree locator:** one strict reserved locator line under existing `REQUEST.md -> ## User constraints`;
- **frozen base branch/commit:** existing `CURRENT.json.base_branch` and `CURRENT.json.base_commit`;
- **reviewed branch:** derived only as `reviewed/<task_key>`.

No new authorization database, permission token, ledger, workflow class, or schema family is added. The current-user kickoff remains the authorization source. A caller-supplied worktree/base/repo value is only an equality assertion against the frozen artifact; it cannot select another effect.

## 1. What changed from v0.1 to v0.2 — and only this

v0.2 changes exactly these design points:

1. **GitHub CLI direct-read surface is reduced.**
   - Remove direct `gh repo view`, `gh pr view`, `gh issue view`, and all other positional `view` forms from global allow.
   - Keep only bounded auth/status/list candidates with no repository positional selector.
   - Add explicit cross-repository/private-scope negative tests.

2. **The existing-branch publisher gets an exact-effect preflight.**
   - Add expected repo + expected branch equality assertions.
   - Require a single effective destination after Git URL rewriting.
   - Fail on multiple push URLs/destinations, push/fetch identity mismatch, mirror mode, active pre-push hook, and branch drift.
   - Explicitly suppress follow-tags and recursive submodule publication.
   - Preserve Review watcher ownership.

3. **Reviewed worktree materialization now consumes frozen scope from existing task artifacts.**
   - Exact worktree comes from `REQUEST.md` User constraints.
   - Base branch/commit comes from existing `CURRENT.json`.
   - Caller values are assertions only.
   - Both sibling-worktree and `/tmp` worktree cases are required.
   - Wrong path/base/branch/lineage fails closed.

4. **Gate Matrix G1/G2/G4/G5/G6/G7/G13/G15 is clarified/expanded only where these blockers require it.**
   - G15 now forbids generic/Host-wide `approval_policy=never` without misclassifying the existing narrow `plugin-replay` child’s fixed isolated contract.

Everything else from v0.1 remains intentionally unchanged.

## 2. Unchanged overall architecture

The proposed release remains **0.9.0**, handled as **one reviewed workflow/release with bounded internal phases**.

The architecture remains:

1. **Read-only Git/GitHub diagnostics:** native execpolicy first; no read-only Bridge wrappers.
2. **Existing selected branch publication:** one bounded Bridge publisher because current prefix rules cannot express the complete dynamic exact-effect predicate.
3. **Reviewed branch/worktree bootstrap/rematerialization:** one bounded operation inside the existing Reviewed Handoff product.
4. **Wrapper minimization:** `candidate-plugin-replay` stays removed; `plugin-replay` stays **KEEP_NARROW** only for its distinct production replay boundary.
5. **Persistent Run progress/ETA:** project-native producer owns truth; Bridge only normalizes/projects; existing authorized Notifier is optional transport; no new daemon/controller/watcher hierarchy.

The required screenshot reproduction remains:

```text
current branch = review/01047-clear-writing
origin/review/01047-clear-writing already exists
local branch is ahead by one ordinary task-owned commit
desired effect = ordinary fast-forward publication of that branch only
```

The user must not be asked again merely because the final ordinary push is reached.

## 5. A — revised Host Policy direct-read design

### 5.1 Local Git direct-read matrix

Unchanged from v0.1 except that all final rules still require Phase-0 real execpolicy verification.

| Need | Canonical shape | Decision |
|---|---|---|
| status | `git status ...` | DIRECT_ALLOW candidate |
| repo/ref parsing | `git rev-parse ...` | DIRECT_ALLOW candidate |
| current branch | `git branch --show-current` | DIRECT_ALLOW candidate |
| branch listing | `git branch --list ...` | DIRECT_ALLOW candidate |
| origin URL | `git remote get-url origin` | DIRECT_ALLOW candidate |
| effective origin push URL inspection | `git remote get-url --push --all origin` | DIRECT_ALLOW candidate |
| worktree listing | `git worktree list ...` | DIRECT_ALLOW candidate |
| tracked files | `git ls-files ...` | DIRECT_ALLOW candidate |
| tags | `git tag --list ...` | DIRECT_ALLOW candidate |
| configured remote refs | `git ls-remote origin ...` | DIRECT_ALLOW candidate |
| safe working diff | `git diff --no-ext-diff --no-textconv -- <pathspec...>` | DIRECT_ALLOW candidate |
| safe staged diff | `git diff --cached --no-ext-diff --no-textconv -- <pathspec...>` | DIRECT_ALLOW candidate |
| bounded log | `git log --max-count=50 --no-ext-diff --no-textconv -- <pathspec...>` | DIRECT_ALLOW candidate |
| HEAD show | `git show --no-ext-diff --no-textconv HEAD -- <pathspec...>` | DIRECT_ALLOW candidate |

Broad raw `git remote -v`, `git diff`, `git log`, `git show`, arbitrary URL `git ls-remote`, generic shell/Python composition remain non-allow.

### 5.2 Revised GitHub CLI direct-read matrix

The v0.2 default candidate set is intentionally smaller:

```text
gh auth status --
gh pr list --
gh pr status --
gh issue list --
gh issue status --
gh run list --
```

Rationale:

- the retained list/status commands do not accept a positional repository selector;
- the inherited `--repo` selector appears before the option terminator and therefore does not match the proposed canonical prefix;
- `gh auth status --` prevents a later `--show-token` from being parsed as an option.

These are still candidate shapes, not a claim that every installed GH/Codex version has already been exercised. Phase 0 must test both the command parser and Codex execpolicy on the execution host.

### 5.3 Removed from direct allow

v0.2 explicitly removes:

```text
gh repo view ...
gh pr view ...
gh issue view ...
gh run view ...
```

from the global direct-allow proposal.

Reason: current prefix rules cannot express “this command ends here”, while these command families have positional selectors or a richer targeted-object surface. They therefore remain on normal approval.

No replacement Bridge read wrapper is added.

### 5.4 Cross-repository/private-scope negative matrix

At minimum the final candidate must keep these outside direct allow:

```text
gh repo view other-owner/private-repo
gh pr view https://github.com/other-owner/private-repo/pull/1
gh issue view https://github.com/other-owner/private-repo/issues/1
gh pr list --repo other-owner/private-repo
gh pr status --repo other-owner/private-repo
gh issue list --repo other-owner/private-repo
gh issue status --repo other-owner/private-repo
gh run list --repo other-owner/private-repo
gh auth status --show-token
gh api repos/other-owner/private-repo
```

A direct-read PASS requires both:

1. normal current-repository list/status diagnostics work without interruption;
2. explicit cross-repository/private-scope selection remains on the approval path.

### 5.5 Failure semantics remain unchanged

An Auto-review denial is a policy result, not evidence that auth or the remote is broken.

Only an actually executed supported diagnostic that returns an auth/transport failure can establish that blocker.

## 6. B — revised bounded existing-branch publisher

### 6.1 Native-policy verdict remains unchanged

Current Codex execpolicy cannot safely express:

```text
exact repo
+ exact existing remote branch
+ current selected branch
+ exactly one ref update
+ no config-expanded extra destinations/effects
+ no executable hook
+ already-authorized task effect
```

with one static prefix rule.

The selected operation remains one bounded Host product capability, tentatively:

```text
ai-bridge host publish-current-branch   --expected-repo <canonical-repo-identity>   --expected-branch <branch>
```

Both arguments are **assertions only**.

They do not choose the Git remote, branch, refspec, URL, upstream, force mode, tag mode, or destination.

The helper always derives:

- repository from current working directory;
- branch from current symbolic HEAD;
- remote as literal `origin`;
- remote ref as the same-name `refs/heads/<current-branch>`.

If an assertion differs from derived reality, the helper fails before mutation.

### 6.2 Canonical repository identity

Before mutation:

1. resolve current Git top-level and common Git directory;
2. query `git remote get-url --all origin`;
3. query `git remote get-url --push --all origin`;
4. require exactly one effective fetch URL and exactly one effective push URL;
5. normalize both to one canonical repository identity;
6. require:
   - fetch identity == push identity;
   - push identity == `--expected-repo`;
   - no unknown/custom remote-helper transport;
   - no non-default `remote.origin.receivepack` override.

The normal production supported transport set is the repository’s ordinary HTTPS or SSH/scp-style Git remote. Local/file remotes may be used by tests but are not evidence that arbitrary custom remote helpers are safe.

Any multiple URL/pushurl condition or identity mismatch returns a bounded failure and performs no push.

This closes:

- unexpected `pushurl`;
- multiple push destinations;
- `insteadOf` / `pushInsteadOf` redirection, because `git remote get-url` expands them;
- wrong repository publication.

### 6.3 Branch/upstream equality

Required before mutation:

1. current HEAD must be symbolic, not detached;
2. current branch must exactly equal `--expected-branch`;
3. `branch.<current>.remote` must be exactly `origin`;
4. `branch.<current>.merge` must be exactly `refs/heads/<current>`;
5. `origin/refs/heads/<current>` must already exist;
6. fetch exact origin branch;
7. require remote is an ancestor of the intended local HEAD;
8. require behind=0;
9. capture the intended local HEAD OID.

Immediately before push, re-read:

- symbolic current branch;
- current HEAD OID;
- effective push URL set.

If branch, HEAD, or destination changed from the preflight snapshot, fail closed.

Thus the sequential regression:

```text
authorized branch A
-> helper preflight/assertion for A
-> checkout/switch to B
-> helper invocation/assertion for A
```

must fail before remote mutation.

### 6.4 Prevent config-expanded push effects

The trusted helper must not inherit Git configuration that broadens the single-ref effect.

Required behavior:

- if `remote.origin.mirror=true` -> fail closed;
- invoke push with `--no-follow-tags`;
- invoke push with `--no-recurse-submodules`;
- clear inherited `push.pushOption` for this subprocess;
- disable push signing for this bounded transport invocation so repository/user-configured signing programs cannot become an additional local executable path;
- generate exactly one refspec:
  `<captured-local-oid>:refs/heads/<expected-branch>`;
- no `--tags`, `--all`, `--mirror`, `-u`, `--set-upstream`, force form, delete form, extra refspec, push option, or caller-provided Git argv.

The helper is allowed to override `push.followTags` / submodule recursion only in this one subprocess because the product claim is explicitly “publish this one branch ref only”.

### 6.5 Pre-push hook boundary

A trusted Host helper must never execute arbitrary local `pre-push` hook code merely because `ai-bridge` itself is preauthorized.

Before mutation the helper resolves the **effective** pre-push hook using the current Git configuration, including inherited/process-local `core.hooksPath`.

If an executable pre-push hook is active, or the effective hook location cannot be determined safely:

```text
PUSH_HOOK_REQUIRES_ORDINARY_APPROVAL
```

and no push occurs.

The user/Codex can then use ordinary raw `git push` through the normal approval path, where running that hook is part of the explicitly reviewed effect.

If no active hook exists, the helper uses the Git no-hook form for its internally generated push solely to guarantee that a hook cannot appear between preflight and mutation and execute under the trusted helper. This is **not** an override path for an already-active hook: an active hook always makes the helper refuse.

### 6.6 Reviewed watcher ownership

Existing `reviewed_runner` publication remains the sole publisher for canonical Reviewed Executor events.

This is preserved mechanically as well as by prose:

- `reviewed_runner.push_guard_environment()` installs an effective process-local pre-push guard via `core.hooksPath`;
- the generic publisher’s effective-hook preflight must observe that inherited guard and refuse;
- it must not use its no-hook push path after detecting that guard;
- Watcher publication continues through `reviewed_runner`’s existing clean-diff, authority, CURRENT, and workflow validation path.

Therefore the new generic publisher cannot be used by a Review Executor as a shortcut around watcher authority.

### 6.7 Existing raw main push rule

The v0.1 decision remains: once the bounded publisher is proven on the same final candidate, remove the global raw direct allow for:

```text
git push origin main
```

because its prefix has the same suffix-widening problem.

Main remains low-friction through the bounded current-branch publisher when main is the selected same-name existing origin branch.

## 7. C — revised Reviewed worktree frozen-scope binding

### 7.1 Operation stays inside existing Reviewed Handoff

The selected capability remains a single operation under the existing Reviewed Handoff product, tentatively:

```text
ai-bridge reviewed-handoff materialize-worktree   --task-key <semantic-task-key>   --expected-repo <canonical-repo-identity>   --expected-worktree <absolute-path>   --expected-base-ref <origin/branch>   --mode bootstrap|resume
```

The assertion arguments do not select free-form effects.

- repo is derived from cwd and compared to `--expected-repo`;
- branch is always derived as `reviewed/<task_key>`;
- worktree path is read from the frozen task artifact and compared to `--expected-worktree`;
- base is read from existing task state and compared to `--expected-base-ref`.

No caller-provided branch exists.

### 7.2 Canonical frozen artifacts

v0.2 uses existing task artifacts only.

#### Exact worktree locator

The exact locator is one strict reserved line under the existing:

```text
automation/reviewed_handoff/tasks/<task_key>/REQUEST.md
## User constraints
```

Canonical line:

```text
- Reviewed worktree locator: <normalized absolute path>
```

This is not a new authorization store or schema family. It is a minimal frozen locator inside the existing user-constraint artifact.

At task creation/freeze, a sibling path such as:

```text
../AI_Skills_Collection-science-communication-project-thread-handoff
```

is normalized once against the canonical repository location and recorded as an absolute locator.

A `/tmp/...` path is recorded as the corresponding absolute locator.

Cross-host use with a different path is a different effect and requires an amended/current-user decision rather than silent substitution.

#### Frozen base/ref

Use the existing machine-owned fields in:

```text
automation/reviewed_handoff/tasks/<task_key>/CURRENT.json
```

specifically:

```text
task_key
base_branch
base_commit
```

The frozen base ref is derived as:

```text
origin/<base_branch>
```

The helper must require:

- `--expected-base-ref == origin/<CURRENT.base_branch>`;
- `CURRENT.base_commit` resolves to a commit;
- the fetched base ref contains that commit in the expected lineage.

For bootstrap, the new local reviewed branch starts from the **frozen base_commit**, not from a later moving origin tip.

The `PLAN.md -> ## Frozen decisions` section may repeat these locators for human readability, but the helper does not scrape arbitrary natural language from PLAN to choose an effect.

### 7.3 Authorization remains outside the artifact

The repository artifact proves only:

```text
this task's frozen repo/base/worktree scope
```

It does not prove:

```text
the user currently authorizes the mutation
```

Current-user kickoff/resume authorization must explicitly bind the same:

- repository;
- task key;
- derived reviewed branch;
- worktree locator;
- frozen base/ref.

The helper stores no permission receipt/token/database.

Its assertion parameters are a drift fence between the current-user instruction and the frozen task artifact; copying the values from the repository without current-user authorization remains prohibited by Host/Reviewed behavior rules.

### 7.4 Path safety and equality

The helper must:

1. read the frozen locator;
2. canonicalize the assertion without following it to a different existing symlink target silently;
3. require exact equality to the frozen normalized locator;
4. reject a changed symlink resolution relative to the frozen path;
5. reject the canonical checkout itself, Git common directory, or a path occupied by unrelated content/worktree;
6. allow both:
   - sibling task-owned worktree paths;
   - task-authorized `/tmp` paths.

No “helpful fallback” to another sibling path, another `/tmp` path, canonical checkout, or default temp directory is allowed.

### 7.5 Bootstrap

Bootstrap requires:

- semantic task key;
- derived branch exactly `reviewed/<task_key>`;
- no existing conflicting local reviewed branch;
- no existing remote reviewed branch for this mode;
- exact frozen worktree path;
- frozen base commit/ref validation.

It creates only:

```text
local reviewed/<task_key> branch at CURRENT.base_commit
+
the exact frozen worktree
```

It does not push or create a remote branch.

### 7.6 Resume/rematerialization

Resume requires remote:

```text
origin/reviewed/<task_key>
```

to already exist.

Before materializing it, inspect the task metadata at that remote ref and require at least:

- expected `CURRENT.json` path exists;
- `task_key` matches;
- `base_commit` matches the canonical frozen task;
- `base_branch` matches;
- remote reviewed head descends from the frozen base commit.

Then:

- if exact local worktree/branch already exists -> idempotent success;
- if local branch exists and equals remote head but worktree is missing -> attach exact worktree;
- if local branch is absent -> create local branch exactly at remote reviewed head and attach exact worktree;
- if local branch tip differs from the remote reviewed branch, or another worktree owns it -> fail closed.

### 7.7 Partial failure / rollback

Rollback owns only objects proven to have been newly created by the current invocation.

It may remove a newly created empty/helper-owned local worktree registration/local branch only when no user/task work has appeared and identity still matches.

It must never:

- delete a remote branch;
- reset/clean user work;
- remove a pre-existing local branch;
- remove an unrelated worktree;
- substitute another path/base/branch.

If ownership cannot be proven, preserve the partial state and return an operational recovery result.
