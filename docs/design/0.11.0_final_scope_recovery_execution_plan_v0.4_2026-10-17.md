## 1. 本轮实际核查事实与外部依据

### 1.1 Bridge 当前实现

实际读取当前 `main@24b703235a7e6a583653c59d560c809304cf6db3` 的 AGENTS、README、CHANGELOG、`pyproject.toml`、Lite/Reviewed/readiness/Persistent Run/Host/Notifier/private/plugin-replay 源码及相关模板。关键事实：

- `ai-bridge task run --target <repo> --task-key <key>` 是现有 Lite 正常入口。它在启动 `codex exec` 前调用 `readiness.preflight_lite_task()`，绑定 `AGENTS.md`、`prompts/AGENT_RULES.md`、`prompts/tasks/<task_key>.md`；失败时不启动子 Codex。
- Reviewed `watcher_once() / run_codex_event()` 在真正 launch 边界重新调用 `preflight_reviewed_event()`，不能靠 caller 传入旧 preflight 绕过；mandatory source 失败不启动 child。
- Lite/Reviewed mandatory source 都通过 `bind_repo_texts_isolated() -> read_control_file_isolated()`。后者使用隔离 `GIT_OBJECT_DIRECTORY`、原对象库作为只读 alternate，并核对 protected Git 状态前后不变。因此 partial clone 缺 blob 是正常入口内部机制，不应让普通用户学习 object directory。
- `exchange_linked_worktrees()` 已有三次 `git worktree move`、journal、失败回滚、A/B 交换后状态比对，但 CLI 需要手工提供 `--path-a/--path-b/--temp-path/--expected-branch-*`，目前缺正常恢复引导。
- `host sync-current-branch` 已有严格 non-main、clean、same-name origin、fast-forward-only 语义，README 已有真实用法，本轮不重设计。
- 当前 `persistent_run.py` 没有启动/恢复/supervisor/status 入口，周期 reporter 只有“被调用时”才工作。
- 当前 `notifier.py` 只支持 Gmail 主机、587、STARTTLS；配置只合并项目 `.ai-bridge/private/notifier.env` + process env；`status` 不报告 readiness/source/sender/recipient/suppression。
- 当前 `private sync --profile notifier` 要求 rclone 与 `AI_BRIDGE_PRIVATE_RCLONE_SOURCE`，目标仍是项目局部文件。
- 当前 `plugin-replay` 确实提供 installed production plugin + fresh unattended child + explicit local/private inputs + staging/write-isolation/evidence 的窄边界；当前 AI Skills maintenance/Reviewed Executor 仍真实消费它，因此保持 `KEEP_NARROW`。

README 当前没有 `ai-bridge task run` 和 `exchange-worktrees` 的正常用户说明；`validate --strict` 只出现在 0.11 版本摘要，不能算用户路径已经完成。

### 1.2 Git 官方机制

本轮核对 Git 官方文档：

- partial clone 明确允许省略对象并在真正需要时 demand-fetch；`git clone --filter=blob:none` 会让 blobs 在 Git 需要时才取得。
- `GIT_OBJECT_DIRECTORY` 指定新对象存储位置；`GIT_ALTERNATE_OBJECT_DIRECTORIES` 只作为搜索旧对象的 alternate，不向其写新对象。这与 Bridge 当前 isolated mandatory-source reader 的方向一致。
- `git worktree move` 是官方 linked-worktree 移动机制；主工作树和带 submodule 的 linked worktree不能直接用该命令移动，`repair` 用于已移动后重连。这支持当前 G02 “严格准入、原生 move、不能泛化所有拓扑”的设计。

因此 G02/G03 不需要重造 Git abstraction；需要修的是正常入口与错误/恢复呈现。

### 1.3 Codex 0.160.1 Progress thread

目标稳定运行身份仍以实施时实测为准；本轮重新核对 `openai/codex rust-v0.160.1@d27764b82f7118f674371e6d6e76271d9d606edb`：

- `thread/start` 支持 non-ephemeral thread、config、sandbox、approval、runtime workspace roots、environments、dynamic tools、selected capability roots、base/developer instructions 等。
- 官方 `temporary_structured_request.rs` 在 model turn 前读取 effective config，关闭 shell/unified exec、web、apps/plugins、MCP、environment、dynamic tools、multi-agent 等，并使用空 runtime roots；这是 Progress thread 的安全配置参考。
- 官方 temporary structured helper 自身设置 `ephemeral=true`，不能直接作为需要 reconnect/history 的用户 Progress thread。
- 官方文档明确：未使用的 thread 不保证能跨 restart 保存，ephemeral thread不能保存相应持久信息。结合已经发生的真实 canary，v0.4 固定为：`thread/start -> 机械隔离核验 -> 首个 bounded render turn -> 确认 materialized/history -> disconnect -> exact id cold resume`；不再要求首 turn 以前 cold resume。
- `thread/name/set` 在 0.160.1 已存在，可用于可读名称；名称只用于发现，exact thread ID 才是运行 identity。

### 1.4 Gmail 官方事实

当前 Google 官方帮助支持以下产品事实：

- Gmail 外发服务器为 `smtp.gmail.com`，要求认证，TLS/STARTTLS 端口为 587。
- Google App Password 是用于不能走“Sign in with Google”的应用的一次性 16 位应用密码；创建 App Password 需要先启用两步验证。
- App Password 可能因安全密钥专用两步验证、组织账号策略或 Advanced Protection 等原因不可用；Bridge 不能假装一定能生成。
- Google 更推荐支持 OAuth/“Sign in with Google”的客户端，但当前 Bridge 实现没有 OAuth。0.11 不为“通用”而顺手加 OAuth/provider framework。

因此 0.11 的诚实产品范围是：**Gmail SMTP + App Password**。任意 SMTP provider、Google OAuth、Workspace SMTP relay 都不属于本版正式承诺。

## 3. 普通用户从零到可用

### 3.1 新机器：一次性机器设置

正常入口：

`pip install -e /path/to/GPT_Codex_AI_Bridge_Kit`  
`ai-bridge host status`  
`ai-bridge host install`  
`ai-bridge host validate`

用户提供：目标 `CODEX_HOME` 身份（显式参数、环境变量或默认路径）以及现有 Bridge 源码安装。

Bridge 自动：
- 确认实际 `codex`、`ai-bridge`、import source/version；
- 安装/验证 Host Policy；
- 只报告本地可验证的 source HEAD/dirty、local formal release ref、distribution metadata；
- **不做远端 fetch/readback 时，remote formal release freshness 明确显示 `UNKNOWN/UNVERIFIED`**，不得假装知道 GitHub 最新 release。

成功时用户看到“本机 Host ready + 当前本地身份”；远端新鲜度另列 UNKNOWN。失败时直接给最小动作，例如重新 `host install`、换正确 `CODEX_HOME`、开启 fresh Codex session。

### 3.2 新项目：一次性项目设置

正常入口：

`ai-bridge init --target <repo>`  
`ai-bridge validate --strict --target <repo>`

`validate --strict` 定位为**安装/升级后与诊断时**使用，不要求用户每次任务手敲。日常 Lite/Reviewed launch 自己重新做受检 preflight。

如果项目选择 Reviewed、Control、Persistent Run 或 Notifications，再安装/配置对应可选层；不因为“装 Bridge”静默全装。

### 3.3 Lite 普通任务：日常最小路径

1. GPT 按 Task Writer 写 `prompts/tasks/<task_key>.md`，把用户目标、授权范围、通知最终 intent 和必要 source 冻结进去。
2. 用户/Codex 从正常入口运行：
   `ai-bridge task run --target <repo> --task-key <task_key>`
3. Bridge 自动检查 Host/工作树/指令预算/mandatory source；partial clone 缺 blob 时内部通过 isolated reader 安全取得。
4. preflight PASS 后才启动真实 `codex exec`。

用户不需要知道 object OID、`GIT_OBJECT_DIRECTORY`、alternate object dir 或 mandatory-source helper。

失败时只显示：哪一项必读来源/Host/预算不满足、为什么不能安全启动、怎样恢复同一任务。例如：
“必读来源 `prompts/tasks/x.md` 未冻结到 HEAD；先提交该任务文件再重试。”
或：
“必读文件在 partial clone 中缺失且无法从已验证 GitHub HTTPS origin 取得；恢复网络/凭据/remote identity 后重试。”
不得把低层 object-dir 命令甩给用户。

### 3.4 Reviewed / Control 选择

- Lite 默认。
- 需要 GPT 先规划并由独立 GPT 复核时选择 Reviewed；继续使用现有 `task bootstrap / publish-first / watcher`。
- 只有高风险、已经明确需要严格角色隔离与 Final Critic 时才选择 Control。
- 长运行不自动升级 Reviewed/Control；execution lifetime 与 workflow type 分开决定。

### 3.5 分支与 worktree 异常恢复

普通 non-main 同名分支严格落后：继续使用 `ai-bridge host sync-current-branch`。

只有当 Reviewed/materialize 正常入口发现**两个普通 linked worktree 正好形成可支持的 reciprocal placement conflict**时，才进入 G02 恢复：

- desired path A 当前是 branch B；
- expected branch A 当前登记在 path B；
- 两端均同 common-dir、非主工作树、同一文件系统、无 submodule/symlink/lock/活动进程等禁止条件；
- Codex 从 `git worktree list --porcelain` 与 frozen task locator 自动确定 A/B/expected branches；
- T 由 Bridge 确定为 A 所在文件系统上的唯一空闲 sibling 临时路径；
- Codex 只向用户展示一次自然语言请求：将 A→T、B→A、T→B，最终两分支位置怎样变化；询问是否授权这一次准确搬迁 effect；
- 用户只回答同意/拒绝，不拼 CLI 参数；
- 同意后 Codex 调已有 `exchange-worktrees` helper；
- helper失败则按 journal 回滚；不能证明恢复时保留全部证据并停止，不做 reset/stash/clean。

其他拓扑不强行“智能恢复”。

### 3.6 判断 execution lifetime

GPT Task Writer 在冻结任务前依次判断：

1. 普通 live：断开即允许停止，不使用 Persistent Run。
2. scheduler-owned：提交后由 scheduler 管寿命，不套 tmux。
3. existing service/job-owned：由既有 supervisor 管寿命，不新建 Bridge service。
4. terminal-owned 且必须 survive disconnect：选择 Persistent Run。

只有第 4 类使用 `persistent-run start`。这个选择与 Lite/Reviewed/Control 正交。

### 3.7 Persistent Run：一次授权后自动运行与自动进度

正常链条：

`GPT 冻结 execution lifetime + Persistent Run contract`  
→ `ai-bridge persistent-run prompt kickoff ...` 生成绑定 Goal hash 的一次授权文本  
→ 用户发送该 kickoff  
→ Codex 调 `ai-bridge persistent-run start --target <repo> --goal <goal> --expected-goal-sha256 <hash>`  
→ Bridge 幂等 start-or-resume canonical tmux run  
→ 同一个 run supervisor 保证 reporter 同生命周期启动  
→ project-native progress source → canonical snapshot  
→ dedicated Progress thread 自动 create/reuse  
→ cadence/event 主动更新  
→ 用户可断开  
→ exact Progress thread reconnect/history  
→ runtime terminal 最后一条运行状态  
→ reporter cleanup  
→ semantic completion 仍归原 Lite/Reviewed/Control 合法 owner。

用户不用手工 attach tmux、调用 `latest`、创建 Progress thread 或每小时问 status。

### 3.8 Notifications：一次机器配置，多项目复用

0.11 正式邮件 provider：**Gmail SMTP only**。

首次机器配置：

`ai-bridge notifier configure`

交互式读取：
- Gmail 账号；
- Google App Password（不回显；不是普通 Google 密码）；
- 发件地址（默认账号）；
- 默认收件地址；
- 可选 subject prefix。

机器 profile 保存到 `${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/private/notifier.env`。一个机器配置一次，多项目复用。

项目要不同 sender/recipient 时才使用 project override；process env 只作高级临时覆盖。

rclone：
`ai-bridge private sync --profile notifier`
保留为多机器恢复/已有私密源同步，不再是第一次配置的必修课。

项目通知偏好是**非 secret**，独立于 transport credential。一次设置项目默认：

`ai-bridge notifier defaults --target <repo> --progress-email ENABLED|DISABLED --semantic-completion-email ENABLED|DISABLED`

Task Writer/Reviewed Planner/Control Planner 在**冻结新任务时**读取项目默认并写入任务的最终 intent；运行时不再动态读取默认值改变旧任务授权。

### 3.9 disconnect / reconnect

- 普通 live task：按原 workflow 处理。
- Persistent Run：`persistent-run status` 显示 run owner/reporter/progress thread；用户在 Codex UI 直接打开同名 Progress thread看历史。
- Reviewed：现有 watcher/status + GitHub state。
- Progress thread exact ID 才是恢复 authority；名字只帮助用户发现。

### 3.10 blocked / failed / runtime completion / semantic completion

- runtime failed/blocked/stalled：Progress thread立即显示；若 frozen Progress email=ENABLED，可自动发运行层邮件。
- runtime completion：立即显示“运行已结束”，但**绝不等于 Goal PASS**。
- Reviewed semantic completion：只有 current Reviewed PASS artifact + frozen Semantic completion email=ENABLED 才自动发完成邮件。
- Control：只有 current Final Critic PASS artifact + frozen intent 才自动发。
- Lite：0.11 没有 canonical semantic-owner PASS artifact，因此 **automatic semantic completion = UNSUPPORTED**；用户可明确执行一次 `notifier send`，或选择 Reviewed/Control。不能给 Lite 一个看似可开的自动完成邮件开关却永远不发生。

### 3.11 状态/诊断

普通用户不读内部 JSON。

- Bridge/Host：`ai-bridge host status` / `host validate`
- 当前项目 setup：`ai-bridge validate --strict`
- Reviewed：`ai-bridge reviewed-handoff status` / watcher status
- Persistent Run：新增 `ai-bridge persistent-run status --target <repo> --goal <goal>`
- Notifier：增强 `ai-bridge notifier status --target <repo>`

### 3.12 正式发行身份

日常状态只显示本地已知：
- source/import version；
- source HEAD/dirty；
- local formal release ref；
- remote freshness = UNKNOWN/UNVERIFIED，除非本次明确做了远端读取。

最终发布再执行真实远端 `refs/heads/release` exact SHA readback；普通 status 不偷偷联网冒充最新。

## 5. ER11-05 — Persistent Run 端到端正常入口

### 5.1 两个启动方案比较

**方案 A：继续由 Codex 按 kickoff 手工拼 canonical tmux launch**

优点：不新增 CLI。  
缺点：每个任务都要重做 session/run/reporter/thread 绑定逻辑；最关键的是 reporter 可以被忘记，已经直接违反“没有 caller 不能 periodic reporting PASS”；恢复语义也容易因 Codex 当次实现漂移。

**方案 B：新增受边界约束的 `persistent-run start`，语义固定为 start-or-resume**

优点：
- 用户只有一次 kickoff；
- helper 统一核 frozen contract、Goal hash、run/session、primary process、reporter 和 Progress thread；
- reporter 必然随真实 run owner启动；
- reconnect/status有统一 machine-local binding；
- 不重复实现领域 launcher。

代价：增加一个小型生命周期 supervisor，但只属于**这个 run 的前台/tmux 子进程**，不是机器 daemon、controller 或下一任务决策者。

**决定：采用 B。**

### 5.2 Frozen Persistent Run contract 增补

现有 Markdown contract继续使用，不建新数据库。至少新增/冻结：

`Persistent execution: REQUIRED`  
`Backend: tmux`  
`Goal source: <repo-relative path>`  
`Run/session key: <stable key>`  
`Working directory: <repo-relative path>`  
`Launch argv JSON: ["executable", "..."]`  
`Resume argv JSON: SAME_AS_LAUNCH | ["..."]`  
`Progress producer: project-native | lifecycle-only`  
`Progress source locator: <path or NONE>`  
`Stage/status evidence: <source>`  
`Completed/total evidence: <source or UNKNOWN>`  
`ETA basis source: <source or UNKNOWN>`  
`Heartbeat/checkpoint evidence: <source or NONE>`  
`Report interval: 60 minutes ...`  
`Stall threshold: <value or UNSUPPORTED>`  
`Progress thread: AUTO`  
`Progress render max turns: <bounded integer derived from run time/cadence>`  
`Progress email: ENABLED | DISABLED`  
`Semantic completion email: ENABLED | DISABLED | UNSUPPORTED`

复杂 shell 激活逻辑应放进已经冻结、受 Git 追踪的 project-owned launcher script；Bridge helper执行 JSON argv，不接受随意 shell 字符串作为新的通用 orchestrator。

### 5.3 Kickoff 与 Goal hash

`persistent-run prompt kickoff` 升级为：

- 读取/验证 frozen Goal + Persistent Run contract；
- 要求 Goal/contract已冻结且没有相关 dirty drift；
- 计算 Goal/contract content SHA-256；
- 生成包含 exact goal path、hash、run key、资源/时间边界、Progress render turn 上限和已授权外部 effects 的自然语言 kickoff；
- 给 Codex明确的 `persistent-run start ... --expected-goal-sha256 <hash>` 调用参数。

Repo 文件本身仍不能自授权。只有用户把该 prompt 发回当前会话，Codex才执行 `start`。

### 5.4 `persistent-run start` 的幂等 start-or-resume 语义

入口只支持 terminal-owned + tmux contract：

1. 重读 Goal/contract并核 expected hash。
2. 检查 repo、branch/worktree、已授权资源/launch argv、canonical tmux session、现有 machine run binding。
3. 在启动长任务前创建/恢复 Progress thread并机械验证 tool isolation；无法验证则**不启动新 primary run**。
4. 若已有同 hash/run key 的兼容 primary run：不重复启动，修复/确认 reporter lifecycle后返回 `RESUMED_EXISTING_RUN`。
5. 若无 active run：
   - 使用 exact JSON argv，不经通用 shell拼接；
   - 在 canonical tmux中启动一个 run-scoped supervisor；
   - supervisor启动 primary child + reporter child；
   - supervisor等待 primary，primary结束后触发最后 runtime snapshot、停止 reporter并退出；
   - 不维持额外机器服务。
6. helper不提交 scheduler job、不申请资源、不改数据/model/budget；这些 effect若由 launcher需要，必须已在 Goal/kickoff明确授权，否则停止。
7. checkpoint resume只按 frozen `Resume rule/Resume argv`；Bridge不自行猜恢复命令。

### 5.5 scheduler/service topology

scheduler-owned 与 existing service/job-owned任务继续使用原 owner，不调用 tmux `persistent-run start`。

若用户仍要求 Bridge 主动 progress，现有 scheduler/service lifecycle hook必须显式启动同一个 reporter primitive并在 owner结束时清理。不能保证 hook/caller，就不能 claim proactive reporting。Bridge不为此新建 systemd/daemon。

### 5.6 Progress source 的 truth owner

Progress source由**项目原生 launcher/任务代码/调度器/既有服务**产生；Bridge只规范化。

有真实量化证据：
- completed/total 合法时才算 fraction；
- ETA必须带真实 basis；
- heartbeat/checkpoint可用于 last real progress / stall。

没有量化证据但任务仍合法长期：
- stage只从直接证据给出；
- completed/total/fraction = UNKNOWN；
- ETA = UNKNOWN；
- 不因为 tmux/PID活着猜 30%、80% 或预计完成时间；
- 若没有可靠 heartbeat，也不能仅因一段时间没新日志自动宣称 stalled。

lifecycle-only source可以报告 starting/running/runtime-failed/runtime-complete，但不冒充领域 progress。

### 5.7 reporter cadence

继续使用已批准规则：

- start/resume：立即；
- meaningful stage transition：立即；
- stalled/blocked/failed：立即；
- runtime completion：立即；
- material ETA：提前；
- normal active：默认约 60 分钟；
- 无任务特定理由不得低于 15 分钟；
- known ↔ UNKNOWN 永远 material；
- material ETA阈值：`abs(expected_finish_delta) >= max(15 minutes, 25% of prior remaining time)`；
- observation 与 last logical delivery分开；
- 普通 fraction/count变化只更新观察态；
- 高频观察不能重置 last-delivered 导致 cadence starvation。

### 5.8 dedicated Progress thread

每个 run 自动 create-or-reuse：

- non-ephemeral；
- exact `progress_thread_id` 是 identity；
- `thread/name/set` 的人类可读名字只用于发现；
- Bridge-owned display thread，不执行业务、不做 Planner/Reviewer/Executor；
- 不写原 Executor/task thread；
- Bridge先计算 canonical snapshot，render turn只呈现；
- 无 semantic completion authority。

### 5.9 0.160.1 正确 persistence canary 顺序

开发 canary与最终 G14 都使用正确顺序：

1. `thread/start` 创建 non-ephemeral Progress thread。
2. **在任何 model turn前**读取 effective config并机械验证 shell/unified exec/web/apps/plugins/MCP/environment/runtime roots/dynamic tools/multi-agent/connectors/permission escalation等全部关闭。
3. 隔离无法证明 → `PROGRESS_THREAD_ISOLATION=UNVERIFIED_BLOCKER`，0 render turn。
4. 隔离通过 → 第一个 bounded render turn。
5. 第一个 turn完成后验证 rollout/history真正 materialize/persist。
6. 断开 app-server/client。
7. exact `progress_thread_id` cold resume同一 thread。
8. 验历史仍在且未新建第二 thread。
9. development canary可执行第二个且最后一个 render turn。
10. 原 Executor/task thread前后完全未变化。
11. canary结束停止自动消息。

**不再要求在首 turn以前 cold resume**；“unused thread 不保证跨 restart”是已知生命周期，不制造假 blocker。

### 5.10 Progress thread tool isolation

复用官方 temporary structured helper 的 deny configuration recipe，但 `ephemeral=false`。

至少：
- read-only sandbox；
- thread-local no-approval，仅作用于这个无工具 thread，不改 Host-wide policy；
- `runtime_workspace_roots=[]`；
- `environments=[]`；
- `dynamic_tools=[]`；
- `selected_capability_roots=[]`；
- 禁用 shell/unified exec/code mode；
- web/search；
- apps/plugins；
- MCP（先 `config/read` 枚举 effective servers，再逐一 disabled）；
- environment；
- multi-agent；
- image generation；
- hooks；
- skills/instruction loading；
- permission request/tool；
- 其他 actual runtime 出现的 execution/external capability。

无法机械证明全部关闭则不发 render turn，也不退回原 Executor thread。

### 5.11 bounded render 与成本

每个 logical delivery最多一个 render turn：
- 输入是已冻结 canonical snapshot；
- model不得重估 stage/status/fraction/ETA；
- 输出值与 snapshot不一致 = fidelity FAIL；
- 上一 render未完成时 coalesce成最新待发 snapshot，不并发；
- foreign/business input出现 → `PROGRESS_THREAD_CONTAMINATED`，停止自动投递；
- 每次记录 snapshot digest/turn id/token/time。

Frozen contract必须有 `Progress render max turns`，由任务时间边界、60min cadence和有限 immediate-event余量预先确定；超过上限停止自动 render并要求用户决定，不无限消耗模型。

### 5.12 `persistent-run status`

用户至少看到：
- active / terminal / unavailable；
- run locator / session key；
- lifecycle owner；
- Goal/hash；
- stage/status；
- completed/total/fraction 或 UNKNOWN；
- ETA/basis/uncertainty 或 UNKNOWN；
- last real progress；
- reporter active/last heartbeat；
- Progress thread human name + exact ID；
- latest logical delivery time/reason；
- primary runtime exit code/terminal state；
- Progress thread isolation status；
- 不显示 secret。

`report/latest` 保留兼容/诊断，不再是用户获得主动进度的必要步骤。

### 6.7 Frozen intent 存放位置

- Lite task：任务 frontmatter/固定 `Notification Intent` 区域。

- Control：`FROZEN_CONTRACT.md` 中冻结 intent；CURRENT只做状态，不新建 notifier authority state。
- Persistent Run：contract复制 underlying task的最终 resolved intent供 reporter查看；semantic completion仍以 underlying workflow的 canonical decision artifact为 authority。

最终枚举：
- `Progress email: ENABLED | DISABLED`
- `Semantic completion email: ENABLED | DISABLED | UNSUPPORTED`

`UNSUPPORTED` 只用于该 workflow没有 automatic semantic owner（0.11 Lite）。

### 6.9 Manual vs automatic

保留现有用户显式一次性入口：

`ai-bridge notifier send <brief>`  
`ai-bridge notifier send-test`

automatic：
- Persistent Run progress；
- `notifier once/run`；
- Reviewed/Control自动 terminal/milestone；
都必须读取 frozen intent。

automation不得 shell out 到 manual CLI绕过 intent。manual live path必须区分 current interactive user与 Bridge/Codex automation上下文；dry-run/render无外部 effect可非交互。

### 6.10 Semantic authority

- `AWAIT_HUMAN_DECISION` + `human_gate_reason=PASS` + `last_review_decision=PASS`；
- current implementation commit；
- matching latest REVIEW PASS；
- valid FINAL_REPORT；
- Reviewed validator全 PASS。

Control：
- exact task/request_nonce/review_target；
- valid current `FINAL_CRITIC_AUDIT.json`；
- `CRITIC_FINAL_PASS`；
- source snapshot/review bundle/frozen contract/ledger/planner pass candidate全部绑定；
- Control task validator无 blocking identity error。

Lite：无上述 artifact → automatic completion不支持。

Notifier只验证 existing workflow decision locator + render/dedupe/send，不做领域判断。

## 8. G01–G14 正常入口与最终验收矩阵

所有 release-critical Gate 必须由**同一个人类可读 release candidate + 同一个 exact Git SHA**直接通过。开发期测试只进入 regression bank，不能拼接为正式 PASS。

### G01 — 不同分支长期 worktree 并行

- **用户能力声明**：两个独立任务在不同分支/linked worktree长期运行时互不覆盖。
- **普通入口**：Lite在当前已选 worktree用 `task run`；Reviewed用现有 `task bootstrap/materialize` 生成/恢复确定性 sibling worktree。
- **内部自动机制**：每个入口核 repo/common-dir/current branch/worktree identity；不要求用户管理 common-dir。
- **用户成功结果**：两个任务各自在自己的 cwd/branch运行、原脏内容不被另一任务接管，产物留在各自树。
- **失败结果**：路径/branch占用时出现明确 readiness/recovery分类，而不是静默切目录。
- **最小恢复**：正确现有 worktree直接继续；只有 reciprocal dirty conflict才进入 G02。
- **分类/消费**：日常；Lite CLI、Reviewed runtime、README工作流说明。
- **最终真实证据**：同一 0.11.0 release candidate 上两个真实 worktree任务并行；记录 cwd/branch/原脏状态/产物。
- **最终候选要求**：必须由同一 candidate exact SHA直接通过。

### G02 — 双脏关联 worktree 冲突恢复

- **用户能力声明**：受支持的 reciprocal linked-worktree位置冲突可以一次授权、无损交换，用户不拼 A/B/T CLI。
- **普通入口**：Reviewed materialize/bootstrap正常恢复路径检测冲突后提出一条自然语言授权请求；`exchange-worktrees` 保持 recovery helper。
- **内部自动机制**：从 worktree registry + frozen task locator确定 A/B/branches；确定同文件系统空 sibling T；准入检查；journal；三次 `git worktree move`；postcheck/rollback。
- **用户成功结果**：用户只看到最终 branch→path 归属和“原 staged/unstaged/untracked保持”。
- **失败结果**：不支持条件或 rollback状态，明确原数据是否已经恢复。
- **最小恢复**：拒绝/不支持时保持两边原状；支持但需移动时只索一次 exact effect授权。
- **分类/消费**：recovery；Reviewed runtime/README高级恢复。
- **最终真实证据**：真实支持平台的双脏 linked worktree，含 staged/unstaged/untracked，中断/回滚；不包含主 worktree/submodule/cross-fs。
- **最终候选要求**：同一 candidate exact SHA。Git官方 `worktree move` 限制保持。

### G03 — partial clone mandatory blob

- **用户能力声明**：受检任务即使本地缺必读 blob，也能安全取得并读取，不污染原 Git 状态。
- **普通入口**：`task run` / Reviewed watcher自动消费；没有独立用户命令。
- **内部自动机制**：isolated object dir + original alternate + verified GitHub HTTPS promisor fetch + exact blob read + protected state前后比对。
- **用户成功结果**：任务正常启动；用户不用知道 object dir/OID。
- **失败结果**：明确缺哪个 mandatory source、remote/network/credential/identity哪个前提失败。

## 9. 跨 Gate 端到端真实旅程

最终评估不能只把每个 Gate拆成 unit test。至少固定以下真实旅程；能共享同一受控环境就共享，但不能让一个 proxy PASS替另一能力：

1. **fresh-machine-like Bridge/Host setup**：干净/受控 CODEX_HOME identity → install/status/validate → fresh Codex规则消费。
2. **fresh Lite task**：`init -> validate --strict -> task run -> mandatory source -> real Codex`。
3. **existing non-main branch safe sync**：strict FF。
4. **supported worktree conflict recovery**：normal Reviewed/materialize发现 reciprocal conflict → 一次自然语言授权 → helper交换/恢复。
5. **stale Host recovery**：prelaunch阻断 → 获授权修 exact CODEX_HOME → fresh session同任务恢复。
6. **Persistent Run完整生命周期**：task lifetime分类 → frozen contract → kickoff → `start` → primary+reporter → progress source → Progress thread → cadence → disconnect/reconnect → runtime terminal → cleanup。
7. **fresh Gmail setup**：`notifier configure -> status -> send-test`；用户真实输入 App Password，不回显。
8. **第二个项目复用 machine notifier profile**：不重新填 Gmail credential，status显示 machine source。
9. **project override -> remove override -> machine default**：sender/recipient source切换可见且不泄 secret。
10. **task notification default/override真实冻结**：project default → task writer override → frozen task intent；随后改 project default，旧任务 intent不变。
11. **Reviewed semantic completion notification**：current Reviewed PASS artifact + frozen intent → automatic notifier → Gmail正例。
12. **Lite对应语义**：Lite frozen semantic field明确 `UNSUPPORTED`；automatic不会假发完成邮件，explicit one-shot仍可用。
13. **same exact 0.11.0 release candidate identity**：所有 release-critical Gate、CI、安装身份指向同一个 `0.11.0-rc.N @ SHA`。
14. **final release exact SHA readback**：用户授权 old release SHA → exact candidate SHA 后推进，远端 readback确认。

这些旅程的真实 production entry/CLI/render/remote效果是能力证据。unit tests、schema、JSON存在、receipt、fixture只能作为开发回归，不能替代上述旅程。

## 11. Deterministic regression bank

### 11.1 Normal-entry / docs

- README 命令实际存在且 help一致。

### 11.2 Persistent Run

- Task lifetime分类：live/scheduler/service/persistent四类。
- frozen contract缺 launch argv/progress source/intents时 `start` fail before long run。
- expected Goal hash mismatch fail。
- start new run只创建一次 canonical session/binding/reporter。
- 第二次 `start` 幂等 resume，不重复 primary/progress thread。
- supervisor primary exit/signal时 final runtime snapshot + reporter cleanup。
- no caller/owner不能 periodic PASS。
- project-native quantitative source / lifecycle-only source / no ETA source三类。
- fraction/ETA不造假。
- 5min observations到60min仍基于 last-delivered投递。
- immediate event/material ETA。
- render-turn上限。
- Progress thread non-ephemeral、isolation config、first-turn materialization、cold resume、no duplicate、contamination stop。
- original Executor thread untouched。
- reporter结束后等待超过一个观察 tick，无新消息。

- machine configure不回显 secret。
- POSIX 0700/0600 + symlink/path escape。
- Windows ACL verifier无法确认时fail closed。
- machine < project < process merge。
- clear project override后回machine。

- selected safe native reads current execpolicy allow。
- malicious pager/ext-diff/textconv/fsmonitor/credential/helper仍 gated。
- Host status remote freshness UNKNOWN without network。

## 13. 最终外部预算与不换样本

### Fresh Codex

沿用默认最多4个 session/campaign，建议：
1. development Progress-thread isolation canary；
2. final release candidate G14 Progress-thread full lifecycle；
3. G01/G04/G07/G08正常入口组合；
4. G09/G10/G11 authority/refusal/recovery组合。

第5个只有存在真正独立失败模式、pre-final Critic同意且用户明确授权才可增加。创建新 task/thread编号不能重置预算。

### GitHub

用户另批一个 exact disposable/test repo或分支集合。最多1次 ordinary non-force positive publication；read-only partial clone/fetch可复用。不得 force/delete remote branch/修改消费者repo。

### Gmail

最多2封真实邮件，见 `6.13。账号/recipient/App Password使用必须在真正发送前另获当前用户 exact authorization；本 execution package和未来开发 Kickoff都不预授权真实 Gmail。

### CODEX_HOME / Machine Policy

真实安装只在 pre-final PASS后对 exact路径另获授权；必须有backup/restore。开发回归使用 disposable身份。

### 最终样本

一旦 final 输入产生结果：
- 不因失败换 thread/repo/task；
- 不拼最好一次；
- 只能分类为产品失败、基础设施失败或评审错误；
- 产品修复后形成新的 release candidate label+SHA并重跑受影响 Gate。

## 14. 失败与恢复边界

- Lite mandatory source失败：child不启动，保留同task，修source后重试。
- G02不支持拓扑：两边原数据不动，返回 `UNSUPPORTED_WITH_EVIDENCE`，不尝试 reset/stash。
- isolated blob fetch失败：不污染原 object store；用户只修网络/credential/remote/source。
- Host remote freshness未知：显示 UNKNOWN，不把它当stale；只有实际remote evidence才能判 freshness。
- Persistent contract缺真实 launch/progress evidence：不启动长run。
- Progress thread isolation无法机械证明：不启动新 Persistent primary run；已有运行若后续投递隔离失败，不自动cancel primary，标 progress blocker并停止新 render。
- first Progress render后无法materialize/cold resume：G14-C失败，不创建第二thread冒充历史。
- reporter崩溃但primary仍active：`persistent-run start` 同一run可按现有授权边界恢复reporter；不得重复primary。
- progress source不足：显示 UNKNOWN，不推断。
- Gmail未配置/ACL不安全/App Password不可用：自动邮件suppressed + status原因；不改用普通Google密码或另一个provider。
- automatic intent缺失：no-send。
- semantic artifact不合法：no semantic completion mail。
- explicit manual send继续只在current-user one-shot路径。
- final release candidate生产字节改变：新 `0.11.0-rc.N`，旧 final evidence不拼。
- 四个 final sessions用尽仍缺证据：停止并请求新预算。

## 15. Critic 重点复核

下一独立 Critic 应优先确认：

1. `ER11-04`：G01–G14是否都已经从“内部机制”转成真实用户入口/成功/失败/恢复合同，而不是新增一堆命令。
2. `ER11-05`：`persistent-run start` 是否是最小有价值的 helper，是否真正保证 reporter启动；是否仍让 scheduler/service保留原生 owner；progress source是否不会造假。
3. Progress thread canary顺序是否正确吸收已知0.160.1“首turn前未materialize”的事实；persistent history和temporary-helper-level isolation能否同时成立。
4. `ER11-06`：Gmail-only 是否诚实匹配现有代码与Google官方要求；`configure/status/defaults` 是否够简单；rclone是否已退到恢复用途；machine/project/process优先级是否安全。
5. Lite semantic completion设为 `UNSUPPORTED` 是否比造一个假开关更诚实，且 explicit one-shot仍可用。
6. `ER11-07`：所有用户可见执行合同是否只用 `0.11.0-rc.N @ SHA`；所有release-critical Gate是否同一SHA。
7. Host status是否明确本地ref与remote freshness UNKNOWN的事实边界。
8. G02用户是否只需一条自然语言授权，不需要自己拼 `exchange-worktrees` 参数。
9. README/CLI/templates是否作为正式产品修改范围进入freeze，而不是发布前最后补文档。
10. 是否没有引入 daemon、credential DB、machine registry、新workflow/role、通用Git wrapper或任意SMTP framework。
