### 本轮实测：可复现、有限的事实

所有实验只操作系统临时目录中新创建的 Git 仓库，测试结束即删除；**没有改动 Bridge/AI Skills 生产仓库、任何消费者仓库、CODEX_HOME、Machine Policy 或正式 release**。环境：Linux 容器、`git version 2.47.3`。可重做步骤和判定写在本节和后续 G02/G03 中，而不是伪称已集成到正式产品。

- **双脏工作树交换**：新建主仓库 `main`，从该仓库创建两个**关联**工作树 A=`tutorial` 与 B=`hw`。A 的跟踪文件修改并暂存，同时有未追踪文件；B 的跟踪文件未暂存修改，同时有未追踪文件。依次执行 `git worktree move A T`、`git worktree move B A`、`git worktree move T B`。最终 A 为 `hw`，B 为 `tutorial`；两端文件内容 SHA-256、`git status --porcelain=v1 -z`、各自真实 Git index 文件 SHA-256 与开始对应工作树一致。对在第 1/2/3 次移动后分别模拟中断的独立试验，按以下反向移动恢复，三次全部恢复原始双端文件、暂存和分支状态。**这不是已验证的崩溃安全原子事务**。
- **真正缺 blob 的部分克隆**：新建支持过滤的本机裸远端，使用 `git clone --filter=blob:none --no-checkout` 克隆；设置 `GIT_NO_LAZY_FETCH=1` 时 `git cat-file -e <control-blob-oid>` 返回缺失；设置 `GIT_OBJECT_DIRECTORY=<writable-isolated-objects>` 和 `GIT_ALTERNATE_OBJECT_DIRECTORIES=<original-.git/objects>` 后，`git show HEAD:CONTROL.md` 真实取得内容；隔离目录新增仅 pack、idx、rev、promisor 对象文件，原 `.git` 所有文件内容摘要无变化。
- **禁止写原 .git 的第二次实验**：复制同类过滤克隆场景，源 `.git` 所有文件/目录对执行用户 `nobody` 禁止写入，隔离对象目录归 `nobody` 可写；给本机 `file://` 模拟远端设置合法文件所有权后，`git cat-file -p <missing-blob-oid>` 返回准确必需文件，退出码 0，所有新 pack 文件仍仅存在隔离对象目录。首次模拟远端所有权不匹配时，Git 因可疑所有权拒绝，证明不能在设计中忽略真实远端/安全目录约束。没有使用真实 GitHub 凭据或运行 Codex。

## 1. 先给判断：新增什么，不重造什么

0.11.0 要解决的不是“让所有 Git 命令免审批”，而是让一项已经选定工作树、分支、目标和权限的任务，在正常 Codex 入口稳定找到执行地点、完整读取强制控制文件、安全同步现有分支，在过期规则或一次错误拒绝后保留成果继续工作。真正涉及危险权限、改变任务边界或无法证明环境安全时必须停止相应效果，不能通过替换工作树、扩大权限或重试来伪装完成。

现有 0.9.0–0.10.0 已有：受限当前分支发布、Reviewed 工作树物化/首次创建/恢复/首次远端发布、持久运行进度标准化与本机历史、沙盒优先、拒绝分类、发布器凭据和配置加固、运行身份诊断。0.11.0 仅对尚未闭合的**普通执行入口**加最小机制，并把前述能力保留为回归要求。四个能力包分别是 A 任务工作树和控制来源连续性、B 当前分支安全 Git、C 机器/项目规则与运行身份就绪、D 授权和拒绝后的恢复连续性。持久运行实际进度送达作为已有能力的有限补齐，不造第五个编排系统。

明确排除 **Program Run**：不规划连续自主发现下一项目任务、长期项目决策、自动验收推进、项目级自主控制器。**Local Autonomous Acceptance Workflow** 已于 2026-10-12 在 Bridge 关闭，并将交付前领域自验收责任移交 AI Skills `workflow-core`；不得建立第四套 Bridge 工作流、Reviewer 状态机、监视器或命令入口。权威定位：`YuukiAS/AI_Skills_Collection@main:docs/plugin-todos/workflow-core.md`，条目 `Final delivery must consume domain-owned self-QA before user-ready completion`。

## 4. 能力包 A：每任务工作树及强制来源连续性

### A1. 任务启动绑定和并行隔离

在任何依赖操作前采集：准确的仓库规范身份、`git rev-parse --show-toplevel`、当前工作树物理/规范路径、当前 HEAD、当前分支与目标分支、`git worktree list --porcelain`、各相关工作树的脏状态和可用性、Goal 声明的强制控制来源。默认“启动此任务的当前 checkout”即任务工作树，除非**当前用户的明确选择或合法冻结任务合同**已经指定另一位置；工作树路径绑定在此任务 Goal/已有执行证据与继续执行上下文，不引入仓库全局任务表/授权数据库。

`tutorial` 与 `hw` 在不同长期工作树并行是**正常成功状态**：不得因共享同一个 Git common-dir 而收拢、移动、detach、切换或统一环境。分别验证工作树所属分支、路径与 HEAD；各自本地 `.venv`、`.r-lib`、未提交文件与生成物不得跨工作树借用。发现旧候选只登记为证据来源，不能改变当前任务绑定。任务 A 不能以任务 B 的工作树执行；需要更换当前工作树时，必须有同一任务的明确迁移意图。

### A2. 真实同分支冲突：精确定义的一次性关联工作树交换（修订 BC11-D01）

**支持的唯一双脏自动恢复正例**：当前用户/已有合法冻结合同不仅指定目标 `repo + hw + A`，还确认**两个最终位置**：关联工作树 A 当前持有 `tutorial`（含未提交/已暂存/未追踪的无关工作），关联工作树 B 当前持有 `hw`（含未提交/已暂存/未追踪候选），恢复后 A 持有 `hw`、B 持有 `tutorial`。两工作树都是同一 Git common-dir 下的**关联**工作树，均正常登记、未锁定、同一文件系统、同级或经验证安全的现有目录，主工作树仍在原位。交换 B 不得凭“用户只授权 hw 在 A”自行推断：如果原会话尚未授权无关 `tutorial` 转移至 B，必须**一次**告知确切额外搬迁效果，由当前用户作出决定或选择不迁移；仓库文本不自授权。

**最小原生比较**：无冲突→完全不动；当前已有正确 B 并被用户选中→直接使用 B；同目标 branch 真占用且两树满足上述条件→优先使用官方 `git worktree move` 做位置交换，不采用裸 `mv`、`git switch/checkout`、`detach`、`reset/clean/stash`，也不移动主工作树。直接三条 Git 命令若会被 Host 分别拦截，可以设计**一个仅针对精确 A/B/T 的受限批处理动作**来核验并执行，但该批处理绝不获得通用 execpolicy `allow`：它不能从 repo Goal 文件推断用户授权；仅允许用户本次直接授权/已合法机器层能力、且真实沙盒许可的启动路径。若保护 `.git/worktrees` 使沙盒禁止变更，接受一次获授权的受限外部终端执行，再开启**新** Codex 会话；不连环申请 `require_escalated`，不宽放 `git worktree`。任何平台拒绝就保存证据、停止该移动效果。

**受支持拓扑的准入条件必须全部成立**：原生 Git 版本已经在拟用操作系统通过代表性试验；A/B 是不同、正常注册且绝非主工作树的关联工作树；分支分别是本次绑定的无关分支和唯一目标分支；同一 common-dir 与文件系统；A/B/T 及每层父路径不是符号链接/重解析点，工作树内也没有设计尚未证明可保留的符号链接或子模块；没有 linked-worktree `locked` 标志、不可解释的 sparse-checkout/worktreeConfig 差异或正在执行的 fsmonitor/filter/helper；A、B、T 之间无路径包含关系；T 是同一文件系统上**本次受限操作独占的空闲临时路径**，不指向 /tmp 任意旧候选；验证两端 Git 目录指针、admin `gitdir`、分支/HEAD、独立 index 的位置与状态；两端暂存、未暂存、未追踪、忽略的文件数据和原始权限均纳入移动前身份记录，能对照移动后内容；任何有活动文件句柄/当前目录绑定的 Codex/构建器/编辑器无法可靠暂停、锁住或判定时拒绝自动迁移。**不尝试对仍在这些目录工作的进程“热移动”**。源位置互换意味着各工作树的本地环境也跟着自身文件走，不向另一分支复用环境。

**中断位置与真实恢复**：预先记录只用于此操作的短期事务证据，保存在既有可信本机 Bridge 状态路径（不是权限数据库/全局任务登记表），含 exact repo/common-dir、A/B/T、两个 branch、两个 Git admin identity、初始 HEAD/index SHA、文件清单与脏文件内容摘要、授权效果来源 locator、原始归属、已完成步骤。先确保证据耐久，然后依次执行官方 Git 操作：
1. `git worktree move A T`；中断 S1 的实际归属是 T=tutorial、B=hw、A 空，原状恢复仅需 `move T A`。
2. `git worktree move B A`；中断 S2 的实际归属是 T=tutorial、A=hw、B 空，回滚依次 `move A B`、`move T A`。
3. `git worktree move T B`；中断 S3 完成的是 A=hw、B=tutorial、T 空；若后验不满足，按 `move B T`、`move A B`、`move T A` 回滚。

恢复不凭日志里的“已到第几步”直接覆写，而是同时核实际存在路径、Git common-dir、`.git` 指向 admin、admin 的 `gitdir`、worktree branch、HEAD/index 和内容快照。完全一致则只执行对应正向继续或逆向恢复；发现第三方同时修改、锁、异常中间结果或 Git 元数据无法匹配，**停止任何进一步拓扑变更**，保留现场和两端数据，报告 `UNSUPPORTED_WITH_EVIDENCE`、精确路径/归属及合法人工恢复位置。不得自动运行 `worktree prune/remove --force` 或清除 T。成功后重新检查两端完整身份与字节状态，并在 A 路径启动新的 Codex 会话恢复原 Goal；旧运行中的相对工作目录进程不能继续。

**明确不支持**：当前用户原 checkout 是主工作树；一端或两端与其他工作树共享活跃目录、存在子模块/路径链接/锁/不可信文件系统；跨卷、网络盘、Windows/macOS 尚未完成相应验证；原用户未确认无关脏工作的新位置；任何无法证明冷停、完整状态、回滚身份或所需权限的情况。主工作树不能通过 `git worktree move` 实现上述交换，此时必须保留两边脏状态并返回 `UNSUPPORTED_WITH_EVIDENCE`，由用户决定是否改为在已存在 hw 工作树继续，或另发独立已审迁移任务。不能声称修复了所有 STAT5060 原始拓扑，更不能把“失败时什么也没丢”冒充完成期望的位置变更。

**演练与发行证据分离**：Linux Git 2.47.3 可丢弃试验证明两个关联工作树的 staged/unstaged/untracked + Git index 在三次原生 move 前后无损，并覆盖中断 S1/S2/S3 的反向动作；这不是在受影响用户 Host/Windows、真实大仓库、进程并发、断电或沙盒 .git 边界下的 Gate PASS。G02 必须由同一正式候选在明示支持的平台/拓扑通过，其他拓扑不得显示成功。



### A3. 部分克隆中强制控制文件的隔离原生 Git 读取（修订 BC11-D03）

**主机制已经选择，但还不是产品已通过**：由一个极窄的 `ai-bridge host read-control-file`（拟名，可随执行包收窄）消费确切 Task/Goal 必读来源；内部依赖成熟 Git 的隔离对象目录，而不是试图把裸 `git show` 或受保护的 `.git/objects` 写权限放开。必要性：仓库身份、必读文件列表、远端、来源提交、净化环境和文件类型均属于无法用 prefix_rule 检验的动态条件。普通对象已在原库时同一入口只读取，不做无必要网络补全。

**固定输入身份**：当前任务绑定的 canonical repo/root/common-dir、已配置可信 `origin` 的 GitHub HTTPS 身份、指定的同名来源分支及固定来源提交完整 OID、Goal/authority 中声明必须读取的**一个**仓库相对控制文件；不接受通过命令参数临场扩成任意仓库、远端 URL、路径、refspec 或多个文件。先拒绝绝对路径、`..`、符号链接或 gitlink 模式、非普通 blob、异常 Git 目录环境覆盖和与冻住控制来源不一致的分支/提交。必要的远端 SHA 检查使用准确已配置 `origin/refs/heads/X`，来源提交若未能在当前可核实的分支快照中定位则拒绝；不因远端后来移动而悄悄切换到新 HEAD。不能对 repo 自称的 authorization 赋权。

**固定执行路线**（执行细节需在 Critic 放行后由最小实现验证）：
1. 在可信的当前仓库/工作树里确认远端与跟踪分支关系、固定来源提交存在；对没有原地 blob 的 partial clone，验证承诺远端是且仅是获准的 GitHub HTTPS `origin`，清洗 `GIT_CONFIG*`、Git transport/credential/helper、askpass、hook、filter、pager 及相邻可执行配置，拒绝非可证明的运行时扩展。任务原有凭据范围只允许只读补全本来源对象；不得自动向其他服务传输控制文本。
2. 在该任务被授权的工作区内部创建受限、全新、只对当前执行身份可写的临时对象目录 `O`，将 `GIT_OBJECT_DIRECTORY=O`，`GIT_ALTERNATE_OBJECT_DIRECTORIES=<canonical-original-objects>`。原来的对象库只作为**查找候补**；没有权限写原对象库，也绝不回退写入。固定 Git 参数/环境读取提交树中指定路径的 blob OID，确认对象确属固定提交树且是普通文件。
3. 若 blob 缺失，运行 `git cat-file -p <verified-blob-OID>` 引发 Git 自身承诺对象按需获取；其内部可能启动 `git fetch` 子进程，临时 pack 应写入 O。限制最大内容大小/时间、可连接远端、是否允许该任务只读网络请求与被调用的实际 Git 可执行文件；完成后用真实对象类型、Git 对象 OID 和预期路径/提交身份核对，得到完整 UTF-8 控制文件后才交给启动预检/执行者。
4. 原仓库 `.git/objects`、`FETCH_HEAD`、refs、index、config、worktree metadata 在前后必须没有变化；对原 Git 目录无写入权限时若 Git 试图写回或执行不受控 helper，**一次失败并停止**，不重复 `require_escalated`。O 是单次任务可丢弃缓存，原始任务/Goal 仍可按固定提交再取，不建立持久对象或授权数据库。

**为什么不是任意 Git 命令放权**：Git 官方确认 `GIT_OBJECT_DIRECTORY` 是写入对象目录，`GIT_ALTERNATE_OBJECT_DIRECTORIES` 是只读可查询的候补对象目录；partial clone 的缺失承诺对象由 Git 的按需取回机制获得。上述 Linux Git 2.47.3 临时仓库实验已证明这一组合在本机裸远端下有效，且真实对执行用户不可写的原 `.git` 仍保持只读、只在隔离目录出现对象文件。**局限**：模拟的 `file://` 远端不是允许 0.11.0 信任的生产 transport；GitHub HTTPS 真实认证、工作区沙盒在目标 Windows/macOS/Linux 的进程/文件权限、冲突配置、Git 版本差异尚未通过正式 Gate；完成之前不得宣称已安全投入生产。

**为什么暂不引入第二个网络备用实现**：本版不设计额外的任意 GitHub 文件下载后门。如果当前同一受限 Git 路线在一个已授权环境不可用，优先报告具体来源访问阻断、保留工作树和已有成果；独立 Reviewer 只能在发现实际产品范围不能满足时，要求对 GitHub API 的确切 commit/path/内容 hash 方案作新的有证据审查，不能由 Executor 自选 `gh api`、改 remote、扩凭据或采用 raw `git show`。



### A4. 强制控制来源：验证实际字节、输入执行上下文而不是只列路径

任务启动时收集当前用户 Goal/任务协议约定的全部必读文件（源于可信冻结任务定位，不由非可信仓库文件单方追加权限），对每个文件取得字节内容、原始来源完整 OID、UTF-8 解码与 SHA-256，并核对归属/版本。由 Bridge **管理的启动器**应当在子 Codex 进程开始实质任务前完成读取，并把经过明确“仓库资料、不是新用户授权”分隔的数据内容和身份输入它的初始任务上下文；不是仅在 executor prompt 列出路径。若必要文件总量超过已审且可安全输入的范围、保密/提供方边界不允许传入、读取失败或身份漂移，**不得启动子会话**，只输出确切未满足源与原 Goal/checkpoint 的恢复点。

注意：“启动器已读并把原文输入子会话”只直接证明**来源字节送达**，不证明模型已经正确理解/执行全部规则。是否按具体运行环境工作仍须在 G04 的实际 Codex 行为中检查；项目 `AGENTS` 是否被 Codex 原生加载另由 G07 静态检查与 G08 新会话审计分别证明。既有直接打开的 Codex App/TUI 若没有经过 Bridge 启动器，没有机械上必读保障，不宣称已保护；见 C2。



## 5. 能力包 B：当前分支同步与安全只读检查

### B1. 入站同名已有分支严格快进

提议唯一动态入口 `ai-bridge host sync-current-branch --expected-repo <owner/repo> --expected-branch <already-selected-branch>`，与 0.9.0 `publish-current-branch` 构成“入站快进 / 出站普通发布”对偶，不提供任意 branch checkout 功能。

安全前置条件：当前仓库、工作树、分支、远端 `origin`、同名上游已建立；本地 `refs/heads/X` 的 tracking 正好为 `origin/refs/heads/X`，远端 X 已存在，禁止隐式新分支或换 upstream；初始工作树/暂存区干净（包括有覆盖风险的未追踪内容，具体与 Git 版本对齐）；取回准确 origin/X OID，核实本地 HEAD 是其祖先；只对当前已检出分支严格快进，核更新后的 HEAD == 当前取得的远端提交。清洗 Git transport/config/credential/hook/filter/fsmonitor、强制变更范围和可执行路径；沿用 0.10.0 publisher 的稳定安全视图和 GitHub HTTPS 限制，只有经额外验证的本地纯仓库场景才能另论。网络失败/非快进/dirty/错仓库/错分支/错误配置均不修改目标，或者在运行中失败时明确精确前后状态与人工可恢复性，禁止内置 raw 更宽权限回退。

“直接 `git pull --ff-only origin X`”看似更简单，但前缀规则不能识别 X 是当前分支、是否追踪同名 origin、是否干净、是否有危险额外参数、远端是否可靠，因此**不全局允许**。用户已经明确同一工作分支的普通更新，不应再要求逐字提供 raw Git 授权。

### B2. 本地 Git/GitHub 安全观察：直接规则优先

审查后才扩充 Host execpolicy 的小型**形状可证明安全**原生命令集合：`git branch --show-current`、限定的 `git rev-parse`、`git worktree list --porcelain`、`git ls-files`、安全状态显示、配置好的远端只读信息及窄 `gh ... view/list` 命令；先证明这些固定前缀及其**任意尾随参数**不会开启写入、执行外部程序、读出凭据或跨仓库定位。真实 `codex execpolicy check` 是必要检查，不能仅数规则存在。

特别保守处理 `git diff/log/show`：`--ext-diff`、textconv、pager、属性文件、外部配置、子模块 helper、路径选择和尾随选项可能执行程序或改变作用域。未经净化/结构可证明，不直接开放通用前缀；优先选择原生显式安全参数且实际 execpolicy 验证足够窄的子形状，不成立则保持 gated。拒绝“只因 read-only 子命令名称安全就直接 allow”的形式证明。简单 `git status` 也检查可能的 fsmonitor/index 刷新副作用及受保护 Git 目录，必要时使用只读/无可执行过滤的本机安全方式。

已有 0.9.0 `gh auth status --`、受限列表及发布器不能重复重做。对 `git ls-remote origin` 需先证明有效 fetch URL 不会重写为危险 helper/custom transport；否则经现有动态身份防线处理，不泛化 `ls-remote <URL>`。不为每个常见只读命令建立单独的 Bridge 包装入口。

### B3. 既有包装器裁减

`ai-bridge plugin-replay` 保留既有生产能力与安全回归，开展一次有限只读用途/真实消费清点，与官方本机插件安装、重装、fresh-session 测试比较。其独特的可信本机私有输入、隔离写入与无人值守 child 能力如仍不可替代则保留；若已有成熟正常入口可替代，0.11.0 再提兼容迁移和逐步退役，无真实证据不得突然删除。无新增“万能审批绕行”框架；Reviewed 的现有三个受限功能性入口不是多余 Git status 包装器。

## 6. 能力包 C：规则预算、任务启动就绪与分发身份

### C1. `ai-bridge validate --strict` 的有效指令预算

必须按**实际受影响 Codex 可执行版本**决定发现规则。基于 2026-10-12 读到的当前官方源码模型：选有效工作树/当前目录/项目根，遵循根标记与多层配置可信度；从项目根到 cwd 每层依序检查 `AGENTS.override.md`、`AGENTS.md`、已配置回退名称，**一层取一个**；对每一实际选中文件按原始字节累计并给出剩余额度。全局用户指令和项目预算分开计量；多执行环境的同一总项目预算不能被错误按环境重置；实际版本对空 override/非 UTF-8/符号链接的处理要从源码与新鲜运行复核，不能推断。非自动发现的 Markdown 引用不计入默认预算。

从真正的有效配置中确定 `project_doc_max_bytes`，包括具体 `CODEX_HOME`、项目受信任状态、config 层、启动时 overrides、目录以及根标记；能核实则报告整数和来源，不能观测 session-only 覆盖时明确 `UNVERIFIED`。逐文件记录规范路径、选择优先级、原始 UTF-8 字节数、已读字节、累计/剩余、准确截断字节位置及可能损坏的 Unicode 边界；检查 BOM、CRLF、多字节、有效覆盖、重复托管块/缺少成对标记；托管块只作为文件内部字节计量一次，不能双计。明确指出**哪些尾部没有被加载**，不得只输出“文件太大”。

严格模式中确认超预算、截断有效必需控制文本或托管标记格式损坏时 **非零退出**；未知发现/配置情形返回带原因的未验证，不能 `RULE_LOADING_PASS`。非严格模式保留既有兼容性，允许准确警告。静态预算通过只能称静态验证，通过后仍需真实新会话加载证据，**不可用关键词打印代替**。前述 Bridge 根 39,688 字节作为通用回归；不得为了让测试绿而删改控制语义。

### C2. 必然被调用的启动就绪关卡及其真正覆盖范围（修订 BC11-D02）

**现有生产源码证明的事实**：

- `ai_bridge_kit/cli.py:validate_workspace()` 只检查 Lite 项目结构与协议，不启动执行者；现有 CLI 仅提供 `init`、`validate`、host 等；`init_workspace()` 在第 273–279 行提示“Codex 自己读 AGENTS/任务”，因此**现有 Lite 没有能自动阻断直接 Codex 会话的启动点**。
- `ai_bridge_kit/reviewed_runner.py:watcher_once()` 在大致第 891–950 行选择任务、同步分支并调用 `run_codex_event()`；`run_codex_event()` 第 776–819 行唯一执行 `subprocess.run([codex_bin, "exec", "-C", target, "-"])`。这是 **Bridge 实际拥有的**、可在启动前硬性阻断的入口；目前 `executor_prompt()` 只是让子进程“去读 REQUEST/PLAN/CURRENT”，没有由启动器亲自验证读取并提供内容。
- `ai_bridge_kit/agent_flow.py` 的 `task init`、`transition plan/apply`、`prompt <role>` 管流程状态/角色提示词，`RuntimeAdapter.launch_role` 是抽象接口，**没有 Bridge 生产级通用 Codex 角色启动器**。不得因为 Control 的状态转为 `EXECUTOR_RUNNING` 就声称检查一定先于外部角色启动。
- `plugin-replay` 是不同的插件回放/沙盒语义，不能拿来代替普通任务启动，也不把其特殊子进程策略扩散到 Lite/Reviewed/Control。

**0.11.0 的确定性入口表（仅增加最少一个通用启动表面）**：

| 正常入口与所有权 | 谁实际调用，何时 | 必需的检查和阻断 | 能宣称的范围 |
|---|---|---|---|
| 现有 `ai-bridge reviewed-handoff watcher once/run/start` → `watcher_once` → `run_codex_event` | Bridge 已经亲自创建子 Codex | 在任何分支同步前做只读机器/工作树身份检查；在同步、CURRENT/REQUEST/PLAN 定位后、`record_event_start` 前做项目预算和所有 mandatory control source 读取；在直接进入 `run_codex_event` 时再次做同一入口 guard，才允许 subprocess.run | **强制门禁**：任务不满足则既不启动 Codex，也不消耗 Executor attempts/review budget、不跳转 BLOCKED；现有 watcher 记录精确可恢复启动失败原因 |

**共享一次性预检内核**（不是长期控制服务）被上述拥有的入口同步调用：固定当前仓库/工作树/分支/Goal/必读 ref；有效 `CODEX_HOME`、真正被选中的 codex 可执行路径及版本、Host managed 文件/策略、可执行文件与已导入 Bridge 包及正式 release 身份；按当前 runtime 的项目发现顺序与真实配置计算 root/nested 指令字节预算和重复管理标记；按 A3/A4 取得并核对**全部必需**权威文件字节。任何一项“确定不符”非零阻止启动，未知且影响强制效果时 `UNVERIFIED_REQUIRED` 也阻止该入口，**不能因为主仓库本身 `README` 记载了当前版本就视安装正确**。对项目不存在 Lite 可选模板的情况，只验证该入口相关的必需结构，不将所有不相关的可选模板警告错误升级为普遍失败。

**实际入口的调用顺序、成果保留和恢复**：

1. Reviewed watcher 第一次接触任务前只读 Host/分支身份；允许已有安全授权的同步准备，但**不以同步前的旧 Goal 为当前 Goal**。同步后重新读取当前冻结 REQUEST/PLAN/CURRENT，执行严格项目/Host/必读源预检，先于 `record_event_start()` 和 `subprocess.run()`。如果项目根规则截断，即使模型尚未启动也返回明确无法执行；如果部分克隆缺 blob，A3 可读取，失败留在源缺失。
2. Lite 的新一次性入口做同样完整预检→成功才拼接具体已读源和 Goal→固定 `codex exec -C`、使用原本用户批准的默认沙盒/审批设置，不添加 `approval_policy=never`、`danger-full-access` 或任意透传 flag；不自动变更分支/安装/发布。失败**不会消耗付费 Codex 调用**，直接告知最小更新/来源缺口与恢复同一任务的命令；这不是替代原生交互界面。
3. Control 的现有状态/提示 CLI 严格关卡不改旧 state machine；若外部 RuntimeAdapter 自己发起执行，它必须额外证明等价的 prelaunch 调用，而非靠 AGENTS 文本保证。未核实的外部受托启动不得作为 G04/G09 的正例。
4. 需要修 Host Policy 时仅给一次受限外部更新入口，在得到真实用户/平台授权后对**当前** `CODEX_HOME` 备份并更新 Bridge-owned 文件；配置只能在新 Codex 会话确定生效。保留旧任务键、工作树、已完成效果、冻结 Goal 与恢复点；Reviewed watcher 停在可恢复等待，不计为 Executor 不进展；Lite 再次调用同一个 `ai-bridge task run`。如果依赖资料在检查与子会话启动之间改变，拒绝旧身份、不继续错误候选。
5. 新会话运行时的 **G08 行为校验** 是独立发布门禁：应在与候选安装、CODEX_HOME、目录、配置一致的 fresh Codex 上对实际加载的必需规则做受控 canary，并核会话来源/加载证据和可观察行为；不能用静态字数、字符串 grep 或“模型自报已读”代替。每个任务的启动器能硬性保证**文件字节可读并输入上下文**，不等同于逐条证明模型都遵守了全部项目规则；超过可见范围时输出 `RUNTIME_RULE_CONSUMPTION_NOT_PROVEN`，不伪装 G08 PASS。

**验收负例**：手动直开 Codex 会话仍可能在过长 AGENTS 上开始工作，是已经明确披露的**不受控入口**；若审查要求对所有原生会话强制执行，必须依赖未来有实际支持的 Codex 原生启动钩子/配置机制并重新独立审查，不能凭一个额外 CLI 文件声称已实现。这里既不制造新的跨会话状态机，也不自行修改用户 CODEX_HOME。



### C3. 安全修复和同 Goal 恢复

不在运行中的 Codex 会话强求热重载；除非真实 API/Host 权限有可证明的安全更新与生效回执，否则先保存原 Goal/worktree/branch/dirty state/checkpoint 和所有已完成 effects，给出**一次受限外部更新**：由现有 `host install/validate` 在用户允许的活跃 `CODEX_HOME` 上仅修改 Bridge 托管文件、先备份、拒绝链接逃逸/任意配置覆盖，随后开新 Codex 会话，重新按原 Goal 定位、验证并继续。未经本次相应权限不实际安装、不新增网络源、不默改其他 `CODEX_HOME`。已确认同一效果授权不因 fresh session 丢失业务意图；是否被平台审批接受必须由真实入口验证，不能自行取消平台的合法门槛。

### C4. 版本叙述闭环

区分：`main` 开发候选、移动 `release` 正式目标、机器上实际安装并导入的发布包。严格对比来源、SHA、版本和发行元数据，避免 `main` 文档提交导致假漂移；安装冲突严重程度取决于**实际导入的运行代码和命令路径**是否混用，不能把所有多份历史元数据自动判 fatal，也不能把真实冲突一律 warning。正式关闭阶段按现有 AI Skills Maintainer 生产者合同更新 README、CHANGELOG、版本和 `release`，并读回远端验证；**本 Planner 阶段一概不做**。

## 7. 能力包 D：授权、人工专属输入与拒绝恢复

权限区分三层：当前用户在本次会话中给出的具体效果授权；Goal/AGENTS 的任务内容及权限线索（**不能自授权**）；已由用户配置的机器层受边界约束预授权及平台真实沙盒/审批。执行器不能从“repo 文件写了 authorized”推断当前用户已授权；当前用户已经对同一 repo、工作树、分支、路径、来源、用途、外部副作用明确授权后，也不得在后续同一效果内部把一次授权拆成多个 `HUMAN_ONLY` 请求。命令运行被平台拒绝不等于用户不存在授权；要分别报告平台能力/权限边界。

必须 `HUMAN_ONLY` 时，一次说明：**拟执行什么**、**当前已授什么**、**新增或缺失的确切效果/范围**、**为何原授权不能覆盖**；若四项对比后没有新增权限或效果，禁止重复问“是否授权”来掩盖执行路径缺陷。真正必须用户参与的凭据、账号、付费、外部发布、不可逆效果继续使用原审批。

每次拒绝归为 `OPTIONAL_NOT_REQUIRED` / `SANDBOX_CAPABLE_BUT_ESCALATED` / `BOUNDED_NORMAL_ENTRY_BLOCKER` / `TRUE_AUTHORITY_OR_SAFETY_BOUNDARY`。可选诊断被拒继续必须工作；普通沙盒操作误升级则回正常沙盒；受限入口失败只报告该精确 effect 并保留局部成功，不能继续 raw `git push`、任意 `git worktree` 或追加更大升级；真实权限边界进入合法人工/Planner/STOP。相同拒绝未改变来源/效果/运行时信息前只允许一次分类及受限重路由，不能串行请求不同高权限变体。build、render、QA、commit 等已经完成的效果按准确阶段保留，发布失败不使前面实际通过的事实失效，也不代表总体完成。

安全性实质要求：新受限 helper 的形状和默认 preauthorization **不能**让恶意仓库 Goal 单凭文本授予分支拓扑权限。**双脏关联工作树交换不会获得机器全局免审批前缀**；只有当前用户直接给出确定的双端搬迁授权，并且平台许可已生效，才允许作为一次完整受限效果执行。对用户明确要求的工作树搬迁等更高影响效果，只有实际经过一次当前用户指令/受限机器层权限及真实命令安全检查的路径才可执行；不得仅增加一个 `--authorized` 布尔参数当伪授权，不能设 `approval_policy=never` 或关闭沙盒。运行时若既没有可合法执行的受限路径也没有现有平台许可，必须按真正阻断报告，而非使用扩大权限的另一命令。

## 8. 原生机制 vs 受限 Bridge 入口：受 D01–D03 修订的最小取舍

| 功能 | 首选原生机制 | 仅必要时的 Bridge 受限入口 | 不能宣称 / 禁止 |
|---|---|---|---|
| 不同分支两个长期 worktree | 已有工作树和 `git worktree list`；**不移动** | 无 | 不做仓库级单任务互斥、不自动收拢 |
| 双脏且目标分支真实占用 | **两个普通关联工作树**可用三步 `git worktree move` 交换，已在 Linux Git 2.47.3 暂存/未暂存/未追踪 + 故障回滚演练成功 | 如三步命令的单次权限/动态状态无法可靠核验，只做一个“预核验→三步 Git→后验/反向恢复”的受限操作；只接收用户确认的双最终位置，不全局预授权 | 主工作树、子模块、跨卷、锁、活跃句柄、不明符号链接或未许可位置一律 `UNSUPPORTED_WITH_EVIDENCE`；不称覆盖所有原故障拓扑 |
| partial clone 缺 mandatory blob | `GIT_OBJECT_DIRECTORY` 写隔离 O、原 `.git/objects` 为只读候补、固定 OID `cat-file` 按需获取；本地可丢弃受保护 .git 实验已成功 | 一个 `read-control-file` 仅证明 repo/origin/frozen OID/白名单控制文件/安全传输/无原元数据写；否者停依赖效果 | 不开放任意 `git show`，不推断 HTTPS/凭据/Codex 真实 Host Gate 已通过 |
| 当前非 main 同名快进 | Git 原生快进 | v0.1 已拟定的 `sync-current-branch` 动态检查保持不变 | 不允许通用 pull/branch/remote |
| 安全只读观察 | 固定形状原生命令 | 常规观察不加 wrapper | 有 textconv/ext-diff/helper 的泛化形状仍 gated |
| 项目规则静态校验 | 现有 `validate --strict` + 有效 Codex 配置计算 | 内核复用，不新增规则服务 | 静态通过不等于新会话消费通过 |
| Bridge 实际任务启动 | Reviewed 现有 watcher→`run_codex_event`；Control 原状态/提示 CLI | **仅 Lite 增加一次性 `ai-bridge task run`**，内部做同一只读 preflight 再启动原生 Codex CLI | 用户直接打开原生 Codex 不受保证，不以 AGENTS 文本替代进程入口 |
| stale Host 恢复 | 原 `host install/validate` + fresh session | 无自动后台自刷新 | 不热重载、不改未授权 CODEX_HOME |
| Persistent Run 定期真实进度 | 现有进度来源、latest/history、Notifier | 仅保留 v0.1 的有限现有进程/调度器通知适配 | 不新增 daemon、自动决策、假 ETA |

本表没有降低 A、B、C、D 四包的目标；它只把 D01 受支持范围、D02 真实拥有的启动位置与 D03 已验证的安全读取路线固定下来。相比“仅靠原生命令、不建 helper”，A2 的准确两树交换在单次封装必要时使用受限动作；D03 的动态源检查需小型可信受限入口；普通 Git 检查不包装。任何帮助程序都不具有因存在于 repo 中而自授权的资格。

## 11. 安全、失败恢复与角色/权限边界

- **当前阶段**：Planner 只写此文档；Critic 独立核实并对 v0.1 给 `PASS` 或 `REVISE`。PASS 仅批准设计，不批准 implementation、Machine Policy、CODEX_HOME、消费者修改或移动 release。
- **后续若 PASS**：Planner 按角色合同另备一致版本的完整执行 Plan、Canonical Goal、Kickoff Draft 给 Critic 做 execution-ready review；这不是本轮已授权的实现动作。本次不提前写高权限 Codex 执行提示词。
- **本机权限**：裸 Git 危险变更、机器策略写入、发布 ref、外部/付费/凭据、跨 repo 消费者更改，均需所适用的用户实际授权/平台准许；不生成通用 allow、`danger-full-access`、`approval_policy=never`、脚本/R/Python/shell 任意执行预授权。
- **可恢复但不虚假完成**：一次外部更新 + fresh session 是被接受的安全路线；工作树重绑定失败时保留两个 dirty 集合及恢复证据；partial clone 读不到强制文件则停依赖操作；发行未完成则不可宣称全面交付。
- **不新增**：权限数据库、程序级任务控制面、新工作流/状态机、无穷重试、每个拒绝一层包装、repo-specific STAT5060/Lucerna 判断；AI Skills 领域 QA 不归 Bridge。
- **进度残余**：不把 Persistent Run 的本机报告器变成自动控制器；来源任务应提供真实进度，交给既有可用通知器；没有已授权投递表面时不宣称用户会自动收到消息。
- **应中止和回 Planner 的条件**：受限双关联工作树恢复在拟支持平台无法完整验证；字节规则与目标运行时发现行为无法核实；新 helper 需要更大 Git 权限/新的平台授权方案；Host Policy 执行前验证不能接入真实任务入口；已有发布能力产生安全回归。实现中的局部修复不改变方案时不为每条 bug 重新发起审查。

## 12. 0.11.0 如何既不过重也不过简

只改常见开发时必经的四个接缝：工作地点和强制资料、已有分支与安全诊断、有效规则与环境、拒绝后的相同效果恢复。所有“更大更好的长期运行”想法都没有自动成为新能力，第三方原生 Git 优先复用；候选新增受限入口总数保持非常少，每一个都须说明静态规则无法核验的动态安全条件。现有 Reviewed 和持久运行语义不被升级成统一控制器。

反过来，只写“注意遵守 AGENTS，不要申请权限”又太简：39,688 字节根文件在默认预算下可能先被截断，partial clone 对象写受沙盒限制、Git 分支持有人与 dirty 状态不能靠自然语言安全检查、当前实际安装身份可能不同于仓库版本。这些需要真实正常入口与受限代码逻辑。**以真实用户行动次数减少、任务不漂移、控制源真正消费、危险邻近行为仍拦截，以及一次失败后成果保存作为成败标准；不以新增规则/包装器/回执数量作为成就。**

## 13. Critic 特别需要独立反证的六点

1. 双脏工作树恢复：主工作树不可 `worktree move`，受限置换能否在实际受支持文件系统安全实现并自动回滚？是否应按路径/工作树类型收窄支持，而不是为了“无损”发明更危险的通用 Git 事务？
2. `GIT_OBJECT_DIRECTORY` + 只读候补对象库能否在当前 Git/partial clone/沙盒中真正完成缺 blob 读取，是否隐含 `.git/FETCH_HEAD`、配置 helper 或新权限写入？有无不增加 wrapper 的更成熟路径？
3. `prefix_rule` 对尾随参数与环境的匹配是否足以直接放行所选 Git/gh 命令；尤其 `status` 的 fsmonitor、`show/diff/log` 的可执行扩展和 `ls-remote origin` 传输重写？
4. 有效项目指令预算是否忠实于**实际受影响安装版本**，而不是照抄 2026-10-12 官方 main 的源代码；32,768 字节截断、空 override、配置可信度、工作目录和跨环境累计的关键条件是否准确？
5. `host task-preflight` 的真正消费点能否防止规则截断后继续进行实质工作；当前 CLI 组合是否足够，还是“新命令存在≠运行前必调用”？
6. 已经直接授权的效果与平台 sandbox/Auto-review 拒绝如何在**不建立授权数据库、不信任仓库自称授权、不加 broad allow**前提下形成合法一次执行路径；0.10.0 启动器层拒绝不能冒充新鲜 child 的真实拒绝证据。
