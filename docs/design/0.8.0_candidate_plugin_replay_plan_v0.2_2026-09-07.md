# Bridge Kit 0.8.0 Candidate Plugin Replay Design Plan

Plan version: **0.2**

Target Bridge Kit release: **0.8.0**

Status: **DRAFT / READY FOR CRITIC REVIEW / NOT EXECUTION AUTHORIZATION**

Current Bridge Kit implementation baseline: `0.7.1` at `3b061167794d593b113ca8f4a8a43c4c8000fc01`.

Prior design revision: `docs/design/0.8.0_candidate_plugin_replay_plan_v0.1_2026-09-07.md` at Bridge Kit commit `cba38647feb1b34bf00b9801e75b67c1961ca2b1`.

Current Codex source inspected for this revision: `openai/codex` `main` at `9f70e348e0227980de97e361cce830236fb18317`.

Primary real consumer trigger: `YuukiAS/AI_Skills_Collection` task `051_writing_style_rebuild`. Its frozen Plan requires an ordinary installed-plugin black-box replay of the candidate `writing-style` build, while Bridge Kit `0.7.1` can replay only plugins already installed in the current Codex identity.

This revision is intentionally narrow. It keeps the v0.1 product boundary, command name, version decision, current-identity lock/journal model, Host Policy boundary, consumer/Bridge responsibility split, and existing `plugin-replay` semantics. It revises only the runtime alternative selection, committed candidate-source lookup, crash ordering/lock semantics, and effective-plugin/no-persistence evidence.

---

## 0. Why this plan exists

Bridge Kit `0.7.1` solved a different lifecycle problem:

```text
already-installed production plugin
-> bounded fresh Codex replay
```

A real AI_Skills production task has now exposed the missing next lifecycle step:

```text
candidate Git commit
-> temporary real plugin installation
-> fresh Codex black-box replay
-> cleanup
```

This distinction matters. A consumer plugin cannot honestly prove its ordinary production entrypoint merely by reading source `SKILL.md`, calling a helper, or forcing a hidden subskill. It must run the candidate through the actual Codex plugin runtime before release.

The 051 failure is therefore not evidence that its writing architecture is wrong. It is evidence that Bridge Kit lacks a reusable way to test a not-yet-released plugin candidate without permanently replacing the user's installed production plugin.

The goal of 0.8.0 is to add exactly that missing capability and no larger deployment system.

## 1. Verified reality

### 1.1 Bridge Kit 0.7.1 boundary

`ai_bridge_kit/plugin_replay.py` deliberately:

- resolves the current Codex identity from the current `CODEX_HOME`;
- rejects selection of another Codex identity;
- requires the requested plugin to already be installed/enabled in that identity;
- stages only explicit task/input files;
- launches a fresh Codex child in a write-isolated replay workspace;
- does not allow arbitrary Codex flag passthrough.

This is correct behavior for `plugin-replay` and must remain unchanged.

### 1.2 AI_Skills 051 requirement

The frozen 051 Plan requires a normal installed `writing-style` replay where the user-facing prompt does not name internal heavy-route components. A forced `scientific-rewrite` invocation is diagnostic only.

Therefore replaying the current production `writing-style@yuukias-ai-skills` cannot prove the candidate branch works. The exact candidate build must enter the real Codex plugin runtime first.

### 1.3 Current Codex plugin/config primitives

Official Codex source at `9f70e348e0227980de97e361cce830236fb18317` confirms the following:

- `codex plugin` exposes `CliConfigOverrides`, so plugin subcommands accept process-local `-c` config overrides;
- `run_plugin_add()` receives those parsed overrides, loads configuration through `Config::load_with_cli_overrides(...)`, then resolves the requested plugin from the resulting effective marketplace configuration before installing it;
- `codex plugin add PLUGIN@MARKETPLACE --json` reports the concrete installed plugin identity/path;
- `codex plugin list --json` reports installed/enabled state and source information for configured marketplace plugins;
- `codex plugin remove PLUGIN@MARKETPLACE --json` uninstalls the plugin, and current Codex tests explicitly cover removal of plugin cache/config entries;
- configured local marketplaces use effective config entries of the form `[marketplaces.<name>] source_type = "local"; source = <path>`;
- the canonical repository marketplace manifest is `.agents/plugins/marketplace.json`, and a local plugin entry declares `source.source = "local"` plus a path relative to the marketplace root;
- `codex exec --ignore-user-config` is explicitly documented as not loading `$CODEX_HOME/config.toml` while authentication still uses the same `CODEX_HOME`;
- current `codex exec` source feeds both `ignore_user_config` loader semantics and parsed CLI `-c` overrides into configuration building, so these mechanisms are designed to coexist.

This exposes a smaller candidate path than v0.1: Bridge can potentially provide a candidate marketplace only through process-local `-c`, install the candidate from that effective marketplace, and avoid persistent `marketplace add/remove` entirely.

### 1.4 What remains inference until a real smoke

Two facts are not frozen as production behavior from source reading alone:

1. An uninstalled candidate may or may not become an effective runtime plugin from repo/cwd marketplace discovery without any install at all. Current source still suggests **no**, but one bounded smoke remains cheaper than building on an assumption.
2. `codex exec --ignore-user-config` plus Bridge-owned candidate marketplace/plugin `-c` overrides may give the fresh child a clean candidate-only plugin view while retaining usable same-identity authentication. This is plausible from source, but the actual installed runtime may also depend on user model/provider/proxy configuration that `--ignore-user-config` removes, and project/managed layers are separate from the user config layer.

Therefore 0.8.0 does not freeze B0 as production until the Phase-0 real smoke succeeds.

One narrow correction to the Critic's proposed proof: current Codex source exposes `--ignore-user-config` on the **exec** CLI, while `codex plugin` exposes `-c` overrides but not the same loader flag. Consequently `codex plugin list --json` is useful preflight evidence, but under B0 it cannot by itself prove the exact `exec --ignore-user-config` effective plugin set. The authoritative B0 proof must combine that preflight with a generic candidate plugin whose harmless observable behavior is consumed by the fresh child.

## 2. Product target

After 0.8.0, a trusted local developer/repository workflow should be able to say, in effect:

> Test plugin `writing-style` exactly as built at candidate commit `abc123`, through a fresh Codex runtime, while leaving the installed production `writing-style` intact after the run.

The stable Bridge Kit product boundary is:

```text
ai-bridge candidate-plugin-replay ...
```

This is a sibling of `plugin-replay`, not an extension of it.

Expected normal shape:

```bash
ai-bridge candidate-plugin-replay \
  --target /path/to/repo \
  --plugin writing-style \
  --candidate-commit <sha> \
  --task <explicit-task-file> \
  --input <explicit-input-file>
```

The caller does **not** get to provide:

- another `CODEX_HOME`;
- arbitrary Codex `-c` overrides;
- arbitrary candidate marketplace names;
- arbitrary additional writable roots;
- raw `codex plugin add/remove` command fragments;
- an arbitrary plugin directory outside the candidate Git commit;
- a `--plugin-path` escape hatch.

---

## 3. Version decision

Target release: **0.8.0**, not `0.7.2`.

Reason: this adds a distinct user capability that 0.7.x does not have:

```text
0.7.x: replay an already-installed plugin
0.8.0: replay a not-yet-released candidate plugin commit through the real plugin runtime
```

This is a new Bridge Kit lifecycle capability, not a compatibility patch to Goal Fidelity or Review Plan validation.

No new Review/Lite/Control role, workflow state, task schema, queue, controller, or ledger is justified by this feature.

## 4. Alternatives

### A. Repo-workspace marketplace discovery without install

Idea:

```text
replay workspace
├── .agents/plugins/marketplace.json
└── plugins/<candidate>/
```

and ask fresh `codex exec` to consume the candidate without plugin installation.

Decision: **bounded Phase-0 smoke only**.

Current official Codex source still indicates effective runtime plugin loading is configuration/store based rather than guaranteed from cwd marketplace presence alone. Run one real probe, capped at roughly ten minutes and requiring no Bridge subsystem.

If A unexpectedly succeeds and the exact candidate identity/runtime consumption can be proven, stop and return to Critic. Do not silently redesign implementation around A.

### B0. Process-local candidate marketplace + persistent plugin install + `--ignore-user-config` child

Decision: **preferred production architecture if the bounded real smoke passes**.

Use a Bridge-generated local marketplace only through `-c` overrides for the plugin command and child runtime. Do **not** run persistent `codex plugin marketplace add/remove`.

Conceptually:

```text
Bridge staging marketplace
    ↓ process-local -c marketplaces.<candidate>=<staging-root>
codex plugin add candidate@candidate-marketplace
    ↓
installed candidate cache/config entry
    ↓
codex exec --ignore-user-config
    + same candidate marketplace -c
    + candidate plugin enabled -c
    + existing fixed replay sandbox/config overrides
    ↓
candidate runtime behavior
    ↓
codex plugin remove candidate@candidate-marketplace
```

This reduces persistent mutation from marketplace + plugin registry changes to candidate plugin install/remove only.

B0 passes only if the actual installed Codex runtime can execute a real generic candidate task with the same current `CODEX_HOME` authentication without copying arbitrary user configuration into the child. If model/provider/proxy or other essential runtime state is lost and cannot be supplied by the existing bounded replay contract, B0 fails; do not create a user-config copying layer to rescue it.

### B1. Persistent temporary marketplace + plugin install + explicit same-name disable

Decision: **fallback production architecture only if B0 fails and B1 smoke passes**.

This is the v0.1 design:

```text
codex plugin marketplace add <staging-root>
codex plugin add candidate@candidate-marketplace
fresh child with explicit same-name production disables
candidate enabled process-locally
replay
codex plugin remove candidate@candidate-marketplace
codex plugin marketplace remove <candidate-marketplace>
```

It remains acceptable because it uses supported Codex primitives and owned cleanup, but it touches more persistent registry state than B0.

Do not choose B1 merely because it is already designed. B0 gets first right of refusal.

### C. Switch to another `CODEX_HOME`

Rejected.

It reopens identity/authentication copying, credential-scope, and cross-identity Host Policy problems that existing `plugin-replay` intentionally avoids.

### D. Temporarily overwrite the production plugin/cache

Rejected.

It makes the production plugin itself unavailable or ambiguous during replay, creates a much more dangerous rollback problem, and can affect unrelated sessions.

### E. Full environment snapshot/restore transaction

Rejected.

Bridge Kit must not snapshot and restore every marketplace, plugin, config file, or cache. Unrelated concurrent user changes remain out of scope. Cleanup owns only resources this run created.

### Frozen selection rule

Phase 0 chooses the smallest proven path:

```text
Smoke A succeeds
    -> return to Critic; no implementation

Smoke A does not establish runtime loading
    -> Smoke B0

Smoke B0 succeeds
    -> freeze B0 for implementation

Smoke B0 fails
    -> Smoke B1

Smoke B1 succeeds
    -> freeze B1 for implementation

Smoke B1 fails
    -> NOT READY FOR IMPLEMENTATION
```

Executor does not invent a fourth fallback.

## 5. Candidate runtime flow

### 5.1 Preferred B0 flow

```text
candidate commit
    ↓
validate commit
    ↓
read committed .agents/plugins/marketplace.json
    ↓
resolve unique local source for --plugin
    ↓
stage one-plugin local marketplace under Bridge machine state
    ↓
generate unique marketplace: ai-bridge-candidate-<run-id>
    ↓
acquire current-CODEX_HOME OS lock
    ↓
atomically write active.json BEFORE first persistent mutation
    ↓
codex plugin add <plugin>@ai-bridge-candidate-<run-id>
    using Bridge-owned process-local marketplace -c
    ↓
verify staged tree == installed candidate tree
    ↓
effective-plugin preflight
    ↓
hash $CODEX_HOME/config.toml
    ↓
fresh codex exec
    - same current CODEX_HOME authentication
    - --ignore-user-config
    - Bridge-owned candidate marketplace -c
    - Bridge-owned candidate enabled -c
    - existing fixed replay sandbox/approval/config overrides
    - natural consumer task unchanged
    ↓
hash $CODEX_HOME/config.toml again BEFORE cleanup
    ↓
require child-period hash unchanged
    ↓
local replay outputs / downstream domain receipt
    ↓
codex plugin remove candidate
    ↓
remove staging directory
    ↓
verify owned cleanup + production plugin unchanged
    ↓
clear journal + release lock
```

B0 does not persist a marketplace registration.

### 5.2 Fallback B1 flow

If and only if B0 fails its bounded runtime proof:

```text
candidate commit
    ↓
committed marketplace lookup + staging
    ↓
unique Bridge candidate marketplace identity
    ↓
acquire current-CODEX_HOME OS lock
    ↓
atomically write active.json BEFORE first persistent mutation
    ↓
codex plugin marketplace add <staging-root>
    ↓
codex plugin add <plugin>@candidate-marketplace
    ↓
verify staged tree == installed candidate tree
    ↓
effective-plugin preflight
    ↓
hash $CODEX_HOME/config.toml
    ↓
fresh codex exec
    - same current CODEX_HOME
    - explicit process-local disable for every pre-existing same-name identity
    - candidate enabled process-locally
    - existing fixed replay sandbox/approval/config overrides
    - natural consumer task unchanged
    ↓
hash $CODEX_HOME/config.toml again BEFORE cleanup
    ↓
require child-period hash unchanged
    ↓
remove candidate plugin
    ↓
remove candidate marketplace
    ↓
remove staging directory
    ↓
verify owned cleanup + production plugin unchanged
    ↓
clear journal + release lock
```

The user's normal production plugin remains installed throughout both modes. The candidate is a distinct plugin identity because the Bridge-generated marketplace name differs.

## 6. Candidate identity and staging

### 6.1 Candidate must be a Git commit

Require `--candidate-commit <sha>` to resolve to a real commit inside the target Git repository:

```text
git cat-file -e <sha>^{commit}
```

Candidate source is read from the Git tree, not the working tree. Dirty/untracked files must not affect the candidate.

### 6.2 Generic committed plugin locator

Do not hard-code:

```text
plugins/codex/plugins/<plugin>/
```

as the Bridge product contract.

Instead, read exactly this file from the candidate commit:

```text
.agents/plugins/marketplace.json
```

Then:

1. find entries whose `name` exactly equals `--plugin`;
2. require exactly one match;
3. require `source.source == "local"`;
4. require a non-empty relative `source.path`;
5. resolve that path relative to the committed marketplace root;
6. require the resolved path to remain inside the candidate commit tree and to identify a committed plugin directory;
7. stage that committed plugin tree.

If the manifest is missing, the plugin name has zero/multiple matches, the source is non-local, the path escapes the repository root, or the committed directory is missing, fail closed.

Do not add `--plugin-path`, source adapters, fallback directory guessing, or a new marketplace schema in 0.8.0.

The source marketplace's own name is not trusted as the runtime candidate identity. Bridge still generates its unique `ai-bridge-candidate-<run-id>` marketplace name for the replay transaction.

### 6.3 Staged marketplace

Bridge Kit constructs a machine-local staging root under its own state directory, for example:

```text
${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/candidate-replay/<identity-id>/<run-id>/marketplace/
```

The staging root contains only:

- the candidate plugin tree resolved from the frozen commit manifest;
- a minimal `.agents/plugins/marketplace.json` pointing to that staged local plugin;
- no unrelated repository source.

The marketplace name is Bridge-generated and caller-unselectable:

```text
ai-bridge-candidate-<run-id>
```

### 6.4 Minimal provenance

Bridge records only the evidence needed to prove which build and selection ran:

```text
candidate_commit
candidate_manifest_path
candidate_source_path
staged_plugin_tree_digest
installed_plugin_id
installed_path
installed_plugin_tree_digest
effective-plugin preflight result
exact child argv / Bridge-owned config-selection set
child-period config.toml pre/post hash result
replay run/output locator
```

Do not record secrets or the contents of unrelated user config.

Bridge must not understand or validate consumer-domain receipts such as `SCIENTIFIC_REWRITE_HEAVY_ROUTE_RECEIPT_V2`. Those remain owned by the consumer workflow.

## 7. Effective plugin selection in the fresh child

Candidate installation may temporarily coexist with one or more production/test identities sharing the same plugin name, for example:

```text
writing-style@yuukias-ai-skills
writing-style@ai-bridge-candidate-<run-id>
```

Before persistent mutation, inspect and record the pre-existing installed identities whose plugin name equals the candidate name. This is evidence and, under B1, supplies the explicit same-name disable set.

### 7.1 B0 selection

B0 child selection is generated entirely by Bridge:

```text
--ignore-user-config
-c marketplaces.<candidate>.source_type="local"
-c marketplaces.<candidate>.source=<staging-root>
-c plugins."<candidate-id>".enabled=true
+ existing fixed replay overrides
```

The caller cannot supply or alter these values.

B0 does not need to persistently disable or rewrite the production plugin. It also does not copy arbitrary model/provider/proxy configuration from `$CODEX_HOME/config.toml` into the child. If the real child cannot operate under this contract, B0 fails and B1 is tested.

### 7.2 B1 selection

B1 uses the current user config and adds Bridge-generated process-local overrides equivalent to:

```text
plugins."<existing-same-name-id-1>".enabled=false
plugins."<existing-same-name-id-2>".enabled=false
plugins."<candidate-id>".enabled=true
```

All unrelated plugin identities remain untouched.

### 7.3 Effective-plugin proof

Before the fresh child, run a JSON plugin preflight under Bridge-owned process-local marketplace/plugin overrides and verify at minimum:

- candidate plugin identity is installed;
- installed path/tree digest matches the staged candidate;
- candidate is enabled under the preflight selection view;
- same-name identities are enumerated and the intended selection mode is explicit.

For B1, `codex plugin list --json` can be invoked with the same explicit same-name disable/candidate-enable `-c` set used by the child, so the preflight should show the intended effective selection directly.

For B0, do **not** claim that `codex plugin list --json` alone proves `--ignore-user-config`, because current `codex plugin` does not expose that exec loader flag. Under B0 the proof is deliberately two-part:

```text
plugin-list JSON preflight
    -> candidate is installed/resolvable/enabled under Bridge candidate config

fresh generic codex exec --ignore-user-config smoke
    -> unique harmless candidate behavior is actually consumed
```

Only the combination is sufficient.

The harness selecting **which plugin build** is under test is legitimate test infrastructure. The user task itself remains natural and must not force a hidden internal skill/stage. For AI_Skills 051, selecting the candidate `writing-style` build is allowed; writing `scientific-rewrite`, `REALIZE_MEANING`, or a heavy-route stage into the user task would still invalidate its black-box routing gate.

### 7.4 Child config no-persistence proof

Candidate install itself is an expected persistent mutation. Therefore the no-persistence check isolates the **child selection interval**:

1. after candidate installation and immediately before child launch, hash `$CODEX_HOME/config.toml`;
2. run the child;
3. immediately after child exit and before any cleanup command, hash the same file again;
4. require the two hashes to match.

A mismatch invalidates the replay evidence because Bridge can no longer prove that child `-c` / `--ignore-user-config` selection was process-local. Do not restore the file from a snapshot and do not assume Bridge caused the difference; report the mismatch and fail closed.

This check does not compare or restore the rest of the machine environment.

## 8. Reuse existing replay isolation without changing `plugin-replay`

`plugin-replay` remains semantically unchanged:

```text
installed production plugin
-> bounded fresh replay
```

`candidate-plugin-replay` may internally reuse/refactor common lower-level helpers for:

- explicit task/input staging;
- replay workspace creation;
- fixed child sandbox/approval settings;
- read-scope diagnostic;
- write-isolation canary;
- child-output/run metadata.

But public `plugin-replay` arguments, authorization semantics, identity rules, output semantics, and behavior must not gain candidate-install side effects.

A regression test must prove the existing command still behaves as 0.7.1 documents.

## 9. Persistent mutation boundary

0.8.0 must state the mutation honestly.

### B0

Persistent candidate-owned mutation is limited to:

```text
candidate plugin install/cache/config entry
```

The candidate marketplace exists only in Bridge staging and process-local `-c`; Bridge does not persistently register it.

### B1

Persistent candidate-owned mutation is:

```text
candidate marketplace registration
candidate plugin install/cache/config entry
```

In both modes:

- production plugin identity remains installed and unchanged;
- another Codex session started during the transaction may observe some candidate-owned user-state/cache effects;
- 0.8.0 does **not** claim invisibility to all concurrent Codex processes;
- cleanup never restores an environment snapshot or overwrites unrelated user changes.

If the future product requirement becomes “no other process can even observe candidate-owned state,” both B0 and B1 are insufficient and a different isolation design is required.

## 10. Lock and minimal crash journal

### 10.1 One OS-backed lock per current Codex identity

Keep one candidate-replay lock for the resolved current `CODEX_HOME` so two candidate replays cannot concurrently mutate the same plugin state.

State remains logically keyed by current Codex identity:

```text
${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/candidate-replay/<identity-id>/
├── candidate-replay.lock
└── active.json
```

`identity-id` may be a stable non-secret digest of the resolved `CODEX_HOME` path. This does not authorize caller-selected identities.

The lock must be an **OS-held exclusive lock**, or an equivalently reliable primitive whose ownership is automatically released when the owning process dies. A plain “lock file exists, therefore refuse forever” sentinel is forbidden.

Do not add a machine-global lock across different `CODEX_HOME` identities.

### 10.2 Minimal `active.json`

Keep the same small recovery record:

```text
run_id
candidate_plugin_id
candidate_marketplace_name
staging_path
phase
```

Optional candidate commit/current-identity digest remains acceptable if needed for validation. Do not turn this into a workflow state machine.

### 10.3 Journal-before-mutation ordering

`active.json` must be fully prepared and atomically installed **before the first persistent mutation**.

- Under B0: before `codex plugin add`.
- Under B1: before `codex plugin marketplace add`.

Use an atomic replace/write discipline; do not leave a window where the persistent mutation can succeed but no recovery journal exists.

After each successful persistent step, update `phase` atomically. Recovery must be idempotent: a phase may name a resource that was never created or was already removed, and safe “already absent” must not cause unrelated deletion.

### 10.4 Stale recovery

On the next candidate replay under the same current identity:

1. acquire the OS-backed lock;
2. if `active.json` exists, validate that all names/paths belong to Bridge's candidate namespace/state root;
3. remove only candidate resources named by that journal and only if they are valid Bridge-owned identities;
4. under B0, do not invent marketplace cleanup for a marketplace that was never persistently registered;
5. remove only that run's staging directory;
6. verify owned resources are absent;
7. clear the journal;
8. start the new run.

Never restore unrelated marketplaces/plugins/config from a snapshot.

If stale cleanup cannot be completed safely:

```text
CANDIDATE_REPLAY_CLEANUP_FAILED
```

and stop.

## 11. Cleanup contract

Normal cleanup belongs in `finally`, but `finally` is not sufficient for hard process termination; the journal above covers restart recovery.

Cleanup owns only resources created by the selected mode.

B0:

```text
candidate plugin
candidate staging directory
```

B1:

```text
candidate plugin
candidate marketplace
candidate staging directory
```

After cleanup, verify:

1. candidate plugin identity is absent;
2. under B1, candidate marketplace registration is absent;
3. staging directory is absent;
4. the pre-existing same-name production plugin identity/path/tree digest still matches its pre-run observation.

The child-period `config.toml` hash check happens **before** cleanup and proves only that child selection did not persist. Do not require full pre-run/post-cleanup byte identity for the entire user config, and never restore the whole config from a snapshot.

A cleanup command failure is a hard failure even if the child replay itself succeeded. Keep `active.json` when cleanup is incomplete so the next run can recover safely.

---

## 12. Host Policy

This remains a new Host Policy capability, separate from existing `plugin-replay` authorization.

Host Policy should allow only the trusted Bridge executable prefix for:

```text
ai-bridge candidate-plugin-replay ...
```

It must **not** broadly allow:

```text
codex plugin add ...
codex plugin remove ...
codex plugin marketplace add ...
codex plugin marketplace remove ...
raw codex exec ...
```

Even if B0 becomes the selected production path and no longer needs persistent marketplace add/remove, raw marketplace/plugin commands remain outside broad Host Policy authorization.

Existing `ai-bridge plugin-replay ...` authorization and behavior remain unchanged.

`ai-bridge host validate` for 0.8.0 must verify:

- the candidate wrapper has its intended narrow allow;
- raw plugin/marketplace mutation commands did not gain a broad allow rule.

Installing/upgrading Host Policy to 0.8.0 is the explicit machine-level authorization step for this new capability.

## 13. Failure behavior

Use explicit, small failure classes rather than broad fallback. Expected classes include:

```text
CANDIDATE_COMMIT_INVALID
CANDIDATE_MARKETPLACE_MANIFEST_INVALID
CANDIDATE_PLUGIN_NOT_FOUND
CANDIDATE_PLUGIN_SOURCE_INVALID
CANDIDATE_MARKETPLACE_ADD_FAILED        # B1 only
CANDIDATE_PLUGIN_ADD_FAILED
CANDIDATE_INSTALL_IDENTITY_MISMATCH
CANDIDATE_EFFECTIVE_PLUGIN_NOT_PROVEN
CANDIDATE_CHILD_CONFIG_CHANGED
CANDIDATE_REPLAY_FAILED
CANDIDATE_REPLAY_LOCKED
CANDIDATE_REPLAY_CLEANUP_FAILED
```

Names may be refined during implementation; do not create a large error taxonomy.

B0 smoke failure is not automatically a product failure because B1 is the frozen fallback. B1 failure after B0 failure means the design is not ready for implementation and must return to Planner/Critic.

A consumer-specific test failure is not converted into a Bridge infrastructure failure. Bridge may prove it ran the correct 051 candidate while `writing-style` itself returns a failed heavy-route receipt; that is a 051 product result, not `CANDIDATE_PLUGIN_ADD_FAILED`.

## 14. Tests and real evidence

### 14.1 Deterministic tests

At minimum:

- invalid/nonexistent candidate commit rejected;
- missing committed `.agents/plugins/marketplace.json` rejected;
- zero/multiple matching plugin entries rejected;
- non-local candidate source rejected;
- candidate source path escaping the committed repo root rejected;
- working-tree dirty content cannot change staged candidate tree;
- generated marketplace identity is unique and caller cannot override it;
- candidate has no `--plugin-path` bypass;
- B0 command construction does not invoke persistent marketplace add/remove;
- B1 command construction uses persistent marketplace add/remove only after B0 has been rejected by the frozen Phase-0 selection result;
- install result ID/path is parsed and installed tree digest matches staged candidate;
- same-name production identities are discovered without persistent mutation;
- B1 wrapper generates explicit same-name disable/candidate-enable overrides;
- B0 wrapper generates `--ignore-user-config` plus Bridge-owned candidate marketplace/plugin overrides;
- effective-plugin preflight is recorded;
- B0 does not treat plugin-list JSON alone as proof of exec `--ignore-user-config` semantics;
- child-period `config.toml` pre/post hashes must match;
- existing `plugin-replay` behavior remains unchanged;
- `active.json` is atomically present before the first persistent mutation in both B0 and B1;
- a killed owner releases the OS-backed candidate-replay lock rather than permanently wedging future runs;
- child/replay exception executes owned cleanup;
- cleanup command failure reports `CANDIDATE_REPLAY_CLEANUP_FAILED` and retains recovery journal;
- stale journal is recovered on the next run;
- concurrent candidate replay for the same current identity refuses the second run;
- different current `CODEX_HOME` identities do not share one machine-global lock;
- stale recovery never deletes a marketplace/plugin outside the Bridge candidate namespace.

Do not build a chaos-testing subsystem, source adapter framework, or transaction ledger.

### 14.2 Required Phase-0 real probes

#### Smoke A — bounded workspace-only discovery probe

One short probe only, roughly ten minutes maximum. No infrastructure investment.

Question: can an uninstalled candidate become the actual effective runtime plugin from repo/cwd marketplace discovery alone?

If yes with identity/runtime proof, stop and return to Critic before implementation.

If no/not proven, continue to B0.

#### Smoke B0 — process-local marketplace + `--ignore-user-config`

Use a harmless generic local test plugin with a unique observable behavior and a same-name production/test identity available for collision testing.

Required sequence/evidence:

- stage a candidate marketplace from a real committed manifest;

Run only after a genuine B0 failure.

Using the same harmless generic candidate:

## 16. Red-team paths

Before release, actively test for these fake-PASS paths:

1. candidate source was guessed from a generated directory instead of resolved from the committed marketplace manifest;
2. candidate was installed from dirty worktree state or stale cache rather than the requested commit;
3. B0 silently called persistent `marketplace add` even though its purpose is to avoid that mutation;
4. B0 was declared PASS from `plugin list` even though the fresh `exec --ignore-user-config` never consumed the candidate behavior;
5. B0 failed because user runtime config was missing and Bridge quietly copied arbitrary model/provider/proxy config into the child;
6. B1 was chosen without first attempting the bounded B0 smoke;
7. child still used production plugin while candidate appeared installed/enabled in preflight;
8. tree digest was calculated on staging but not checked at installed path;
9. production plugin was persistently disabled to make candidate selection easy;
10. child process changed user `config.toml` and the replay still claimed process-local selection;
11. persistent mutation occurred before recoverable `active.json` existed;
12. a dead process left an existence-only lock that permanently blocked replay;
13. candidate cleanup succeeded but a B1 marketplace entry remained;
14. cleanup restored an old global snapshot and overwrote an unrelated user change;
15. two candidate replays raced in one current identity;
16. state keyed by one `CODEX_HOME` caused cleanup of a different identity;
17. caller escaped candidate namespace through a custom marketplace/source path;
18. current `plugin-replay` gained candidate-install mutation as an accidental refactor side effect;
19. Bridge declared 051 Product PASS merely because the correct candidate plugin ran;
20. documentation claimed “isolated/no global effect” while candidate-owned user state/cache is temporarily observable.

Any of these blocks 0.8.0 release.
