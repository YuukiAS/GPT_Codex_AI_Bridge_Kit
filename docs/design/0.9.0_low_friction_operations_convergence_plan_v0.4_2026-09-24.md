This is a deliberately narrow amendment. It changes only one user-facing capability claim in the bounded current-branch publisher:

> the trusted low-friction publisher in 0.9.0 is a **GitHub HTTPS-only** publication path.

SSH/scp-style Git remotes are no longer a supported positive path for the trusted helper. They fail closed to ordinary raw Git approval.

Everything else in Plan v0.3 remains unchanged.

## 0. Why v0.4 is necessary

The pre-final recovery reached a single remaining gate:

```text
G4 standard SSH agent/config positive publication
```

The target environment showed:

```text
standard strict SSH -> Host key verification failed
temporary known-hosts auth probe -> Permission denied (publickey)
ssh-add -l -> no usable agent
SSH_AUTH_SOCK -> stale/nonexistent socket
```

The user's actual normal Git publication path is GitHub HTTPS, not SSH.

Current Bridge source already proves the mismatch between product scope and user need:

- the real `origin` is `https://github.com/YuukiAS/GPT_Codex_AI_Bridge_Kit.git`;
- normal bounded HTTPS publication has already succeeded;
- current `host.py` still accepts `git@github.com:...` and `ssh://git@github.com/...` as valid canonical repository identities;
- the recovery Gate therefore required a real positive SSH publication even though no current user workflow depends on SSH.

This is not an implementation bug that should be repaired by configuring an SSH key or agent. It is an over-broad 0.9.0 product claim.

**Planner decision:** remove the unused SSH-positive claim instead of creating machine configuration purely to satisfy a gate.

## 1. Target product behavior after v0.4

### Trusted low-friction current-branch publication

Supported production remote shape for 0.9.0:

```text
https://github.com/<owner>/<repo>.git
```

Normal path:

```text
current authorized branch
+ existing same-name origin branch
+ GitHub HTTPS origin
+ existing system/global credential manager or gh credential helper
        ↓
ai-bridge host publish-current-branch
        ↓
bounded exact non-force publication
        ↓
no repeated approval
```

### SSH/custom transport path

For:

```text
git@github.com:<owner>/<repo>.git
ssh://git@github.com/<owner>/<repo>.git
other SSH/scp-style remote
custom remote helper/transport
```

the trusted helper does not attempt publication.

It returns a bounded result equivalent to:

```text
SSH_REMOTE_REQUIRES_ORDINARY_APPROVAL
```

or the existing generic unsupported/custom-transport approval result.

The user/Codex may still use ordinary raw `git push`, subject to normal approval.

Bridge Kit does **not**:

- generate an SSH key;
- upload an SSH key to GitHub;
- start/manage ssh-agent;
- modify `~/.ssh/config`;
- modify `known_hosts`;
- switch a repository remote from HTTPS to SSH;
- add an SSH transport wrapper.

## 2. Evidence that HTTPS-only is the correct current product boundary

### Current repository reality

Latest recovery evidence records:

```text
origin = https://github.com/YuukiAS/GPT_Codex_AI_Bridge_Kit.git
normal HTTPS bounded publication = PASS
GitHub SSH auth/agent environment = unavailable
```

No current Bridge TODO, current task, or user workflow requires SSH publication to be low-friction.

### External official sources rechecked

GitHub documents HTTPS and SSH as separate remote URL/authentication choices. GitHub HTTPS remotes support PAT/credential-helper authentication, and `gh auth setup-git` configures GitHub CLI as a Git credential helper.

References checked on 2026-09-24:

- GitHub CLI `gh auth setup-git`:
  https://cli.github.com/manual/gh_auth_setup-git
- GitHub remote repositories:
  https://docs.github.com/en/get-started/git-basics/about-remote-repositories
- GitHub managing remote URLs:
  https://docs.github.com/en/get-started/git-basics/managing-remote-repositories
- Git push URL protocols:
  https://git-scm.com/docs/git-push

Adopted conclusion:

- HTTPS publication does not require GitHub SSH key/agent setup;
- supporting HTTPS does not imply Bridge must also support SSH as a trusted low-friction path;
- a narrower HTTPS-only trusted capability is technically coherent and matches the current real user entry.

## 3. What changes from v0.3

Only these semantics change.

### 3.1 Publisher supported transport

v0.3:

```text
trusted low-friction positive path:
HTTPS + standard SSH
```

v0.4:

```text
trusted low-friction positive path:
GitHub HTTPS only

SSH/custom:
fail closed -> ordinary raw push approval
```

### 3.2 G4 positive evidence

Remove:

```text
real standard SSH agent/config positive publication
```

Keep:

```text
real GitHub HTTPS publication with existing system/global credential manager
```

### 3.3 G4 SSH security negatives

Keep all SSH-related negative protection.

These still matter because the trusted helper must not become an arbitrary executable launcher through environment/config injection.

Keep negative regressions for:

- `GIT_SSH`;
- `GIT_SSH_COMMAND`;
- `GIT_SSH_VARIANT`;
- `core.sshCommand`;
- command/config-source overrides that could rewrite transport;
- SSH/scp-style effective origin URL itself.

For every rejected case:

```text
no injected executable runs
no remote/network mutation occurs through trusted helper
ordinary approval remains available
```

### 3.4 No global canonical-identity regression

Do **not** blindly rewrite the shared `_canonical_repo_identity()` helper to HTTPS-only if that would break Reviewed Handoff or disposable local tests.

The implementation should make the transport support boundary **publisher-specific**.

Preferred shape:

```text
publisher preflight
    -> read effective origin fetch/push URL locally
    -> require exactly GitHub HTTPS for trusted publisher
    -> derive owner/repo assertion
    -> otherwise fail closed before ls-remote/fetch/push
```

The existing general repository-identity helper may remain broader where another approved Bridge product legitimately needs it.

## 5. Updated publication preflight contract

For `ai-bridge host publish-current-branch`, before the first remote/network command:

1. reject process transport/config/askpass injection as already approved;
2. derive current repository/current branch locally;
3. read exactly one effective `origin` fetch URL and exactly one effective push URL;
4. require fetch and push URLs both be GitHub HTTPS URLs for the same `owner/repo`;
5. require equality with `--expected-repo`;
6. require all already-approved branch/upstream/effect/config/hook conditions;
7. construct sanitized environment;
8. only then perform remote `ls-remote` / publication.

If either effective URL is SSH/scp-style or any other unsupported transport:

```text
fail before remote/network command
-> ordinary raw push approval
```

Do not mutate the remote URL as a fallback.

## 6. Gate Matrix delta

Only G4/G14 evidence semantics change.

### G3 — unchanged

Real screenshot-equivalent bounded publication still must succeed without repeated approval on an existing authorized branch.

The final positive path is GitHub HTTPS.

### G4 — revised transport boundary

G4 now proves:

**Positive**

- real GitHub HTTPS bounded publication succeeds;
- existing system/global credential manager / GitHub CLI credential-helper path remains usable.

**Negative exact-effect/security**

All existing v0.3/v0.3-recovery negatives remain, including:

- wrong repo/branch/upstream;
- missing/diverged branch;
- multiple destination/pushurl;
- mirror;
- follow-tags;
- recursive submodule push;
- push options;
- signed push side effect;
- active pre-push hook;
- Review executor guard;
- `GIT_SSH`;
- `GIT_SSH_COMMAND`;
- `core.sshCommand`;
- credential-helper injection;
- askpass injection;
- `GIT_CONFIG_COUNT/KEY/VALUE`;
- `GIT_CONFIG_GLOBAL`;
- `GIT_CONFIG_SYSTEM`;
- `GIT_CONFIG_NOSYSTEM`;
- changed branch/HEAD/destination/config at final recheck.

**New explicit transport negative**

- effective SSH/scp-style origin -> trusted helper refuses before first remote/network Git operation.

Failure condition:

- SSH/custom remote reaches remote/network publication through the trusted helper;
- injected executable runs;
- wrong/extra remote effect occurs;
- ordinary HTTPS credential-manager path is broken.

A real positive GitHub SSH publication is **not** a release requirement.

### G14 — final candidate

Same-final-candidate requirement remains unchanged, except the final evidence must describe the truthful transport claim:

```text
Trusted low-friction publication support:
GitHub HTTPS

SSH/custom transport:
ordinary approval path
```

No release documentation may claim trusted SSH publication support.

### All other gates

G1-G3, G5-G13, G15 remain semantically unchanged.

## 9. User-visible workflow

For the user's normal repositories:

```text
origin=https://github.com/YuukiAS/repo.git
        ↓
existing gh/system/global credential helper
        ↓
publish-current-branch
        ↓
low-friction publication
```

No SSH setup is expected or requested.

For a repository that intentionally uses SSH in the future:

```text
origin=git@github.com:...
        ↓
publish-current-branch
        ↓
SSH_REMOTE_REQUIRES_ORDINARY_APPROVAL
        ↓
ordinary git push approval if the user wants to proceed
```

That is a supported fallback behavior, not a Bridge failure.

If future repeated real usage demonstrates a need for low-friction SSH publication, that may be proposed as a separate capability on evidence. It is not part of 0.9.0.
