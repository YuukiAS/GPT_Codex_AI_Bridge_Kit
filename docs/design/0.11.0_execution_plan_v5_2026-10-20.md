## 1. 当前实现与 v5 的差距

当前 branch@894f8bb 已有可保留基础：

- Host 低打扰规则和 bounded current-branch sync；
- exact execution/source preflight；
- writer projected-byte budget；
- Persistent exact tmux/binding/start/status 的最小生命周期；
- progress normalize/report/latest 的部分逻辑；
- Clear Writing 的 one-shot codex exec、skill consumption proof、fidelity/fallback；
- mature Review watcher 和 Control transition machinery。

必须替换/扩充的地方：

- private.py/notifier.py 仍以 repo-local .ai-bridge 为配置/state，且当前 notifier_env() 会让 AI_BRIDGE_NOTIFY_* 进程环境覆盖文件配置；v5 必须同时删除 repo-local runtime authority 和 production process-level transport override；
- Persistent supervisor 仍只 Popen + child.wait，没有进度循环、主动 ETA、共享 Notifier 和 recovery；
- 三个 AGENTS writer 没有共同写锁；
- notifier 自动 input 仍可带 details/jobs/evidence_paths；
- notifier 没有 migrate-legacy、validate/readiness、DELIVERY_UNKNOWN lineage 或显式 retry；
- Lite/Review/Control/Persistent 四个真实 caller 尚未统一接到 machine Notifier；
- Clear Writing timeout 与 SMTP timeout 没有一个共同的 120 秒 end-to-end deadline；
- README/QUICKSTART/root AGENTS 仍描述旧 project-local Notifier。

## 2. 实施顺序

### Phase 1：建立机器级 Notifier 核心

修改 ai_bridge_kit/private.py 和 ai_bridge_kit/notifier.py：

1. machine config 路径统一为 Path.home()/.ai-bridge/private/notifier.env，state 为 Path.home()/.ai-bridge/state/notifier/；AI_BRIDGE_STATE_HOME 仅用于明确测试/隔离，不让 repo 相对路径重新获得 authority。
2. production normal entry 不读取/合并 AI_BRIDGE_NOTIFY_SMTP_USER、AI_BRIDGE_NOTIFY_SMTP_PASSWORD、AI_BRIDGE_NOTIFY_FROM、AI_BRIDGE_NOTIFY_TO、AI_BRIDGE_NOTIFY_SUBJECT_PREFIX 或其他 AI_BRIDGE_NOTIFY_* 环境变量作为 transport config；它们即使存在也不能改变 effective machine config。AI_BRIDGE_PRIVATE_RCLONE_SOURCE 等 private sync 导入变量不受此限制；测试只能通过显式函数参数、dependency injection 或 temporary config/state root 注入，不形成 production authority。
3. private sync 使用 temp + validate + chmod 0600 + atomic replace。
4. 新增 notifier validate、migrate-legacy、retry、增强 status。
5. 自动路径新增严格 NotificationRequest；manual legacy send 保持兼容但不作为自动 consumer API。
6. event state 改为 per-event atomic claim/attempt/receipt，event identity 含 repo identity 和 source event identity，解决跨 repo/并发碰撞。
7. DELIVERY_UNKNOWN 与 explicit retry lineage 按 Proposal 冻结实现。
8. 不启用新的长期 notifier run；旧 polling 命令只能作为兼容。

停止条件：若实现需要数据库、长期 service、中央 event bus，立即停止回 Planner/Critic。

### Phase 2：统一 AGENTS 写事务

在 readiness.py 中建立一个共用 target-level AGENTS transaction helper，并把：

- cli.py 的 Lite/core writer；
- persistent_run.py writer；
- overleaf.py writer

全部改为调用它。

要求：

- lock 在第一次读取前取得；
- read/splice/budget/temp write/fsync/replace 在同一锁内；
- overflow/config-unverified 时零 AGENTS mutation；
- AGENTS write 成功后才继续写该安装入口的其他项目文件；
- user-owned bytes 不因 Bridge writer 重组；
- 不宣称对不遵守 lock 的外部 writer 具有 portable CAS。

### Phase 3：Persistent 进度 producer、ETA 和 recovery

修改 persistent_run.py 和 templates/persistent_run/*：

1. contract 增加 progress_mode、progress_owner、source、expected cadence、Notify、Recipient override、Notification cadence。
2. supervisor 注入 Proposal 冻结的 progress/runtime environment。
3. 新增标准 progress update 子命令，原子写 machine-local run progress。
4. supervisor 从 child.wait 改为 child.poll + 60 秒 observation loop；progress 读取故障全部 nonfatal。
5. 保存 last-good progress 和 bounded history。
6. 按 v5 算法实现 count/fraction 主动 ETA，stage/none 证据不足时保持 UNKNOWN。
7. 实现 recover/resolve 真值表；binding 增加可获得的 boot/process start identity，但仅用于 duplicate-risk。
8. resolve 只关闭 SAFE_TO_CLOSE_STALE，保留审计 binding，不写 exit code/semantic completion。
9. supervisor 的通知只调用 shared Notifier，不拥有 SMTP config。

### Phase 4：四类 consumer 真正接线

#### Lite

在现有 task template 增加：

notify: false  
recipient_override: ""

run_lite_task 启动前若 notify=ON，先验证 machine Notifier readiness；process 返回后发送 runtime_terminal facts。若 AI_BRIDGE_RUNTIME_OWNER=persistent，则 suppress Lite runtime terminal，由 Persistent 发。

#### Review

在现有 REQUEST.md 增加 Notification 小节。Reviewed task 初始化/校验消费该字段。

reviewed_runner.watcher_once 只在 reviewed_handoff 已经记录 Reviewer 决定、validate_task 已确认事实后发送。transport failure 只记录，不更改 Reviewer/CURRENT state。

不得给 Review watcher 再套 Persistent。

#### Control

在现有 REQUEST.json task contract 增加 notification_policy，validator 校验它。

agent_flow.apply_transition 只有在 predicate、角色 artifact、state mutation、post-validation 成功以后才发送。transport failure 不回滚 transition。semantic authority 来自对应角色 artifact，而不是 Controller/Notifier。

不得给 Control controller 因 duration 再套 Persistent。

#### Persistent

supervisor 按 start/progress/stall/runtime terminal 调用 Notifier；绝不发送 semantic completion。

### Phase 5：Clear Writing 和 120 秒总 deadline

修改 clear_writing.py/notifier.py：

1. REQUIRED_SKILLS 冻结为 writing-fidelity + response-clarity；不得再把 chinese-prose 用作 automatic status/progress notification 的正式依赖。
2. 保留 NotificationRequest safe allowlist；clear_writing 内新增 reader-facing projection，使 consumer/fact_class/decision_authority/runtime_id/source_event_id/schema 不再成为默认可见 literal。runtime start/terminal 无有意义 ETA 时不强制显示 UNKNOWN；机械 fidelity 仍从原始 request/fact_class 守住 runtime 不得升级 semantic completion。
3. Clear Writing 单次模型最大 90 秒；一 turn，retry=0。
4. 自动 deliver 用一次性 helper/subprocess，父进程使用 monotonic 120 秒 absolute deadline。
5. helper 将 attempt stage 原子写入 machine event state。
6. transport socket timeout 不得超过剩余 deadline。
7. timeout 前未 transport => definitive failed；transport started 后结果不明 => DELIVERY_UNKNOWN；已 SMTP_ACCEPTED => 恢复 accepted receipt。
8. 任何 notification failure 不影响 workflow state 或 primary child。

- AGENTS 两 Bridge writer 并发；

## 6. Gate Matrix

### C1_LOW_FRICTION_BOUNDARY

真实 Host normal-entry 正负例。证明安全读取/受限同步少打扰，危险邻近仍 prompt/拒绝。

### C2_CONTEXT_AND_SOURCE_TRUTH

Lite、Review、Control、适用 Persistent 的真实 final spawn boundary。wrong repo/worktree/branch/commit/mandatory source mismatch 时 model/Executor child=0；unrelated dirty 不阻断。

### C3_MANAGED_INSTRUCTION_WRITE

真实 Lite/Persistent/Overleaf writer under-limit 正例、overflow 零 mutation；两个 Bridge writer 并发操作同一 AGENTS.md，最终两块都存在且 user bytes byte-identical。

### C4_PERSISTENT_LIFECYCLE_PROGRESS_RECOVERY

真实 persistent-run start/status。canary primary child 自己通过正式 progress update 生产至少 3 个 count/fraction 点并跨 warm-up 窗口形成 ETA；child 自己制造一次 malformed/half-written project-native progress，再恢复合法数据，supervisor/child 不死并重新形成 ETA。另做 stale、machine restart、supervisor-loss recover/resolve；无重复 child、无 semantic completion inference。

### C5_MACHINE_NOTIFIER_AND_CONSUMERS

同一机器配置一次，在两个无关 repo 中直接使用，不存在 repo secret authority，也不存在 production process-level SMTP/config override。Gate 必须在设置冲突的 AI_BRIDGE_NOTIFY_* 环境变量后证明 effective config 仍来自 machine file；测试注入只走显式 DI/temporary root。真实 migrate-legacy 同/冲突语义；explicit retry；跨 repo 同名 task；并发 dedupe。Lite、Review、Control、Persistent 四个现有 normal caller 都走 shared Notifier，且 runtime terminal 与 semantic decision 不重复、不越权。受控 transport hang 证明 delivery deadline 结束后业务仍继续。

### C6_ONE_SHOT_CLEAR_WRITING_AND_GMAIL

在同一 frozen candidate 上，installed/enabled writing-style 真实消费 writing-fidelity + response-clarity；reader-facing projection 保留人需要的事实而不堆内部 routing labels；turn<=1、model retry=0；fidelity failure 立即 fallback。最终 live 不再直接调用 deliver_notification，而从 persistent-run normal entry 走 primary child→supervisor→shared Notifier→Clear Writing→Gmail。

## 7. Final candidate discipline

顺序固定：

1. 所有实现和 cheap deterministic regressions 完成。
2. 运行 C1–C5 及 C6 非 live 部分。
3. 若 production bytes 需要再改，受影响 Gate 重跑。
4. 冻结一个 exact final candidate SHA。
5. 只有该 SHA 才能运行用户授权的 C6 live model/Gmail。
6. 同 SHA 跑完整 tests、CI、安装/版本/README identity。
7. 交 pre-final/final Critic。
8. formal release movement 另行请求用户明确授权。

不得跨 SHA 拼证据，不得无限追加 canary 跑到成功。

- 需要 daemon、数据库、event bus、持久 Codex thread、第二 workflow state machine；
- 必须修改 AI_Skills 才能让 Bridge Clear Writing 工作；
- 需要自动 takeover/relaunch 才能恢复 Persistent；
