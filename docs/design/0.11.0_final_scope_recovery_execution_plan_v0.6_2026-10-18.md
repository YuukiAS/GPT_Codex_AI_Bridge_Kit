## 2. v0.6 总体产品原则与复杂度选择

### 2.1 LOW FRICTION FIRST

低危害、高频、正常开发必需的动作优先 direct allow。真正继续强门控的是：

- destructive；
- branch/worktree topology change；
- force/delete；
- arbitrary remote/URL/refspec/helper/transport；
- credential disclosure；
- private/external transfer；
- paid/resource allocation；
- deployment；
- provider/data/cost/scope变更。

Auto-review造成 unattended task错误中断、反复批准、误判Git/网络坏掉，本身就是产品失败。

### 2.2 不引入的新系统

v0.6 禁止新增：

- Bridge daemon/system service；
- notification service；
- machine registry；
- credential DB；
- authorization DB；
- wrapper registry；
- 新workflow；
- 新reasoning role；
- 通用Git wrapper；
- 每个Git read一个wrapper；
- Bridge内复制Clear Writing；
- Persistent第二套邮箱配置；
- generic SMTP/OAuth；
- PIE运行依赖。

### 2.3 六项 blocker 的最小路线

- 指令预算：共享 projected-byte preflight + 根 AGENTS瘦身，不造PIE。
- worktree：正式 sibling path + Linux/procfs bounded quiescence；不支持平台 typed unsupported。
- Host：native direct rules + safe flags，不造read wrappers。
- 授权：当前用户/Kickoff + exact effect identity + Codex session approval，不造数据库。
- 通知：统一event model，不造第二套emailer。
- 写作：正式writing-style skill selection +确定性fallback，不造writing service。

## 4. ER11-08 — instruction budget / recovery ownership

### 4.1 user-owned instructions

Bridge不是通用 Project Instructions Editor。

若 user-owned AGENTS / project instructions超限：

- 只诊断，不自动删、摘要、改写；
- 显示 actual `project_doc_max_bytes`；
- 显示 effective total UTF-8 bytes；
- 逐source显示 bytes；
- 按native discovery顺序显示累计bytes；
- 标出**第一个使累计值达到/超过native limit的source**，作为 truncation-risk start；
- 用户修正后retry same task。

禁止静默提高 `project_doc_max_bytes`。

### 4.2 Bridge-owned mutation preflight

所有真正写root AGENTS managed block的Bridge入口统一调用同一个 projected-byte preflight。当前至少：

- Lite `init`；
- Persistent Run install/update；
- Overleaf install/update。

Reviewed/Control当前若不写root AGENTS，就不为了本 blocker新增writer；未来任何writer必须先接同一preflight。

算法：

1. 读取actual runtime `project_doc_max_bytes = L`。
2. 在内存中构造mutation后的root AGENTS bytes；不落盘。
3. 用与readiness相同的instruction discovery顺序，重算projected effective total `P`。
4. Bridge-owned mutation必须同时满足：
   - `P <= L`；
   - `P <= L - H`，其中 `H = max(1024, floor(0.20 * L))`。
5. 不满足则 `BRIDGE_MANAGED_INSTRUCTION_HEADROOM_INSUFFICIENT`，零mutation。
6. 错误显示现有user-owned bytes、各Bridge block bytes、projected total、limit、required headroom；只允许缩Bridge-owned block或让用户自行改user-owned内容。

这用“最小保留headroom”替代为每个block建立新的quota registry。

### 4.3 Bridge仓库自身 root AGENTS 收口

当前root AGENTS = 32355 bytes，默认limit=32768。

0.11实现必须把Bridge自身root AGENTS缩到：

**≤ 24576 UTF-8 bytes**

即默认至少保留8192 bytes headroom。

root AGENTS只保留：

- repo identity /主安全不变量；
- Host / workflow选择不变量；
- 不越权/不破坏Git的底线；
- 指向正式docs/templates的locator。

细节移到已有正式来源，不新造一份同义总规范：

- README
- `docs/V0_5_REVIEWED_HANDOFF_IMPLEMENTATION_SPEC.md`
- `docs/V0_4_AGENT_FLOW_IMPLEMENTATION_SPEC.md`
- `docs/V0_6_OVERLEAF_BRIDGE_IMPLEMENTATION_SPEC.md`
- `docs/design/0.8.0_persistent_run.md`
- 当前0.11 design docs
- Host/Prompt templates

必须有语义覆盖回归：被移出root的约束仍可从locator实际找到，不能为省bytes删掉安全语义。

### 4.4 Gate

G07最终必须证明：

- actual budget detection；
- user-owned overflow只诊断；
- Bridge-owned projected overflow在写前失败；
- root AGENTS ≤24576；
- 默认limit下headroom≥8192；
- runtime实际读取的新root AGENTS + locators仍支持正常行为；
- 没有修改用户 `project_doc_max_bytes`。

## 5. ER11-09 — worktree path / quiescence safety

### 5.1 新正式 task worktree 路径规则

未来 Bridge自动创建、恢复、替代的**新正式 task worktree**：

**绝不自动fallback到 `/tmp` 或系统temp。**

当前 Reviewed bootstrap 已经默认派生 repo sibling，这个方向保留：

`<repo-parent>/<repo-name>-<task-key>`

规则：

- new bootstrap/task creation必须派生或冻结repo sibling正式locator；
- 如果新task的请求试图把formal worktree冻结在系统temp根下，返回 `NEW_TASK_WORKTREE_TEMP_FORBIDDEN`；
- 历史已经存在且frozen locator明确是 `/tmp` 的旧task只保留原locator，不静默迁移；它不能成为新task策略；
- test fixture/disposable probe可使用系统temp；
- partial-clone isolated objects继续使用Bridge state下bounded temp；
- 不把这些临时对象描述成formal task worktree。

### 5.2 G02 的临时 T

正常 reciprocal exchange 中，用户不提供T。

Bridge根据effect内部派生一个稳定的同文件系统 sibling：

`T = A.parent / ".ai-bridge-exchange-" + sha256(common_dir,A,B,branchA,branchB)[:16]`

必须：

- `A.parent` 与 `B.parent` 同filesystem；
- T的parent = A.parent；
- T不是A/B；
- T不存在；若残留存在则先按journal恢复/清理，不能换随机T绕过；
- 不接受正常entry传入任意 `/tmp` T；
- low-level CLI为向后兼容可保留 `--temp-path`，但它只作为**assertion**：必须精确等于Bridge自己派生的T；不等则 `WORKTREE_EXCHANGE_TEMP_ASSERTION_FAILED`。

### 5.3 Git/path准入保持

继续拒绝：

- main worktree；
- cross-common-dir；
- cross-filesystem；
- symlink/redirection；
- locked worktree；
- submodule-bearing linked worktree；
- unsupported registry topology；
- ambiguous branch/path mapping。

`git worktree move` 仍是唯一搬迁mechanism；不改成手工rename。

### 5.4 quiescence 支持平台

自动exchange只在**Linux + procfs**、且Bridge能完成以下bounded current-user proof时支持。

点时刻proof必须对A/B同时检查：

1. Bridge自己的Reviewed/Persistent/task runtime state中没有active PID/lease声明使用A/B。
2. Git/worktree lock与journal状态无冲突。
3. 枚举当前UID可见的 `/proc/<pid>`：
   - `cwd`；
   - `root`；
   - `fd/*` symlink targets；
   - `maps` 中的文件路径；
   - `cmdline` 中解析出的绝对A/B路径。
4. 任一当前用户进程的上述对象落在A/B树内，返回 `WORKTREE_EXCHANGE_ACTIVE_PROCESS`。
5. 任一应可读取的current-UID proc entry因permission/race无法完成核实，返回 `WORKTREE_EXCHANGE_ACTIVITY_UNVERIFIED`。
6. helper自身不在A/B内执行；如果当前Codex/terminal/editor/build的cwd/fd落在A/B，负例必须命中。

该proof是明确的平台支持合同，不宣称对所有OS/所有未来编辑器做数学保证。

macOS/Windows/无procfs环境本轮**不自动exchange**：

`WORKTREE_EXCHANGE_ACTIVITY_UNVERIFIED`

用户仍可自行停止相关程序后采用普通人工Git/worktree恢复；Bridge 0.11不为了G02新增系统级监控daemon。

### 5.5 exchange顺序 / interruption

通过activity proof后，保持：

A → T  
B → A  
T → B

每一步前后写machine-state journal并fsync/atomic replace。

Gate必须覆盖：

- active-process negative；
- activity-unverified negative；
- S1 / S2 / S3 interruption；
- journal residual；
- rollback success；
- rollback failure evidence；
- staged / unstaged / untracked / file mode 保持；
- no `/tmp` formal fallback；
- T derivation/assertion。

## 6. ER11-10 — Host Policy / native read / wrapper boundary

### 6.1 threat model 与默认

Bridge正常处理用户主动选择的trusted development repo。v0.6不把“恶意local Git config理论上可能执行helper”单独当成把所有高频read/fetch重新prompt的理由。

原则：

**low risk + high frequency + bounded current repo ⇒ direct native allow优先。**

### 6.2 必须 KEEP_DIRECT_ALLOW

现有以下规则不得撤销：

- `git fetch origin main`
- `git fetch --all --prune`
- `git pull --ff-only origin main`
- safe current-repo `gh auth/pr/issue/run list/status`
- Slurm read-only inspection
- current-user process inspection
- `tmux ls/list-sessions/has-session`

当前没有具体可复现的高风险失败证明 `git fetch --all --prune` 在真实trusted环境不可接受，所以本轮保持。

如果未来要撤销已经low-friction的入口，必须同时提供：
1. 可复现危害；
2. trusted-repo threat model下的重要性；
3. 为什么窄规则/安全flag/负例关不掉；
4. unattended user cost；
5. 比重新prompt更轻的替代。

### 6.3 新增安全 direct native reads

v0.6正常Codex应使用下列canonical shapes；不为它们造wrapper。

#### Git identity/status

Direct allow：

- `git status`
- `git rev-parse --show-toplevel`
- `git rev-parse --git-common-dir`
- `git rev-parse --show-prefix`
- `git rev-parse --is-inside-work-tree`
- `git rev-parse --abbrev-ref HEAD`
- `git rev-parse --verify HEAD`
- `git branch --show-current`
- `git branch --list -- <patterns...>`
- `git worktree list`
- `git worktree list --porcelain`
- `git ls-files -- <pathspec...>`
- `git tag --list -- <patterns...>`
- `git remote get-url origin`

对 `branch/tag/ls-files` 使用 `--` 固定option边界；execpolicy rule必须配 `match/not_match` regression，不能仅写宽泛 `git branch` / `git tag`。

#### diff

允许：

`git --no-pager diff --no-ext-diff --no-textconv -- <pathspec...>`

以及 staged：

`git --no-pager diff --cached --no-ext-diff --no-textconv -- <pathspec...>`

Git官方确认 `--no-ext-diff` 和 `--no-textconv` 分别禁止 external diff driver / textconv。`--` 后只允许pathspec。

#### log

允许固定当前历史形状：

`git --no-pager log --no-ext-diff --no-textconv --max-count=50 --format=%H%x09%aI%x09%s -- <pathspec...>`

它不接受任意revision/helper/format作为suffix。

#### show

允许固定HEAD读取：

`git --no-pager show --no-ext-diff --no-textconv --format=fuller HEAD -- <pathspec...>`

任意commitish的raw `git show <arbitrary>` 本轮不做宽prefix allow；没有必要为此造wrapper。Codex若确需其他commit，走普通prompt或已存在可信产品入口。

#### configured-origin remote inspection

优先 direct allow：

`git ls-remote --refs -- origin <patterns...>`

`--` 后第一项固定为configured `origin`，其余只能作为ref pattern。Implementation必须用当前Git真实argv parser + execpolicy `match/not_match` 负例证明：

- `--upload-pack` / arbitrary URL / arbitrary remote不会被该allow rule吃掉；
- transport/helper override仍prompt。

如果当前Git/execpolicy实测不能可靠冻结这个shape，只收窄**这一条**为prompt，不得连带撤销fetch/read direct allow。

### 6.4 KEEP_PROMPT

继续prompt/强门控：

- arbitrary URL / remote / refspec；
- transport/helper/config override；
- credential/token disclosure；
- shell composition；
- branch create/switch/delete/rename；
- worktree add/move/remove（除已批准bounded helper）；
- remote add/remove/set-url；
- upstream change；
- rebase / autostash；
- reset / clean / restore；
- force / force-with-lease；
- remote delete；
- deployment/resource/private external transfer等高影响effect。

### 6.5 semantic helpers 继续保留

以下不是“多余wrapper”：

- `host sync-current-branch`
- `host publish-current-branch`
- Reviewed bootstrap/materialize/publish-first
- `exchange-worktrees`

它们依赖dynamic repo/branch/upstream/path/ancestry/current-state语义，simple prefix allow无法替代。保持窄职责，不继续吸收普通reads。

### 6.6 plugin-replay

`plugin-replay = KEEP_NARROW`。

当前真实consumer仍存在。唯一独特边界：

installed production plugin  
+ fresh unattended child  
+ explicit local/private input  
+ write isolation  
+ bounded evidence。

不得用于：

- generic Reviewer；
- generic child Codex；
- 普通Git reads；
- Clear Writing reader；
- Persistent reporter。

只有官方成熟normal entry完整替代上述五项，才另提迁移。

### 6.7 G06关闭条件

必须在actual target Codex运行：

`codex execpolicy check`

对每个allow shape和危险邻近负例核 exact matched rules/decision。

G06还要证明：
- `git fetch origin main` 不产生无意义approval；
- `pull --ff-only` / `fetch --all --prune` 仍低摩擦；
- dangerous neighbors仍prompt；
- 未增加read wrapper；
- unattended normal task不会因本轮规则退化进入错误BLOCKED。

## 7. ER11-11 — authorization continuity binding

### 7.1 不建立 authorization DB

v0.6只使用已有三层能力：

1. **direct allow**：ER11-10中的低风险动作本来不需要授权。
2. **当前用户可见授权**：approved Kickoff或当前thread中的exact bounded user approval。
3. **Codex原生 session approval**：当Auto-review提供 `AcceptForSession / ApprovedForSession` 时，由Codex自己在当前session范围内机械消费。

Bridge不复制Codex内部approval store，不签发token，不把repo字段变成authority。

### 7.2 exact effect identity

对真正HUMAN_ONLY bounded effects，Bridge生成稳定human-readable effect identity并可附SHA-256 digest；digest只用于比较，**不等于authority**。

至少冻结以下字段：

#### worktree exchange
- repo/common-dir identity；
- task_key；
- A / B / derived T；
- expected branch A/B；
- purpose = reciprocal exchange。

#### Persistent launch / resume
- repo；
- task/run key；
- Goal/contract hash；
- backend；
- launch/resume argv digest；
- resource boundary；
- Progress shared-server backend kind。

#### GitHub publication
- repo；
- branch；
- old remote OID；
- proposed new OID；
- non-force mode；
- purpose。

#### Gmail真实send
- provider = GMAIL_SMTP；
- account/from；
- recipient；
- task/event identity；
- purpose；
- data class（只允许bounded notification text）。

#### CODEX_HOME / Machine Policy写
- exact CODEX_HOME；
- target files；
- source candidate SHA；
- purpose。

#### formal release
- repo；
- old release SHA；
- new exact `0.11.0-rc.N` SHA；
- non-force fast-forward。

### 7.3 owner / comparison / helper消费

Authority owner只能是：
- 当前用户message/Kickoff；或
- Codex自己真实session approval机制。

Repo Goal/AGENTS/`authorized=true`/CLI flag永远只是scope evidence，不能产生authority。

Bridge helper只做两件事：

1. 从frozen inputs + actual machine state重新计算effect identity。
2. 拒绝actual effect与已授权human-visible scope不一致的调用。

helper不保存“这个用户以前批准过”的数据库。

### 7.4 lifetime 与 reconnect

#### Bridge-level current-thread authorization

同一个current user-visible Codex thread中，只要：

- exact effect identity不变；
- frozen task/run未结束；
- 当前context仍可消费那条用户授权；

Bridge/Codex不得再发第二个Bridge级HUMAN_ONLY问题。

#### Codex native session approval

`ApprovedForSession` 只按Codex真实session lifetime成立。Bridge不得声称它跨：

- app-server restart；
- new thread；
- new conversation；
- incompatible remote/backend切换。

若同一thread reconnect后platform仍机械暴露有效session approval，可以继续；若平台无法证明，允许重新prompt。**诚实缩窄no-repeat claim优先于造authorization DB。**

#### Kickoff

Approved Kickoff可以一次授权其正文明确列出的所有可预见bounded effects；以后到达这些effect时，Bridge不重复问**Bridge自己的问题**。如果Host/Auto-review对原生命令仍要求平台审批，那是平台approval；首次平台approval后应优先使用其 `AcceptForSession` 机制避免同session重复。

### 7.5 invalidation fields

任一关键字段变化都必须新询问：

- repo/branch/path/target；
- artifact/hash/OID；
- provider/account/recipient；
- purpose/data class；
- resource/backend；
- CODEX_HOME；
- run/task/Goal hash；
- release old/new SHA；
- force/delete/destructive mode。

无关字段变化不能制造新approval。

### 7.6 Gate

G10 positive：
- 同一exact effect在有效lifetime内只出现一次Bridge级用户问题；
- 同一native approval选择AcceptForSession后，同session重复同effect不再prompt（若Codex该approval类型支持）。

G10 negative：
- 变recipient/provider/resource/backend/path/hash后必须重新问；
- repo自写`authorized=true`无效；
- new thread/restarted app-server且平台无法证明旧approval时允许重新问；
- 不存在authorization DB/state machine。

## 8. ER11-12 — unified Notifier event model

### 8.1 唯一 transport pipeline

Notifier是Bridge唯一automatic email出口：

`Lite / Reviewed / Control / Persistent Run / explicit manual caller`  
→ canonical notification event  
→ frozen intent gate  
→ reader layer  
→ Notifier deterministic MIME/dedupe  
→ Gmail SMTP

Persistent Run：

- 只产生progress/runtime lifecycle event；
- 不保存sender；
- 不保存recipient；
- 不保存App Password；
- 不存在第二套email configure。

Transport唯一配置：

`ai-bridge notifier configure`

Persistent lifecycle唯一入口：

`ai-bridge persistent-run start`

二者职责不合并。

### 8.2 三个彼此独立的 frozen intent

项目默认与task override在freeze时解析成：

`Progress email: ENABLED | DISABLED`  
`Runtime terminal email: ENABLED | DISABLED`  
`Semantic completion email: ENABLED | DISABLED | UNSUPPORTED`

默认全部关闭。

`automation/notifier/DEFAULTS.json` 相应升级为：

- `progress_email`
- `runtime_terminal_email`
- `semantic_completion_email`

task启动后project default变化不得反向改变frozen intent。

Lite：
- semantic completion = `UNSUPPORTED`。

Reviewed/Control：
- 可由真实semantic owner支持。

Persistent overlay：
- 复制underlying task三个resolved intent；
- 不获得semantic authority。

### 8.3 canonical event classes

0.11内部冻结三个automatic event class：

#### A. `progress`

用于运行中状态与进展，不表示runtime已结束或Goal已通过。

subtype至少：

- `start`
- `resume`
- `stage_transition`
- `blocked_transition`
- `stalled_transition`
- `eta_material_change`
- `cadence_progress`
- `milestone` / `awaiting_human` 兼容映射

#### B. `runtime_terminal`

某个canonical runtime/process进入真实terminal：

- success exit；
- failed exit；
- cancelled/terminated（只有runtime直接支持时）。

事实字段至少：

- runtime_id；
- runtime owner；
- terminal status；
- exit code（若有）；
- started_at / ended_at；
- run/task identity。

**绝不写：**

`Goal PASS`  
`READY`  
`RELEASE_READY`

#### C. `semantic_completion`

只有underlying workflow真正的positive-completion authority形成current PASS后才产生。

- Lite：UNSUPPORTED。
- Reviewed：current合法 Reviewed PASS artifact。
- Control：current合法 Critic / Final Critic completion artifact。
- Persistent：不产生semantic authority，只可转交underlying workflow event。

### 8.4 progress logical-delivery rule

Progress email与Progress thread共享原批准规则：

立即logical delivery：

- start；
- resume；
- meaningful stage transition；
- blocked transition；
- stalled transition；
- ETA known→UNKNOWN；
- ETA UNKNOWN→known；
- material ETA movement。

material ETA：

`abs(new_expected_finish - old_expected_finish) >= max(15 minutes, 25% * previous_remaining_time)`

周期：

- active默认约60分钟；
- 无任务特定理由不得低于15分钟；
- 从last logical delivery计时；
- observation不重置delivery clock。

普通count/fraction小变化只更新observation，不即时通知。

每行log、每epoch、每file、单纯PID alive都不能触发logical delivery。

### 8.5 runtime terminal intent独立

`Runtime terminal email=ENABLED` 与Progress、Semantic都互不推导。

因此明确支持：

> 不要每小时发，只要跑完通知我。

这种task冻结：

- Progress email = DISABLED
- Runtime terminal email = ENABLED
- Semantic completion email按workflow另定

runtime terminal只发一次每个 `runtime_id`，dedupe key至少绑定 task/run/runtime_id/terminal status。

### 8.6 fixed emitter ownership

Executor不能现场猜谁发event。

#### Lite

`ai-bridge task run` 是canonical runtime owner：
- child `codex exec` 启动后可产生runtime_id；
- child真实exit时发一次 `runtime_terminal`；
- Lite没有automatic semantic completion。

#### Reviewed

Reviewed runner是每次canonical Executor runtime的emitter：
- 每个implementation/revision runtime有独立runtime_id；
- 其进程结束可发runtime terminal；
- Review PASS是另一个后续 `semantic_completion`，不能混成同一事件。

#### Control

Control execution owner产生runtime terminal；
Control Planner draft不发semantic completion；
只有Critic/Final Critic canonical PASS artifact可产生semantic completion。

#### Persistent Run

Persistent supervisor是它所包裹primary process的runtime owner：
- proactive progress；
- primary runtime terminal；
- 不产生semantic completion。

如果Persistent supervisor已经拥有某primary runtime，underlying launcher不得为同一 `runtime_id` 再发第二封runtime terminal；**lifecycle owner wins**。

### 8.7 legacy Notifier compatibility

现有event type不删除，避免G12回归：

- `operational_progress` → progress
- `operational_blocked` → progress/blocked_transition
- `milestone` → progress/milestone
- `awaiting_human` → progress/awaiting_human
- legacy `terminal=complete`：
  - explicit manual send保持旧render；
  - automatic路径只在真实semantic artifact + Semantic intent允许时映射为semantic_completion；
- legacy `terminal=blocked/awaiting_human` → automatic progress/status，不冒充runtime terminal。

新增正式 `runtime_terminal` 与 `semantic_completion` structured event type；新代码不再把runtime exit塞进旧 `terminal`。

### 8.8 automatic / manual

Automatic：

- Persistent progress/runtime；
- Lite/Reviewed/Control runtime；
- `notifier once/run`；
- Reviewed/Control semantic。

必须走frozen intent。

当前用户在交互终端直接：

`ai-bridge notifier send <brief>`  
`ai-bridge notifier send-test`

仍是one-shot current authorization，不要求task intent。Automation不得shell out到manual path绕过intent。

### 8.9 semantic authority

Reviewed automatic semantic event必须验证：

- exact task；
- current implementation commit；
- matching current REVIEW PASS；
- FINAL_REPORT；
- CURRENT PASS/human-gate binding；
- existing validator全PASS。

Control必须验证：

- exact task/request_nonce/review_target；
- Critic冻结的 `FROZEN_CONTRACT.md`；
- current `FINAL_CRITIC_AUDIT.json=CRITIC_FINAL_PASS`；
- source snapshot/review bundle/ledger/planner-pass bindings。

brief里的 `decision_authority` 字符串单独没有authority。

## 9. ER11-13 — Clear Writing reader layer

### 9.1 ownership

Bridge拥有canonical facts：

- notification class/subtype；
- stage；
- runtime status；
- completed/total/fraction；
- ETA/expected finish；
- ETA basis；
- uncertainty；
- last real progress；
- delta；
- runtime terminal facts；
- semantic authority result。

Clear Writing只拥有reader-facing expression，不能改变事实、数字、UNKNOWN、路径、状态或结论强度。

### 9.2 正式production调用边界

目标能力：

`writing-style@yuukias-ai-skills`

实施时不硬编码插件cache路径。

在actual selected `CODEX_HOME` / shared app-server上：

1. 用官方 `plugin/list` 或 `codex plugin list --json` 验证 installed/enabled plugin id = `writing-style@yuukias-ai-skills`，记录actual version。
2. 用官方 `skills/list` 取得enabled skills及 `plugin_id/name/path`。
3. 必须解析：
   - `chinese-prose`
   - `writing-fidelity`
   且两者 `plugin_id = writing-style@yuukias-ai-skills`。
4. 在reader turn里以structured `UserInput::Skill {name,path}` 显式选择这两个skills。

Bridge不读取后复制SKILL正文，不扩 `plugin-replay`，不启动writing daemon/service。

当前AI Skills source main显示writing-style source version 0.4；final Gate必须记录实际installed version。若缺插件/skill、disabled、identity不匹配，则正常reader不可用，进入`9.7` fallback，不自动安装/升级真实CODEX_HOME。

### 9.3 调用时机：只在logical delivery

Observation永远不调用reader。

只有一个notification event已经通过：

- cadence/event decision；
- frozen intent gate（若只发email）；
- Progress thread delivery decision（若有thread）；

才进入reader。

**每次logical delivery最多一个reader-model转换阶段。**

### 9.4 输入必须bounded

单次reader input只包含：

- canonical notification event；
- notification class/subtype；
-必要reader language preference（默认自然中文）；
-结构化 `UserInput::Skill` 选择；
-固定保真指令：不得修改任何canonical值。

禁止显式拼入：

- root AGENTS全文；
- Goal全文；
- task全文；
- Executor thread；
- source code；
- raw logs；
- history；
- private data；
-整个业务thread context。

Persistent Progress thread中的model天然能看到**它自己的既有progress消息历史**；这个thread从设计上只含先前reader notices，不含Executor/task业务上下文。当前canonical event仍是本turn唯一事实来源，instruction明确要求忽略历史中的旧数字，不可把旧ETA带入新消息。

### 9.5 Persistent路径：reader turn就是Progress render turn

Persistent已有bounded Progress render，不再做：

Bridge generic render  
→ Clear Writing second model rewrite

而是直接：

canonical event  
→ **同一个Progress-thread turn + writing-style structured skills**  
→ reader_result  
→ Progress thread显示  
→ 若对应email intent也启用，复用**同一个reader_result**构造email

所以thread/email不能各跑一次模型。

### 9.6 非Persistent email-only路径

Lite/Reviewed/Control的runtime-terminal/semantic automatic email没有Progress thread时：

- 在当前合法shared app-server上创建**ephemeral、tool-free reader thread**；
- 使用与Progress thread相同的no-execution deny config；
- structured选择writing-style两个skills；
- 一个event最多一个turn；
- 得到reader_result后销毁/放弃ephemeral thread；
- 不创建用户可见长期thread，不新增daemon。

如果当前环境没有可用shared reader app-server，直接进入fallback；业务runtime不因reader失败停止。

### 9.7 唯一fallback决定

v0.6选择：

**所有已经应当对用户交付的automatic notification，在Clear Writing不可用/失败/超预算/保真失败时，使用严格确定性的短中文fallback；不suppression。**

理由：
- blocked/failed/runtime-terminal不能消失；
- normal progress也不能因为reader层坏掉让“主动汇报”失效；
- fallback只拼canonical facts，不引入第二模型。

状态：

`reader_layer=DEGRADED_FALLBACK`

并记录：

`reader_failure_reason`

fallback模板只允许：
- event中文类别；
- stage/status；
- verified count/fraction；
- ETA或“预计完成时间未知”；
- last real progress；
- runtime terminal exit；
- verified semantic result。

不推断原因、不扩写建议、不修改结论强度。

### 9.8 reader fidelity

正常reader result目标2–5句自然中文。

Bridge在发送前机械验证所有canonical token：
-数字/比例；
-关键status；
-UNKNOWN；
-runtime exit；
-semantic result。

若reader改值、删掉必须字段或升级结论，reader result丢弃，改用deterministic fallback，并记 `READER_FIDELITY_FAIL`。

### 9.9 single bounded reader budget

不增加第二套无限model预算。

Frozen task/contract新增：

`Reader render max turns: <integer>`

规则：

- Persistent旧 `Progress render max turns` 在0.11升级时映射/合并为同一个reader ceiling，不再另算writing-style turn；
- nonPersistent task根据enabled automatic runtime/semantic events与existing workflow max rounds冻结有限ceiling；
- budget耗尽时使用deterministic fallback，不追加模型turn；
- project default变化不能改变旧task reader budget。

development Progress canary现有最多2 turns，**这两turn本身就是Clear Writing reader turns**，不另加2次。

### 9.10 status

`persistent-run status` 和 `notifier status` 都显示最近一次：

- `reader_layer=NORMAL_WRITING_STYLE` + actual plugin version；
- 或 `DEGRADED_FALLBACK`；
- renderer/skill discovery/fidelity/budget failure reason；
- last reader turn timestamp/token usage（若normal）；
- suppressed仅用于intent本身DISABLED或transport policy suppress，不把reader失败叫suppressed。

Reader/Gmail failure默认不杀primary。

## 10. Persistent Run / Progress thread 保持的完整合同

### 10.1 normal entry / lifecycle

`persistent-run start` 仍是terminal-owned tmux场景的幂等start-or-resume：

- frozen Goal/contract hash；
- exact Launch/Resume argv；
- shared app-server readiness；
- Progress thread；
- run-scoped primary + reporter；
- primary terminal后final runtime event + reporter cleanup；
- 不提交scheduler、不改资源/scope、不成为daemon/controller。

scheduler/service-owned继续由原owner管理；若需要Bridge progress，它们必须显式接reporter lifecycle hook。

### 10.2 shared app-server ownership

正式Progress thread与用户viewer必须连接同一个official shared app-server：

- 同一 `CODEX_HOME` local shared daemon；或
- trusted current-session exact explicit remote。

Bridge只discover/probe/connect，不调用daemon start/restart/update/bootstrap，不另起embedded writer。

不能证明shared binding时，在新primary前：

`PROGRESS_THREAD_SHARED_APP_SERVER_UNAVAILABLE`

### 10.3 Progress thread

- non-ephemeral；
- exact thread ID identity；
- human name只用于发现；
- no execution/external tools；
-不写Executor/task thread；
- no semantic authority；
- reporter+viewer同server并发时reporter仍能继续render；
- first turn后materialize，再cold resume；
- contamination停止自动投递。

### 10.4 progress truth / cadence

保持v0.5所有truth规则与60min/15min/material ETA/last-delivered语义。

### 10.5 runtime terminal

Persistent supervisor是其primary runtime terminal唯一emitter。final runtime event：

- 总是写Progress thread（通过reader/fallback）；
- email只由 `Runtime terminal email` intent决定；

## 12. G01–G14 正常入口与最终验收矩阵

### G01 — 两个不同分支长期 worktree 并行

## 13. v0.6 冻结的 18 个真实用户 journey

v0.5 已关闭的 normal-entry coverage 不删除；下面18条把本轮六项 blocker 合并进最终release acceptance，并覆盖此前14条旅程的用户能力。

1. **低摩擦 fetch**  
   trusted repo内普通 `git fetch origin main` 直接执行，不出现无意义approval；随后仍能正常继续task。

2. **危险Git邻近负例**  
   arbitrary URL/refspec/helper、force/delete/reset/clean/rebase等仍prompt/拒绝；safe direct rules不能被suffix绕成高影响操作。

3. **Bridge-owned AGENTS projected overflow**  
   在mutation前构造会超headroom的managed block；install/update返回稳定overflow错误，root AGENTS原bytes完全不变。

4. **user-owned rules overflow**  
   user AGENTS超限时显示limit/total/source bytes/first truncation-risk source；Bridge不自动删/摘要/重写；用户自行修正后same task retry。

5. **formal worktree no `/tmp` fallback**  
   new Reviewed task/bootstrap即使sibling path被占用，也不得自动落到system temp；明确失败/恢复。历史frozen `/tmp` locator保持但不迁移。

6. **active worktree exchange fail closed**  
   Linux supported topology下让current-user process的cwd/fd落在A或B；自动exchange返回 `WORKTREE_EXCHANGE_ACTIVE_PROCESS`。非支持平台返回 `WORKTREE_EXCHANGE_ACTIVITY_UNVERIFIED`。

7. **same authorized effect no duplicate Bridge question**  
   current thread用户批准一个exact bounded effect后，后续同identity到达helper时Bridge不再问第二次；如果Codex native approval支持session persistence，选择AcceptForSession后同session也不重复平台prompt。

8. **changed effect must reprompt**  
   修改recipient/provider/path/resource/backend/hash/OID任一关键字段，生成不同effect identity并重新请求一次授权；repo `authorized=true`不能绕过。

9. **progress-only notification**  
   Progress=ON、Runtime=OFF、Semantic=OFF；cadence/stage/blocked/ETA事件可进Progress thread与email，runtime exit不发email，semantic PASS不发email。

10. **runtime-terminal-only notification**  
    Progress=OFF、Runtime=ON、Semantic=OFF；运行中不发邮件；实际runtime终止只发一次事实邮件，不写Goal PASS。

11. **semantic-only notification**  
    Progress=OFF、Runtime=OFF、Semantic=ON（Reviewed/Control）；只有current合法semantic PASS artifact后发；运行结束本身不发。

12. **all-three intents**  
    三者ON；progress、runtime terminal、semantic completion分别有独立event key/intent/authority，不互相推导、不重复。

13. **普通非Persistent Lite runtime-terminal**  
    Lite `task run` child真实结束；Runtime terminal=ON时Notifier发一次runtime事实；Semantic字段=UNSUPPORTED，不能自动写任务完成。

14. **Reviewed semantic completion**  
    Executor runtime terminal与Reviewed PASS分成两个不同事件；只有matching implementation/review/final report的current PASS产生semantic email。

15. **Persistent progress + runtime terminal**  
    supervisor拥有primary runtime；proactive progress +最后runtime-terminal；underlying workflow不得重复同runtime_id终态邮件；semantic仍归underlying owner。

16. **Clear Writing正常reader path**  
    actual installed `writing-style@yuukias-ai-skills` 被plugin/skills discovery解析；同一logical delivery structured选择 `chinese-prose` + `writing-fidelity`；输出2–5句自然中文且canonical值完全保真；若thread+email同时存在，两者复用同一reader_result。

17. **Clear Writing degraded fallback**  
    plugin missing/disabled、skill identity不匹配、reader turn失败、fidelity fail或budget耗尽；不杀业务run，改用确定性短中文并显示 `reader_layer=DEGRADED_FALLBACK` 和reason，不调用第二模型。

18. **Gmail / reader failure不杀业务任务**  
    Gmail未配置、credential失败或SMTP发送失败时，主runtime/Progress thread继续；Notifier记录失败/suppression；reader failure同样只影响表达层。

另外最终release仍必须覆盖既有：
- fresh-machine Host setup；
- fresh Lite normal entry/partial clone；
- two real parallel worktrees；
- stale Host recovery；
- shared app-server Progress viewer+reporter；
- Gmail machine/project layering；
- same exact release candidate；
- final release remote SHA readback。
