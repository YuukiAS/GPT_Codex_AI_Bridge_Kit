## 2. R0 blocker closure

### BR11-RESET-R0-F01_CLEAR_WRITING_SCOPE_REGRESSION — CLOSED

v0.1 的问题是为了删除旧 app-server reader 而连用户要的结果一起延期。v0.2 已正确把“自动通知最多调用一次 Clear Writing”恢复为 0.11.0 的独立薄能力，并把实现边界压回一次性 CLI 转换。

关闭依据：

1. 产品输入已经变成 immutable canonical facts；Clear Writing 不拥有 runtime、semantic completion、recipient、transport 或业务状态 authority。
2. 每个 logical delivery 最多一次 fresh `codex exec --ephemeral`，不 `resume`，不做第二次模型修复。
3. 正常路径必须实际消费当前 installed `writing-style@yuukias-ai-skills` 的 `writing-fidelity` 与 `chinese-prose`；模型自报或 fake fixture 不能算证据。
4. `--json` / 等价正式入口必须证明该 delivery 的 `turn.started <= 1`。
5. plugin/skill/model/parse/one-turn proof/fidelity 任一失败都立即 deterministic fallback；fallback 仍进入现有 Notifier 发送流程。
6. transport failure 只记录通知失败，不改变业务状态、不杀 primary，也不再调用模型。
7. manual `notifier send` / `send-test` 继续保持 0.10 兼容，不被强制 Clear Writing。
8. C5 不引入 app-server、persistent reader、Progress display thread、shared server、第二模型、跨 workflow event bus 或 three-intent propagation。

OpenAI 当前文档直接支持这条简化路线：`codex exec` 是非交互脚本/流水线入口，`--ephemeral` 可避免 rollout 持久化，`--json` 提供 turn/item 事件；Skills 文档也支持通过正式安装后的 metadata/routing 消费 skill。Proposal 同时要求 final C5 重新证明当前 production skill 真实消费，因此没有拿历史 0.3 smoke 冒充最终 0.4/未来 final-candidate proof。

F01 已关闭。

### BR11-RESET-R0-F02_SOURCE_BINDING_TRUTH_UNDERSPECIFIED — CLOSED

v0.2 已把 mandatory source 的 truth owner 从“当前工作树大概正确”冻结为：

```text
exact repo + exact expected commit + exact repo-relative path
→ exact Git blob content
```

关闭依据：

1. task locator 必须携带 exact expected commit，当前 HEAD 必须与之一致。
2. unrelated dirty worktree 不再触发全局 `require_clean`。
3. mandatory path 的 worktree bytes 若与 frozen commit 不一致，不能被当作 authority；v0.2 选择 typed block，且交给 Executor 的文本始终来自 exact commit blob。
4. exact blob 本地存在时走普通 object read，不把 isolated fallback 变成所有读取的默认路线。
5. 只有确认 local blob 缺失时才允许进入 isolated-object fallback。
6. fallback 被限制为 exact repo / 40-hex commit / repo-relative path，并要求临时对象只写 Bridge machine state、原 Git state/object store 保持不变。
7. 任一 mandatory source 失败时，模型 child 与 Executor child 都必须保持 0。
8. 新 `readiness` 边界明确删除通用 authorization、Host/runtime controller 倾向，只保留 exact execution/source preflight 与 managed-writer projection。

这同时避免两个相反的失败：无关 dirty 文件不再把整个任务误判为不可执行；dirty mandatory file 也不能覆盖 frozen source truth。

F02 已关闭。

### BR11-RESET-R0-F03_PERSISTENT_STALE_RUN_RECOVERY_UNDERSPECIFIED — CLOSED

v0.2 已将 Persistent Run 收敛为有限的 run-local lifecycle，而不是后台服务：

```text
one exact tmux session
+ one run-scoped supervisor
+ one binding JSON
+ one child
+ existing progress/report/latest
```

关闭依据：

- no binding + no session 才允许 new start；
- compatible binding + exact active session 只返回 existing，不重新建 child；
- nonterminal binding + missing session 返回 stale/unknown，不自动 relaunch；
- session 存在但 binding 缺失或 identity mismatch 时 conflict，不接管；
- terminal binding 只读 terminal facts，同 run key 不自动再跑；
- partial start 不通过重试猜 child 是否启动；
- supervisor 异常消失且 child lifecycle 不可证明时保持 `UNKNOWN/UNAVAILABLE`；
- exit code 只有 supervisor 实际观察 `child.wait()` 返回后才成为 terminal fact；
- status 由 binding facts + exact session existence 派生，不建立第二数据库或全局状态机。

这些语义足以阻止 R0 指出的 duplicate run、false terminal 和 automatic takeover，同时没有引入 daemon、watcher、database 或跨 run recovery protocol。

Execution Plan 后续仍需把“exact session identity”的具体可验证实现写清，但这是已经批准语义的实现细化，不构成新的设计 blocker。

F03 已关闭。

## 3. Capability Gate Matrix 独立判断

当前 C1–C5 可以 PASS 设计审查，因为它们证明的对象不同，且都绑定普通入口和 same-final-candidate SHA：

### C1 — 低打扰边界

证明 safe 高频读取与 bounded current-branch sync 真正减少重复打扰，同时 dirty/diverged/arbitrary remote/refspec/helper/force/reset 等危险邻近仍被 prompt/拒绝。

它证明权限与低摩擦，不证明 source truth。

### C2 — execution context + mandatory source truth

证明真实 Lite/Reviewed/Control launcher 只有在 exact repo/worktree/branch/commit 和 mandatory source exact blob 已绑定后才启动。正例包含 unrelated dirty 仍可运行、local exact blob 与真实 partial-clone fallback；负例要求 model/Executor child count=0。

它证明执行位置与 source truth，不证明 Host authorization。

### C3 — managed instruction write

证明 Lite/Persistent/Overleaf 的真实 writer 都在写前发现 projected overflow，并在失败时保持原文件 exact bytes。用户自有内容不能被自动删改。

它证明 writer mutation safety，不证明模型 runtime 是否消费 source。

### C4 — Persistent local lifecycle

证明 fresh start、existing-run idempotency、disconnect/status、真实 terminal observation，以及 stale/partial/supervisor-loss 不自动 relaunch、不猜 terminal。

它证明本地进程生命周期，不证明语义完成或邮件。

### C5 — one-shot Clear Writing notification

证明 automatic notifier delivery 正常时只执行一次正式 Clear Writing，实际消费 installed `writing-style`，机械保护 facts，随后进入 existing transport；失败时 deterministic fallback，业务不受影响。

它证明 reader-facing expression，不重新承担 runtime/semantic authority。

旧 G14 reader canary 仅作为“旧路线为什么被删除”的历史反证，不迁移成 C5 证明。这一点正确。

Gate 执行顺序也合理：先 cheap deterministic regression 与 C1–C4，稳定 final candidate 后才消费一次真实 C5 model run，避免再次把昂贵/脆弱表面放到开发最前面。

## 4. 复杂度判断

v0.2 加回 C5 后仍然满足 reset 的复杂度目标：

- 0 daemon；
- 0 长期 background service；
- 0 watcher；
- 0 database；
- 0 cross-workflow state machine；
- 0 persistent Codex thread；
- 0 custom app-server/WebSocket client；
- 0 generic Git wrapper/controller；
- 0 authorization store；
- 0 automatic worktree exchange；
- 每个 Persistent Run 最多一个 run-scoped supervisor + 一个 binding JSON；
- 每个 automatic logical delivery 最多一次 fresh `codex exec --ephemeral`，失败不做模型重试。

代码行数预算也被正确降级为架构复审触发器，而不是实现 PASS 指标。

没有发现 v0.2 因加回 Clear Writing 又重新长出旧 runtime architecture。

## 5. 正常用户路径

相比 R0 前和旧 v0.8，用户侧实际变化是：

- 普通开发：在当前 repo/worktree 继续工作，安全读取低打扰；launcher 只做一次 exact context/source preflight，然后启动原 Executor。
- 长任务：`persistent-run start` 启一个 tmux run；断线后用 `status` 看事实；stale/partial 不自动重启。
- 自动邮件：原 owner 先决定“该发邮件”，Bridge 只把 immutable facts 做一次 Clear Writing；失败就 fallback；邮件或表达层失败都不改变业务运行。
- 用户无需理解 shared app-server、reader thread、Progress thread、injection、viewer concurrency、multi-agent readback、worktree exchange transaction 或跨 workflow event owner。

这满足本轮 reset 的核心目标：删掉复杂运行层，但没有通过删需求换简单。
