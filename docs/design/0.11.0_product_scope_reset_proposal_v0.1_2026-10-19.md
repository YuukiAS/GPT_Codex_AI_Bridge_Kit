## 1. 核心结论

当前 `0.11.0` 已经整体过度设计，问题不是某个 G14 blocker 没修好，而是产品边界失控。正式 `0.10.0` 到被审计的当前 `main` 累计 47 个提交；新实现把低摩擦读取、执行位置、控制源读取、长期任务进度、邮件通知、Clear Writing、Codex app-server、持久线程、工作树交换和跨工作流完成语义绑成同一个候选。结果是一个本应可选的通知表达层，可以阻塞整个版本；内部线程拓扑、字段和注入行为反而成为主要 Gate，而用户真正需要的能力迟迟不能形成稳定候选。

本提案建议保留版本号 `0.11.0`，但将其重置为一个小而完整的“执行连续性”版本，只新增四项能力：

1. 低风险高频操作通过现有 Host Policy 低打扰执行，危险邻近操作继续由 Codex/Host 权限边界拦截；
2. 在任何 Executor 启动前绑定当前仓库、工作树、分支、提交和必读控制源，禁止静默漂移到 `/tmp`，必读源不可用时在执行前失败；
3. Bridge 管理的 `AGENTS.md` 写入在落盘前计算预计字节并拒绝超限，不建立通用 instruction 运行子系统；
4. 长任务采用本地状态文件和普通命令行状态入口，保留一个运行级 `tmux` supervisor，但不依赖 Codex app-server、Progress thread、Clear Writing 或邮件才能启动和存活。

`0.10.0` 已有的通知器、进度证据规范化、Reviewed、Control、Lite、Persistent Run 模板和其他成熟能力继续作为兼容基线。0.11.0 不再扩展跨工作流通知事件总线，不引入 dedicated Progress display thread，不把 Clear Writing 自动调用纳入本版本核心，也不提供自动工作树交换。

## 2. 为什么当前 0.11.0 失控

### 2.1 产品目标被运行机制替代

真实需求是减少无意义审批、保持执行位置和控制源连续、让长任务可见、在需要时发送可靠通知。当前设计却逐步把这些需求改写为：共享 app-server、专用 Progress display thread、每次通知一个 fresh ephemeral reader thread、`thread/inject_items`、线程持久化与 reconnect、`instructionSources=[]`、多代理关闭回读、reader turn 预算、三类 intent、跨 Lite/Reviewed/Control/Persistent 的 emitter ownership。产品是否可用开始取决于这些内部结构是否全部成立。

这不是必要复杂度。尤其 Clear Writing 的真实任务只是把一段已经确定事实的通知文字做一次自然中文改写；它不拥有执行、完成或安全 authority，也不需要持久会话、专用 reader daemon 或显示线程。

### 2.2 可选能力成为全局发布阻塞项

当前 G14 同时要求证明长期运行生命周期、进度节奏、共享 app-server、持久显示线程、并发 viewer、注入、重连、三类通知意图、语义 authority、Clear Writing plugin 解析、fresh reader 隔离和 fallback。任何一个次要表面失败都会阻止整个 0.11.0 候选冻结，即使低摩擦读取、执行位置绑定和控制源读取已经可以独立交付。

当前 development canary 已给出直接反证：所选 Codex CLI `0.160.1` 无法把 machine-level `AGENTS.md` 从 reader 的 `instructionSources` 中清空，请求的 multi-agent mode 也被当前接口标为 deprecated/ignored；因此 canary 以 `UNSUPPORTED_WITH_EVIDENCE` 和 `FAIL_CLOSED` 结束，未创建 durable Progress thread，也未开始 final G01–G14。这不是继续堆恢复合同的理由，而是说明该产品路线不应成为发布前提。

### 2.3 Bridge 重做平台和 Git 已有职责

当前实现自行承担了 WebSocket handshake、frame parsing、JSON-RPC、app-server thread 生命周期、assistant item 注入、会话隔离、授权 effect digest、instruction discovery、工作树交换 transaction 和恢复 journal。平台已有 `codex exec`、Host execpolicy、session approval、普通 Git worktree 和 tmux；Bridge 只应补足它们不能直接覆盖的窄缺口。

### 2.4 成熟工作流被迫同步扩张

`agent_flow.py`、`reviewed_runner.py`、`reviewed_handoff.py`、Lite task runner 和 Persistent Run 都被加入相似的 readiness、event ownership、intent 和 notification 路径。很多改动不是因为这些工作流各自存在真实失败，而是为了让新总架构在所有 workflow 中形式一致。统一不是独立用户价值，反而扩大了回归面。

### 2.5 Gate 逐渐验证内部实现而非用户结果

从 G01–G14 到 18 条 journey，很多检查证明的是 schema、thread topology、readback 字段、共享 server 和注入路径，而不是用户能否顺利读取、在正确工作树执行、看到真实状态、收到可靠通知。测试和 fixture 大量增加，但最终真实 canary 仍在运行前提上失败，说明机械覆盖没有转换为正常入口能力。

### 2.6 沉没成本已经开始左右范围

Final Scope Recovery v0.1–v0.8 不断修改 Gate、恢复语义和执行合同，v0.8 Execution Plan 接近两千行。继续以“已有实现很多”为理由补齐所有机制，只会增加下一轮耦合。旧实现可以保留为证据，但不能自动获得产品保留资格。

## 3. 如果今天从正式 0.10.0 重新开始，我们还会这样设计 0.11.0 吗？

不会。

从 `release@9db19b0409816c22042a246b35a33e1d34fedd0a` 出发，合理路线是：先扩充 Host Policy 的精确低风险规则；再为 Executor 增加一个窄的上下文与必读源 preflight；给 Bridge 管理的指令写入增加一次落盘前字节检查；最后仅用 tmux、一个本地 binding 文件和现有项目原生进度证据补齐长期任务的 `start/status`。通知、Clear Writing 和 UI 显示都作为可独立失败、可独立发布的附加能力。

因此当前 main 不应被视为“接近完成，只差最后 canary”；它应被视为一组混合实验和历史证据。新版候选应按今天从 0.10.0 会采用的设计重建，而不是按旧架构删掉几个 blocker 后继续。

## 5. 五遍预检

### 5.1 产品

正常用户入口仍是现有 `ai-bridge host ...`、Lite/Reviewed/Control launcher 和 `ai-bridge persistent-run ...`，不是新的控制台、服务或线程管理器。用户新增得到的是：安全读取更少打断、执行前可以确定“正在正确位置并已读到正确控制源”、Bridge 不会写爆指令预算、长任务断线后可用命令行查看真实状态。

### 5.2 现实

当前 main 的真实 canary 已证明 reader isolation 假设在所选 Codex runtime 上不成立。相反，Host Policy、Git 当前分支快进、普通工作树身份、tmux、本地 JSON 和现有 progress normalizer 都已有实现或成熟原生基础。新版应围绕已存在、可直接验证的能力构建。

### 5.3 替代方案

- 继续 v0.8：拒绝。它把不可靠的可选表面设为全局 blocker。
- 全部回退到 0.10.0，不做 0.11.0：不采用。上下文漂移、partial clone 控制源和指令写入前检查仍是已证实缺口。
- 新建中央 daemon / database：拒绝。没有相应用户价值。
- 本提案：在 0.10.0 上选择性增加四个薄能力，其他全部保持独立。

### 5.4 反证

本提案主动接受以下结果：进度可能是 `UNKNOWN`；Clear Writing 不可用时不影响业务；没有可靠 quiescence proof 时不自动交换工作树；session approval 无法证明跨会话连续时允许重新审批；mandatory source 无法安全读取时直接停止。这些是诚实边界，不以伪造状态或低配替代换取 PASS。

### 5.5 执行

本轮只形成 Proposal。Critic PASS 后仍需形成同版的简短 Execution Plan、Canonical Goal 和 Kickoff Draft，再做 execution-ready Critic review。产品重建应使用一个新实现分支，但本提案不创建该分支，也不授权代码改动。

## 6. 外部与平台现实核查

### 6.1 Codex 普通执行优先于 app-server

OpenAI 当前官方文档把 `codex exec` 定位为脚本、持续集成和一次性非交互任务入口，支持结构化事件流、明确 sandbox/approval、ephemeral 执行和 session resume。官方“Codex as a platform”材料进一步区分：脚本或后台一次性任务使用 `codex exec`；应用代码需要程序化 start/resume/stream 时使用 SDK；只有产品 UI 需要深度生命周期控制时才考虑 app-server。

这支持两项删减：一段通知文字的 Clear Writing 不需要 app-server；普通 Bridge 长任务也不应因为显示线程而依赖 app-server。

### 6.2 app-server 持久线程不是简单可靠的状态存储

OpenAI 当前 app-server 源码文档仍将多项线程能力标记为 experimental，并明确说明未使用的 thread 不保证跨重启存活，ephemeral thread 不能持久化相应状态。Bridge 当前自建 WebSocket client 和注入/重连合同会承担平台内部接口变化与持久化语义的不确定性，不适合作为 0.11.0 release-critical 基础。

### 6.3 execpolicy 已能表达低风险和危险边界

Codex rules 可以对精确命令形状给出 allow、prompt 或 forbidden 决策，且更严格规则优先。安全 Git 读取和受边界约束的当前分支快进应继续在 Host Policy 中表达；无需再造通用 Git controller。

### 6.4 Git worktree 已有原生对象，但没有可靠 quiescence authority

Git 已提供 `worktree add/list/lock/move/remove/repair`。Bridge 可以检查当前位置、注册关系和锁，但不能把 `ps`、`lsof` 或“没看到进程”升级为排他性 quiescence 证明。因此 0.11.0 应删除自动 reciprocal exchange，而不是为永远 fail-closed 的生产入口继续维护 transaction/journal。

## 8. 新的最小 0.11.0 产品范围

### 8.1 能力 A：低打扰 Host Policy

**用户实际获得什么：** 当前可信仓库中的常用安全读取和明确的当前非 main 分支快进同步不再反复打断；危险 Git、任意 remote/refspec、force/delete/reset/rebase、凭据和外部高影响操作仍由平台拦截。

**没有它会复发什么：** 普通状态、差异、分支和同步读取反复触发审批，用户已经批准的开发位置又被拆成多个低层授权。

**最简单实现：** 继续使用 `$CODEX_HOME/rules/ai-bridge-global.rules` 的精确命令形状；只保留 `sync-current-branch` 这一窄 helper。不得新增通用 Git parser/controller。

**正常入口：** Codex 正常执行安全命令；必要时用户或工作流调用 `ai-bridge host sync-current-branch`。

**失败行为：** 规则未匹配时回到 Codex 正常 prompt；helper 发现 dirty/diverged/wrong upstream/unsafe transport 时返回具体原因，不自动 stash、merge 或 rebase。

**发布资格：** release-critical。

### 8.2 能力 B：执行上下文与必读控制源连续性

**用户实际获得什么：** Executor 启动前明确知道当前仓库、工作树、分支、HEAD 和必须读取的控制文件；这些对象与冻结任务不一致或文件内容无法取得时，不会继续执行。

**没有它会复发什么：** 任务漂移到 `/tmp`、错误工作树；partial clone 中只看见路径却没有读到内容；控制源读取失败后仍自行发明替代路线。

**最简单实现：** 一个 `preflight_execution_context(...)`：

1. 读取当前 `git rev-parse --show-toplevel`、当前 worktree path、branch、HEAD；
2. 与任务已冻结 locator 比较；
3. 对必读文件优先读取 clean worktree/HEAD-bound 内容；
4. blob 本地缺失时，只允许一个固定 repo/commit/path 的 isolated object read，临时对象写入 Bridge state，不修改受保护 Git 状态；
5. 记录 path、size、sha256 和实际文本；
6. 任一步失败均在启动模型或 child process 前终止。

该 helper 不负责分支创建、worktree move、自动 fetch-all、authorization storage 或 workflow state transition。

**正常入口：** Lite `task run`、Reviewed runner 和真正需要控制源的 Control launcher 在启动 Executor 前各调用一次；没有必读源的普通命令不调用。

**失败行为：** 返回 typed reason 与最小恢复信息，保持当前仓库零业务改动；禁止 `/tmp` fallback 和“先执行再补读”。

**发布资格：** release-critical。

### 8.3 能力 C：Bridge 管理指令的写入前预算

**用户实际获得什么：** `host install`、Persistent Run install、Overleaf 等 Bridge-managed block 不会把目标指令链写到 Codex 截断边界之外。

**没有它会复发什么：** Bridge 自己追加的块使后续规则静默不被消费，或写到一半才发现溢出。

**最简单实现：** 单一 projected-byte helper，只在 writer 写文件前使用。它读取当前支持的 byte limit 和相关 instruction chain，计算更新后的总字节；Bridge 管理块同时有各自上限。超限时原文件 byte-for-byte 不变。用户自有内容只报告，不自动删改或摘要。

**正常入口：** 现有 install/update writer 自动执行，不要求用户单独运行 audit。

**失败行为：** `BRIDGE_MANAGED_INSTRUCTION_PROJECTED_OVERFLOW`，给出 limit、projected total、first risk source 和需要释放的最小字节；零 mutation。

**发布资格：** release-critical。

### 8.4 能力 D：本地长期运行与真实状态

**用户实际获得什么：** 对确实由终端拥有、需要断线存活的命令，用户可以启动一次、断开、随后重新运行 `status` 查看是否仍在运行、最后 exit code、项目原生 progress 和 ETA；无法估计时明确显示 `UNKNOWN`。

**没有它会复发什么：** 任务是否还在运行只能靠原 Executor thread；断线后没有稳定入口；显示层故障反过来杀掉业务任务。

**最简单实现：**

- 一个 run-scoped tmux session；
- 一个 run-scoped supervisor，它只负责启动 child、记录 PID/start/end/exit，并在 child 结束后退出；
- 每个 run 一个本地 binding JSON；
- 复用 0.10 `progress/report/latest` 读取项目原生进度证据；
- `persistent-run start` 对相同 repo/run key/Goal hash 幂等返回现有活动 run；
- `persistent-run status` 合并 tmux 存在性、binding 和 latest progress。

supervisor 不是 daemon、watcher 或中央 controller；不拥有 semantic completion，也不创建 Codex thread。没有 progress file 时业务照常运行，状态显示 `UNKNOWN`。

**正常入口：** `ai-bridge persistent-run start --target ... --goal ...`、`status`、`report`、`latest`。

**失败行为：** 启动前验证失败则不创建 session；状态证据不完整时报告 `UNAVAILABLE` 或 `UNKNOWN`；任何 notifier、Clear Writing、Gmail 或 UI 失败都不得终止 child，因为这些能力不在核心生命周期中。

**发布资格：** release-critical。

### 8.5 明确不属于 0.11.0 的产品承诺

- Codex App 中的专用 Progress thread；
- reader daemon、fresh app-server reader topology、shared app-server；
- automatic Clear Writing；
- notification event bus 和跨 workflow emitter ownership；
- 自动 reciprocal worktree exchange；
- authorization database 或长期授权服务；
- 通用 Git wrapper；
- 通用 instruction discovery 产品；
- 为所有 workflow 统一的新 schema/state machine。

## 9. 通知与 Clear Writing 的最小未来模型

本节只冻结边界，不把功能加入 0.11.0。

### 9.1 通知

0.10 notifier 继续提供 Gmail transport、配置、dedupe 和显式 send。未来自动通知如有必要，只接受由 owner 直接提供的一份 immutable facts：

- `progress`：只表示运行进展；
- `runtime_terminal`：只表示进程结束和 exit facts；
- `semantic_completion`：只有已有 workflow authority artifact 才可产生。

三者可以共享一个很小的数据结构，但不得形成事件总线、生命周期服务或所有 workflow 的强制 schema。每个入口决定是否调用 notifier；transport 失败只记录，不改变业务状态。

### 9.2 Clear Writing

唯一允许的未来路线是：

```text
canonical facts
→ 一次 fresh codex exec / 正常 writing-style skill 调用
→ 数字、状态、UNKNOWN、路径和结论强度的机械检查
→ email 或其他已有表面
```

skill 不可用、模型失败、输出越界或保真检查失败时，立即使用确定性短中文 fallback；不 suppression，不重试第二模型，不启动持久 session，不要求 `instructionSources=[]`，不引入 Progress thread。该能力必须单独通过 normal-entry 证据后才能进入某个未来版本，失败不得阻塞 0.11.0 core。

## 10. 简化后的组件职责

```text
Host Policy
  └─ 精确低风险 allow / 高风险 prompt-or-forbidden

Execution preflight
  ├─ current repo/worktree/branch/HEAD binding
  ├─ mandatory source content binding
  └─ managed instruction write projection

Existing workflows
  ├─ Lite / Reviewed / Control 保持各自状态和 authority
  └─ 只在真正启动 Executor 前调用 execution preflight

Persistent Run
  ├─ tmux session
  ├─ run-scoped supervisor
  ├─ local binding/status
  └─ existing project-native progress normalization

Notifier 0.10
  └─ 独立 transport / manual delivery / dedupe，不拥有 runtime
```

不存在新的中央调度器、跨 workflow event owner、app-server client、持久 Codex display thread、authorization store 或工作树事务服务。

## 11. 复杂度预算

以下是硬边界；任何偏离都必须回到 Planner–Critic，而不能由 Executor 临场增加：

- 新 daemon：0；
- 新长期 background service：0；
- 新 watcher：0；
- 新 database：0；
- 新跨 workflow state machine：0；
- 新 persistent Codex thread：0；
- 新自建 WebSocket / app-server client：0；
- 新通用 Git wrapper/controller：0；
- 新 authorization store：0；
- 新自动 worktree exchange：0；
- 允许的新增运行对象：每个 Persistent Run 最多一个 run-scoped supervisor 和一个 binding JSON；
- release-critical capability gates：4；
- 文档：本 Proposal，后续一个简短 Plan、一个 Goal、一个 Kickoff Draft 和对应审查记录；不再制造多卷 dossier。

代码行数不是质量 Gate，但作为过度设计触发器：以 0.10.0 为产品基线，新 0.11 核心生产增量目标应控制在约 800–1200 行；若超过 1500 行或再次出现单一新模块接近 1000 行，Execution Plan 必须暂停并回 Critic 说明为什么现有机制无法替代。目标是较当前 main 的 0.11 生产增量减少至少约 60%，同时删除两个独立 runtime abstraction（reader/display）。

## 12. Capability Gate Matrix

旧 G01–G14 不再继承。新 Gate 按真实用户能力设计，所有 release-critical Gate 必须由同一个 final candidate SHA 直接通过；candidate identity 是发布不变量，不另设一个产品 Gate。

| Gate | Capability / claim | Why distinct | Normal entry | 必须证据 | 明确失败 | Regression boundary | Final candidate |
|---|---|---|---|---|---|---|---|
| `C1_LOW_FRICTION_BOUNDARY` | 安全高频读取与当前非 main 快进同步低打扰，危险邻近仍受控 | 证明权限边界，不证明执行上下文 | 真实 Codex + Host Policy；`host sync-current-branch` | 代表性 safe commands 无重复 Bridge 问答；dirty/diverged/arbitrary remote/force/reset 等负例 prompt 或拒绝 | safe 正例仍被 Bridge 重复询问，或危险负例被 allow | 0.10 sandbox/refusal/publisher；既有高风险边界 | 是 |
| `C2_CONTEXT_AND_SOURCE` | Executor 在正确 repo/worktree/branch/HEAD 且实际读到必读控制源后才启动 | 证明位置与内容连续性，不证明一般权限 | Lite/Reviewed/Control 的真实 launcher | 用户选定工作树不漂移；真实 partial clone 情形下要么内容成功绑定，要么 child/model 启动前 typed block；受保护 Git 状态不被意外改变 | `/tmp` fallback、只验证路径、读取失败后继续、source/HEAD 漂移未阻断 | 0.10 Lite/Reviewed/Control 状态机与正常启动 | 是 |
| `C3_MANAGED_INSTRUCTION_WRITE` | Bridge-managed writer 写前发现 overflow 且零 mutation | 证明写入安全，不证明 runtime source 是否被模型消费 | `host install`、Persistent Run install、Overleaf writer | under-limit 正例成功；projected overflow 下原文件 exact bytes 不变并给出可恢复诊断 | 部分写入、静默截断、自动删用户内容、只在写后报告 | 0.10 root AGENTS 保留、模板安装和现有用户内容 | 是 |
| `C4_PERSISTENT_LOCAL_STATUS` | 终端拥有的长任务可启动、断线、再次查看真实状态并得到 terminal facts | 证明本地生命周期，不证明 semantic completion 或邮件 | `persistent-run start/status/report/latest` | 同一 Goal 幂等 start；真实 tmux child 跨客户端断开继续；status 显示 running/terminal/exit；无 progress 时 `UNKNOWN`；状态读取失败不杀 child | 依赖 app-server/reader/email 才能启动；显示失败终止业务；runtime exit 冒充 Goal PASS | 0.10 progress normalizer、ETA/UNKNOWN、模板与授权边界 | 是 |

### 12.1 Regression bank 归属

- 高频 Git 误打断与危险邻近绕过 → `C1`；
- `/tmp` 漂移、错误 branch/worktree、mandatory source 未读、partial clone lazy hydration 失败后继续 → `C2`；
- Bridge-managed `AGENTS.md` overflow → `C3`；
- 断线、状态 UNKNOWN、运行终态和 UI/通知失败隔离 → `C4`。

旧 G14 reader canary failure 不迁移为新 Gate；它是删掉旧架构的反证。`reader_layer.py` 的 fake app-server 单元测试也不能作为任何新 Gate 的 production evidence。

### 12.2 执行顺序

1. cheap deterministic 单元与 should-not-change 回归；
2. C1 真实 Host execpolicy 正负例；
3. C2 真实 selected worktree + partial clone；
4. C3 真实 writer under/over limit；
5. C4 真实 tmux disconnect/reconnect/terminal；
6. 同一候选的 README/CHANGELOG、安装身份和完整回归。

不运行 Clear Writing、app-server display、Gmail 真实发送或旧 G01–G14 作为 0.11.0 release blocker。若后续单独决定发布通知增强，应建立独立、非耦合的 capability gate。

## 14. 从当前 main 收敛到新候选的最短路径

1. 独立 Critic 审查本 Proposal，确认范围、删减、复杂度预算和四个 Gate；
2. 若 PASS，Planner 形成一个简短 Execution Plan、Canonical Goal 和 Kickoff Draft，不继承旧 v0.8 包；
3. Critic 对同版 execution package 做 execution-ready review；
4. 用户发送 approved kickoff，授权创建 reset branch、修改代码、运行本地测试与四个 Gate；
5. Codex 在 branch 上先完成 product-path reset，再按 `Host → context/source → writer budget → Persistent local status` 顺序实现；
6. 每完成一个能力先跑其 cheap regression，不启动旧 canary；
7. 冻结一个候选 SHA，按 C1–C4 顺序跑真实 normal-entry Gate；
8. 同步 README/CHANGELOG/TODO，完成 final Critic 审查；
9. formal release 移动仍需单独明确授权和远端 SHA readback。

任何阶段如果为了通过 Gate 又需要 app-server、持久 Codex thread、database、自动 exchange、authorization store 或新的跨 workflow state machine，立即停止并返回 Planner–Critic，不得恢复旧架构。

## 15. 用户是否需要决定

当前无需用户选择产品路线。本提案已经作出明确建议：保留 `0.11.0` 版本号，按四项执行连续性能力重建；通知扩张、Clear Writing、Progress display thread 和自动 worktree exchange 不进入本版。

后续真正需要用户的只有执行授权，而不是产品偏好：在 Proposal 和 execution package 均获 Critic PASS 后，用户再一次性授权创建 reset implementation branch、修改相应生产路径、运行四个 Gate，并决定是否最终推进正式 `release`。本轮不请求这些授权。

## 16. 风险与恢复

- **删得过多：** 通过 0.10 should-not-change 回归和按路径恢复控制；成熟 workflow 不随新架构一起重写。
- **mandatory source helper 仍过重：** Execution Plan 必须先证明普通读取与一个窄 isolated fallback 已足够；不得恢复整个 readiness subsystem。
- **Persistent Run 又膨胀：** 核心仅接受 tmux、run-scoped supervisor、binding/status 和现有 progress；任何 notification/UI/model 依赖都退回未来版本。
- **Host allow 过宽：** 每个 allow shape 必须有危险邻近负例；无可靠 parser 时保持 prompt。
- **reset branch 与 main 历史冲突：** 使用普通提交恢复路径，不 force push，不删除历史设计证据。
- **平台能力变化：** 只依赖官方稳定普通入口；可选表面变化不得阻塞核心。若 Codex 或 Git 接口变化导致核心假设不成立，停止对应 Gate 并回 Critic，不静默降级。

## 17. 阶段价值

本 Proposal 获得 Critic PASS 后新增的不是代码能力，而是一个可执行的产品决定：0.11.0 不再以 v0.8 为 authority，明确只交付四项执行连续性能力，并给出必须删除的组件、复杂度上限和四个真实 Gate。只有后续同版 execution package 再获 PASS，才会形成 Codex 可执行入口。
