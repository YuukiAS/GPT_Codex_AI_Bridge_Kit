## 四、BR-NAC-R0-01：五个安全入口、真正的权限与有限修复

### 4.1 为什么 sync 真的过宽

Host Issue #1 为已有已跟踪、非 main 的工作分支提供低打扰快进，明确只在 GitHub HTTPS canonical origin、同名 tracked upstream、干净工作树与严格 fast-forward 成立时启用。0.11.1 host.sync_current_branch 取出有效 fetch/push URL 后却调用 _canonical_repo_identity，函数允许 `git@github.com:`、`ssh://git@github.com/`、file/local 与 HTTPS。这意味着传输要求原本不满足的目标仍可能借同名 identity 进入低打扰入口。

只在 sync_current_branch 的 fetch/push 两个实际 URL 上改用现成 `_publisher_github_https_identity` 的严格 GitHub HTTPS 断言，核对 repo=push_repo=expected_repo，且在 fetch/merge 等任何网络或工作树写入前拒绝 SSH/scp/file/local、重写 URL、自定义传输、多 URL 或非同名远端。继续要求 clean、origin upstream、祖先、FF 和 post-OID。使用原错误家族 `UNSUPPORTED_TRANSPORT_REQUIRES_ORDINARY_APPROVAL` 或同等精确拒绝。**不修改通用 `_canonical_repo_identity`**，因为 Reviewed 及合法 disposable 本地 Git 仓库仍用它；`publish-current-branch`/`publish-first` 已是 HTTPS-only，不重造安全机制。

### 4.2 “没有规则命中”绝不是“用户已经被询问”

_ execpolicy_decision 能返回 `allow`、`prompt`、`forbidden`、`no_match`；当前 `_effective_execpolicy_decision` 却把 `no_match` 转成 `prompt`，导致 host validate 对一些危险邻近直接命令错误报告“审批保护已命中”。OpenAI 官方 codex-execpolicy README 中没有匹配时 `matchedRules=[]` 且不提供 decision；此时实际许可还依赖当前 Codex 原生危险命令启发式、审批配置、沙箱和工具通道，不能凭规则文件判定。官方原始实现 `codex-rs/core/src/exec_policy.rs` 亦按审批/沙箱处理 unmatched。

最小修复：保留原始匹配诊断，明确区分 `RULE_MATCH_ALLOW`、`RULE_MATCH_PROMPT`、`RULE_MATCH_FORBIDDEN`、`RULE_NO_MATCH`；不再强行将最后一项写为 prompt。对于本来宣称“原始危险操作需要明确审批”的测试，只有真实 explicit rule match prompt/forbidden，或来自同一 CODEX_HOME/CLI/模式的实际原生审批负例，才可计为已验证；否则注明 `NATIVE_APPROVAL_UNVERIFIED`，不能合成 PASS。实际存在缺失且影响用户安全的直接危险 Git 形状，可为**已证实的那个具体命令形状**补当前 Host policy 的最小 prefix_rule/入口指引，同时回归已允许的正常安全 Git 读取、main FF、add/commit 和包装器 allow。不能滥加通用规则使安全工作全部重新审批。

### 4.3 五个包装入口为什么不能直接删掉

| 正式命令 | 防止的历史失败 | 真实内部检查和下游 |
| --- | --- | --- |
| `reviewed-handoff task bootstrap` | 首个任务工作树创建额外重复索权或污染 canonical main | 从 task_key 派生 reviewed 分支与 sibling worktree，核对 origin/main 精确 SHA、唯一 origin fetch、危险 hooks/filter/重定向，创建初始 REQUEST/CURRENT，**不联网** |
| `reviewed-handoff task publish-first` | 因远端尚无首次 reviewed 分支而多问一次 `git push -u` | 校验 HEAD 是 base 唯一直接子提交、diff 只有初始 REQUEST/CURRENT、任务身份、空远端、HTTPS、空目标 lease，发布后远端 OID 核对 |
| `reviewed-handoff materialize-worktree` | 本地 worktree 丢失后猜工作树、错收养远端分支 | 本地或精确远端冻结 REQUEST/CURRENT、base ancestry 与工作树断言；恢复前拒绝歧义，不复制到 canonical main |
| `host publish-current-branch` | 当前已存在同名分支发布反复审批 | repo/branch/upstream、已有同名远端、HTTPS fetch/push、credential/hooks/config 与祖先，唯一非强制 refspec 发布 |
| `host sync-current-branch` | 当前已跟踪非 main 分支落后同名远端时陷入原始 Git 审批 | 需修成 HTTPS-only，校验 repo/upstream/clean/ancestry，实际 fetch + ff-only + post OID |

它们做的是原始 `git` 本身不理解的动态任务/范围检查。**包装器保证只在调用了包装器时成立**。Host execpolicy 的精确命令匹配是另一层；AGENTS/Goal 禁止绕过只是行为约束；独立 OS shell、Python、其它 MCP、不同 CODEX_HOME 或已经获得高权限的用户进程，不会神奇地执行包装器动态检查。承诺应是“在已加载并实际验证的 Codex 身份下，冻结的危险直接路径不会被当作安全低打扰操作放行”，不是“全机所有绕行都不可行”。

### 4.4 唯一需要的额外 Host 验证

新候选在隔离 Git repo 对合法 GitHub HTTPS 同名远端 FF 做一次真实正常入口，错误 SSH/local/改写传输应在 fetch/merge **前**拒绝并验证 ref/worktree 不变；其它 wrong repo/branch、dirty、diverged 同样失败。已通过的旧 bootstrap、publish-first、publisher 实际正例在代码未变且新候选回归通过后按原身份保留，不再盲目推送。

从真正选定的 CODEX_HOME 中读取真实已加载规则与 Codex 版本/审批/沙箱，运行只读 `codex execpolicy check` 并记录原始 matchedRules/decision；另选一个当前授权的隔离真实 Codex 会话测试受控危险直接 Git/`git -c`/shell/Python/绝对路径及对应 wrapper：区分 prompt、forbidden、allow、no match，确定实际副作用未发生。不得未经授权真实 push/delete。若发现某个危险 direct effect 真正绕过当前 Codex 层才修精确 Host/调用入口；不安装全局拦截器，失败后不能用 raw Git 当替代解法。

## 五、BR-NAC-R0-02：进度真实性、ETA 与 durable-first

### 5.1 谁定义进度、何时可以 none/stage

批准的 Goal 和专业项目 owner 决定可否量化、完成单位/总量、阶段、生产者和正向业务完成条件；Bridge 不从 GPU/PID/日志行数推断专业比例，也不替论文/算法作“完成”结论。当前模板原样 `Progress mode: none`，启动检验只拒绝 count/fraction+owner none，因此一个本可报告 1000 个单位的任务可能没有理由就永远 UNKNOWN。

新正式 Goal 必须冻结可量化性及依据。count/fraction 要说明真实 producer 可执行入口、进度单位/总量身份、有效进度源与更新时间；没有专业进度来源或无法量化时允许 stage/none，但要有具体原因、责任项目及替代观察。对于已在跑的旧冻结 Goal，只读恢复、不倒改 identity、不自动重启；新 Goal 或新身份按新合同检查。不能靠用户当前 shell 环境任意字段自己升级授权。

### 5.2 生产者要证明在持续发布，不是填了字段

新增的是既有合同的验证约束，而不是进度数据库：

- `Progress mode` 属于 count/fraction 时，`Progress owner` 必须为 bridge-child 或 project-native，有**真实的生产者命令/函数/模块与项目 owner**，source 为 bridge-state 或 repo-relative JSON；`Expected progress update seconds` 必须是有依据的正整数，不准随意 UNKNOWN。
- bridge-child 继续使用已有 `AI_BRIDGE_RUN_KEY/AI_BRIDGE_PROGRESS_PATH/AI_BRIDGE_PROGRESS_MODE/AI_BRIDGE_PROGRESS_OWNER/AI_BRIDGE_RUNTIME_ID` 环境，业务程序通过 `ai-bridge persistent-run progress update` 原子生成本次真实事件。
- project-native 只能通过项目已有正式进度文件或一层有限 mapping 得到 run identity、原始事件时间/单调发布序号、stage、completed/total/fraction；需要最小改动时由原项目 owner 适配，Bridge 不发明科学含义。
- 既有 count/fraction 输入只有“producer 名字”但无法确定与当前 run 对应，不视为可靠数据；过期、未来时间、倒退序号、另一个 run 的 JSON、伪造总数不能变成新有效点。已经认证为有效的 last-good 继续保留，错误来源只提示观测不可用，不杀 child。

### 5.3 新增来源时效分类，保留原估计公式

监督器继续大约每 60 秒检查，但保存“项目生产者真正的新发布事件身份与时间”和“Bridge 本次检查时间”两个概念。重复读同一份 JSON 不会制造新的有效 ETA 点，也不能刷新生产者健康度。对量化任务，首次有效报告及以后两次真实发布之间的允许间隔冻结为 `max(900, 3 × expected_update_seconds)` 秒；超过判来源 `PROGRESS_SOURCE_OVERDUE`。这是产品观察防抖规则，不是判业务卡死的统计门槛；额外观察延迟至多约一个 60 秒周期。只有有正当长阶段不更新的专业任务可以在 Goal 中冻结更合理的真实预期更新秒数，不允许运行后临时拖长来避免报警。

实际状态要区分：
- 尚不足三个合法点及十分钟：正常 **预热**；
- 按期新发布但未发生量化增长：**有效平台期**，producer 仍健康；如速度不足则暂停/降低 ETA，不推断进程 blocked；
- 原数据文件临时丢失、半写或坏 JSON：**来源不可读**，保留上次有效进度但标注其时间；
- 生产者在应汇报的期限内没有任何新有效发布：**来源超期**，即便进程仍活着也显式报告，旧 ETA 不再装作实时；
- stage/total 变化、回退、长 gap：恢复原 ETA 预热；明确说明依据失效；
- 真正业务进程异常：由原 runtime owner/项目诊断，不能仅由停报推断。

这些仅是既有 binding/progress 的原因字段，不产生第四种 workflow 或独立状态机。

已有 `estimate_progress_eta` 继续以最近不超过 60 分钟/12 点的合法记录、同一 stage/total 至少三个点跨十分钟、正向速度中位数推算 ETA。上下限只代表历史速率分布的**经验范围**，不是概率校准的 95% 区间。来源超期、缺近期支持或平台期无可信速度时，ETA 可以诚实 UNKNOWN，但必须解释**为何**，不能永久悄然 UNKNOWN。

### 5.4 status、history、邮件真正共用一个权威快照

目前 `observe_binding_progress` 保存 `binding.last_good_progress`（包括主动 ETA），但 `status_persistent_run` 的 `_progress_status` 重新标准化原始文件，可能只显示 UNKNOWN。冻结修订：对已有 run binding 的正常 `status`，用户主要 progress、last-good、进度历史、ETA、数据实际发布时间、数据可信分类都来自监督器**已持久化的同一规范化快照**；通知读相同快照及来源时间，不单独推算不同 ETA。status 只读，不以查询时间“补”新生产者进度。

原来独立的 `persistent-run report/latest` 继续服务项目原生和 Slurm-owned 来源，未绑定本次 managed run 的独立报告**不能**冒充该 run 的权威 status；若显式属于相同 run，消费同一规范化规则与真实身份并展示准确绑定条件。中断后恢复仍沿现有 binding/session 关系，不复制第二状态数据库。

### 5.5 为什么启动/终态要先持久化再发信

0.11.1 中 `supervise_binding` 在 Popen 成功后先发 runtime_start 通知，之后才持久写 child_started_at/PID 等；在 child.wait() 确认 exit code 后也是先发送 terminal 再保存 terminal binding。邮件可阻塞最长 120 秒，进程崩溃会让真实已发生的进程事实尚未落盘，影响断线后安全恢复。

不增加通知后台。保持现有每 run 一个 tmux、一个 supervisor、一个 binding、一个 primary child：

1. launcher 在创建 tmux 前继续原子保存 START_REQUESTED/exact Goal；承认“创建 OS 进程与写 binding”不是可移植的跨进程事务，崩在极窄窗口只能按现有 UNKNOWN/重复风险安全恢复，不得盲目重启。
2. supervisor Popen 成功后立即原子写 RUNNING、pid/start identity 与已有初始观察，**之后**才发 runtime_start。不得依赖 Gmail 成功才能写运行状态。
3. 中间进度/stale 新事实先原子写 binding.last_good/history/freshness/最近逻辑发送时钟，再请求 Notifier；后者已有 per-event claim/receipt/idempotency。HTTP/SMTP 是否接受不明确时按 DELIVERY_UNKNOWN，只可显式人工 retry，不自动补发。
4. child.wait() 取得真实退出码后，在终态邮件之前做一次**有界最终读取**；有效末次数据归档，读坏则保留 last-good 并注明未确认。随后原子写 TERMINAL、exit_code、child_exit_observed_at、最终可信 progress，然后才发 runtime_terminal。
5. SMTP/Clear Writing 失败、helper 超时或 supervisor 异常不改变已经持久的 child/terminal 真值；恢复者只能依据 session/PID boot/start identity 与绑定/Notifier receipt 确认发生了什么，exit code 丢失时不可猜语义完成，也不自动另起 child。已有 recover/resolve 的防重复边界不变。
6. 对“last_notification 还没更新”不能直接推断“没有发送”，要先查看已有 Notifier 事件 ledger 的事实；没有凭据/回执时报告 DELIVERY_UNKNOWN。不得增加第二数据库或 daemon。

这样用户刚启动查询能看到真实 child；最后一个进度不会仅因 60 秒观察间隔而失踪；终态即使邮件卡住也已经可以从状态接口读到；报错或断线后不用删除 state，也不会自动启动第二份实验。

### 5.6 唯一真实量化正常入口 Gate

最终必须从**实际已批准、工作天然可以量化并持续超过 ETA 预热的现有任务**出发。任务业务 child 自己在正常代码里提交有效事件，Gate 驱动程序不得从旁代填 fraction，不得仅以 sleep 十分钟冒充业务工作。批次必须覆盖：Goal 选 count/fraction 有根据；child 单例启动；3 个不同合法点跨 ≥10 分钟；status/history/ETA 同源；在 primary child 活着时从原 producer 暂停发布→识别来源超期→恢复发布；有效平台期与源失联不同；坏 JSON 不杀 child；最终 child 真实末次数据 + exit 0 被保留但不写 Goal PASS；断开/再次 start 不重复运行；如已明确批准 Notify ON，邮件与同一快照一致、不重复、不因错误影响 child。

首选在已批准且实际可量化的 Bridge/AI_Skills 现有 QA 工作任务中选一条真实 CPU 工作负载；**不能**为了凑十分钟而反复跑无必要的无意义循环，也不能在没有新许可的情况下重新跑 DII 的 GPU/M&Ms 或 Slurm 任务。执行包冻结前必须把唯一项目、Goal SHA、业务 producer、工作单位和预期运行时间读明白；无此输入，保持 Gate 未能实施和总体 NOT_COMPLETE，不能让 Codex 自由换题。

- **替代**：只改 README/多加一轮 helper tests 阻止不了 SSH 误授权、运行状态先发信后落盘；借 PID/日志自己猜百分比不可靠；创建通用 daemon/强制 OS 拦截过重而且侵犯已有 owner。选现有 Host/监督器中最小必要修复。
- **反证**：特别检查不同版本拼 Gate、用测试脚本代 child 上报、假 ETA、无授权邮件、跳过项目专业 reviewer、执行中断后另跑一份 Goal、没有匹配规则却报 prompt。任一反例成立不得 PASS。
- **执行**：本文件只是设计 v0.2。独立 Critic 先判断三个 finding 及完整十二项 Gate/预算 `PROCEED / REVISE`；若 PROCEED，Planner 才冻结对应同版 Plan/Goal/Kickoff，**执行开始前**须解决真实机器、数据、账户、限额、工作树/任务选择和关键授权，不留给 Codex 猜。完整执行包经唯一 Critic `PASS + READY_FOR_CODEX=YES` 并由用户授权后，才允许普通实施。开发回归和必要自检通过后再由独立 Critic `PROCEED_TO_FINAL_EVALUATION / REVISE` 决定是否可消耗唯一 live 批次。无任何本轮自动 release 授权。

退出/恢复：若合同内普通实现或回归失败，在**同一** Codex 任务修；如果要改认证、预算、产品用户承诺、专业来源或恢复语义，停止回 Planner/Critic；用户真正独有的外部数据/账户决定只问一次精确边界；无法取得关键授权则保留明确未完成并停止收费/邮件/远端变更。不得创建下一个自主 Goal 来绕过未完成事实。

## 九、用户关键决定（正常语言）

未来一个实际可量化的长期任务，必须先说清单位、生产者和多久汇报；如果来源停报，Bridge 告诉你“进程仍在，但最后一份进度已经超期”，而不是永远 UNKNOWN 或错报任务卡死。已经算出的 ETA 会和 status、邮件、终态同源，最后的有效进度和进程退出先保存，再发邮件。已经由 Slurm 等系统拥有进程寿命的任务继续使用其原生调度，Bridge 不套多余 tmux，也不推断专业实验成功。

原有五个安全 Git 包装入口继续可用；新增修正使低打扰同步只走明确批准的 GitHub HTTPS。Codex 规则根本未命中时会准确显示“未匹配，平台行为还需核实”，不能装成用户必然已看到审批。不会安装一个全机命令拦截服务。

旧的真实正常路径证据能复用就复用，尚缺完整交付的能力必须在当前固定的十二项中通过一次合法、有限、真正实际入口的验收。真实邮件、模型、GitHub/Overleaf 写入或额外费用需一次明确授权；用户未授权时保留缺项，不把真实产品完整性改成纸面 100%。
