## R2-01：候选 Host 程序与现有 Codex 执行策略分层验证（本轮唯一修订）

**原因与责任分开：**正式 0.11.1 的 `templates/host/rules/ai-bridge-global.rules` 用 `host_executable(name="ai-bridge", paths=[实际已安装的绝对路径])` 固定可信程序，`prefix_rule(["ai-bridge","host","publish-current-branch"/"sync-current-branch"])` 仅能在匹配这个身份后自动允许。新 0.11.2 仅供最终候选验收的 `/overflow/htzhu/mingcheng_new/GPT_Codex_AI_Bridge_Kit/private/exports/bridge-core--normal-entry-acceptance/candidate-venv/bin/ai-bridge` 是另一个可执行路径，不会由于文件名称相同或它通过源码安全检查就获得现有机器的 `allow`。在当前 `on-request` Codex 策略下，候选路径 `no_match` 只意味着**没有预先自动放行，进入正常审批**；绝不能把它当作 `allow`、当作产品安全失败，或用不安全 `PATH` 替身、软链接、通用 Python/shell 白名单绕过。

**一、候选版动态安全检查（实际代码行为）。**完整核对候选安装来源及 CLI 路径后，用**候选的上述绝对路径**在现有 `workspace-write` 及 `on-request / auto_review` 边界内直接调用原 CLI（不通过正式旧版代执行）。廉价正反回归在隔离任务仓库/受控传输下直接触发候选 Host 的 `publish_current_branch` / `sync_current_branch` 命令，而不仅调用内部判断辅助函数；实测 canonical GitHub HTTPS、当前分支与远端同名、clean、正确 upstream、祖先关系及快进后 OID，且 SSH/file/非 GitHub URL/rewrite/hook/错误 branch/upstream/dirty/diverged/非法 Git 环境均在危险操作前拒绝。唯一真实现有分支快进正例保持 v1.2 已冻结的 AI_Skills 消费者分支：只有 pre-final 通过、现有用户外部作用授权生效且第三次 Actions 结果已合法推送后，才从该消费者本地同名 `work/bridge-core--normal-entry-acceptance-text-transform` 分支运行 `/overflow/htzhu/mingcheng_new/GPT_Codex_AI_Bridge_Kit/private/exports/bridge-core--normal-entry-acceptance/candidate-venv/bin/ai-bridge host sync-current-branch --expected-repo YuukiAS/AI_Skills_Collection --expected-branch work/bridge-core--normal-entry-acceptance-text-transform`，核对 before/local/remote/post OID 与完整结果；无新远端写。调用由真实 Codex 审批决定是否可以运行，候选无需预先 `allow`。若审核平台要求针对该精确命令的单次审批，由当前用户确认或现有自动审查器按原协议处理；未放行就准确记 `APPROVAL_REQUIRED`，不得改规则、改调用路径、声称成功或偷偷执行。

**二、机器现有实际策略（与候选代码行为分开）。**保持正式 0.11.1 的可信 `ai-bridge`、真实 `CODEX_HOME`、`config.toml`、`AGENTS.md`、`rules/ai-bridge-global.rules` 完全不变。使用实际已安装的受信 `ai-bridge host validate` 与真实 Codex 可执行文件，在固定机器身份下**只读**核对配置、`host_executable` 实际绝对路径及具体 `codex execpolicy check --rules <existing-rules> --resolve-host-executables` 的结果：正式已绑定的受信发布/同步命令应 `allow`，候选路径不应作为自动 `allow`；普通 canonical Git read/fetch、add、commit 仍按当前已知低打扰范围放行；原始 `git push origin main`、强制推送、rebase、危险远端 URL/refspec、重置/删除/分支拓扑等均仍需审批（`prompt` 或 `no_match` 的有效审批），绝不因为候选动态检查合格而升级为 allow。注意 `execpolicy check --rules` 检查的是**指定规则文件的推演结果**，不是已加载运行时身份或真实授权的证明；必须分别记录当前真实 Codex 会话里候选调用是否放行/要求审批。候选执行 `host validate` 可能因拿候选包模板/路径与正式安装内容比较而显示 `drifted`，不得把这类预期路径比较直接当成正式机器安装损坏，更不得据此运行 `host install`。
