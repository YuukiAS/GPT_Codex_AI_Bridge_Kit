# Bridge Kit 0.7.3 — Unattended Host Diagnostics Hardening

Status: implementation contract for the next patch release. This document does not itself change the installed Host Policy.

## Why this is a 0.7.3 patch

Bridge Kit `0.7.2` fixes the reproduced Slurm false-positive by preauthorizing a narrow set of direct read-only scheduler inspections. New production evidence shows that unattended Codex work can still be terminated when automatic approval review rejects other low-risk host operations needed for diagnostics, notably:

- host-level current-user process inventory when sandbox-local `ps` cannot see the real host process namespace;
- broad Git synchronization such as `git fetch --all --prune` even when the real need is only to refresh already-configured remotes;
- likely adjacent session inventory such as `tmux` / `screen` status checks used to decide whether an old background task still exists.

This remains a Host Policy reliability/safety correction rather than a new workflow, role, state or schema. It therefore belongs in `0.7.3`.

## Product outcome

On a trusted Codex host with Bridge Kit Host Policy installed:

1. known benign operations that genuinely need host-level visibility should have deterministic bounded routes and should not be delegated to Auto-review;
2. ordinary commands that can stay inside the sandbox should continue to rely on the sandbox rather than being added to a giant allowlist;
3. process mutation, scheduler mutation, destructive Git, arbitrary host file reads, arbitrary shell/script execution and other broader capabilities must remain gated;
4. unattended work should use canonical narrow commands instead of broader equivalents that create unnecessary approval surface;
5. release claims require real execpolicy checks plus a smoke test on an affected remote Codex identity.

A unit-test PASS is insufficient if an overnight task still dies on one of the reproduced low-risk checks.

## Critical execpolicy fact: `allow` is a sandbox-bypass capability

Current Codex behavior makes the design boundary stricter than a simple “read-only command list”. When every parsed command segment is explicitly matched by an execpolicy `allow` rule, Codex can run that command outside the normal sandbox boundary.

Therefore Bridge Kit must **not** solve approval friction by globally allowing every superficially read-only Unix executable. Commands such as `ls`, `cat`, `grep`, `find`, broad `ps`, broad `git fetch`, `du`, `journalctl`, or generic network/system tools can expand host read or mutation scope when moved outside the sandbox.

The intended rule is:

> Keep ordinary safe commands sandboxed. Add Host Policy only where the task genuinely needs a host boundary crossing and the capability can be bounded.

This is also why broad `bash`, `sh`, `zsh`, `env`, `xargs`, Python and arbitrary script prefixes remain prohibited.

## Critical prefix-rule fact: a prefix is not an exact argv contract

`prefix_rule` authorizes matching command prefixes; trailing arguments may still be supplied. Do not describe a long prefix as an “exact command” unless the remaining grammar is itself harmless.

This affects both `ps` and Git:

- `ps -u <user> -o ...` is not safe merely because the first tokens select the current user; later selection/output flags can broaden what is exposed;
- `git fetch --all --prune` is not a clean exact boundary because trailing fetch options such as `--prune-tags` can materially change local-ref behavior.

When trailing argv must be rejected rather than merely discouraged, use a Bridge-owned CLI wrapper whose parser enforces the complete contract.

## Reality: what 0.7.2 already solves

`0.7.2` directly allows:

- `squeue`, `sinfo`, `sacct`, `sstat`, `sprio`;
- `scontrol show ...` and `scontrol ping`;
- existing narrow Git synchronization including `git fetch origin main`.

Deploying `0.7.2` to the affected Longleaf Codex identity remains mandatory. `0.7.3` addresses the additional production failures rather than replacing `0.7.2`.

## Process inspection: one small bounded wrapper is the right tradeoff

Do **not** blanket-allow raw `ps`.

GNU/procps `ps` has useful same-EUID selection semantics, but its option language is too flexible for a reusable prefix rule: selection options are additive, output fields can include `environ`, and a prefix rule does not prevent later arguments from broadening the command.

Implement one small Bridge-owned command:

```text
ai-bridge host processes
```

This is intentionally a thin host capability boundary, not a daemon, service, process manager or new workflow.

### Required wrapper contract

The command must:

- accept **no user-supplied username, UID, PID list, format string, ps option or shell fragment**;
- derive the current effective user internally;
- invoke a fixed process query outside the sandbox through the trusted `ai-bridge` executable;
- show only processes owned by the current effective UID;
- use a fixed conservative field set sufficient for “is an old background worker still alive?” diagnosis, at minimum PID, PPID, state, elapsed time, TTY and executable/command name;
- not include process environment variables;
- not invoke `sudo`;
- never signal, kill, renice, attach to, suspend or otherwise mutate processes;
- reject unexpected trailing arguments through the CLI parser;
- return deterministic plain text or JSON suitable for Codex reasoning.

Prefer the conservative executable/command-name view for 0.7.3. Do **not** make full command-line arguments part of the default output merely for convenience, because command lines can contain credentials. If later production evidence proves that executable name plus PID/PPID/elapsed information is insufficient, design a separately reviewed detail mode instead of silently widening 0.7.3.

The wrapper may be Unix/Linux-only with an explicit unsupported-platform result if that keeps the implementation materially simpler; do not build a cross-platform process abstraction unless current repository requirements already demand one.

### Execpolicy

Only the trusted wrapper invocation is directly allowed. Raw `ps`, cross-user inspection and process mutation remain outside direct allow.

## Session inventory: direct read-only subcommands are safe enough

The reproduced workflow explicitly considered `tmux` / `screen` as possible old-task owners. Session-listing subcommands have bounded read-only semantics and are a better fit for prefix rules than raw `ps`.

Subject to real execpolicy validation, 0.7.3 should preauthorize:

```text
tmux ls
tmux list-sessions
screen -ls
```

Do not authorize generic `tmux`, generic `screen`, `tmux kill-*`, `screen -X`, attach/detach mutation, or session creation merely because list operations are allowed.

If the affected environment does not have tmux/screen installed, validation may check policy semantics without treating command absence as a release failure.

## Git synchronization: canonicalize the safe route instead of broadening `git fetch`

The second reproduced failure used:

```text
git fetch --all --prune
```

For the actual source-of-truth check shown in the incident, that command was broader than necessary. When the task only needs `origin/main`, the canonical command remains:

```text
git fetch origin main
```

which is already preauthorized by Bridge Kit.

When an unattended task genuinely needs to update all configured remotes and prune stale remote-tracking refs, prefer the narrower Git grammar:

```text
git remote update --prune
```

Git documents `remote update` as updating configured remotes/groups; with no explicit group/remote it updates the default/all non-skipped remotes, and `--prune` applies pruning to those updated remotes. Its trailing arguments are remote/group names rather than arbitrary fetch refspecs.

Subject to real Git/execpolicy validation, 0.7.3 may directly allow:

```starlark
prefix_rule(
    pattern = ["git", "remote", "update", "--prune"],
    decision = "allow",
    justification = "Allows bounded synchronization and pruning of already-configured remotes without arbitrary repository URLs or fetch refspecs.",
)
```

Do **not** add a generic `pattern = ["git", "fetch"]` rule.

Do **not** directly preauthorize `git fetch --all --prune` in 0.7.3 unless implementation testing proves a safe way to prevent trailing options such as `--prune-tags` from widening local-ref mutation. The preferred production fix is to teach unattended Codex to use the canonical bounded route rather than preserving every broader command spelling.

## Unattended-operation behavior contract

Automatic approval denial can terminate the current Codex operation before repository-level workflow prose can recover. Therefore prevention is primary.

Update Host AGENTS guidance so unattended/overnight work follows this order:

1. first try an ordinary command inside the sandbox;
2. if host visibility is genuinely required, use an existing preauthorized narrow command or Bridge-owned bounded wrapper;
3. prefer canonical safe routes (`git fetch origin main`, `git remote update --prune`, `ai-bridge host processes`, read-only Slurm/session queries) rather than broader equivalents;
4. do not escalate to a broader command merely because it is more familiar;
5. if a task genuinely requires a mutating capability that is not globally authorized, leave it gated or use a separately reviewed repository-local bounded entry point.

Do not claim AGENTS prose alone can recover after Auto-review has already terminated a run.

## Two policy layers, not one giant global allowlist

To reduce overnight friction without making the global Host Policy dangerous, keep two conceptual layers:

### Global Bridge Kit Host Policy

Own only broadly reusable, high-confidence capabilities such as:

- read-only Slurm inspection;
- current-user bounded process inventory;
- read-only tmux/screen session inventory;
- canonical Git source synchronization.

### Repository-local policy / wrapper

If a specific unattended project is expected to perform mutations such as submitting a known Slurm launcher, starting a durable project worker, publishing an artifact, or invoking a particular deployment script, authorize the **project-specific bounded entry point**, not generic `sbatch`, `setsid`, shell, Python or arbitrary scripts globally.

This separation is how Bridge Kit should achieve low friction without turning every trusted host into danger-full-access.

## Auto-review remains enabled

Do not disable `approvals_reviewer = "auto_review"` as the solution. The target architecture remains:

- sandbox for ordinary execution;
- narrow Host Policy for known boundary-crossing low-risk capabilities;
- repository-local bounded authorization for explicitly intended project mutations;
- Auto-review/human approval for the remaining higher-risk or unclassified operations.

Turning Auto-review off would trade false denials for unattended approval stalls rather than solve overnight reliability.

## Required 0.7.3 acceptance matrix

### Must resolve to direct `allow`

All existing 0.7.2 positive cases, plus:

- trusted `ai-bridge host processes` with no extra arguments;
- `tmux ls`;
- `tmux list-sessions`;
- `screen -ls`;
- `git remote update --prune` if implemented as the canonical all-remotes sync route.

### Must remain effective `prompt` / outside direct allow

- raw `ps` forms, including the originally reproduced `ps -u <user> -o ...`;
- any attempt to pass extra process-selection/output arguments through `ai-bridge host processes` (the CLI itself must reject them);
- process environment inspection;
- cross-user process inspection;
- `kill`, `pkill`, `killall`, `renice`;
- generic `tmux` / `screen` mutation and session creation/kill commands;
- `sudo`;
- arbitrary `bash -lc`, `sh -c`, Python or script wrappers;
- generic `git fetch <url>` / arbitrary refspec fetch;
- `git fetch --all --prune --prune-tags`;
- destructive Git operations already gated by 0.7.2;
- all Slurm allocation/mutation cases already gated by 0.7.2.

## Regression requirements

Preserve all 0.7.2 Host Policy contracts:

- Slurm read-only direct allow and mutation gating;
- trusted `ai-bridge plugin-replay` executable pinning;
- existing `origin/main` Git synchronization;
- ordinary task-owned staging/commit/push behavior;
- dangerous Git operations remaining gated;
- managed-block preservation and host-install backup/idempotency;
- narrative-language and external-review waiting policy.

Do not redesign unrelated policy merely to increase allow-count.

## Production smoke-test requirement

Before declaring `0.7.3` complete, deploy the candidate Host Policy to an affected Longleaf Codex identity and verify through the normal production entry point that:

1. formatted `squeue` remains approval-free after 0.7.2/0.7.3 deployment;
2. `ai-bridge host processes` can inspect current-user host processes without Auto-review interruption;
3. session-listing routes work without approval when installed;
4. normal main synchronization uses `git fetch origin main` without approval;
5. all-remotes synchronization, if needed, uses the canonical bounded route without approval;
6. destructive negative cases are validated with `codex execpolicy check`, not actually executed.

Do not mutate or cancel live Slurm jobs merely to prove negative cases.

## Version and release boundary

If all acceptance criteria pass:

- bump `0.7.2 -> 0.7.3`;
- update version constants, README and CHANGELOG;
- extend `ai-bridge host validate` and real-Codex regression tests;
- keep this document as design rationale.

Do not call the release complete because a wrapper exists or synthetic tests pass. The user-visible success condition is that common unattended host observation/synchronization routes no longer die on avoidable Auto-review while nearby mutation and broad host-read surfaces remain gated.
