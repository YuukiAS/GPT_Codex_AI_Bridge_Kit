# Bridge Kit 0.7.2 — HPC Read-Only Host Policy

Status: implementation contract for the next patch release. This document does not itself change the installed Host Policy.

## Why this is a 0.7.2 patch

Bridge Kit `0.7.1` already owns the global Codex Host Policy and installs `$CODEX_HOME/rules/ai-bridge-global.rules`. The current rules deliberately preauthorize bounded plugin replay and selected Git operations, but they do not classify ordinary Slurm inspection commands. As a result, a harmless command such as a formatted `squeue` query can fall through to the default approval path and be rejected by automatic review.

This is a safety/usability correction to an existing Host Policy, not a new workflow, role, schema, runner, or major capability. It therefore belongs in `0.7.2`, consistent with the repository's current `0.x` versioning convention: patch releases are primarily safety, compatibility, and default-behavior corrections.

## Product outcome

On a trusted Codex host with Bridge Kit Host Policy installed:

- common Slurm/HPC inspection should proceed without repeated approval;
- resource allocation, job-state mutation, scheduler mutation, and ambiguous shell composition must still require approval;
- the policy must be enforced through actual Codex execpolicy behavior, not only through prose in `AGENTS.md`;
- `ai-bridge host validate` must exercise representative positive and negative cases with the real installed Codex CLI when available.

A mechanical test PASS is insufficient if a normal direct `squeue` command still enters automatic approval review.

## Source-of-truth reality on 0.7.1

The current Host Policy is generated from:

- `templates/host/rules/ai-bridge-global.rules`
- `templates/host/GLOBAL_AGENTS_SNIPPET.md`
- `ai_bridge_kit/host.py`
- `tests/test_host_policy.py`

`ai_bridge_kit/host.py` treats an unmatched execpolicy command as an effective `prompt` under the configured `approval_policy = "on-request"`. Therefore, adding only narrative guidance will not fix this failure mode.

## Policy model: command-shape allowlisting, not blanket trust

Codex `prefix_rule` should be used to classify exact command prefixes. An alternative list at one token position can represent a bounded family such as:

```starlark
prefix_rule(
    pattern = ["scontrol", ["show", "ping"]],
    decision = "allow",
    justification = "Allows read-only Slurm controller and object inspection.",
)
```

This is the intended meaning of "conditional allow" in this patch: allow only specific command shapes whose semantics are read-only.

Do **not** interpret `prefix_rule` as a general runtime predicate engine. It does not establish dynamic facts such as:

- whether a job ID belongs to the current user;
- whether a Git working tree is clean;
- whether a path is task-owned;
- whether an arbitrary shell pipeline is semantically read-only.

When safety depends on those dynamic facts, use a bounded wrapper that checks them or leave the operation on the approval path. Do not simulate dynamic checks with a broad executable-level allow rule plus prose.

## Proposed direct allowlist

The initial 0.7.2 rule set should be intentionally small and high-confidence.

### Allow directly

These commands are inspection/reporting tools and should be allowed as executable-level prefixes:

```starlark
prefix_rule(
    pattern = [["squeue", "sinfo", "sacct", "sstat", "sprio"]],
    decision = "allow",
    justification = "Allows standard read-only Slurm queue, partition, accounting, step-statistics, and priority inspection.",
)
```

If the current Codex execpolicy syntax or validator does not accept an alternative list in the first token position, emit separate `prefix_rule` entries instead. Do not replace this with `pattern = ["s"]`, shell wrappers, or another broader approximation.

### Allow only bounded `scontrol` inspection

```starlark
prefix_rule(
    pattern = ["scontrol", ["show", "ping"]],
    decision = "allow",
    justification = "Allows read-only Slurm object inspection and controller reachability checks while leaving mutating scontrol subcommands gated.",
)
```

Do not allow bare `scontrol` as a whole. `scontrol` includes mutating operations such as `update`, `hold`, `release`, `requeue`, `suspend`, `resume`, create/delete operations, power operations, reconfigure, shutdown, and takeover.

### Leave gated

The following must remain effective `prompt` unless a future, separately reviewed bounded wrapper is introduced:

- `sbatch`
- `srun`
- `salloc`
- `scancel`
- bare/general `scontrol`
- `scontrol update`
- `scontrol hold`
- `scontrol release`
- `scontrol requeue` / `requeuehold`
- `scontrol suspend` / `resume`
- `scontrol create` / `delete`
- scheduler/controller reconfiguration, shutdown, takeover, or power mutations
- `sacctmgr add` / `modify` / `delete`

No new rule should preauthorize `bash`, `sh`, `zsh`, `env`, `xargs`, or generic script execution merely to make Slurm commands easier to run.

## Optional read-only commands: evidence before expansion

Do not automatically expand 0.7.2 into a large HPC allowlist. Commands such as `sdiag`, `sshare`, `sreport`, or `sacctmgr show/list` may be read-only in normal Slurm semantics, but they are outside the reproduced failure and are less frequently needed in the current workflow. Add them only if implementation review confirms both read-only semantics and a real workflow need.

Likewise, do not use this incident as justification for a generic Unix diagnostic allowlist (`ps`, `df`, `du`, `free`, etc.) unless real approval friction is reproduced. The objective is to remove demonstrated false positives without turning Host Policy into a broad shell trust policy.

## Shell-composition boundary

The direct allow rules are for direct executable invocations. A command such as:

```text
bash -lc 'squeue ... | xargs scancel'
```

must not inherit trust merely because it contains `squeue`. The executable prefix is a shell, and it must remain outside the Slurm inspection allowlist.

Similarly, a read-only command whose output is used to construct a later mutating command does not authorize that later command.

## Required execpolicy acceptance matrix

Extend both `validate_host_policy()` and the real-Codex tests so at least the following are proven against the generated rules.

### Must resolve to direct `allow`

- `squeue -j 156911 -o "%.18i %.9P %.30j %.8u %.2t %.12M %.12l %.20R %.30b"`
- `squeue -u testuser -h`
- `sinfo -h`
- `sacct -j 156911`
- `sstat -j 156911.batch`
- `sprio -j 156911`
- `scontrol show job 156911`
- `scontrol show partition`
- `scontrol ping`

### Must remain effective `prompt`

- `sbatch job.sh`
- `srun --pty bash`
- `salloc -t 00:10:00`
- `scancel 156911`
- `scontrol update JobId=156911 TimeLimit=30`
- `scontrol hold 156911`
- `scontrol release 156911`
- `scontrol requeue 156911`
- `scontrol suspend 156911`
- `scontrol resume 156911`
- `sacctmgr modify user name=test set Fairshare=2`
- `bash -lc "squeue -h | xargs scancel"`

For unmatched mutating commands, it is acceptable for the direct execpolicy result to be `no_match` so long as Bridge Kit's effective Host Policy semantics under `on-request` are verified as `prompt`. Do not add gratuitous explicit prompt rules if the default path already provides the desired behavior, unless a concrete precedence or regression reason requires them.

## Regression checks on existing Host Policy

0.7.2 must preserve the existing contract for:

- trusted `ai-bridge plugin-replay`;
- `git fetch origin main`;
- clean fast-forward `git pull --ff-only origin main` policy;
- ordinary task-owned staging/commit/push behavior;
- dangerous Git operations remaining gated;
- narrative language and external-review waiting policy;
- backup/idempotent Host Policy installation.

Do not weaken these unrelated contracts to make the new Slurm tests pass.

During implementation, red-team any **new** broad prefix rule against nearby mutating forms. Existing broader Git rules are not automatically in scope for redesign in this patch unless a concrete test demonstrates that the 0.7.2 change alters their behavior or creates a conflict. Record unrelated concerns separately rather than silently expanding the patch.

## Documentation and version updates after implementation

If the acceptance matrix passes in the normal Host Policy entry point:

- bump package/version constants from `0.7.1` to `0.7.2`;
- add a `0.7.2` changelog entry describing HPC read-only Host Policy classification and negative guards;
- update README Host Policy documentation with the boundary between read-only Slurm inspection and state/resource mutation;
- keep this document as the design rationale.

Do not claim `0.7.2` complete merely because the Starlark file parses. The generated installed rules and `ai-bridge host validate` must prove the intended decisions using the real Codex execpolicy when available.

## Release acceptance

`0.7.2` is ready only when all of the following are true:

1. A normal formatted `squeue` invocation no longer triggers approval under the installed Bridge Kit Host Policy.
2. `scontrol show ...` and `scontrol ping` are allowed, while mutating `scontrol` forms remain gated.
3. `sbatch`, `srun`, `salloc`, and `scancel` remain gated.
4. Shell-wrapped or composed mutating commands do not gain trust from the Slurm inspection allowlist.
5. Existing Host Policy tests and repository tests pass.
6. `ai-bridge host install` remains idempotent and preserves user-owned config outside Bridge Kit managed surfaces.
7. The version, changelog, and README match the production behavior actually verified.
