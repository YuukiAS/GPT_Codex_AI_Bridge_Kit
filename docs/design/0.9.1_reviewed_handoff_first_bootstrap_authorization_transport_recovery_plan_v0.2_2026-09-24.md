This v0.2 replaces the over-broad cross-repository authorization framing in recovery Plan v0.1 with the actual long-term product model:

> **each repository's Codex owns that repository; Bridge provides a bounded repo-local primitive.**

This is still a recovery amendment, not a redesign of Reviewed Handoff lifecycle. Remote-only resume, shared task initializer, task state graph, workflow-core owner split, candidate-pair semantics, and Bridge 0.9.1 version target remain unchanged.

No production code, Machine Policy, branch/worktree, workflow-core source, paid API, automation, or rollout is changed in this design round.

---

## 1. Product correction: stop designing for Bridge-Codex -> other-repo mutation

The real architecture-build round accidentally tested this shape:

```text
Bridge repo Codex
    -> tries to create AI_Skills sibling worktree
    -> command crosses workspace/repo boundary
    -> prompt
    -> Auto-review rejects
```

That is **not** the normal long-term use model.

The normal product model is:

```text
AI_Skills Codex
    -> cwd is AI_Skills canonical repo
    -> calls installed Bridge Reviewed helper
    -> helper creates AI_Skills' own canonical sibling worktree

Bridge Codex
    -> cwd is Bridge repo
    -> manages Bridge repo only
```

Bridge remains reusable across repositories, but it is not a central cross-repo orchestrator.

### Consequence

0.9.1 first bootstrap only needs to solve:

> **repo-local Codex -> same repo's canonical Reviewed sibling worktree**

It does **not** need to guarantee:

> repo A Codex -> repo B worktree.

Cross-repo mutation is outside the 0.9.1 low-friction product claim.

---

## 2. Actual failure attribution

### A. Execpolicy `prompt`

The installed rule worked as configured.

`prompt` means “route this command to an approval decision”; it does not mean “the prior Kickoff has already granted this action”.

### B. Auto-review

The observed blocker is the Auto-review/approval layer.

Current Codex source treats `auto_review` as an independent risk reviewer. It is not a deterministic mechanism for consuming an earlier Kickoff as a stored authorization.

Therefore:

```text
explicit Kickoff + prompt + auto_review
```

is **not** a reliable low-friction transport.

The real FB-G1 rejection proves this assumption must be removed.

### C. Sandbox

The failed run did not get far enough to prove sibling write.

Current official workspace-write semantics permit cwd plus writable roots. A sibling worktree is not automatically inside cwd.

Current Codex source also shows that an explicit execpolicy `allow` can skip approval and bypass the sandbox for a direct allowed command.

Therefore the correct real gate is:

```text
repo-local safe helper -> allow
-> no approval
-> real sibling write
```

not another prompt experiment.

### D. Bridge helper scope

The current 44965d candidate still accepts caller-selected target/worktree/base assertions. That was designed around an exact approval prompt.

For permanent low-friction `allow`, the helper should become simpler and self-scoping.

---

## 3. Design principle

For normal Bridge operations:

> if an operation is a routine repo-local action and Bridge can mechanically make every accepted invocation safe enough, Machine Policy should allow the Bridge helper directly instead of asking Auto-review to rediscover the user's intent.

This already matches the successful Bridge pattern:

- artifact-bound `materialize-worktree` -> allow;
- bounded current-branch publisher -> allow;
- raw generic Git mutation -> prompt.

0.9.1 first bootstrap should follow the same pattern.

This amendment does **not** propose globally auto-approving arbitrary Git/worktree creation.

---

## 4. Alternatives

### A. Keep `prompt + auto_review`, rewrite justification

**REJECT.**

Real FB-G1 already disproved reliability. Wording is not a mechanical authorization channel.

### B. Install a temporary exact per-task execpolicy rule, then remove it

**REJECT for 0.9.1.**

It creates a new per-task policy lifecycle:

```text
provision exact rule
-> reload/evaluate rule
-> execute
-> restore/delete rule
-> recover if interrupted
```

The rule provisioning itself needs a trusted path and current execpolicy is prefix-based. This is more machinery than the product problem warrants.

### C. One-shot authorization file/token

**REJECT.**

A file written by Codex is not proof of user authorization. Making it trustworthy introduces signatures/tokens/trusted writers or receipt infrastructure, which is explicitly out of scope.

### D. Permanently allow the existing 44965d bootstrap shape

**REJECT.**

The current command can select another target/path/base. That is broader than needed.

### E. Project-local writable roots / additional permissions

**REJECT as the primary fix.**

Writable roots solve filesystem scope, not the current explicit `prompt` rule. Dynamic per-task writable-root configuration also adds a config lifecycle/reload problem and has had client-specific inconsistencies upstream.

### SELECTED — F. repo-local self-scoped bootstrap helper + standing allow

Make `task bootstrap` intrinsically repo-local:

```text
current cwd repo
-> task-derived branch
-> deterministic sibling path
-> current origin/main OID
-> local-only worktree/control-state creation
```

Then Machine Policy can safely allow that bounded helper.

No task-specific rule lifecycle, auth store or cross-repo orchestration is needed.

## 5. Repo-local command contract

### 5.1 The command operates on cwd, not an arbitrary target

Normal trusted entry:

```text
cd <canonical repo>

ai-bridge reviewed-handoff task bootstrap \
  --task-key <semantic-task-key> \
  --expected-repo <owner/repo> \
  --expected-base-commit <40-char oid> \
  [existing task-init metadata]
```

For the trusted route:

- the target repository is always the Git top-level containing the process cwd;
- no caller-selected cross-repo target is accepted;
- remove `--target` from the first-bootstrap normal entry, or retain it only as a compatibility assertion that must equal the current cwd Git top-level before any mutation.

The preferred implementation is to remove it from the trusted bootstrap parser while 0.9.1 is unreleased.

### 5.2 Repo identity is an assertion, not a selector

`--expected-repo` must equal the actual current repo origin identity.

It cannot redirect execution to another repository.

### 5.3 Branch is fully derived

Always:

```text
reviewed/<task_key>
```

No `--branch`.

### 5.4 Worktree is fully derived

Always:

```text
<current-repo-parent>/<current-repo-directory-name>-<task_key>
```

Example from AI_Skills cwd:

```text
current repo:
/home/yuukias/AI_Skills_Collection

task:
workflow-core--reviewed-first-bootstrap-normal-entry

derived worktree:
/home/yuukias/AI_Skills_Collection-workflow-core--reviewed-first-bootstrap-normal-entry
```

There is no caller-selected `--expected-worktree` in the preferred normal entry.

If compatibility keeps that option temporarily, it is equality-only against the derived sibling and cannot change the effect.

### 5.5 Base is repo-local and current

Trusted first bootstrap supports only:

```text
base ref = origin/main
```

The normal workflow first performs the already-low-risk repo-local:

```text
git fetch origin main
```

Then bootstrap requires:

```text
--expected-base-commit
==
current local refs/remotes/origin/main OID
```

The helper itself does not fetch, push, change remote, set upstream or contact GitHub.

A stale/wrong base OID fails before topology mutation.

This keeps the Kickoff's exact-base contract without letting the caller choose an arbitrary commit.

## 6. Machine Policy

Change only:

```text
ai-bridge reviewed-handoff task bootstrap
prompt -> allow
```

after the repo-local self-scoping checks above are implemented and tested.

Keep:

```text
materialize-worktree -> allow
raw git worktree add -> prompt
```

### Why permanent allow is acceptable here

The allowed class is no longer:

> create a Reviewed task in any caller-selected repo/path/base.

It is:

> in the repo the current Codex is already working in, create one deterministic local Reviewed sibling worktree for a semantic task, from the current fetched origin/main OID.

The helper cannot use this permission to operate another repo.

This is the key simplification relative to recovery Plan v0.1.

## 7. Sandbox and checkout-executable safety

An execpolicy `allow` may bypass the outer workspace sandbox, which is necessary for the sibling worktree.

That means the helper must prevent Git checkout from becoming an arbitrary executable escape.

Before mutation, fail closed if the current repo has checkout-time executable behavior that the trusted helper would run outside the sandbox.

Minimum fence:

- effective executable `post-checkout` hook, including `core.hooksPath`;
- configured external `filter.*.smudge`;
- configured external `filter.*.process`.

The simplest implementation is conservative:

```text
any active checkout hook/smudge/process executable
-> BOOTSTRAP_CHECKOUT_EXECUTABLE_REQUIRES_ORDINARY_APPROVAL
-> no mutation
```

Do not silently disable legitimate repo hooks/filters.

This is the only material extra safety fence required by using `allow`.

No generic shell allow, writable-parent allow or danger-full-access is introduced.

---

## 8. CLI / prefix-rule safety without overengineering

Current execpolicy is prefix based.

The helper is safe by validating the **final parsed values**, so it does not need a task-specific exact-rule generator.

Required parser behavior:

- use `allow_abbrev=False`;
- unknown arguments fail normally;
- no branch/path/base-ref selector exists in the preferred normal entry;
- final `task_key`, `expected_repo` and `expected_base_commit` are mechanically validated against the repo-local derived effect.

A special duplicate-option framework is **not required** if every final safety-critical parsed value is still restricted to the same safe class.

If implementation keeps compatibility-only selector options, duplicates must not be able to escape the derived repo/path/base invariant.

## 9. Authorization semantics

This amendment stops pretending that local code can prove which chat message authorized a command.

The honest model is:

```text
current-user Kickoff
= workflow authority telling Codex which Reviewed task to perform

Machine Policy allow
= standing permission for the safe repo-local bootstrap capability

Bridge helper
= mechanical enforcement of repo-local scope

raw Git
= still prompt
```

The user still sends the exact task/repo/base in the Kickoff.

But machine safety does not depend on Auto-review reading that Kickoff.

This is intentionally the same separation used for other safe Bridge helpers.

## 13. Why this is neither too complex nor too simple

### Not too complex

No:

- temporary per-task rules;
- rule installation/restoration lifecycle;
- auth receipts/tokens;
- authorization files;
- writable-root mutation per task;
- cross-repo orchestration;
- daemon/controller/watcher;
- extra workflow/state machine.

The new permanent permission is one existing Bridge command.

### Not too simple

The design does not merely change `prompt -> allow`.

It first removes the unsafe degrees of freedom:

- other repo;
- arbitrary path;
- arbitrary branch;
- arbitrary base/ref;
- checkout executable escape;
- hidden network/remote mutation.

Only then is the helper allowlisted.
