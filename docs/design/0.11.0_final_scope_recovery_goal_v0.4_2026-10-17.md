## 2. 正面完成标准：普通用户从零到可用

最终 0.11.0 必须让普通用户完成以下旅程，而不理解 Bridge 内部 object store、journal、execpolicy 或状态 JSON：

1. **新机器**：安装 Bridge，`host status/install/validate` 明确当前 executable/import/source/CODEX_HOME/Host Policy；未做远端读取时 remote release freshness 明示 `UNKNOWN/UNVERIFIED`。
2. **新项目**：`ai-bridge init` + 一次 `ai-bridge validate --strict` 完成 setup/诊断；日常任务不要求每次先手敲 strict validator。
3. **Lite 日常任务**：`ai-bridge task run --target <repo> --task-key <task_key>` 自动 preflight mandatory sources/instruction budget/Host/worktree，然后才启动真实 Codex；失败直接给用户可读原因和最小恢复。
4. **Reviewed/Control**：继续使用既有正式入口；只在真实产品风险需要时选择，不因为运行时间长而升级工作流。
5. **branch/worktree recovery**：现有 non-main strict FF保持；受支持 reciprocal linked-worktree conflict由正常 Reviewed recovery自动识别 A/B/T，用户只收到一条准确自然语言授权请求，不手工拼 `exchange-worktrees` 参数。
6. **Persistent Run**：Task Writer先判断 live/scheduler/service/terminal-owned 四种 lifetime；只有 terminal-owned survive-disconnect 使用 `persistent-run start`。一次用户 kickoff 后，Bridge幂等 start/resume真实 run、同生命周期 reporter和dedicated Progress thread。
7. **Notifications**：一台机器只需一次 `ai-bridge notifier configure` 配置 Gmail；多个项目复用 machine profile；项目有不同 sender/recipient才用 override；rclone只是多机恢复/同步。
8. **状态诊断**：Host、task readiness、Persistent Run、Notifier、Reviewed均有正常 status/validate入口；用户不读内部 JSON。
9. **正式身份**：产品版本始终 0.11.0；冻结候选按 `0.11.0-rc.N @ SHA`；正式 `release` 只有用户另批 exact old SHA -> exact candidate SHA 后才推进并远端读回。

## 3. Lite / readiness / partial clone

### 3.1 Lite normal entry

README 必须正式说明：

`ai-bridge task run --target <repo> --task-key <task_key>`

它不是新 workflow，只是已有 Lite task 的受检启动器。它必须：

- 在 child 启动前重新读取当前 frozen task和 mandatory source；
- 核 Host/CODEX_HOME/Bridge identity、worktree/branch、instruction byte budget；
- 对 partial clone 缺 blob 自动使用现有 isolated mandatory-source reader；
- preflight失败时 child process=0，并说明 exact失败项、没有启动 Codex、最小恢复和“修复后重试同一 task”。

用户不得被要求手工设置 `GIT_OBJECT_DIRECTORY`、alternate objects、blob OID。

### 3.2 `validate --strict`

定位为：
- 新项目 setup；
- Bridge/项目升级后检查；
- readiness问题诊断。

日常 `task run` / Reviewed launch 必须自己消费同一 preflight；单独 validator PASS不能代 normal-entry Gate。

## 4. G02 reciprocal worktree recovery

`exchange-worktrees` 保持 narrow recovery helper，不成为普通用户每日命令。

当 Reviewed materialize/bootstrap发现：
- desired path A被 branch B占用；
- branch A又恰在 linked worktree B；
- 两树同 common-dir、非main、同filesystem、无submodule/symlink/lock/活跃进程等禁止项；

Bridge/Codex自动：
- 从 registry + frozen task确定 A/B/expected branches；
- 选同 filesystem空闲 sibling T；
- 生成 exact三步 move和最终归属；
- 向用户只问一次是否授权这一次位置交换；
- 获准后调用现有 helper。

失败/不支持必须保留原数据并说明；禁止 reset/stash/clean或要求用户自己拼复杂参数。

## 5. Persistent Run 完整产品合同

### 5.1 execution lifetime

Task Writer冻结任务时必须明确：
- ordinary live；
- scheduler-owned；
- existing service/job-owned；
- terminal-owned survive-disconnect。

只有最后一类进入 Bridge tmux Persistent Run；scheduler/service继续由原 owner管理，不因为多小时运行就再套 tmux。

### 5.2 normal entry

用户发送由：

`ai-bridge persistent-run prompt kickoff --target <repo> --goal <goal>`

生成并绑定 frozen Goal/hash/run key/资源边界的 kickoff 后，Codex使用：

`ai-bridge persistent-run start --target <repo> --goal <goal> --expected-goal-sha256 <hash>`

`start` 是受限、幂等 start-or-resume helper：

- 只解析 frozen Persistent Run contract；
- 使用 frozen `Launch argv JSON` / `Resume argv JSON`，不接受任意 shell字符串作为通用 orchestrator；
- 无 active run时由 run-scoped supervisor启动 primary child + reporter child；
- 有同 hash/run key compatible run时返回 `RESUMED_EXISTING_RUN`，不重复 primary；
- reporter损坏但 primary仍活着时只恢复 reporter；
- primary terminal后写最后 runtime snapshot、清理 reporter、supervisor退出；
- 不申请scheduler资源、不更改data/model/budget/scope；
- 不成为daemon/controller。

### 5.3 progress truth / cadence / Progress thread

项目原生 launcher/task/scheduler/service 是 progress truth owner，Bridge只规范化：

- completed/total有直接证据才有fraction；
- ETA必须有真实basis；
- heartbeat/checkpoint可用于last real progress/stall；
- 没有量化证据仍可合法长期运行，但fraction/ETA为`UNKNOWN`；
- 没有可靠heartbeat不从沉默时间猜stalled；
- tmux/PID只证明运行层存在，不证明领域进度。

cadence继续保持：

- start/resume immediate；
- meaningful stage immediate；
- stalled/blocked/failed immediate；
- runtime completion immediate；
- material ETA immediate；
- active约60分钟；
- 无任务理由不得低于15分钟；
- known↔UNKNOWN永远material；
- `abs(expected_finish_delta) >= max(15 minutes, 25% of prior remaining time)`；
- observation与last logical delivery分离；
- 普通fraction/count变化不刷屏；
- 高频observation不饿死cadence。

每个run自动create-or-reuse dedicated Progress thread：

- non-ephemeral；
- exact `progress_thread_id` 是identity；
- human name只用于发现；
- 无业务执行权限；
- 不做Planner/Reviewer/Executor；
- 不写原 Executor/task thread；
- 不拥有semantic completion authority；
- Bridge先算canonical snapshot，render只呈现既定值。

### 5.4 Progress thread isolation 与0.160.1 persistence顺序

复用官方 temporary structured helper 的deny-config模式，但明确`ephemeral=false`。

任何render前机械关闭/验证：
- shell/unified exec/code mode；
- web/search；
- apps/plugins；
- MCP全部effective servers；
- environment/runtime workspace；
- dynamic tools/capability roots；
- multi-agent；
- image generation/hooks/skills；
- permission escalation；
- actual runtime中其他execution/external connector。

无法证明：
`PROGRESS_THREAD_ISOLATION=UNVERIFIED_BLOCKER`，0 render turn，不回退原 Executor thread。

开发canary和final G14-C固定顺序：

1. `thread/start` 创建 non-ephemeral thread。
2. 首turn前机械核隔离。
3. 隔离PASS后第一个 bounded render。
4. 首turn完成后验证rollout/history materialized。
5. disconnect。
6. exact thread id cold resume。
7. 验历史一致且无第二thread。
8. 开发canary如需第二个且最后一个render。
9. 验原 Executor/task thread完全没变化。
10. canary结束无新消息。

**不得要求首turn前就cold resume**。

### 5.5 bounded render

- 每个logical delivery最多一个render turn；
- frozen contract预先写 `Progress render max turns`；
- snapshot digest/turn/token/time有记录；
- model不重新估stage/status/fraction/ETA；
- 输出改值 = fidelity FAIL；
- 前一turn未完成时coalesce最新pending snapshot，不并发；
- foreign/business input => `PROGRESS_THREAD_CONTAMINATED` 并停止自动投递；
- 超turn上限停止并交用户决定，不无限消耗。

### 5.6 status

`ai-bridge persistent-run status --target <repo> --goal <goal>`

直接显示run/lifecycle owner、Goal hash、stage/status、count/fraction或UNKNOWN、ETA/basis/uncertainty或UNKNOWN、last real progress、reporter heartbeat、Progress thread name/id、latest logical delivery、runtime terminal/exit、thread isolation；不显示secret。

`report/latest` 保留兼容/诊断，不再是用户看到主动progress的必要入口。

## 6. Notifications / Gmail 产品合同

### 6.1 provider

0.11正式provider = **Gmail SMTP only**：

`smtp.gmail.com:587 + STARTTLS + authentication`。

使用 Google App Password，不使用普通Google账号密码；App Password需要账号已启用两步验证且账号策略允许。0.11不新增generic SMTP、Google OAuth或Workspace relay。

### 6.2 machine configure

新增：

`ai-bridge notifier configure`

交互输入 Gmail账号、App Password（不回显）、from、default recipient、optional prefix。默认写：

`${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/private/notifier.env`

重跑修改；`--clear` 删除对应scope credential。

Machine secret必须：
- POSIX dir 0700/file0600/owner current user；
- symlink/reparse/path escape拒绝；
- safe temp + validate + permission/ACL + atomic replace；
- Windows current-user ACL无法机械确认则 `PRIVATE_ACL_UNVERIFIED`；
- stdout/stderr从不显示secret。

### 6.3 config layering

固定：

`machine < project < process env`

- machine：一台机器一次配置，多项目复用；
- project：现有 `.ai-bridge/private/notifier.env` 作为可选兼容override；
- process env：高级临时override。

`ai-bridge private sync --profile notifier` 只作为多机恢复/已有私密源pull，不再是首次配置前提。

### 6.4 notifier status

`ai-bridge notifier status --target <repo>` 至少显示：

- `provider=GMAIL_SMTP`；
- configured/not configured；
- ready/invalid；
- active config source(s)；
- sender/recipient/prefix；
- private storage safety；
- last send-test；
- last send；
- last failure；
- last automatic suppression reason；
- 永不显示secret。

Ready只表示字段+私密存储边界满足；真实credential/到达结果单独看send-test/send。

### 6.5 project defaults + task freeze

新增非secret项目默认：

`automation/notifier/DEFAULTS.json`

字段：
- `progress_email: ENABLED|DISABLED`
- `semantic_completion_email: ENABLED|DISABLED`

入口：

`ai-bridge notifier defaults --target <repo> --progress-email ... --semantic-completion-email ...`

不存在默认 = 双DISABLED。

Task Writer / Reviewed Planner / Control Planner在**freeze任务时**读取project default +当前task override，写成最终frozen intent。之后default变化不改变旧任务。

最终task枚举：

`Progress email: ENABLED | DISABLED`  
`Semantic completion email: ENABLED | DISABLED | UNSUPPORTED`

Lite没有canonical semantic-owner PASS artifact，因此 automatic semantic completion固定`UNSUPPORTED`；不能假装ENABLED。需要自动完成邮件则用Reviewed/Control；当前用户explicit one-shot仍可用。

### 6.6 manual vs automatic / semantic authority

当前用户亲自在交互终端执行：

`ai-bridge notifier send <brief>`  
`ai-bridge notifier send-test`

本身授权这一封one-shot，不要求历史task intent。

Persistent Run、`notifier once/run`、Reviewed/Control automatic send必须读frozen intent；automation不得调用manual路径绕过。

automatic semantic completion不能只信brief的`decision_authority`字符串。

Reviewed必须验证current task、PASS human gate、matching implementation/REVIEW/FINAL_REPORT和完整validator。

Control必须验证current task/request_nonce/review_target + current `FINAL_CRITIC_AUDIT.json=CRITIC_FINAL_PASS`及其snapshot/bundle/contract/ledger/planner-pass bindings。

Lite无artifact => automatic no-send。

Notifier只验证existing decision locator并render/dedupe/send，不重新做领域判断。

### 6.7 progress mail

Progress email启用时正文直接包含stage/status/completed/total/fraction/ETA/basis/uncertainty/last real progress/progress delta；无可靠ETA写“预计完成时间未知”。
