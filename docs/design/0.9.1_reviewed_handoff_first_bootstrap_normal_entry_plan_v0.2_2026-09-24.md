## 5. Selected architecture after B1 repair

The v0.1 idea of reusing the permanently allowed `materialize-worktree --mode bootstrap` for a missing task is withdrawn.

### 5.1 Existing artifact-bound command remains unchanged in trust class

Keep:

```text
ai-bridge reviewed-handoff materialize-worktree
```

It remains permanently allowlisted because it must derive/freeze its effect from **existing task artifacts** before branch/worktree mutation.

It continues to own:

- existing artifact-bound bootstrap compatibility;
- resume/rematerialization;
- exact path/base/repo assertions against frozen state;
- idempotent existing worktree behavior.

### 5.2 New first-bootstrap execution entry

Add one **nested subcommand inside the existing Reviewed Handoff product**:

```text
ai-bridge reviewed-handoff task bootstrap
```

This is not a new workflow, product mode or generic Git facade.

It is the missing first-task transaction:

```text
current-user authorized exact assertions
-> exact branch/worktree creation
-> shared task initialization
```

It exists separately only because its authorization source is different from artifact-bound materialization.

### 5.3 Machine Policy boundary

The current permanent allow for:

```text
ai-bridge reviewed-handoff materialize-worktree
```

does **not** match:

```text
ai-bridge reviewed-handoff task bootstrap
```

For defense-in-depth, 0.9.1 should add an explicit Machine Policy rule:

```text
prefix_rule(
    pattern = ["ai-bridge", "reviewed-handoff", "task", "bootstrap"],
    decision = "prompt",
    ...
)
```

not `allow`.

Current execpolicy strictest-match semantics mean this prompt boundary remains effective even if some broader allow is added later.

Therefore an arbitrary Codex process cannot obtain permanent authority to create a new Reviewed branch/worktree merely by choosing CLI assertions.

The authorization chain is:

```text
user sends Critic-approved Kickoff naming exact repo/task/worktree/base
        ↓
Codex invokes task bootstrap for that exact effect
        ↓
Machine Policy routes the command through approval/current-user authorization
        ↓
Bridge validates the exact effect
        ↓
one bounded bootstrap transaction
```

If the platform's normal approval path cannot consume the explicit Kickoff without another user-visible confirmation, **FB-G1 fails**. Implementation must return Planner/Critic; it must not solve that failure by changing `task bootstrap` to a permanent allow or by falling back to raw Git.

This keeps:

```text
current-user Kickoff = authorization
Machine Policy = bounded execution permission
```

rather than turning CLI assertions into authorization.

## 7. Exact first-bootstrap lifecycle

For the exact state:

```text
canonical task metadata absent
local reviewed branch absent
remote reviewed branch absent
exact worktree free
current-user Kickoff authorizes exact repo/task/worktree/base
```

### Step 1 — local/remote preflight, no topology mutation

From the canonical source checkout:

1. verify repository identity == `--expected-repo`;
2. validate semantic task key;
3. derive `reviewed/<task_key>`;
4. require both canonical local REQUEST and CURRENT are absent;
5. if only one exists, fail `LOCAL_TASK_METADATA_PARTIAL`;
6. lexicalize exact absolute worktree path and reject symlink/path redirection;
7. reject unrelated/occupied/registered path;
8. require local reviewed branch absent;
9. fetch/check the exact frozen base ref;
10. require `expected-base-commit` exists and is in the required lineage;
11. require exact remote `origin/reviewed/<task_key>` absent for first bootstrap;
12. final recheck of repo/base/path/branch facts.

No task control file is created in canonical main.

### Step 2 — create exact branch/worktree

Create exactly:

```text
branch = reviewed/<task_key>
start = expected-base-commit
worktree = expected-worktree
```

No `-B`, branch guessing, remote guessing or force.

### Step 3 — initialize control files only in the new reviewed worktree

Invoke the shared task initializer in the new worktree with:

- exact task key;
- original frozen base branch;
- original frozen base commit;
- exact absolute Reviewed worktree locator;
- task-init metadata.

Create:

```text
automation/reviewed_handoff/tasks/<task_key>/REQUEST.md
automation/reviewed_handoff/tasks/<task_key>/CURRENT.json
results/<task_key>/
```

The first tracked REQUEST/CURRENT never pass through canonical main.

### Step 4 — bounded handoff result

Successful first bootstrap proves only:

- exact branch exists;
- exact worktree exists;
- exact task metadata exists there;
- canonical main was not polluted.

It does not claim `PLAN_FROZEN`, implementation completion or review completion.

## 9. Canonical metadata discovery for resume — B2 closure

Introduce one shared task-scope loader for materialization/resume.

Conceptual result:

```text
TaskScopeSource =
    LOCAL_TRACKED
  | REMOTE_REVIEWED_BRANCH
```

This is an internal return type/branch in code, not a new persisted state/schema.

### 9.1 Local-complete path

Inspect canonical local:

```text
automation/reviewed_handoff/tasks/<task_key>/REQUEST.md
automation/reviewed_handoff/tasks/<task_key>/CURRENT.json
```

If **both exist**:

- parse/validate task key;
- parse/freeze base branch/commit;
- parse exact worktree locator;
- compare caller assertions;
- for resume, fetch exact reviewed remote branch and require its frozen identity/lineage is compatible with local scope before mutation.

If exactly one exists:

```text
LOCAL_TASK_METADATA_PARTIAL
```

Fail closed. Do not silently fall back to remote.

This protects legacy/current tasks whose canonical checkout already has task artifacts.

### 9.2 Remote-only discovery path

If **both local REQUEST and CURRENT are absent** and mode is resume:

1. derive only `reviewed/<task_key>`;
2. fetch exact:
   `origin/reviewed/<task_key>`
   into its remote-tracking ref;
3. do **not** check it out yet;
4. read the exact files from the remote commit tree, e.g. Git object/tree access equivalent to:
   - `git show <remote-ref>:automation/reviewed_handoff/tasks/<task_key>/CURRENT.json`;
   - `git show <remote-ref>:automation/reviewed_handoff/tasks/<task_key>/REQUEST.md`;
5. require both files exist;
6. parse and validate:
   - task_key;
   - base_branch;
   - base_commit;
   - exact frozen worktree locator;
   - expected repo/path/base assertions;
   - remote head descends from frozen base commit;
7. only after the metadata is valid may the helper create/attach the local branch/worktree.

A branch name alone is never enough to adopt a remote task.

### 9.3 Remote mismatch cases

Fail closed on:

- remote reviewed branch missing;
- REQUEST missing;
- CURRENT missing;
- metadata task key mismatch;
- base mismatch;
- worktree locator mismatch;
- remote lineage mismatch;
- local branch exists at a different OID;
- branch belongs to another registered worktree;
- occupied/redirected path.

### 9.4 No canonical-main copy

Remote-discovered REQUEST/CURRENT remain source objects on the reviewed branch.

Do not write/copy them into canonical main to make future resume easier.

After rematerialization, the worktree checkout naturally contains the same tracked task artifacts.

## 10. Revised bootstrap / resume decision table

| Observed state | Canonical source | Action |
|---|---|---|
| **A. task metadata absent locally; local/remote reviewed branch absent; worktree absent** | current-user Kickoff assertions | `task bootstrap` through approval path |
| **B. complete exact local task metadata exists; remote reviewed branch exists; local worktree missing** | local REQUEST/CURRENT, cross-checked against exact remote | artifact-bound `materialize-worktree --mode resume` |
| **C. local task metadata absent; exact remote reviewed branch exists with valid REQUEST/CURRENT; local branch/worktree missing** | exact remote branch metadata read before checkout | remote-only resume/rematerialize |
| **D. exact task branch/worktree already materialized and metadata matches** | worktree/local metadata | idempotent success / continue |
| **E. local branch exists but metadata absent/mismatched and not current-invocation-owned** | ambiguous | fail closed |
| **F. remote branch exists but metadata missing/mismatched** | invalid remote | fail closed |
| **G. worktree path occupied/redirected** | conflict | fail closed |
| **H. current bootstrap invocation created clean exact partial objects** | invocation-local facts | bounded rollback |
| **I. partial state dirty/ambiguous/unowned** | ambiguous | preserve + recovery evidence |

No new workflow/state machine is created.

- task key;
- objective/review/CI/visual/text settings;
- explicit internal base branch;

## 12. Partial-failure rollback remains conservative

Accepted v0.1 recovery semantics remain.

### Before branch creation

No cleanup.

### Branch created / worktree add fails

Remove the current-invocation branch only if:

- it still points to expected base commit;
- no worktree owns it;
- no user/task commit appeared.

Otherwise preserve + evidence.

### Worktree created / task initialization fails

Remove only exact invocation-created bootstrap control paths and the invocation-created worktree/branch if:

- path/branch identity still matches;
- no unexpected user/task files exist;
- no unexpected commit exists;
- normal non-force worktree removal succeeds.

Never use force removal to turn ambiguous/dirty state into a PASS.

### Later invocation

A later invocation cannot infer that matching branch/path state belongs to a prior bootstrap call. If there is no validated task metadata and it was not created in the current invocation, it is ambiguous and fails closed.
