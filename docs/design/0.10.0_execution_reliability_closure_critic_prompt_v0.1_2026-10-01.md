三、本轮需要审什么
==================================================

请重点攻击以下问题。

A. 是否真的应该把这批问题作为一个 0.10.0 convergence release，而不是继续
0.9.4/0.9.5 patch train。

Critic 不能仅因为“diff 大”要求拆分；如主张拆分，必须说明真实安全、恢复、
验收或 owner 边界为什么无法在一个 release 中闭合。

B. P1 sandbox-first 是否属于 Bridge Machine Policy 的正确 owner。

必须防止两种错误：

- 过简：只加一句“不要 escalation”但真实 Codex 仍会误分类；
- 过重：为了避免误分类而全局 allow generic Python/shell。

C. P2 refusal classification 是否能阻止 escalation cascade，而不会发明新的
workflow/state machine 或让真正的 authority blocker 被静默跳过。

D. P3 bounded-entry no-widening 是否应该成为 Bridge-owned通用行为，范围是否
足够窄。

特别检查：

publish-current-branch failure
-> raw git push

是否应明确禁止自动 fallback。

E. P4 ambient SSH_ASKPASS 方向是否安全。

重点确认：

- GitHub HTTPS positive path 是否可以在任何 credential/network-capable Git command
  之前构造 sanitized environment；
- 哪些 local Git config/read operations 不会执行 askpass；
- 仅允许 ambient SSH_ASKPASS 是否足够窄；
- GIT_ASKPASS/core.askPass/custom helper/GIT_SSH_COMMAND 等负例是否仍应 fail closed；
- 是否存在 Planner 漏掉的 credential execution surface。

如果不能证明 askpass 不执行，应 REVISE，不要为了“低打扰”放宽安全边界。

F. P5 runtime identity validation 是否正确区分：

- formal release target；
- later evidence-only main commits；
- genuinely stale runtime；
- executable/import split；
- duplicate metadata；
- dirty editable source。

不要让 host validate 误把 main HEAD 当 release identity，也不要让它变成依赖网络的 updater。

G. ER-G1 至 ER-G8 是否证明真正用户能力，而不是 source presence / keyword /
synthetic-only PASS。

尤其检查：

- 是否有真实 normal Codex entry；
- 是否在用户明确不升级的 codex-cli 0.142.0 上验证；
- 是否真正复现 optional refusal + build + commit + existing-branch publication；
- 是否同一 final candidate；
- 是否保护 0.9.1-0.9.3 已发布行为。
