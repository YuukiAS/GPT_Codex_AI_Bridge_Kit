## 3. Verified failure attribution

### A. Bridge Kit product/runtime gap — PRIMARY: YES

Current materialize_worktree() cannot first-bootstrap a task that has no control files. It unconditionally reads automation/reviewed_handoff/tasks/<task_key>/CURRENT.json and REQUEST.md before the Git branch/worktree transaction.

At the same time, current task init:

- writes REQUEST/CURRENT into whichever checkout is passed as --target;
- derives base_commit/base_branch from that checkout;
- does not accept/freeze the exact Reviewed worktree locator;
- leaves the REQUEST locator placeholder unless something edits it later.

Therefore 0.9.0 materialize-worktree --mode bootstrap is really “bootstrap an exact worktree from already-existing task state”, not a complete brand-new-task bootstrap.

### B. AI_Skills / workflow-core consumer wiring gap — SECONDARY BUT REAL: YES

AI_Skills already says the Kickoff should authorize exact branch/worktree early. Verified Workflow also owns source discovery and isolated execution placement.

However, current workflow-core does not expose a canonical routing rule equivalent to:

task missing -> bounded first bootstrap  
task existing -> bounded resume/rematerialize

and the current Project Thread Handoff recovery still routes a rejected bootstrap to raw Git/user action.

So even after Bridge gains the primitive, the consumer must actually call it. Merely shipping a helper is not enough.

### C. Kickoff contract gap — NO for this reproduced failure

The observed Project Thread Handoff Kickoff already contains exact repo/task/branch/worktree authorization.

Future task authoring must continue to freeze exact base semantics as well, but that is part of authoring the same bounded effect, not a reason to make the user approve each internal branch/worktree/control-file step separately.

### D. Machine Policy gap — NO

Machine Policy is correct to prompt raw git worktree add because it is a generic branch/worktree mutation primitive.

Machine Policy already allows the bounded ai-bridge reviewed-handoff materialize-worktree entry. The repair should preserve this model. Raw arbitrary worktree creation stays gated.

### E. One-off Executor misuse — NO as primary cause

The Executor followed the current recovery contract: try the available bounded route; if it cannot first-bootstrap, fall back to the documented human-bootstrap recovery.

The recurring problem is therefore product + consumer entry, not an individual bad command choice.

## 5. Selected architecture: one existing command, two lifecycle situations

No new top-level command is added.

Keep the existing:

ai-bridge reviewed-handoff materialize-worktree

and the existing Machine Policy allow prefix.

Expand only --mode bootstrap so it has a task-missing first-bootstrap path in addition to the existing task-state-backed path.

### 5.1 Minimal CLI contract

Existing assertions remain:

- --task-key
- --expected-repo
- --expected-worktree
- --expected-base-ref
- --mode bootstrap|resume

For task-missing + mode=bootstrap, add one explicit immutable base locator:

- --expected-base-commit <sha>

and expose the existing task-init metadata needed to create REQUEST/CURRENT, using the same option definitions and validation as task init rather than creating a parallel schema:

- --objective
- --max-review-rounds
- --ci-required
- --visual-review-required
- --visual-review-manifest-path
- --text-review-required
- --text-review-manifest-path

Implementation should share a parser/helper for these fields so task init and first bootstrap cannot silently drift.

For an already-existing task, current REQUEST/CURRENT remain authoritative. If --expected-base-commit is supplied it must equal CURRENT; current compatibility behavior remains otherwise.

### 5.2 Branch remains derived, never caller-selected

The reviewed branch remains reviewed/<task_key>. There is no --branch argument.

This keeps the task key as the branch identity authority and prevents first bootstrap from becoming a generic branch creator.

## 6. Exact first-bootstrap lifecycle

For task state missing + local reviewed branch missing + remote reviewed branch missing + exact worktree free + current-user Kickoff already authorizing repo/task/worktree/base:

### Step 1 — local preflight, no mutation

From the canonical source checkout:

1. verify Git repository identity equals --expected-repo;
2. validate semantic task_key;
3. derive branch reviewed/<task_key>;
4. require the task root is absent in the canonical checkout;
5. lexicalize the exact absolute worktree path and reject symlink/path redirection;
6. require the path is not an unrelated registered/occupied worktree;
7. require local reviewed branch is absent;
8. require remote reviewed branch is absent for first bootstrap;
9. resolve/fetch the frozen origin/<base_branch> represented by --expected-base-ref;
10. verify --expected-base-commit exists and has the required lineage to that base ref;
11. capture the facts needed for final pre-mutation recheck.

No task control file is written to canonical main during this phase.

### Step 2 — create exact reviewed branch/worktree

Create exactly:

- branch = reviewed/<task_key>
- start OID = expected-base-commit
- worktree = expected-worktree

using normal Git safeguards. Do not use -B, --guess-remote, path-derived branch guessing, or --force.

The implementation may continue the current explicit branch-create + worktree-add pattern if that gives clearer rollback ownership, or an equivalent safe worktree add -b composition. The invariant is one exact branch at one exact base in one exact worktree.

### Step 3 — initialize control files inside the new reviewed worktree

Only after the new worktree exists, initialize:

- automation/reviewed_handoff/tasks/<task_key>/REQUEST.md;
- CURRENT.json;
- results/<task_key>/.

The first tracked task-control files therefore exist on the reviewed branch/worktree, not canonical main.

REQUEST must contain the exact frozen absolute line:

- Reviewed worktree locator: <expected-worktree>

CURRENT must contain the frozen source base_branch and expected-base-commit, not reviewed/<task_key> as the base branch.

### Step 4 — reuse, do not duplicate, init_task()

Refactor existing initialization logic into one internal implementation used by both task init and first-bootstrap materializer.

The shared initializer accepts explicit internal base metadata and optional exact worktree locator.

Normal existing task init stays compatible: without explicit frozen bootstrap context it derives base from its target checkout as today.

The first-bootstrap path invokes the same initializer with the frozen base branch, frozen base commit, exact worktree locator, and existing task-init options.

No second REQUEST/CURRENT generator is allowed.

### Step 5 — bounded result only

Successful first bootstrap proves:

- exact branch exists;
- exact worktree exists;
- exact REQUEST/CURRENT exist in that worktree;
- canonical tracked checkout did not gain task-bootstrap files.

It does not mean the task Plan is frozen, implementation complete, CI passed, or review complete.

## 7. Bootstrap / resume decision table

| State | Canonical action |
|---|---|
| A. task absent; branch absent; worktree absent | materialize-worktree --mode bootstrap first-bootstrap transaction |
| B. task exists; remote reviewed branch exists; local branch/worktree missing | existing --mode resume/rematerialize |
| C. task exists; exact branch/worktree already exists and identities match | idempotent success / normal continue |
| D. branch exists but task metadata absent/stale/mismatched and not created by the current invocation | fail closed; do not adopt/delete automatically |
| E. exact worktree path occupied/unrelated/redirected | fail closed |
| F. current bootstrap invocation created clean exact local objects and a later step fails | bounded rollback of only those invocation-created objects |
| G. partial state ambiguous, dirty, unexpected, or ownership unprovable | preserve state; emit recovery evidence; no destructive cleanup |

A first-bootstrap request encountering an already-existing remote reviewed branch does not silently adopt it. If canonical task metadata proves it is the same existing task, use the resume lifecycle; otherwise fail closed.

## 8. Canonical checkout and control-file ownership

The chicken-and-egg answer is explicit:

**REQUEST/CURRENT first exist in the newly created reviewed worktree.**

The canonical checkout is only the existing Git source used to create the bounded linked worktree.

It must not temporarily receive tracked automation/reviewed_handoff/tasks/<task_key>/ or results/<task_key>/ just so the materializer can read them.

This removes the current inversion:

create state in main -> patch locator -> create isolation.

Pre-existing unrelated dirty canonical work is never stashed/reset/restored or absorbed into the reviewed task. If ownership prevents safe bootstrap, fail with exact evidence rather than selecting another path.

## 9. Authorization model

No auth store, receipt graph, token, database, schema family, or second state machine is introduced.

The model remains:

- current-user Kickoff = authorization for the exact effect;
- Goal / Plan / REQUEST / CURRENT = frozen scope and identity evidence;
- Machine Policy = permission for the bounded Bridge command;
- Bridge helper = derive/validate exact effect and execute;
- AGENTS != authorization.

For a task-missing first bootstrap, REQUEST/CURRENT cannot be prior authorization because they do not exist yet.

Therefore bootstrap consumes exact assertions supplied by the already-authorized normal entry:

- repo;
- semantic task key -> derived branch;
- exact worktree;
- exact base ref;
- exact base commit.

After initialization, REQUEST/CURRENT become the canonical frozen task evidence for later resume/rematerialization.

The same exact effect must not be re-asked merely because it internally consists of branch creation, worktree association and task-control initialization.

A different repo/task-derived branch/path/base/remote remains a different effect and fails closed.

## 10. Recovery semantics

Git's default safeguards help but do not make the entire Bridge transaction atomic because control-file initialization happens after Git worktree creation.

Track invocation-created objects in memory during the one helper call; do not create a persistent ownership ledger.

### Failure before branch creation

No rollback needed.

### Branch created; worktree creation fails

Delete only the invocation-created branch when it still points to the expected base, is not checked out elsewhere, and no task/user commit appeared. Otherwise preserve and report recovery evidence.

### Worktree created; control initialization fails

Remove the invocation-created worktree/branch only if:

- worktree identity still matches;
- no unexpected user/task content or commit appeared;
- any uncommitted paths are only known invocation-created bootstrap control paths that can be removed exactly;
- ordinary safe worktree removal succeeds.

Do not use general git clean, reset --hard, arbitrary destructive cleanup, or force removal of unowned state.

### REQUEST written but CURRENT fails

If all partial paths are known invocation-created task control/result paths, remove only those exact paths and then perform the bounded worktree/branch rollback.

If any unknown modification appears, preserve the partial state and return recovery evidence naming created branch/worktree/control paths, failing step and dirty/identity facts.

A later invocation cannot infer ownership merely from a matching branch/path name. Without durable ownership evidence, orphan partial state is ambiguous and fails closed.

## 13. External Git reality check

Official Git documentation checked:

- https://git-scm.com/docs/git-worktree
- https://git-scm.com/docs/git-branch

Relevant upstream behavior:

- git worktree add -b <branch> <path> <commit-ish> creates a new branch from the named commit and checks it out in a linked worktree;
- normal -b refuses when the branch already exists;
- normal worktree add refuses conflicting already-checked/assigned worktree states;
- --force and -B override/reset safeguards;
- worktree remove refuses an unclean worktree unless forced.

Adopted:

- exact branch/path/base;
- default Git conflict safeguards;
- no -B, branch guessing, or force shortcut;
- Bridge identity/authorization checks around Git;
- Bridge-owned bounded rollback for failures after Git creation but before control-state completion.

Not adopted:

- raw git worktree add as the complete product transaction, because it cannot atomically create Bridge REQUEST/CURRENT;
- --guess-remote, because branch identity is task-derived/frozen;
- forced dirty-worktree cleanup.
