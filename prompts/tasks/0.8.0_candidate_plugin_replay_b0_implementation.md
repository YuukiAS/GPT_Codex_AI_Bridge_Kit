## Production command

新增独立 public command：

```text
ai-bridge candidate-plugin-replay \
  --target <repo> \
  --plugin <plugin-name> \
  --candidate-commit <sha> \
  --task <explicit-task-file> \
  --input <explicit-input-file> [...]
```

它是 `plugin-replay` 的 sibling，不是对现有 `plugin-replay` 的扩权。

复用 `plugin_replay.py` 已成熟的低层能力（显式 input staging、workspace、sandbox child contract、write-isolation、read-scope diagnostic、local output metadata）时，只抽取真正共享的 helper；不要为了 DRY 大规模重构现有 `plugin-replay`。

## Candidate commit / manifest contract

`--candidate-commit` 必须解析为 target Git repo 中真实 commit。candidate 内容来自 commit tree，不得读取 dirty/untracked working tree 作为候选实现。

从该 commit 的：

```text
.agents/plugins/marketplace.json
```

按 `--plugin` 找唯一 entry。

0.8.0 至少支持 Phase 0 / AI_Skills 当前使用的 canonical object-local 形式：

```json
{
  "name": "writing-style",
  "source": {
    "source": "local",
    "path": "./plugins/codex/plugins/writing-style"
  }
}
```

如果支持 Codex 当前另一种简单 local-path 表达只需极少代码和测试，可以兼容；否则明确 fail/document，不要因此创建 source adapter framework。

必须拒绝：

- manifest 缺失；
- 0 个或多个同名匹配；
- 非 local source；
- candidate local path 越出 candidate repository tree；
- caller-supplied arbitrary plugin path。

## B0 staging 与 install

在 Bridge machine state 下创建 run-owned staging root，内容只包括：

- commit 中解析出的 candidate plugin tree；
- 一个 Bridge 生成的 minimal local marketplace manifest；
- 本次 replay 必需的 local inputs/outputs。

生成唯一 candidate marketplace identity，例如：

```text
ai-bridge-candidate-<run-id>
```

marketplace 名称由 Bridge 生成，caller 不可指定。

安装只能使用 Phase 0 已证明的 process-local marketplace config：

```text
codex plugin \
  -c marketplaces.<candidate>.source_type="local" \
  -c marketplaces.<candidate>.source="<staging-marketplace-root>" \
  add --json <plugin>@<candidate>
```

禁止 persistent marketplace registration。

安装后必须验证并记录：

- candidate commit；
- committed manifest entry / local source path；
- staged plugin tree digest；
- installed plugin ID；
- installed path；
- installed plugin tree digest；
- staged == installed digest。

若 identity/path/digest 无法绑定到本次 candidate，fail closed。

## OS lock 与 tiny crash journal

对 resolved current `CODEX_HOME` 使用一个独立 candidate-replay lock。不同 `CODEX_HOME` 不共享 machine-global lock。

优先复用成熟、很小的 OS/file-lock 实现；不要设计自己的 lock framework。要求：

- exclusive；
- owner process 死亡后自动释放，或使用等价可靠 primitive；
- unsupported/unreliable platform fail closed，而不是退化成 existence-only sentinel。

machine state 维持极小布局：

```text
${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/candidate-replay/<identity-id>/
├── candidate-replay.lock
└── active.json
```

`active.json` 只保存恢复真正需要的信息，例如：

```text
run_id
candidate_plugin_id
candidate_marketplace_name
staging_path
phase
```

可以增加 candidate commit / current identity digest 这类直接用于安全校验的最小字段；不要扩大成 workflow state machine。

**关键顺序：** `active.json` 必须在第一次 persistent mutation，也就是 `codex plugin add` 之前原子落盘。使用 temp + atomic replace 或等价安全写法。

每个 persistent step 后只原子更新必要 `phase`。恢复必须 idempotent。

## Stale recovery / cleanup ownership

新 run 获得当前 identity lock 后，如果发现 stale `active.json`：

1. 验证 plugin ID / staging path / namespace 确实属于 Bridge candidate replay；
2. 只删除 journal 指定的 candidate plugin；
3. 只删除该 run 的 staging directory；
4. 验证 owned candidate 资源已消失；
5. 清 journal；
6. 才允许开始新 run。

B0 没有 persistent candidate marketplace，因此 stale recovery / cleanup 不得执行或发明 marketplace remove。

cleanup failure 是 hard failure；journal 保留供下一次恢复。绝不 restore 全局 config snapshot，也不删除或恢复 unrelated plugin/marketplace/config state。

## Fresh child：必须使用真实 B0 contract

fresh replay child 必须使用同一个 current `CODEX_HOME` authentication，并至少包含：

```text
codex exec --ignore-user-config
-c marketplaces.<candidate>.source_type="local"
-c marketplaces.<candidate>.source="<staging-marketplace-root>"
-c plugins.<candidate-plugin-id>.enabled=true
```

并继续满足现有 `plugin-replay` 已冻结的 child sandbox / approval / network / ephemeral / write-isolation 约束。

使用 Phase 0 已验证的实际 CLI override key 语义；不要把 TOML 文件中的 quoted-key 写法机械搬到 `-c` 后导致 plugin name 中出现 quote 字符。

不需要也不得重新枚举后逐个 disable 用户 production same-name plugin；B0 的 user-config isolation 已经由 Phase 0 证明。

## Actual candidate-consumption evidence

这是不可降级 gate。

下面这些只能算 preflight，不能单独证明 candidate 真正运行：

```text
plugin add succeeded
installed digest matched
plugin list says enabled
child argv/config looks right
```

production wrapper 必须保留一个**低成本、真实 runtime consumption evidence**，证明 fresh child 实际消费了 installed candidate。

优先利用当前 `codex exec --json` event/runtime 已提供的最小真实证据，例如事件中实际读取/消费了 installed candidate cache 下的 plugin/skill path。Phase 0 的可信证据是：

```text
child event stream
→ candidate installed cache path / SKILL.md was actually read
→ candidate-exclusive harmless behavior occurred
```

正式 generic wrapper 不要求每个 consumer 都输出 test marker，但必须从当前 runtime 能稳定提供的证据中证明 candidate 被实际消费，而不能只从 config 推断。把最小证据写进本次 run metadata/result 即可；不要为此创建 provenance framework。

如果当前 JSON runtime 无法对某次 replay建立可靠 actual-consumption proof，返回明确 failure（例如 `CANDIDATE_EFFECTIVE_PLUGIN_NOT_PROVEN`），不要假装 PASS。

## Child config no-persistence check

candidate plugin install 本身会修改 user plugin config，这是预期 persistent mutation。

因此只检查 child selection interval：

```text
candidate plugin add 完成
→ hash $CODEX_HOME/config.toml
→ fresh child
→ hash $CODEX_HOME/config.toml（cleanup 前）
```

两次必须相同。

不相同则 fail closed；不要 restore，不要猜是谁修改了 config，也不要把 mismatch 当作成功 cleanup 可以覆盖的问题。

## Smoke C — one crash recovery proof

只做一次，不做 chaos matrix。

1. 启动真实 candidate replay；
2. 等 `active.json` 已存在且 candidate-owned persistent mutation 已发生；
3. 从外部终止 owner process，模拟 hard interruption；
4. 验证 OS-backed lock 随 owner death 释放；

7. 验证 unrelated production/test plugin 未变化；
