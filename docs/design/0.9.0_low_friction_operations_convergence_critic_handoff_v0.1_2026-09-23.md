3. REVIEW QUESTION A — READ-ONLY HOST POLICY
==================================================

Plan v0.1 没有选择“把所有候选命令直接按原始 prefix allow”。

它区分：

- 可以直接 allow 的纯观察 family；
- git diff/log/show 的 canonical safe shape；
- gh auth status 的 option terminator 形态；
- 明确不允许 broad raw prefix 的命令。

请独立攻击：

1. Planner 选择的 canonical Git/GH command shape 在 prefix matching 下是否真的保持低风险；
2. 使用 -- 作为 option terminator 是否真的关闭了 Planner 声称关闭的危险后缀；
3. 是否遗漏了仍可：
   - 执行外部命令；
   - 泄露 token/secret；
   - 修改 local Git topology；
   - 修改 remote；
   - 扩大 repository/private-data scope
   的 suffix/path；
4. raw git remote -v 不直接 allow 是否正确；
5. raw git diff/log/show 不直接 allow 是否正确；
6. raw gh auth status 不直接 allow 是否正确；
7. configured origin 的 git ls-remote 规则是否足够窄；
8. nearby dangerous forms 是否仍会 prompt/forbid。

同时审查 failure semantics：

Auto-review 拒绝 optional/read-only diagnostic
不能自动推导成
“Git auth broken / remote inaccessible / user must repair credentials / terminal BLOCKED”。

只有 supported diagnostic 真正执行并返回 auth/transport failure，
才可以把该 evidence 用于真实 blocker 判断。

4. REVIEW QUESTION B — AUTHORIZED EXISTING BRANCH PUSH
==================================================

真实 reproduction：

current branch:
review/01047-clear-writing

remote branch:
origin/review/01047-clear-writing 已存在

local:
ahead 1 ordinary task-owned commit

唯一希望发生的 effect：

ordinary non-force same-branch publication

用户不希望同一个 branch 再次询问授权。

Planner 的关键判断是：

不能安全写成：

allow:
git push origin review/01047-clear-writing

因为 current execpolicy 是 prefix matching，
而 Git push 允许在这个 prefix 后继续追加 refspec/options。

请独立验证这个判断。

然后攻击 Planner 提出的最小 helper：

ai-bridge host publish-current-branch

它不接受 caller-supplied branch/remote/refspec，
只从 cwd/current branch/同名 origin tracking 关系推导。

必须攻击：

- extra refspec；
- --tags / --all / --mirror；
- force / force-with-lease；
- delete；
- -u / --set-upstream；
- missing remote branch；
- current branch tracking different remote；
- current branch tracking differently named remote branch；
- detached HEAD；
- behind/diverged；
- remote remap；
- hooks；
- wrong branch publication；
- branch switch 后滥用；
- main 的现有 raw allow 是否也存在同类 prefix widening。

判断：

1. native current Codex 是否已经能安全表达 exact existing-ref-only effect；
2. 如果不能，这个 helper 是否真的是最小 bounded capability；
3. 是否应把 raw git push origin main allow 一并收口到 bounded publisher；
4. 是否会破坏/绕过 Review watcher publisher ownership。

如果 current Codex 已经有更好的 exact/dynamic permission primitive，
必须 REVISE，要求优先 native。

7. REVIEW QUESTION E — PERSISTENT RUN PROGRESS / ETA
==================================================

Planner 的方向是：

project-native producer owns truth
+
Persistent Run normalization/projection

不是 Bridge 猜 progress。

审查：

- stage；
- progress since last report；
- last_real_progress_at；
- completed/total 只有真实 denominator 才使用；
- ETA 只有真实 basis + uncertainty 才显示；
- 否则 ETA=UNKNOWN；
- stalled 只根据真实 no-progress threshold；
- slow 需要真实 pace evidence / materially worsened ETA；
- tmux/process alive 不能等价为 normal。

Planner 暂定：

- start/resume、stage transition、stall/block/failure/completion：及时 report；
- long active stage 默认约 60 min；
- 没有 task-specific 理由不默认低于 15 min；
- ETA expected finish 的变化 >= max(15 min, prior remaining 的 25%) 视为 material；
- UNKNOWN <-> known 始终 material。

请判断这些默认值：

- 是否合理；
- 是否过度设计；
- 是否需要简化；
- 是否会产生假精度。

同时审：

ai-bridge persistent-run report --progress <project-native-progress-json>

是否足够小。

关键要求：

- 不能变成 daemon/controller/watch hierarchy；
- 不自动 cancel/restart/resource mutate；
- 不要求每个 repo 安装 Notifier；
- reporter failure 不杀掉 healthy underlying run；
- reconnect 后 latest + bounded recent history 可检查；
- local progress evidence 不是 workflow state/auth state。
