## 0. 核心判断与本轮真正解决的问题

Bridge Kit **不是空壳**。0.11.1 已发布；历史上有来自真实 Codex/跨仓库的限定正例，例如 Review 首次创建和远端发布、GitHub HTTPS 的受边界约束发布、Persistent Run 正常入口发出两封邮件、Longleaf 实际升级至 0.11.1。

但它也**尚不能凭这些证据宣布“除 Program Run 外所有正式能力的正常入口已充分验收”**。至少两条正常使用链目前证据与机制存在缺口。

**长期运行**：冻结 Goal 允许直接沿用模板里的进度模式 none；即使合同声明 count/fraction，也只核对生产者身份字段，不验证运行中是否实际持续上报。监督器没有独立按生产者最近有效更新时间判定“本应汇报但已经失联”。正常 status 展示的是另行读取并标准化的源文件，而主动算出的 ETA 存在 binding.last_good_progress 中；两条读取路径可能给用户不同结果。子进程刚退出时没有最后一次进度读取，末次有效进度可能不进入终态邮件。这些是 0.11.1 源码可支持的局部实现缺口，并非声称已在用户具体项目复现过。

**受边界约束包装器**：包装器执行时能真正检查复杂的仓库、工作树、远端、历史与授权形状；但这些动态检查只对**实际调用了包装器**的动作有效。Codex 命令策略对已识别的危险直接 Git 命令配置了 prompt，但对任何 shell/Python/其他可执行环境的等价效果并不存在 Bridge 自带的全机强制拦截。当前证据足以支持“规范使用包装器时守住边界”，不能支持“所有绕行都已被系统阻断”。本轮须把承诺范围、正式入口调用与真实平台审批的区别核清，再决定是否存在需要最小修补的具体绕行。

其余能力不因本轮重新作废。新缺陷归回负责的既有机制，单纯缺乏正常入口证据先补证，不用“又建一套系统”解决。Program Run 继续有意排除。

## 3. 重点 A：Progress/ETA 为什么会“明明能报告却一直 UNKNOWN”

### 3.1 谁拥有事实，Bridge 在哪个位置消费

正常路线应为：已获批准的 Goal 和所属专业项目先决定有无可量化进度、单位/总量、生产者与合理更新时间；真实业务程序在执行中持续写出项目原生 JSON，或调用 ai-bridge persistent-run progress update；supervisor 定时读取并只依据有效量化历史估计 ETA；status、绑定、last-good/history 和需发送的邮件共享同一解释过的观察结果。只有真正的项目 owner/Goal 有资格决定工作是否完成，Bridge 只管理运行层事实。

当前正式代码已落实其中大部分：parse_persistent_contract 绑定冻结 Goal SHA、进度模式/owner/source/expected update cadence；child 环境注入进度接口；写入采用原子更新；estimate_progress_eta 在同一阶段/总量下至少 3 点、跨至少 10 分钟，以最近不超过 60 分钟/12 点的正向速度中位数估算 ETA，并给出经验速率区间；运行恢复不自动重启；调度器已拥有的 Slurm batch 不额外套 tmux。

### 3.2 四个已经能从正式代码看出的缺口

**P1：none 默认放行没有理由。** 当前 CONTRACT_TEMPLATE.md 字面默认 Progress mode/owner/source = none/none/NONE；parse_persistent_contract 仅拒绝 count/fraction+owner none。一个实际上会运行 1,000 个批次的量化任务，只要沿用模板，就可能从头到尾合法处于 UNKNOWN。没有证据说所有 Goal 都这样，问题是**现有合同没挡住这个低配选择**。

**P2：声明生产者不等于实际产出；失联不报警。** count/fraction 填了 bridge-child/project-native 就过合同检验；update_run_progress 需要业务 child 主动调用。supervisor 在读取坏/缺失进度文件时继续 child，这是对的；但是没有根据 Expected progress update seconds 和最后一次真实生产者更新时间判断“超期未产出”。normalize_progress_evidence 的 stalled 依赖源自身携带 seconds_since_progress 或另有显式阈值，supervisor 常规读取并未传入该阈值。表现可能是进程仍活着而进度来源早已停报，用户只看见 running/UNKNOWN 或过期数字。

**P3：status 返回的 ETA 不一定是 supervisor 算出来的 ETA。** observe_binding_progress 将估计 ETA 放进 binding.last_good_progress；status_persistent_run 调用的 _progress_status 则重新读原始文件并 normalize_progress_file，它不调用主动 ETA estimator。若生产者只报 count/fraction、未给自己算 ETA，status 的主要 progress.normalized.eta 仍可能为 UNKNOWN，即使 binding.last_good_progress 已有 Bridge 估计。邮件从 binding.last_good_progress 发送，因此可能出现状态与邮件不一致。

**P4：退出时最后一次更新未再次读取。** supervise_binding 在 child.wait() 返回后立刻标记终态并使用已缓存的 last_good_progress 发终态通知，没有在真正退出后做一次有界读取。任务退出前刚写出的最后数据可能没有进入终态 history/status/email。反过来，退出码 0 本来也不证明 Goal 语义完成，两者必须继续区分。

额外表达问题：当前 eta_low/eta_high 由有限历史速度的四分位数换算，不是经过校准的概率置信区间；不能包装成“95% 预测保证”。

### 3.3 最小必要改法（不造新控制系统）

**Goal 写作与启动前**：在现有 Persistent 合同/模板与 GPT/Codex 任务入口要求声明进度适用性及依据。可量化且任务已有真实生产者时，应选 count/fraction，明确单位、总量来源、生产者正常入口、source 路径和预期报告间隔；若确实无法量化或项目还没有可用 producer，可用 stage/none，但必须给可审查的具体原因、对应项目 owner 和替代观察，不准不填就默认 none。仅有外部调度器生命周期的任务继续使用其原生报告，不要求安装 tmux。

**启动与运行时**：在现有 parse/start 的前置检查里校验合同字段与生产者的可接线证据；不能在启动前证明未来必会产出，所以监督器应按首次合理等待窗口和之后 expected cadence 比较生产者的**有效新发布时间/进度事件身份**与当前观察时间。区分四种状态：预热未满、当前有有效进度但不足以估 ETA、生产者超期没有更新、源数据临时不可读。生产者超期应报告“进度来源失联/滞后”，不直接宣称业务进程停滞或任务失败。连续平台期但按期上报应区别于失联；阶段变更和总量变化继续重启 ETA 预热。

**统一读数**：只复用现有 binding/last-good/history 与 _progress_status 的结构，不新建另一套 state。确保正式 status 返回的用户主要进度与 supervisor 真正记录的有效 point、估算 ETA 和观察时间一致；邮件用同一份快照和一套估算理由。项目自己提供带依据 ETA 时要分清其来源，Bridge 自算 ETA 标为“基于近期速度的经验估计”。

**结束前**：supervisor 真正 child.wait() 后，在发送 terminal 通知及写终态之前，做一次有界的最后进度读取：有效数据更新则记录，无效则保留 last-good 并标明末次数据时间。exit code/status、最后有效进度、邮件事实保持一致，仍不升级到 Goal PASS。

**失败与恢复**：缺失/坏 JSON 非致命；邮件失败也不杀 child；重复 start 仍返回同一身份；已失去 session 用现有 recover/resolve，绝不自动重跑。暂停上报仍可由项目 owner 诊断原因，Bridge 不推断统计或模型业务语义。

实现优先复用 parse_persistent_contract、observe_binding_progress、_progress_status、supervise_binding、_delivery_decision、report/latest，扩一个明确的进度来源时效判别，不引入 timer daemon、中央 controller 或新数据库。

### 3.4 必须如何真实验收

选**现有获批准、真实有量化进度的任务**，不重造假的专业进度。其 child 在正常代码里实际持续调用标准 update 或写项目原生 JSON，不能靠 Gate 驱动程序从旁边代填百分比。若所选项目尚无生产者，则先由项目 owner 做最小适配；不能用 Bridge 猜科学进展代替。

一次完整运行验收必须同时观察：原 Goal/当前授权身份；真实 child 唯一启动且断线后仍在；跨至少三点和十分钟出现依据真实数据的 ETA；status 与同一时刻 binding/history 和有授权时的 progress 邮件表达一致；**停止上报而 child 仍活着**时按合同进入“进度来源超期”，恢复上报后退出失联状态并正常估算；最终 child 写最后有效点后退出时终态消化该点；重复 start 不产生第二份 child；SMTP 故障不会杀任务、不会虚报语义完成。

如果需要运行真实机器任务、占用 Slurm/设备/数据、模型或邮件，先冻结精确对象/资源/时间/次数/收件人并请求用户单独批准；本设计阶段只读取证据、设计验收，不消费外部资源。已经证明的 0.11.0 两封邮件和 0.11.1 cadence 回归不必盲目重跑，只重跑本次新增的跨层实际链及受影响边界。

## 4. 重点 B：受限包装器究竟挡住什么，哪些绕行仍需证据

### 4.1 五个值得保留的命令各解决一种不同故障

**reviewed-handoff task bootstrap**：过去从新 Reviewed 任务创建工作树常触发反复分支批准；这个入口从已经同步的 origin/main 和 task_key 派生唯一 reviewed/ 分支与 sibling worktree，确认 repo、base commit、canonical remote fetch profile、危险 hook/filter、输出路径后才本地创建。它本身不联网。价值是“一次冻结任务范围即可创建那个工作树”，不是授权任意 git worktree add。

**reviewed-handoff task publish-first**：新任务尚无远端分支，通用发布器只能发布已存在分支，导致额外 git push -u 索权。这个入口逐项校验首次 REQUEST/CURRENT、HEAD 与 base 的直接父子关系、仅两份元数据变更、未存在远端分支、GitHub HTTPS 传输；采用精确空目标 expected lease 后校验远端 SHA，最后才设置同名 upstream。它不是任意新分支创建器，也不是可以偷偷推业务代码的首次提交器。

**reviewed-handoff materialize-worktree**：某个任务已有冻结 REQUEST/CURRENT，但当前工作树缺失，旧模型可能猜测工作树/分支或错误迁移元数据。它依据准确的任务范围、本地或远端 frozen artifacts 与 branch/worktree 断言，在 bootstrap 或 resume 模式物化；路径/身份不匹配拒绝，并保持 canonical main 不污染。

**host publish-current-branch**：已经选定的当前分支有同名远端，正常提交后不应每次重新批准泛化 git push；包装器核对 repo/branch、origin 上游、GitHub HTTPS fetch/push 地址和 hook/credential/config 安全、远端分支存在及祖先关系，以一次普通非强制精确 ref 更新提交，禁止 SSH/custom、force、任意 branch/topic rewrite。

**host sync-current-branch**：已选择的非 main 分支只落后同名 origin 分支时，原来需要手工审批或错误地用 rebase/拷贝绕行；包装器要求 clean worktree、同名 upstream、准确 repo/branch、传输/config 安全、local HEAD 是远端祖先，才 fast-forward，更新后核对 OID，不做 rebase、autostash 或 branch switch。

这五个包装器不能仅因命令名多而删除：它们限制的是原生 Git 命令无法静态知道的**动态仓库、任务与提交关系**。如果未来观察到用户原生受批准路径与包装器完全等价且不增加安全收益，可提出单独退役证据；本轮不预先删除成熟入口。

### 4.2 强制边界、实际调用、绕行的准确分层

包装器内代码的动态检查是**在该包装器被调用时**真实执行的安全防线；已经读取到正式源码。Codex Host Policy 的 execpolicy 可对已列出的精确 wrapper 子命令给 allow、对一部分直接危险 Git 给 prompt。验证报告曾在正式 Codex 中测试过若干正常与危险邻近命令，但它只是指定 CODEX_HOME/CLI/策略文件/命令形状下的证据。

**不能把这推广为全机拦截**。原始 Git、经 shell/Python 间接启动的 Git、不同绝对路径、其他 tool/MCP、不同 CODEX_HOME、原生平台已有更高权限的会话，并不自动经过 wrapper 的动态检查。部分危险命令在当前静态规则下只是不匹配而落到原生平台审批/沙箱决策；不匹配不等于 Bridge 自己拒绝。机器级规则里普通 git add/commit 仍允许，这是有意低打扰，不机械核查全部 task-owned 语义。

因此应精确区分：

1. **包装器保证**：使用某个正式 wrapper 时，其内部检查必须通过才会发生对应操作；有真实正例和恶意配置负例。
2. **已验证 Codex 机器策略保证**：当前 CODEX_HOME、当前被加载的规则、当前 Codex runtime 内，对某组实际命令形状为 allow/prompt/forbidden 或 fallback；需现场验证而非凭规则文件存在。
3. **仅行为指导**：AGENTS、Goal、task 里的“不要绕过”，不可能替代系统审批。
4. **边界外**：其他 shell/脚本/执行环境可在 OS 凭据许可范围做事；Bridge 没有全局命令拦截、也不声称能挡住已经拥有直接 Git 权限的人。

OpenAI 官方 execpolicy README 说明 prefix rule 只是按命令 token 匹配，未匹配时可以无 decision，绝对路径与 basename 的处理取决于配置；这支持上述有限边界，而不是“所有原始写命令都已强制禁止”的扩张主张。

### 4.3 本轮最小机制修订

先**证据优先**：从正常用户任务入口取其真正运行的命令、所选 CODEX_HOME、规则文件、Codex CLI/审批/沙箱模式；证明这次执行是否实际进入 wrapper。对五个 wrapper 分别复用历史真实成功与关键失败证据；源代码未变的部分不重新付费测试。

然后在实际生效的 execpolicy 中，使用只读 execpolicy check 和一个受控新会话，针对 **相同效果** 的直接 Git、git -c、shell -c、Python subprocess、绝对路径及其他合法工具路线检查真实“可直通、需要审批、拒绝或无法判断”。禁止为了证绕行而未经授权触发真实 push/delete/资源变更。只读检查不证明真实带副作用执行已被阻断，若关键路径需要真实验证，应在已授权的 disposable repo/remote 使用可逆效果并保留真实审批和未发生副作用证据。

如果发现平台已能在该受控入口让危险直接操作走审批，**本轮只修正常任务选 wrapper 的入口指引/实际调用，不为此再造强制层**。如果关键原始效果被误设成低打扰自动放行，必须定位到具体命令形状与当前策略，尽可能最小修正现有 Host Policy 或原执行入口，再让 Critic核对范围和正常低打扰不退化。原始脚本/非 Codex 权限范围的“所有绕行都阻断”不是本产品现有承诺；若用户将来要求 OS 级强制，必须单独设计并明确授权，本轮不预埋。

### 4.4 包装器的真实验收口径

每个包装入口维持一组紧贴其真实故障的正负对照：正常通过时，真正产生唯一期望的 repo/branch/worktree/remote SHA 改变；危险邻近（错 repo/错 branch、旧 base、dirty、diverged、危险 hook/transport、已有首次远端/错误元数据）在**实际副作用前**拒绝；其他合法直接读取/当前分支 add/commit 不被过度阻止；当包装器 fail-closed 时，不允许执行者换 raw Git 继续同一效果。

“包装器本身能拒绝”与“原始等价操作被当前 Codex 审批层拦住”是两份不同证据，不得合并宣称。机器策略生效范围必须写明当前 CODEX_HOME/Codex version，并对未知或不可访问环境给出明确限制。

## 5. 除重点外的其他能力：最低必要、按风险补证，不无限重新测试

为每项其他正式能力保留一个对应**实际消费者**的最短可信正向链与一条关键失败/恢复链；优先索引既有足够原始证据：

- **Lite**：真实任务从 ai-bridge task run 读取精确提交的规则/Goal 到一次业务执行，再生成 result 与人工可读复核；错误 mandatory source 时 child=0。其业务专业质量由使用方自己验收。
- **Review**：保留已通过的跨仓库 bootstrap/publish-first 正例；补证完整 reviewer 事实 → watcher 合法状态推进 → 返修或等待 → 正确恢复。真实外部 GPT 决定如果已在历史消费方存在，直接取原始 CURRENT/REVIEW/RESULT；不为建证据而新跑付费模型。
- **Control**：取一个已经完成的真实项目，验证原冻结合同、Planner/Critic/Verifier/Executor 决定由独立 authority 产生，并且 Controller 只是验证、路由与恢复；单元测试里的 toy 状态链只证明机制，不能代替真实独立最终审查。
- **Notifier/邮件**：共享机器配置在两 repo 的身份、重复/歧义发送和一次性 Clear Writing/Gmail 正例继续复用；此次只把新量化进度和最终快照与邮件贯通。SMTP_ACCEPTED 不宣称 inbox delivered。
- **Overleaf**：从真正已授权的论文仓库用 Overleaf connection 的正常入口推/pull 一次有意义的文件变化，并验证仅 paper_root、baseline digest、冲突拒绝和原项目工作树不被改坏；如果现成真实记录可证明就复用。
- **视觉复核**：证据必须是实际图像/幻灯片渲染结果被正式入口接受，冻结图片 identity，并有用户可读的实际评审及匹配的专业评分；假 API JSON 只证明协议。
- **文本复核与转换**：明确私有/公开数据、age 加密、来源 SHA、实际有权限的模型调用、结果/密文可交付与接收方消费；专业文本判断属于相关研究项目，不在 Bridge 里再造通用文章评分器。
- **生产插件回放**：指定一份实际已安装并启用的目标插件，在隔离写入的正式 plugin-replay 入口完成回放、返回执行轨迹和不应写入原仓库的负例；不要把“同用户其他文件绝对不可读”错误提升成已有保证。
- **发行/机器同步**：复用 0.11.1 release FF、同候选 CI、Longleaf 安装时读回版本；只有要声称另一个机器已经更新时，才由那个机器 owner 真正回读运行时身份；AI_Skills 机器更新机制由 AI_Skills owner 负责。
- **Program Run**：完全不加入测试、实现与自动 Goal 链；仅保留“有意排除”的说明。

任何真实 external provider、图片、私有文本、付费模型、Gmail、Overleaf 写入、GitHub 远端实写或 Slurm 资源使用，先列 exact provider/data/recipient/task/费用/次数/恢复边界请求授权；缺授权只能做无外部副作用的回归、来源核查和冻结 Gate，不能假称通过。

## 6. 正常使用门槛矩阵与证据纪律

不为了增加编号而复造一套中央 Gate 数据库。沿现有 Gate/RESULT/目录附一张本任务内的覆盖记录，按用户能力归类，确保每个**真正需要补证**的承诺在同一适用 production identity 直接检验。

| 能力组 | 主要正常成功路径 | 最关键失败/恢复 | 不得改变的既有能力 |
| --- | --- | --- | --- |
| Host + 安全包装器 | 当前 Codex host validate + 已批准当前分支操作走窄 wrapper | 直接等价危险 Git 是否触发平台真实审批；wrapper 参数/远端错误时零危险副作用 | 安全读取、已授权 add/commit、HTTPS 正常快速发布保持低打扰 |
| Lite + exact source | task run 执行真实结果并交用户审阅 | 错路径/提交/mandatory blob 不启动 child；不相关 dirty 不阻断 | 最小任务结构不被重型状态机取代 |
| Review | 真实 reviewed task 从 bootstrap/publish-first 经 reviewer、等待/恢复 | stale reviewer 不被采纳，合法 REVISE 可恢复，用户拒绝不滥加轮次 | 原最多两轮与人工决策边界 |
| Control | 已冻结真实任务从角色证据、集成到 final Critic | 假 role receipt / stale snapshot / partial restart 不产生 PASS | Planner/Verifier/Critic 分权 |
| Persistent + ETA | 获批准量化 Goal→child 自产有效点→supervisor→status/ETA→通知→终态 | none 无理由、producer 停报、坏 JSON、断线重复启动、末次更新丢失 | 原 3 点10分钟 ETA、60分钟通知、recover/resolve、主进程不被通知杀 |
| Notifier + Clear Writing | 真实 authorized source → machine config → one-shot expression → SMTP_ACCEPTED | 重复/DELIVERY_UNKNOWN/超时、不能自动重试或改变业务 state | 机器配一次、四消费者 authority、120 秒总 deadline |
| Overleaf | 已授权论文根目录的有限 push/pull | remote ahead、非论文目录写入、token 暴露被拒绝 | origin/branch 不变 |
| Visual/Text Review/Transform | 合法来源与权限→实际外部审查/转换→完整可访问结果 | 未授权外发、SHA mismatch、预算耗尽、密文不可用 | 专业评分不转移给 Bridge |
| 插件回放 | 已安装正式插件→受限回放→本机证据 | 未安装插件、路径越界、危险参数、原仓库写入阻断 | 不改 CODEX_HOME，不成为通用 Codex reader |
| 发行/安装 | release exact SHA → package/where/version on actually selected machine | dev HEAD 与 release 混淆、机器未更新、规则未生效 | 非强制发布、原 owner 授权 |

验收顺序：先核历史证据是否匹配未变的当前源，再运行无外部作用的确定性回归；仅为没有等价实证的关键链设计最小授权测试；所有外部测试事前冻结选择标准、次数、失败记录、恢复办法，失败不得换样挑最优；最终声称完整只能绑定同一 final candidate SHA 和真实入口，不能跨版本拼通过。多环境必需分别记录实际版本和消费者，不许通过一个 Longleaf 代表所有机器。

## 7. 最小实施归属与复杂度比较

优先需要改的仍是**已有 Persistent 合同/模板/启动前校验/观察/status/终态**；用户需要看到的是“不再允许无理由关闭量化进度”“生产者停报有明确分类”“同一真实进度与 ETA 在查询和邮件一致”“最后一个进度不会因为退出被漏掉”。

对于包装器，优先证据核对并仅在发现具体真实误放行时补 Host Policy 或入口使用，而不是增加通用安全代理。对于其它能力，先补实际消费者证据。缺证据不直接产生源码改动。

比较过的替代方向：
- **只写审查 checklist、不改执行链**：无法阻止 none 模板、失联与 status/通知错位，拒绝。
- **用日志/心跳自动猜业务百分比**：违背领域 truth ownership，拒绝。
- **增加统一进度 daemon/长驻模型线程/中央验收控制器**：已有 supervisor 和项目原生 producer 足以承担，成本大且引入新故障层，拒绝。
- **强制所有 Git 写入全走 Bridge 或安装全机命令拦截**：与原生 Codex 权限层、用户既有机器/外部工具相冲突，不能在本轮冒充授权，拒绝。
- **保持现有安全 wrapper、补真正会改变结果的边界校验与正例**：优先方案。

必须先经 Critic 设计审查（PROCEED/REVISE）。后续才可形成 execution-ready Plan/Goal/Kickoff，由独立 Critic 唯一 PASS+READY_FOR_CODEX=YES；再由用户实际授权后交 Codex。具体专业数据/模型/外部服务、机器更新、正式发行均不在本提案的即时授权之内。

## 8. 两个主要风险与收敛原则

一是把所有量化任务强制要求真实进度 producer 可能增加用户和专业项目适配负担。解决办法是让 Goal 作者明确单位、可量化性和现成数据来源；无正当量化来源的 stage/none 保留，但原因与替代观察必须真实。Bridge 检查承诺是否兑现，不替用户发明可量化业务。

二是把“绝对禁止绕行”误写成可实现的 Bridge 单包安全保证。具体行为只在实际载入的 Codex 机器规则、沙箱和审批层有效；如果要求操作系统级不可绕行，必须另行论证/授权。用户看到的应是“规范调用哪条路径、原始危险操作在此会被提示/拒绝、哪些执行面不受这层管辖”，不能宣传抽象永久安全。

本轮提案尚未经过独立 Critic；**没有生产修改、live 模型/邮件调用、Slurm 作业、Overleaf 同步、Git 远端业务写入、正式发行移动，也没有新 production candidate**。开发分支若保存本文，仅属于规划证据提交，不是产品版本更新。
