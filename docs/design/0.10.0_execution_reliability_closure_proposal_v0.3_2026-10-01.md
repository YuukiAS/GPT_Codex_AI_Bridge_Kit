## 1. v0.3 conclusion

Keep the v0.2 architecture, gate structure and 0.10.0 convergence-release direction.

DESIGN_REVIEW_R2 closed all three R1 blockers and identified one new, narrow security
gap on the same Git config-view causal chain:

`BR-ER-F04-GIT-CONFIG-PARAMETERS-COMMAND-SCOPE`.

This revision accepts that blocker and makes exactly three mechanism changes:

1. `GIT_CONFIG_PARAMETERS` is added to the process-level config/command-scope fence;
2. both stable security-inspection and sanitized remote/push environments explicitly
   remove it;
3. ER-G4 gains a `GIT_CONFIG_PARAMETERS` executable command-config canary that must
   fail closed before network/mutation with canary execution count = 0.

No other v0.2 mechanism is reopened. In particular:

- BR-ER-F01/F02/F03 remain CLOSED;
- P1/P2/P3 remain unchanged;
- runtime identity severity remains unchanged;
- ER-G8 remains the real normal-entry `codex-cli 0.142.0` refusal-recovery gate;
- `0.10.0` remains the proposed convergence release.

No implementation is authorized by this revision.

## 2. Critic findings

### BR-ER-F01-GIT-CONFIG-INSPECTION-BYPASS — CLOSED

DESIGN_REVIEW_R2 explicitly closed F01. The v0.2 stable-config-view design remains
binding and is not weakened by this revision.

### BR-ER-F02-SANDBOX-FIRST-AUTHORITY-PREFLIGHT — CLOSED

DESIGN_REVIEW_R2 explicitly closed F02. Sandbox-first remains limited to ordinary
workspace-contained execution, while known authority-sensitive effects continue to
use existing upfront authorization semantics.

### BR-ER-F03-REAL-NORMAL-ENTRY-GATE-BINDING — CLOSED

DESIGN_REVIEW_R2 explicitly closed F03. ER-G8 remains indivisible and bound to the
same final Bridge/Machine Policy candidate, real normal Codex entry, unchanged
`codex-cli 0.142.0`, one genuine refusal event, required build/QA continuation,
ordinary commit, bounded publication and remote-SHA verification.

### BR-ER-F04-GIT-CONFIG-PARAMETERS-COMMAND-SCOPE — ACCEPT

The finding is correct.

Current Git source still treats `GIT_CONFIG_PARAMETERS` as a command-config
environment entry. Git's own source/tests exercise that entry. Current OpenAI Codex
safe Git command construction also explicitly removes `GIT_CONFIG_PARAMETERS`
alongside `GIT_CONFIG` and `GIT_CONFIG_COUNT` before issuing repository-sensitive
Git commands.

Therefore v0.2's security claim was incomplete even though it already fenced
`GIT_CONFIG`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`,
`GIT_CONFIG_NOSYSTEM` and `GIT_CONFIG_COUNT/KEY/VALUE`.

The exact closure is intentionally narrow:

- add `GIT_CONFIG_PARAMETERS` to the process-level config fence;
- remove it from stable security-inspection environment;
- remove it from sanitized remote/read/push environment;
- add a command-config canary in ER-G4;
- do not generalize into an audit of every `GIT_*` variable.

## 4. Production mechanism

### P1 — sandbox-first, authority-aware Machine Policy guidance

For ordinary repo/workspace-contained work:

- build, test, lint, render, QA, deterministic task scripts and task-owned generated
  output use the normal `workspace-write` path first;
- Python, TeX, shell-script or compiler identity alone is not evidence that escalation
  is required;
- do not pre-emptively request `require_escalated` for these operations merely
  because they mutate files inside the allowed workspace.

For known authority-sensitive effects:

- preserve the existing preflight before substantial precursor work;
- current-user authorization, frozen Goal/Plan/contract, or reliable static effect
  analysis can establish the boundary before an attempted command;
- do not intentionally execute a forbidden/out-of-sandbox effect merely to obtain an
  observed failure;
- newly changed provider, artifact, recipient, purpose, resource, cost, backend or
  destructive scope still requires the existing fresh-authorization route.

This mechanism changes route selection, not sandbox permissions.

No generic Python/shell allow rule is added.

### P2 — refusal classification and cascade breaker

After a refusal or unavailable operation, classify the effect before another authority
path is attempted:

```text
OPTIONAL_NOT_REQUIRED
-> skip the effect and continue required work

SANDBOX_CAPABLE_BUT_ESCALATED
-> return only to the normal sandbox route if the operation has not already run

BOUNDED_NORMAL_ENTRY_BLOCKER
-> preserve completed state
-> do not widen to the raw operation
-> report or use the existing legal recovery for that exact effect

TRUE_AUTHORITY_OR_SAFETY_BOUNDARY
-> existing approval / HUMAN_ONLY / Planner route
```

The classification is behavioral guidance and does not create a persistent enum or
new workflow state.

One refusal is not authority for a broader fallback. Without new evidence that the
effect or required authority changed, the executor must not chain alternative
`require_escalated` attempts simply to get past the refusal.

If a sandbox-capable command was rejected only because the executor mistakenly asked
for escalation, the ordinary sandbox route is a correction of execution mode, not a
permission bypass. It must not repeat a side effect that already occurred.

### P3 — bounded-entry no-widening contract

For Bridge-owned bounded normal entries whose purpose is to replace a broader raw
operation:

```text
bounded success
-> continue

bounded deterministic rejection
-> no automatic broader raw fallback
-> preserve earlier artifacts / commits
-> report the smallest unresolved effect
-> use only an already-defined legal recovery route
```

The required concrete regression remains:

```text
publish-current-branch rejection
!= authority to run raw git push
```

Implementation planning may inventory other bounded Host entries, but may apply this
contract only when the helper is genuinely the normal entry for a broader raw effect.
Do not rewrite unrelated product commands around this abstraction.

### P4 — stable config preflight + ambient SSH_ASKPASS-safe publisher

#### P4.1 Process environment fence

Before security-sensitive Git inspection, reject process-level overrides that can
change transport/config semantics.

The minimum config-source fence includes:

```text
GIT_CONFIG
GIT_CONFIG_GLOBAL
GIT_CONFIG_SYSTEM
GIT_CONFIG_NOSYSTEM
GIT_CONFIG_COUNT
GIT_CONFIG_KEY_*
GIT_CONFIG_VALUE_*
GIT_CONFIG_PARAMETERS
```

Retain existing rejection of:

```text
GIT_SSH
GIT_SSH_COMMAND
GIT_ASKPASS
GIT_PUSH_OPTION*
```

Do not reject ambient `SSH_ASKPASS` solely because it exists on the candidate
positive HTTPS path; instead P4.2-P4.4 must prove it cannot execute.

Before implementation freeze, check the exact installed Git version used by the final
real gates against current official Git documentation for any additional formal
config-source / command-scope environment entry with equivalent effect. This is a
bounded compatibility audit, not a scan for every `GIT_*` variable.

#### P4.2 Stable security-inspection environment

All Git commands used to decide whether config/transport is safe must receive an
explicit stable inspection environment.

That environment must remove every rejected config-source/command-scope override
above, including `GIT_CONFIG` and `GIT_CONFIG_PARAMETERS`, before invoking
security-sensitive Git inspection.

It must inspect the repository's actual normal config stack rather than a
caller-selected substitute.

The implementation Plan must identify every preflight helper that reads security-
relevant Git config and route it through this stable environment, including the
current equivalents of:

- config value lookup;
- config key existence lookup;
- config entries with scope/origin;
- remote fetch/push URL resolution when configuration can affect it.

A security decision made under one config view may not be followed by a network
operation under a different config view.

#### P4.3 Local config rejection remains fail-closed

Continue to reject effective unsafe config that would enable executable or expanded
behavior, including:

- effective `core.askPass`;
- repo/worktree/command-scope `credential.helper`;
- effective custom SSH transport;
- active pre-push hook;
- mirror/follow-tags/submodule recursion/push options/signed-push expansion;
- wrong/multiple remote URLs, wrong branch/upstream, unsupported transport.

Existing allowed system/global credential-manager behavior remains a required positive
neighbor because the publisher must still authenticate normally on GitHub HTTPS.

#### P4.4 Positive ambient SSH_ASKPASS path

Only after P4.1-P4.3 pass may ambient `SSH_ASKPASS` be tolerated.

Before the first remote/network Git operation that can reach authentication:

- construct the publication/network environment;
- remove `SSH_ASKPASS`, `GIT_ASKPASS`, every rejected config-source/command-scope
  override including `GIT_CONFIG_PARAMETERS`, and other already rejected
  execution-affecting transport variables;
- set `GIT_TERMINAL_PROMPT=0`;
- use the same sanitized environment for remote read and final push.

The positive gate must use an executable ambient-`SSH_ASKPASS` canary and prove it
was never invoked.

If any required remote/network operation must occur before this sanitized environment
is in force, this P4 mechanism is invalid and must return to Planner/Critic.

#### P4.5 GIT_CONFIG bypass canary

ER-G4 must include at least this exact failure shape:

```text
real repository .git/config
  contains either:
    core.askPass = <executable canary>
  or:
    credential.helper = !<executable canary>

process GIT_CONFIG
  points at a clean substitute config

publisher invoked
```

Required result:

- fail closed before remote/network mutation;
- canary execution count = 0;
- removing `GIT_CONFIG` from the inspection environment exposes the real unsafe
  repository config;
- no raw push fallback occurs.

Both `core.askPass` and executable credential-helper forms should be covered across
deterministic tests/regression, with at least one exact form in the required canary
gate.

#### P4.6 GIT_CONFIG_PARAMETERS command-config canary

ER-G4 must separately cover the verified command-scope entry:

```text
process GIT_CONFIG_PARAMETERS
  injects executable credential.helper command config

publisher invoked
```

Required result:

- fail closed before any remote/network/mutation effect;
- executable credential-helper canary execution count = 0;
- stable security-inspection does not inherit the variable;
- sanitized remote read/push does not inherit the variable;
- no raw push fallback occurs.

This gate exists because `GIT_CONFIG_PARAMETERS` is a verified Git command-config
entry on the same config-view safety chain. It does not authorize a general
`GIT_*` environment sweep.

### P5 — runtime/release identity diagnostics

Keep v0.1 direction with one additional freeze requirement for the later execution
Plan.

Report:

- trusted executable real path;
- actual imported package source;
- package version;
- editable source Git HEAD when applicable;
- active-source dirty state;
- locally known canonical `release` ref/target when available;
- duplicate/conflicting distribution metadata;
- active `CODEX_HOME`;
- installed Machine Policy status/capabilities.

The reference identity is the formal `release` target, not latest `main`.

Proposed severity contract for Critic review:

**Hard incompatible/failure**

- trusted executable and imported package resolve to different active Bridge source
  identities in a way that can change executed behavior;
- loaded package version/source contradicts the intended locally installed formal
  release identity;
- installed Machine Policy lacks required current capability/support.

**Warning, not automatic incompatible**

- duplicate old package metadata exists but executable/import resolution and final
  loaded source are unambiguous;
- active editable source is dirty but loaded identity is otherwise the intended
  release target;
- locally cached `origin/release` is unavailable or cannot be proven fresh when
  validation was not authorized to fetch.

Dirty active editable source must be printed prominently because its bytes may differ
from the committed release target. It remains a warning in `host validate` unless a
specific protected validation claims byte-exact released runtime. A later release or
machine-update gate that requires an exact candidate may impose a stricter check.

`host validate` remains read-only and does not fetch, upgrade, reinstall or clean
metadata.

### P6 — installation hygiene remains downstream

The Bridge product must expose ambiguity; machine-update/distribution ownership cleans
the installation after final release.

No machine-specific `/users` or `/overflow` path is embedded in product semantics.

## 5. External reality check

Planner rechecked current official sources on 2026-10-01.

OpenAI states that Codex should be productive inside a bounded sandbox; low-risk
ordinary actions should be frictionless, while actions crossing the sandbox boundary
are the ones sent for approval/Auto-review. This supports sandbox-first for ordinary
workspace work, but does not contradict existing upfront authority analysis for known
future effects.

Source:

- https://openai.com/index/running-codex-safely/

Git's current `git-config` documentation states that:

- `GIT_CONFIG` redirects `git config` to the named file and does not affect other
  Git commands;
- `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM` and
  `GIT_CONFIG_COUNT/KEY/VALUE` alter config-source/command-scope behavior;
- current Git source continues to define `GIT_CONFIG_PARAMETERS` as command config,
  and Git's own tests exercise that path.

Git's credential documentation states that the prompt order is
`GIT_ASKPASS -> core.askPass -> SSH_ASKPASS -> terminal`, and that credential
helpers are executable programs; a helper beginning with `!` is a shell snippet.

Sources:

- https://git-scm.com/docs/git-config
- https://git-scm.com/docs/gitcredentials
- https://github.com/git/git
- https://github.com/openai/codex/blob/main/codex-rs/worktree/src/git.rs

These facts make BR-ER-F01 a real safety blocker and support the stable-inspection
design above.

### ER-G8 — real 0.142.0 end-to-end refusal recovery

This is one indivisible final capability gate.

Use:

```text
same final Bridge source candidate
+ Machine Policy generated from that candidate
+ real installed candidate on the test identity
+ codex-cli 0.142.0
+ fresh ordinary consumer repository/task
```

The consumer must not receive a one-off workaround instruction that teaches the
expected answer.

The observed sequence must contain:

```text
one predeclared OPTIONAL effect
-> genuine normal Codex approval/Auto-review refusal
-> executor classifies it as optional/recoverable
-> required repo-local build/QA continues
-> ordinary task-owned commit
-> ai-bridge host publish-current-branch
-> remote SHA == local captured HEAD
-> no second/broader escalation fallback
```

The refusal evidence must come from the real normal Codex approval/Auto-review path,
not from:

- a unit-test exception;
- a fake review response;
- a prewritten rejection file;
- a classifier-only fixture;
- a different Codex version/session later stitched to the build/publication result.

The optional refusal probe itself must be predesigned as bounded and non-destructive;
it must not expose secrets, spend money, allocate resources, mutate production, or
damage the repository. The execution Plan must freeze its exact effect before the
final gate.

If current platform behavior safely approves the probe or otherwise cannot produce a
repeatable real refusal, do not keep escalating until one appears. Record
`ER-G8=UNVERIFIED_REAL_REFUSAL_PATH`; this gate does not PASS and release readiness
cannot claim the refusal-recovery behavior was proven on 0.142.0.

One real refusal is the maximum intentional refusal in this gate. No refusal-chasing
loop is allowed.
