## 0. Executive decision

The proposed next Bridge release is **0.9.0**, handled as **one reviewed workflow/release with bounded internal phases**.

The selected architecture is deliberately asymmetric:

1. **Read-only Git/GitHub diagnostics:** use direct native execpolicy allow rules, but only for command shapes that remain read-only under prefix matching. Do not add read-only wrappers.
2. **Ordinary push to an already-selected existing branch:** current native prefix rules cannot safely express “exact one existing branch, no extra refspec/options, no new remote branch” because Git push accepts suffix refspecs/options and current execpolicy has no end-of-command predicate. Use one minimal Bridge-owned bounded publication primitive, not a generic Git wrapper.
3. **Reviewed worktree bootstrap/rematerialization:** current native policy also cannot express dynamic repo + task + branch + worktree + current-user-authorization identity. Extend the existing Reviewed Handoff product with one bounded materialization primitive; raw arbitrary git worktree add remains gated.
4. **Wrapper minimization:** keep ai-bridge plugin-replay only for its still-distinct unattended installed-production-plugin replay boundary; remove ordinary plugin development/candidate installation responsibilities from it. Do not resurrect candidate-plugin-replay.
5. **Persistent Run progress/ETA:** include it in the same 0.9.0 workflow. Add a small progress observation/reporting contract under Persistent Run and reuse the already-existing Generic Notifier one-shot transport when that delivery surface was separately authorized. No new workflow, controller hierarchy, daemon, mandatory notifier, or intervention authority.

The screenshot reproduction is a required Gate case:

~~~text
current branch = review/01047-clear-writing
origin/review/01047-clear-writing already exists
local branch is ahead by one ordinary task-owned commit
desired effect = ordinary fast-forward publication of current branch only
~~~

0.9.0 must complete that effect without asking the user to authorize the same branch push again, while still refusing a new branch, wrong branch, upstream change, force push, delete, tag publication, extra refspec, or remote remap.

### 1.5 Planner command-shape red-team probe

A temporary disposable Git repository was used only to test Git parser behavior; no user repository, Host Policy, credentials, or remote service was changed.

Observed:

- git remote -v add evil <url> **does create a remote**. Therefore “git remote -v” is not a safe prefix allow.
- git diff --ext-diff, git log -p --ext-diff, and git show --ext-diff executed a configured external diff command. Therefore broad “git diff/log/show” prefix allows are not safe merely because the normal intent is inspection.
- git branch --list followed by deletion options failed closed due conflicting action modes; git worktree list followed by remove failed closed; git tag --list followed by delete failed closed.
- git ls-remote origin followed by an --upload-pack-looking suffix treated that suffix as a pattern after the repository token and did not execute the helper in the probe.
- Canonical diff/log/show forms that disable external diff/textconv and place an option terminator before caller-supplied suffixes did not execute the external diff command.

This environment does not contain a Codex executable, so this Planner round could not run the exact installed-client codex execpolicy check matrix. That is **not an architecture blocker** because the current upstream rule semantics are explicit, but execution Phase 0 must run the candidate matrix through the actual installed Codex CLI before production Host Policy files are edited.

## 2. Product target and non-goals

After 0.9.0, the normal experience should be:

~~~text
observe routine Git/GitHub state
  -> no approval interruption for canonical safe forms

publish current already-selected/tracked existing branch
  -> no repeated authorization
  -> no ability to create/push another remote branch or extra ref

bootstrap/resume exact Reviewed task worktree
  -> same user decision is not requested again
  -> branch/path/base cannot silently change

develop/test plugins normally
  -> official Codex Marketplace/plugin flow

need unattended fresh installed-production-plugin replay over explicit private inputs
  -> retained narrow plugin-replay

run a multi-hour Persistent Run
  -> periodic truthful progress is surfaced through an already-authorized existing delivery surface
  -> ETA is evidence-backed or UNKNOWN
~~~

Explicit non-goals:

- no generic shell/Python allow;
- no danger-full-access;
- no approval_policy=never as a host solution;
- no broad git push origin * rule;
- no generic Git wrapper;
- no wrapper registry;
- no authorization database or durable permission token store;
- no task-state controller hierarchy;
- no fourth workflow;
- no mandatory watcher/daemon/notifier;
- no automatic cancel/restart/resource mutation based on progress;
- no project-specific epoch/sample/file semantics in Bridge core;
- no candidate-plugin-replay resurrection.

## 3. Alternatives comparison

| Alternative | Benefit | Failure/risk | Decision |
|---|---|---|---|
| Direct allow every requested Git/GH prefix | smallest apparent code change | prefix suffixes can widen semantics; raw git push cannot express existing-ref-only/exact-arity; gh auth status can expose token | REJECT |
| Create a wrapper for every Auto-review false positive | easy to bound each command locally | wrapper explosion; duplicates mature native commands; increases maintenance | REJECT |
| Project-local exact branch rules | repo-scoped and superficially close to requested model | still prefix-only; cannot encode remote-exists/current-user-task authorization; rule lifecycle becomes task permission state | REJECT for B/C |
| Keep all Git mutation prompt-only | maximally conservative | reproduces screenshot/worktree failures and repeated user interaction | REJECT |
| Selected hybrid: direct safe read rules + two dynamic bounded effects under existing Host/Review products | native where possible; helper only where dynamic facts are required | needs careful normal-entry gates and helper scope | SELECT |
| Split Persistent Run into a separate workflow/release | smaller individual diffs | adds another governance cycle although no shared-runtime conflict exists | REJECT |
| Include E in same release but force a common controller abstraction with A-D | one abstraction | false coupling and unnecessary state machinery | REJECT |
| One reviewed 0.9.0 release with separate Host-operations and Persistent-observability implementation phases | one user-facing closure without hidden runtime coupling | larger release matrix, but phases are independently testable/rollbackable | SELECT |

## 4. A — Host Policy direct-read design

### 4.1 Selected direct allow matrix

The eventual rules should allow the following **canonical command shapes**, not arbitrary English-equivalent variants.

| Need | Canonical shape | Decision | Reason |
|---|---|---|---|
| status | git status ... | DIRECT_ALLOW | status action has no mutating sibling under the same subcommand |
| repo/ref parsing | git rev-parse ... | DIRECT_ALLOW | local parse/introspection |
| current branch | git branch --show-current | DIRECT_ALLOW | conflicting branch mutations fail closed |
| branch listing | git branch --list ... | DIRECT_ALLOW | explicit list action; mutation options conflict |
| origin URL | git remote get-url origin | DIRECT_ALLOW | replaces unsafe git remote -v prefix |
| worktree listing | git worktree list ... | DIRECT_ALLOW | explicit list action |
| tracked file listing | git ls-files ... | DIRECT_ALLOW | read-only index/worktree query |
| tag listing | git tag --list ... | DIRECT_ALLOW | explicit list action |
| configured remote refs | git ls-remote origin ... | DIRECT_ALLOW | repository token is literal origin; arbitrary URLs/helpers do not match |
| safe working diff | git diff --no-ext-diff --no-textconv -- <pathspec...> | DIRECT_ALLOW | caller suffix is pathspec after --; external diff/textconv disabled |
| safe staged diff | git diff --cached --no-ext-diff --no-textconv -- <pathspec...> | DIRECT_ALLOW | same boundary |
| bounded log | git log --max-count=50 --no-ext-diff --no-textconv -- <pathspec...> | DIRECT_ALLOW | no caller-supplied option/revision after terminator |
| HEAD show | git show --no-ext-diff --no-textconv HEAD -- <pathspec...> | DIRECT_ALLOW | current HEAD only; arbitrary revision/options remain gated |
| GitHub auth state | gh auth status -- | DIRECT_ALLOW | -- ends options; gh implementation requires exactly zero positional args, preventing --show-token suffix from becoming an option |
| repository view | gh repo view -- [repo] | DIRECT_ALLOW | view-only family; flags cannot be appended as flags after terminator |
| PR view/list | gh pr view -- [id/url/branch]; gh pr list -- | DIRECT_ALLOW | read-only subcommands |
| issue view/list | gh issue view -- [id/url]; gh issue list -- | DIRECT_ALLOW | read-only subcommands |
| run view/list | gh run view -- [id]; gh run list -- | DIRECT_ALLOW | read-only workflow inspection |

The exact implementation rule text must be generated only after Phase-0 real codex execpolicy checks prove these shapes on the installed client.

### 4.2 Explicitly not directly allowed

Do **not** add broad allows for:

~~~text
git remote -v
git diff
git diff --cached
git log
git show
gh auth status
git ls-remote <arbitrary repository/url>
gh api
~~~

when those patterns omit the safe canonical boundary above.

Nearby examples that must remain prompt/forbidden/effective-nonallow include:

~~~text
git remote -v add evil <url>
git diff --ext-diff
git log -p --ext-diff
git show --ext-diff HEAD
gh auth status --show-token
git ls-remote --upload-pack=<helper> origin
git ls-remote <arbitrary-url>
gh auth login
gh auth logout
gh repo delete
gh pr merge
gh issue create
gh run cancel
gh secret ...
~~~

### 4.3 Failure semantics

Auto-review/control-plane denial is a **policy result**, not evidence of Git/auth failure.

Host guidance must require this sequence:

1. use the canonical direct-read probe;
2. if it executes and returns an auth/transport error, report the observed failure;
3. if it is denied by policy, report “diagnostic unavailable under policy” rather than “Git auth broken”;
4. do not terminally mark an otherwise recoverable Goal BLOCKED solely from a denied optional diagnostic;
5. only request user action when the required supported diagnostic itself produces evidence that current execution cannot continue.

This is a normal-entry behavioral gate, not merely a documentation sentence.

## 5. B — already-authorized existing task-branch push

### 5.1 Native project/repo-local exact branch rule decision

**Decision: native execpolicy alone is insufficient today.**

The proposed-looking rule:

~~~text
allow prefix: git push origin review/01047-clear-writing
~~~

does not mean “allow exactly this one branch push”. Current execpolicy matches prefixes, while Git push accepts more refspecs and options after the branch. A matching command can therefore widen to additional remote refs or other push semantics. match/not_match examples do not add runtime constraints.

Project-local rules do not repair this: they scope where a static prefix file is loaded, but cannot test that origin/<branch> already exists, that the current branch/upstream is the authorized one, or that this is the same current-user task authorization.

### 5.2 Selected minimal bounded primitive

Add one narrow Host product operation, tentatively:

~~~text
ai-bridge host publish-current-branch
~~~

It intentionally takes **no branch, remote, refspec, force, upstream, tag, delete, URL, or arbitrary Git arguments**. It operates only on the Git repository containing the current working directory.

Required preconditions:

1. resolve canonical repository root from cwd;
2. require a non-detached current branch;
3. require branch.<current>.remote exactly origin;
4. require branch.<current>.merge exactly refs/heads/<current>;
5. verify origin/refs/heads/<current> already exists;
6. fetch the exact origin branch;
7. require behind=0 and ahead>0; divergence or behind state fails closed;
8. internally generate exactly one non-force same-name ref update:
   refs/heads/<current>:refs/heads/<current>;
9. do not use -u/--set-upstream, --force, --force-with-lease, --delete, --tags, --all, --mirror, extra refspecs, remote overrides, or --no-verify;
10. verify remote head equals local HEAD after publication;
11. return an explicit already-up-to-date result when appropriate.

The helper does **not** create authorization. Host/AGENTS/current task context may invoke it only when the user has already authorized the current repo/task branch effect. The helper stores no permission receipt and creates no authorization database.

The machine safety gain is that branch choice is derived from the already-selected current branch and its exact same-name origin tracking configuration rather than accepted from caller input.

### 5.3 Interaction with existing Review publisher

Canonical Review watcher publication stays unchanged in ownership:

- Executor still cannot push;
- watcher validates the Review workflow and publishes the selected Review branch;
- publish-current-branch is **not** a shortcut around Review authority validation.

The new Host operation is for ordinary authorized branch publication when no workflow-specific publisher already owns the effect, including the screenshot case.

### 5.4 Existing raw main push rule

0.9.0 should remove the global direct allow for raw:

~~~text
git push origin main
~~~

after the bounded publisher is proven. The same prefix-suffix weakness applies to main. Main remains low-friction through publish-current-branch when main is the current same-name tracked existing branch.

This is a safety improvement, not a reason to make main more interruptive.

## 6. C — Reviewed worktree bootstrap/rematerialization

### 6.1 Native policy decision

**Decision: a static native rule is insufficient.**

The required safety predicate depends on runtime facts:

~~~text
canonical repo
+ semantic task key
+ derived reviewed/<task-key> branch
+ exact user-selected worktree path
+ task base/current lineage
+ whether remote reviewed branch already exists
+ whether local branch/worktree is missing or already exact
+ current-user authorization of this exact effect
~~~

Current prefix rules cannot evaluate that conjunction. Writing/removing task-specific .codex/rules would turn task authorization into a persistent rule-lifecycle subsystem and would still not solve exact-arity/dynamic lineage checks. It also conflicts with Bridge’s current separation in which project Persistent Run installation does not create project .codex/rules.

### 6.2 Selected bounded Reviewed Handoff extension

Add one sub-capability under the existing Review product, tentatively:

~~~text
ai-bridge reviewed-handoff materialize-worktree   --task-key <semantic-task-key>   --worktree <exact-current-user-authorized-path>   --mode bootstrap|resume
~~~

The current repository is derived from cwd. The helper derives the branch as:

~~~text
reviewed/<task-key>
~~~

and does not accept a caller-supplied branch or remote.

Bootstrap:

1. validate Review is installed and task key is canonical;
2. derive reviewed/<task-key>;
3. derive the base from the Review task’s frozen base branch/commit and require the corresponding origin ref to exist;
4. require no conflicting local/remote reviewed branch;
5. canonicalize the exact requested worktree path, reject symlink/path substitution, occupied unrelated content, repository nesting hazards, or an existing unrelated worktree;
6. create only the derived local reviewed branch/worktree;
7. do not publish a remote branch.

Resume:

1. require exact remote origin/reviewed/<task-key>;
2. verify the remote branch contains the same Reviewed task identity, including the expected task metadata/task_key, rather than trusting the branch name alone;
3. if the local branch/worktree already exists exactly, return idempotent success;
4. if local materialization is missing, restore only the derived branch into the exact authorized worktree path;
5. fail closed on ambiguous lineage, occupied path, mismatched local branch, or another worktree owning the branch.

Authorization boundary:

- frozen task documents provide scope/identity evidence;
- the current user interaction provides bounded authorization;
- local worktree existence is merely materialization state.

The helper does not infer authorization from task_key alone, does not save an auth token, and does not treat historical repo metadata as user authorization.

Raw arbitrary git worktree add, branch creation/switch, remote mutation, force/destructive Git remain on the ordinary approval path.

### 6.3 Recovery

If materialization partially succeeds and later validation fails, rollback may remove only a newly created empty/helper-owned worktree/local branch whose ownership is proven for that invocation. It must never delete a remote branch, unrelated worktree, dirty task data, or pre-existing local branch.

If safe rollback cannot be proven, preserve evidence and stop with an operational recovery result rather than running git clean/reset/delete heuristics.

## 8. E — Persistent Run truthful progress and ETA architecture

### 8.1 Core split: producer owns truth, Bridge owns normalization/projection

Do not make Bridge understand epochs, files, samples, scheduler jobs, simulation replicates, or domain phases.

The project-native run remains the source of truth and exposes a small progress snapshot at its existing heartbeat/checkpoint boundary. Persistent Run standardizes only the reusable observation contract and delivery behavior.

### 8.2 Minimal progress snapshot contract

A project snapshot must provide:

- task/run locator;
- observed timestamp;
- current stage;
- human-readable progress since the previous real event;
- last_real_progress_at.

Optional evidence-backed fields:

- completed_units;
- total_units;
- unit_label;
- expected_finish_at or remaining_seconds;
- eta_basis;
- eta_uncertainty;
- explicit blocked_reason;
- project pace hint when the project can defend normal/slow.

Rules:

- fraction is shown only when total_units is real and positive and completed_units is valid;
- v0.9.0 does **not** invent an ETA estimator from arbitrary heartbeat timing;
- ETA is displayed only when the project/runtime/scheduler supplies a defensible estimate together with basis and uncertainty; otherwise ETA=UNKNOWN;
- blocked requires explicit blocking evidence;
- stalled may be derived only from no movement in last_real_progress_at beyond a task-declared stall threshold;
- slow requires an explicit project pace signal or a material evidence-backed ETA deterioration;
- process/tmux alive by itself never implies healthy progress.

This is an observational payload contract, not a workflow state machine.

### 8.3 Reporter

Extend the existing persistent-run CLI with a small event-driven reporter, tentatively:

~~~text
ai-bridge persistent-run report --progress <project-native-progress-json>
~~~

It:

1. validates/normalizes the snapshot;
2. renders a concise user report;
3. keeps machine-local latest report plus bounded recent report history for reconnect;
4. compares with the last delivered report for real progress and ETA movement;
5. rate-limits/deduplicates according to the frozen Persistent Run contract;
6. optionally projects the report through an already-authorized existing delivery surface.

It does not supervise, restart, cancel, mutate resources, or become a long-running process.

### 8.4 Cadence

The Persistent Run execution contract gains explicit observational settings:

- progress source locator;
- report interval;
- delivery mode;
- stall threshold when meaningful.

Default guidance:

- immediate report at start/resume;
- immediate report at meaningful stage transition;
- periodic active report roughly every **60 minutes** by default;
- repository/task may choose another bounded cadence;
- do not default below **15 minutes** without a task-specific reason;
- report blocked/stalled/runtime failure promptly;
- report runtime completion promptly;
- emit an early report when ETA changes materially.

Material ETA change default:

~~~text
absolute change in expected finish >= max(15 minutes, 25% of prior remaining time)
~~~

and known -> UNKNOWN or UNKNOWN -> known is always material.

The producer invokes the reporter at its existing heartbeat/checkpoint/event boundary. Bridge does not add a mandatory watcher just to create timer ticks. A project with no truthful progress signal can still report stage + last real progress + ETA=UNKNOWN, but 0.9.0 must not claim precise percentage/ETA for it.

### 8.5 Existing notifier reuse, no new notification stack

If Generic Notifier is already configured and the current Persistent Run kickoff authorizes progress delivery on that surface, report uses the existing **one-shot** notifier path. No notifier install is forced and no new polling daemon is required.

The existing structured notifier schema should receive the smallest additive semantics needed for an operational progress event. Preferred design:

- add an operational progress event type, or equivalently an explicitly operational milestone mode;
- use existing Watcher operational authority rather than inventing a new semantic decision-maker;
- prohibit the progress event from claiming task PASS/READY/release success;
- statuses such as running, slow, stalled, blocked, run_complete, run_failed refer only to runtime observation.

Semantic terminal decisions remain Planner/Reviewer/Critic-owned.

If no authorized notifier/delivery surface exists, report persists/queryable local progress and states clearly that proactive external delivery is unavailable. It must not silently install credentials or a notifier.

Notifier/send failure does not cancel the underlying run. Record delivery failure and continue the run unless the task separately made delivery itself a required gate.

### 8.6 Reconnect behavior

The user must be able to query the latest normalized progress and bounded recent history after reconnect without attaching to tmux. The state is observational machine-local evidence, not authorization or workflow state.

## 11. Recovery, rollback, and should-not-change

### Host Policy

- installation keeps the existing Bridge backup/non-destructive install contract;
- if real host validation fails, restore the prior managed Host Policy state rather than hand-editing around the failure;
- never downgrade to broad allow rules to rescue a failed gate.

### Branch publication

- preflight must occur before push;
- no remote creation/upstream mutation is ever a recovery action;
- a failed push leaves the current branch for explicit diagnosis;
- post-push verification mismatch is an operational failure, not permission to force.

### Reviewed worktree

- cleanup owns only helper-created local materialization with proven identity;
- no remote deletion;
- no reset --hard / clean;
- preserve dirty/unrelated data and escalate with evidence.

### Persistent Run

- reporting failure must not kill a healthy underlying run;
- progress state can be rebuilt from the project-native source;
- no reporter result changes the scientific/product completion contract;
- external delivery can be disabled without making Persistent Run itself unusable.

### should-not-change

- Lite / Review / Control remain the only workflow classes;
- Review watcher remains the validated publisher where installed;
- current paid Text/Visual Review budget/authority is untouched;
- Overleaf behavior is untouched;
- plugin candidate install/update ownership remains official Codex + AI_Skills consumer-local where applicable;
- Generic Notifier remains a deterministic transport, not a semantic decider;
- Host Policy continues to reject destructive Git and arbitrary shell/Python execution;
- Persistent Run does not become a scheduler/controller.
