## 1. Planner conclusion

Do not ship another one-command patch.

The next Bridge release should be one bounded **execution-reliability closure**
covering the shared normal-entry failure class exposed by STAT5060 and related
historical Auto-review incidents:

1. ordinary workspace-contained execution must stay in the sandbox instead of
   being pre-emptively escalated;
2. a refusal must be classified before another authority path is attempted;
3. Bridge-owned bounded entries must not silently degrade into broader raw
   operations when they reject an environment;
4. `publish-current-branch` must support the normal GitHub HTTPS + ambient
   Remote/Desktop `SSH_ASKPASS` environment without weakening askpass/transport
   injection fences;
5. runtime identity validation must tell the difference between a correct formal
   release checkout and a genuinely stale/ambiguous runtime.

This is broad enough to treat as a substantial compatible capability stage rather
than a narrow bug fix, so Planner proposes `0.10.0`, not `0.9.4`.

The release must remain backward-compatible. It does not add a fourth workflow,
new state machine, approval store, generalized wrapper framework, or broader raw
Git/shell/Python allowlist.

## 2. What the user should gain

After 0.10.0, a representative long normal task should behave as follows:

```text
authorized task
-> ordinary repo-local build/test/render/QA inside workspace-write
-> optional cleanup denied? skip if not required
-> bounded external/publication effect reached
-> canonical bounded Bridge entry
-> success OR one precise unresolved-effect handoff
-> completed local work remains intact
```

It must not behave like:

```text
optional operation
-> escalation refusal
-> broader fallback
-> another escalation refusal
-> another fallback
-> trajectory termination
```

The release therefore closes a user-visible execution capability, not merely a
single error code.

## 3. Evidence and root-cause split

### 3.1 STAT5060 repo-local build

The affected build/check script writes inside the repository and redirects TeX
runtime state under repo-local `results/` paths. No system write, package install,
PATH mutation, or sudo requirement was found.

Conclusion:

`REPO_LOCAL_BUILD_REQUIRES_ESCALATION = NO`

Owner: Machine Policy behavioral guidance / normal-entry execution.

### 3.2 Optional cleanup

Repo-local generated-cache cleanup was not required for task completion. Its refusal
should not have redirected or blocked the Goal.

Owner: Machine Policy refusal classification / continuation semantics.

### 3.3 Existing-branch publication

Bridge 0.9.3 correctly provided the bounded
`ai-bridge host publish-current-branch` normal entry, but current source rejects
any inherited `SSH_ASKPASS` before constructing the sanitized network environment.

The affected environment used the normal host value:

`/usr/libexec/openssh/gnome-ssh-askpass`

Git documentation confirms that `GIT_ASKPASS`, `core.askPass`, then
`SSH_ASKPASS` can be executable credential-prompt paths. The security concern is
real. The normal-path defect is that the helper currently rejects the ambient
fallback value even when the positive HTTPS path can prove that the value will be
removed before any credential-capable network command.

Owner: bounded publisher implementation and tests.

### 3.4 Raw fallback

After the bounded helper rejected the environment, raw `git push` was attempted.
That widened the effect and bypassed the normal-entry architecture.

Owner: Machine Policy / bounded-entry failure contract.

### 3.5 Runtime identity

The affected runtime loaded Bridge 0.9.3 from the exact formal 0.9.3 release target.
Therefore `main` being four later evidence/closure commits ahead is not runtime
drift.

Duplicate old editable metadata and an `/overflow` source checkout are nevertheless
ambiguous machine hygiene and should become visible diagnostics.

Owner: host/runtime identity validation. Machine cleanup itself is a downstream
installation action, not a reason to change product semantics.

## 4. Alternatives considered

### A. Keep 0.9.3 and patch only SSH_ASKPASS

Rejected as too narrow.

It would fix the final publication symptom but leave the more dangerous failure
class intact: unnecessary escalation of sandbox-capable work and retry cascades after
a refusal.

### B. Globally allow Python/shell or raw Git publication

Rejected.

This would reduce friction by weakening the security boundary and would make the
normal entry less trustworthy. It conflicts with the existing product direction and
OpenAI's sandbox/approval model.

### C. Add a new approval/refusal controller or state machine

Rejected.

The required behavior can be expressed through existing Machine Policy guidance,
bounded helper semantics, and task-preserving failure handling. A new controller,
database, watcher, or authorization ledger would be disproportionate.

### D. Upgrade Codex CLI first

Rejected as a prerequisite.

The user explicitly does not want to update Codex for this closure. The affected
`codex-cli 0.142.0` environment is therefore a required compatibility target for
the real normal-entry gates. A future Codex update may improve behavior but cannot be
used to claim this Bridge defect is fixed.

### E. One convergence release

Selected.

A single 0.10.0 candidate can address the shared route-selection, bounded-entry,
refusal-recovery, and runtime-identity surfaces with one regression bank and one
normal-entry acceptance campaign.

## 5. Proposed production changes

### P1 — sandbox-first Machine Policy guidance

Update the managed Host AGENTS contract so the executor must distinguish
**sandbox-capable ordinary work** from a genuine sandbox-boundary effect.

Required semantics:

- repo/workspace-contained build, test, lint, render, QA, deterministic scripts,
  and generated-file writes use normal `workspace-write` first;
- language/runtime identity alone (Python, TeX, shell script, compiler) is not a
  reason to request escalation;
- only observed evidence that a required effect lies outside the current sandbox or
  authority may trigger the approval route;
- do not add generic Python/shell allow rules.

This is guidance, not a claim that prose can mechanically prove filesystem effects.
Release acceptance therefore requires a real Codex normal-entry gate.

### P2 — refusal/recovery classification

Add a compact shared rule to the managed Host behavior:

```text
OPTIONAL_NOT_REQUIRED
-> skip and continue

SANDBOX_CAPABLE_BUT_ESCALATED
-> retry only through the ordinary sandbox path

BOUNDED_NORMAL_ENTRY_BLOCKER
-> preserve completed work; report/recover only that effect

TRUE_AUTHORITY_OR_SAFETY_BOUNDARY
-> existing approval / HUMAN_ONLY route
```

A refusal must not by itself authorize a broader fallback.

Without new evidence that the required authority changed, do not chain multiple
different escalation requests for the same Goal merely to get around a refusal.

No new persistent state enum/schema is required.

### P3 — bounded-entry no-widening contract

For Bridge-owned bounded execution entries, document and enforce at the behavior
layer:

- success -> continue;
- deterministic rejection -> do not silently invoke a broader raw operation;
- preserve task artifacts and commits already produced;
- identify the unresolved effect and the supported recovery path;
- if the effect cannot be completed legally in the current run, return a truthful
  recoverable handoff rather than converting completed earlier phases into failure.

The first concrete regression is:
`publish-current-branch -> raw git push`, which must not happen automatically.

Planner will inventory current bounded Host entries during implementation planning
and apply this shared contract only where the same reasoning genuinely holds.

### P4 — ambient SSH_ASKPASS-safe existing-branch publisher

Refine the publisher preflight ordering rather than weakening the fence.

Candidate implementation direction:

1. before any remote/network Git operation, locally derive current repo/branch,
   upstream, effective origin fetch/push URL and relevant config;
2. keep rejecting:
   - `GIT_ASKPASS`;
   - any effective `core.askPass`;
   - repo/worktree/command-scope executable credential helper injection;
   - `GIT_SSH` / `GIT_SSH_COMMAND`;
   - custom Git config injection;
   - active hook and existing transport/ref-effect negatives;
3. an inherited `SSH_ASKPASS` alone is not an automatic blocker on the positive
   GitHub HTTPS path if all credential-capable remote/network operations receive the
   sanitized environment that removes it and disables terminal prompting;
4. prove by canary that the ambient askpass executable is not invoked;
5. any remote/network probe performed before sanitization is a blocker to this
   design and must be reordered or replaced.

This is a candidate mechanism, not implementation authorization. Critic should attack
whether any pre-network Git invocation could still execute askpass or another helper.

### P5 — runtime identity diagnostics

Extend the Host validation/diagnostic surface without turning it into a networked
package manager.

At minimum report:

- trusted `ai-bridge` executable real path;
- imported `ai_bridge_kit` source;
- imported package version;
- editable source Git HEAD when applicable;
- dirty source state;
- locally known formal `release` ref/target when available;
- duplicate/conflicting installed distribution metadata;
- active `CODEX_HOME`;
- installed Machine Policy configured/incompatible status.

Hard-failure candidates:

- executable/import resolution points at inconsistent active sources;
- loaded package version/source cannot be reconciled with the intended installed
  release identity;
- required Machine Policy capability is incompatible.

Warning candidates:

- duplicate stale metadata that does not affect actual resolution;
- dirty editable source when it is still the expected release target but local
  uncommitted changes exist;
- local `origin/release` unavailable/stale when no authoritative sync was requested.

The final Plan must freeze which are failures versus warnings.

Do not compare blindly to `main` HEAD.

### P6 — installation hygiene as release consumption, not architecture

After final candidate release/distribution, affected machines should converge to one
unambiguous active Bridge installation.

The product change should make ambiguity observable. The downstream machine-update
owner may then clean stale editable metadata and move the active source away from an
ephemeral/overflow location if the machine policy for that environment requires it.

Do not make machine-specific `/users` or `/overflow` paths part of Bridge product
semantics.

## 6. External reality check

Official OpenAI guidance describes the sandbox as the technical execution boundary:
ordinary low-risk work should run inside it, while actions crossing the boundary are
the small fraction sent to approval/Auto-review. This supports P1/P2 and argues
against pre-emptive escalation for ordinary workspace work.

Sources checked 2026-10-01:

- OpenAI, “Running Codex safely at OpenAI”:
  https://openai.com/index/running-codex-safely/
- OpenAI Alignment, “Auto-review of agent actions without synchronous human
  oversight”:
  https://alignment.openai.com/auto-review

Git's official credential documentation confirms the executable prompt order:
`GIT_ASKPASS`, then `core.askPass`, then `SSH_ASKPASS`, with credential helpers
as a separate external credential mechanism. This supports keeping strict injection
fences while proving that a sanitized positive path cannot execute the inherited
fallback.

Sources checked 2026-10-01:

- https://git-scm.com/docs/gitcredentials.html
- https://git-scm.com/docs/git-config
- https://git-scm.com/book/en/v2/Git-Internals-Environment-Variables

## 7. Proposed capability gates

All gates must run on the same final 0.10.0 candidate.

### ER-G1 — sandbox-first ordinary execution

Real normal Codex entry on the affected `codex-cli 0.142.0` identity:

- run a representative repo-local Python build/check and generated-file workflow;
- no `require_escalated` request occurs solely because it is a build/script;
- result and files prove the requested task actually executed.

Negative neighbor:

- a fixture that truly requires a write outside allowed workspace must not be
  silently treated as sandbox-capable.

### ER-G2 — refusal does not cascade

Representative sequence includes a denied optional operation before required work.

PASS requires:

- optional effect is classified as non-required;
- required normal work continues;
- no chain of broader escalation fallbacks;
- completed artifacts/commit survive;
- final status reflects only unresolved required effects.

### ER-G3 — existing-branch publication in real ambient environment

Real GitHub HTTPS consumer, existing same-name remote branch, local branch ahead.

Environment includes representative ambient `SSH_ASKPASS`.

PASS requires:

- `publish-current-branch` succeeds;
- remote exact SHA matches captured local HEAD;
- no approval interruption;
- askpass canary is not executed;
- no raw `git push` fallback.

### ER-G4 — credential/transport negative matrix

Fail closed before unauthorized executable/network effect for:

- explicit `GIT_ASKPASS`;
- effective `core.askPass`;
- executable repo/worktree/command credential helper;
- `GIT_SSH`;
- `GIT_SSH_COMMAND`;
- custom Git config injection;
- HTTPS fetch / SSH push mismatch;
- SSH/scp/custom transport;
- active pre-push hook;
- wrong repo/branch/upstream;
- force/tag/delete/mirror/push-option/signed-push expansions.

Nearby normal global/system credential-manager HTTPS behavior remains usable.

### ER-G5 — bounded-entry failure preserves work

Cause the bounded publisher to fail on a legitimate negative fixture after a local
task commit already exists.

PASS requires:

- no automatic raw Git fallback;
- local commit/artifact identity remains unchanged;
- final report names one unresolved publication effect;
- earlier build/QA phase is not reclassified as failed.

### ER-G6 — runtime identity truth

Fixtures cover:

1. exact formal release target while `main` is ahead only by evidence/docs -> healthy;
2. stale actual package/source -> detected;
3. executable/import source mismatch -> detected;
4. duplicate stale metadata that does not win resolution -> surfaced with the approved
   warning/failure semantics;
5. dirty active editable source -> surfaced truthfully;
6. correct `CODEX_HOME` Machine Policy identity -> verified.

No network fetch is required merely to run `host validate`.

### ER-G7 — released Reviewed/Host regressions stay intact

Regression bank includes:

- 0.9.0 existing-branch publisher safety negatives;
- 0.9.1 Reviewed bootstrap/resume/materialization;
- 0.9.2 unattended/Persistent Run lifetime ownership;
- 0.9.3 Reviewed first remote publication;
- dangerous raw Git and generic shell/Python remain gated;
- external GPT waiting semantics remain unchanged.

### ER-G8 — fresh end-to-end consumer

Use a fresh, ordinary consumer task with the same shape as the STAT5060 incident:

```text
repo-local implementation/build/QA
-> local ordinary commit
-> existing-branch bounded publication
-> remote SHA verification
```

Inject one optional refused operation before completion.

PASS only if the final candidate completes the task without a false escalation
cascade and without manually patching the consumer prompt.

STAT5060 itself remains historical regression evidence and should not be destructively
reused as the fresh final gate.

## 8. Should-not-change boundaries

0.10.0 must not:

- add a new workflow class;
- change Lite/Reviewed/Controlled/Persistent Run ownership;
- broaden raw `git push`;
- globally allow generic Python/shell;
- introduce `approval_policy=never` or danger-full-access;
- add an authorization database/receipt ledger;
- turn Host validate into an auto-updater;
- require a Codex CLI upgrade;
- reopen 0.9.1/0.9.2/0.9.3 architecture without regression evidence;
- copy workflow-core plugin policy into Bridge beyond Bridge-owned Machine Policy
  normal-entry responsibilities.

## 9. Version decision

Planner proposes:

`0.9.3 -> 0.10.0`

Reason:

This package is not a one-line compatible defect fix. It adds a substantial compatible
user-visible reliability stage spanning sandbox-first execution guidance, refusal
recovery, bounded-entry failure semantics, ambient-host publisher compatibility and
runtime identity diagnostics, with one same-candidate normal-entry gate campaign.

If Critic concludes that one of these components belongs elsewhere or should not ship
together, Critic must identify a concrete safety/recovery coupling problem. Merely
preferring smaller diffs is not enough to split the release into serial patches.

No version bump occurs until implementation forms the final candidate.

## 10. Planning risks requiring Critic attack

1. P4 may accidentally under-model Git credential execution if any pre-sanitization
   Git operation can invoke askpass/credential helpers.
2. P1/P2 are partly behavioral instructions; real normal-entry evidence is necessary
   because source wording alone cannot prove Codex will stop mis-escalating.
3. Runtime identity validation could become too strict and falsely reject a valid
   formal release checkout when `main` has moved.
4. Runtime identity validation could become too weak and merely print ambiguous
   metadata without detecting actual active-source drift.
5. A convergence release could become oversized if it reopens unrelated Reviewed,
   Persistent Run, plugin replay or release-distribution architecture.
6. End-to-end gates must use the same final candidate and cannot stitch success from
   different temporary Machine Policies.
