## 1. 先给判断：新增什么，不重造什么

0.11.0 要解决的不是“让所有 Git 命令免审批”，而是让一项已经选定工作树、分支、目标和权限的任务，在正常 Codex 入口稳定找到执行地点、完整读取强制控制文件、安全同步现有分支，在过期规则或一次错误拒绝后保留成果继续工作。真正涉及危险权限、改变任务边界或无法证明环境安全时必须停止相应效果，不能通过替换工作树、扩大权限或重试来伪装完成。

现有 0.9.0–0.10.0 已有：受限当前分支发布、Reviewed 工作树物化/首次创建/恢复/首次远端发布、持久运行进度标准化与本机历史、沙盒优先、拒绝分类、发布器凭据和配置加固、运行身份诊断。0.11.0 仅对尚未闭合的**普通执行入口**加最小机制，并把前述能力保留为回归要求。四个能力包分别是 A 任务工作树和控制来源连续性、B 当前分支安全 Git、C 机器/项目规则与运行身份就绪、D 授权和拒绝后的恢复连续性。持久运行实际进度送达作为已有能力的有限补齐，不造第五个编排系统。

明确排除 **Program Run**：不规划连续自主发现下一项目任务、长期项目决策、自动验收推进、项目级自主控制器。**Local Autonomous Acceptance Workflow** 已于 2026-10-12 在 Bridge 关闭，并将交付前领域自验收责任移交 AI Skills `workflow-core`；不得建立第四套 Bridge 工作流、Reviewer 状态机、监视器或命令入口。权威定位：`YuukiAS/AI_Skills_Collection@main:docs/plugin-todos/workflow-core.md`，条目 `Final delivery must consume domain-owned self-QA before user-ready completion`。

## 4. 能力包 A：每任务工作树及强制来源连续性

### A1. 任务启动绑定和并行隔离

在任何依赖操作前采集：准确的仓库规范身份、`git rev-parse --show-toplevel`、当前工作树物理/规范路径、当前 HEAD、当前分支与目标分支、`git worktree list --porcelain`、各相关工作树的脏状态和可用性、Goal 声明的强制控制来源。默认“启动此任务的当前 checkout”即任务工作树，除非**当前用户的明确选择或合法冻结任务合同**已经指定另一位置；工作树路径绑定在此任务 Goal/已有执行证据与继续执行上下文，不引入仓库全局任务表/授权数据库。

`tutorial` 与 `hw` 在不同长期工作树并行是**正常成功状态**：不得因共享同一个 Git common-dir 而收拢、移动、detach、切换或统一环境。分别验证工作树所属分支、路径与 HEAD；各自本地 `.venv`、`.r-lib`、未提交文件与生成物不得跨工作树借用。发现旧候选只登记为证据来源，不能改变当前任务绑定。任务 A 不能以任务 B 的工作树执行；需要更换当前工作树时，必须有同一任务的明确迁移意图。

### A2. 真实同分支冲突的无损恢复

先比较原生路线：如果分支实际已在正确任务工作树且其他工作树属于其他分支，**不变更**；只有目标分支被另一工作树占用或用户明确选择迁移才进入恢复。对干净可移动的关联工作树优先官方 `git worktree move`；存在无关脏工作时不得用 `reset/clean/restore/stash` 或盲目 `detach` 取得快进假象。

拟在原生功能不足的、**同机同文件系统普通本地工作树**范围内研究一个受限恢复操作，而非通用 branch/worktree 管理器：精确核对两个工作树、相同 common-dir、所有分支持有者、根路径、未追踪/已跟踪内容与暂存区、外部占用、锁/子模块/符号链接与工作树引用；需要“把原本无关的脏工作保留到另一个位置”时，那个位置必须由当前用户/冻结合同**明确绑定**或已是合法稳定工作树，不能自行创建 `/tmp` 替代。以文件系统内可逆的目录置换/搬迁和官方 `git worktree repair` 为候选，必须证明原始文件、暂存区、忽略/未追踪内容、分支归属和路径重新解析前后不变；任何中断必须留可恢复的精确进度记录/回退指令，而不是靠新控制器。成功迁移后使用**新 Codex 会话**在被选择的路径继续原 Goal，避免仍在被移动目录内运行。

这是当前最需要被 Critic 质疑的工程前提：主工作树不支持 `worktree move`，目录操作不是多对象原子事务，子模块、跨卷、打开句柄、locked worktree、异常稀疏检出可能无安全通用解。对这些邻近情况应在修改前返回 `UNSUPPORTED_WITH_EVIDENCE`，不能伪造恢复成功；而本轮承诺的“双脏、不同分支、同分支目标占用、普通本地工作树”必须通过真实双端字节/索引/HEAD 验证才能发布。若不存在可证明的受限实现，独立 Critic 应要求修改范围/门槛，而不是批准概念包装器。

### A3. 部分克隆中强制来源的可靠读取

优先原生 Git：若对象已存在，直接以**准确远端来源及固定提交**读取；若缺失且触发写受保护 `.git/objects`，研究临时**可写的任务局部对象目录**（由 `GIT_OBJECT_DIRECTORY` 指向），以原对象目录作为只读候补（`GIT_ALTERNATE_OBJECT_DIRECTORIES`），让承诺对象补全只写入授权工作区内的隔离位置。实际使用前验证 Git 子进程是否仍要触碰受保护元数据、读取所需 refs、是否调用配置中的可执行 helper、可否避免 FETCH_HEAD/索引等副作用；失败不重复 escalate。

若普通 Git 命令无法同时证明“当前 repo、`origin`、固定目标提交、唯一仓库相对文件、沙盒内临时写范围、净化的凭据/传输环境、只输出内容”，才提供**一个受限** `ai-bridge host read-control-file` 正常入口（精确命名留给实现合同确认），只接受可信 Goal/当前任务核定的必读文件，不做 checkout、branch/ref/upstream/config/原工作树修改。不可凭 CLI 传入任意 URL/ref/path 就绕过检查。必要时研究现有凭据支持的受限 GitHub 读取作为备用实现，但不能自动改为任意 `gh api` 或秘密外传。成功要求真实 partial clone 中原 `.git` 受保护而 mandatory blob 被完整取得，附文件来源提交与内容校验；读取失败即停在该 source-access gate。

### A4. 强制控制来源未读不得执行

区分当前用户直接发出的 Goal、可信冻结合同、仓库包含的引用路径、实际读入的字节四件事。将 Goal/authority/runtime contract 的所有必读定位汇总为**任务本身已有**读取清单；逐项对上版本/ref/内容验证后才允许安装依赖、环境选择、写候选、渲染或依赖该来源的验证。仅看到路径、引用、记忆摘要、错误的远端版本、目录结构不算已读；失败保留 checkpoint 并停止依赖效果。此机制必须通过真实任务启动入口被消费，不是只在 Goal 里添加一句话。

## 5. 能力包 B：当前分支同步与安全只读检查

### B1. 入站同名已有分支严格快进

提议唯一动态入口 `ai-bridge host sync-current-branch --expected-repo <owner/repo> --expected-branch <already-selected-branch>`，与 0.9.0 `publish-current-branch` 构成“入站快进 / 出站普通发布”对偶，不提供任意 branch checkout 功能。

安全前置条件：当前仓库、工作树、分支、远端 `origin`、同名上游已建立；本地 `refs/heads/X` 的 tracking 正好为 `origin/refs/heads/X`，远端 X 已存在，禁止隐式新分支或换 upstream；初始工作树/暂存区干净（包括有覆盖风险的未追踪内容，具体与 Git 版本对齐）；取回准确 origin/X OID，核实本地 HEAD 是其祖先；只对当前已检出分支严格快进，核更新后的 HEAD == 当前取得的远端提交。清洗 Git transport/config/credential/hook/filter/fsmonitor、强制变更范围和可执行路径；沿用 0.10.0 publisher 的稳定安全视图和 GitHub HTTPS 限制，只有经额外验证的本地纯仓库场景才能另论。网络失败/非快进/dirty/错仓库/错分支/错误配置均不修改目标，或者在运行中失败时明确精确前后状态与人工可恢复性，禁止内置 raw 更宽权限回退。

“直接 `git pull --ff-only origin X`”看似更简单，但前缀规则不能识别 X 是当前分支、是否追踪同名 origin、是否干净、是否有危险额外参数、远端是否可靠，因此**不全局允许**。用户已经明确同一工作分支的普通更新，不应再要求逐字提供 raw Git 授权。

### B2. 本地 Git/GitHub 安全观察：直接规则优先

审查后才扩充 Host execpolicy 的小型**形状可证明安全**原生命令集合：`git branch --show-current`、限定的 `git rev-parse`、`git worktree list --porcelain`、`git ls-files`、安全状态显示、配置好的远端只读信息及窄 `gh ... view/list` 命令；先证明这些固定前缀及其**任意尾随参数**不会开启写入、执行外部程序、读出凭据或跨仓库定位。真实 `codex execpolicy check` 是必要检查，不能仅数规则存在。

特别保守处理 `git diff/log/show`：`--ext-diff`、textconv、pager、属性文件、外部配置、子模块 helper、路径选择和尾随选项可能执行程序或改变作用域。未经净化/结构可证明，不直接开放通用前缀；优先选择原生显式安全参数且实际 execpolicy 验证足够窄的子形状，不成立则保持 gated。拒绝“只因 read-only 子命令名称安全就直接 allow”的形式证明。简单 `git status` 也检查可能的 fsmonitor/index 刷新副作用及受保护 Git 目录，必要时使用只读/无可执行过滤的本机安全方式。

已有 0.9.0 `gh auth status --`、受限列表及发布器不能重复重做。对 `git ls-remote origin` 需先证明有效 fetch URL 不会重写为危险 helper/custom transport；否则经现有动态身份防线处理，不泛化 `ls-remote <URL>`。不为每个常见只读命令建立单独的 Bridge 包装入口。

### B3. 既有包装器裁减

`ai-bridge plugin-replay` 保留既有生产能力与安全回归，开展一次有限只读用途/真实消费清点，与官方本机插件安装、重装、fresh-session 测试比较。其独特的可信本机私有输入、隔离写入与无人值守 child 能力如仍不可替代则保留；若已有成熟正常入口可替代，0.11.0 再提兼容迁移和逐步退役，无真实证据不得突然删除。无新增“万能审批绕行”框架；Reviewed 的现有三个受限功能性入口不是多余 Git status 包装器。

## 6. 能力包 C：规则预算、任务启动就绪与分发身份

### C1. `ai-bridge validate --strict` 的有效指令预算

必须按**实际受影响 Codex 可执行版本**决定发现规则。基于 2026-10-12 读到的当前官方源码模型：选有效工作树/当前目录/项目根，遵循根标记与多层配置可信度；从项目根到 cwd 每层依序检查 `AGENTS.override.md`、`AGENTS.md`、已配置回退名称，**一层取一个**；对每一实际选中文件按原始字节累计并给出剩余额度。全局用户指令和项目预算分开计量；多执行环境的同一总项目预算不能被错误按环境重置；实际版本对空 override/非 UTF-8/符号链接的处理要从源码与新鲜运行复核，不能推断。非自动发现的 Markdown 引用不计入默认预算。

从真正的有效配置中确定 `project_doc_max_bytes`，包括具体 `CODEX_HOME`、项目受信任状态、config 层、启动时 overrides、目录以及根标记；能核实则报告整数和来源，不能观测 session-only 覆盖时明确 `UNVERIFIED`。逐文件记录规范路径、选择优先级、原始 UTF-8 字节数、已读字节、累计/剩余、准确截断字节位置及可能损坏的 Unicode 边界；检查 BOM、CRLF、多字节、有效覆盖、重复托管块/缺少成对标记；托管块只作为文件内部字节计量一次，不能双计。明确指出**哪些尾部没有被加载**，不得只输出“文件太大”。

严格模式中确认超预算、截断有效必需控制文本或托管标记格式损坏时 **非零退出**；未知发现/配置情形返回带原因的未验证，不能 `RULE_LOADING_PASS`。非严格模式保留既有兼容性，允许准确警告。静态预算通过只能称静态验证，通过后仍需真实新会话加载证据，**不可用关键词打印代替**。前述 Bridge 根 39,688 字节作为通用回归；不得为了让测试绿而删改控制语义。

### C2. 任务启动就绪预检：现有命令组合而非控制器

以 `ai-bridge validate --strict --target <bound-worktree>` 和现有 `ai-bridge host validate` 为基础，提供**一次性只读**任务开始就绪结果；如分散入口无法原子绑定身份，可增设一个非常薄的 `ai-bridge host task-preflight` 汇总入口，禁止新状态机、后台服务、自动安装或启动新 agent。输出的是诊断与清晰阻断，不是审批本身。

预检绑定：实际工作树/branch/Goal、实际 `CODEX_HOME`、真正生效的 Codex 可执行版本与配置来源、当前安装的 Host AGENTS 托管块及 execpolicy、项目 root/nested 发现和预算、目标仓库需要的工作流技能是否**真正装入当前 Codex identity**；Bridge 可执行路径、`ai_bridge_kit` 导入真实路径、版本、editable Git HEAD/dirty、Python 分发元数据及冲突；真实远程 `refs/heads/release` / package 两处版本，当前选定正式分发来源，与已安装身份的关系。远程不可达时只标 `RELEASE_REMOTE_UNVERIFIED`，绝不能用本地缓存 ref 冒充新鲜正式版本。

注意启动时机：任意由用户直接打开的原生 Codex 对话不保证先经过 Bridge CLI，更不保证损坏/截断的 AGENTS 会主动调用预检。因此本轮应为**使用 Bridge 作为任务入口的正常路径**安排明确的启动前/首个动作验证，并为绕过该入口的会话诚实标出未覆盖；不得声称“加了一个 CLI 所有 Codex 会话从此强制预检”。Critic 必须核对生产消费点，否则 REVISE。

### C3. 安全修复和同 Goal 恢复

不在运行中的 Codex 会话强求热重载；除非真实 API/Host 权限有可证明的安全更新与生效回执，否则先保存原 Goal/worktree/branch/dirty state/checkpoint 和所有已完成 effects，给出**一次受限外部更新**：由现有 `host install/validate` 在用户允许的活跃 `CODEX_HOME` 上仅修改 Bridge 托管文件、先备份、拒绝链接逃逸/任意配置覆盖，随后开新 Codex 会话，重新按原 Goal 定位、验证并继续。未经本次相应权限不实际安装、不新增网络源、不默改其他 `CODEX_HOME`。已确认同一效果授权不因 fresh session 丢失业务意图；是否被平台审批接受必须由真实入口验证，不能自行取消平台的合法门槛。

### C4. 版本叙述闭环

区分：`main` 开发候选、移动 `release` 正式目标、机器上实际安装并导入的发布包。严格对比来源、SHA、版本和发行元数据，避免 `main` 文档提交导致假漂移；安装冲突严重程度取决于**实际导入的运行代码和命令路径**是否混用，不能把所有多份历史元数据自动判 fatal，也不能把真实冲突一律 warning。正式关闭阶段按现有 AI Skills Maintainer 生产者合同更新 README、CHANGELOG、版本和 `release`，并读回远端验证；**本 Planner 阶段一概不做**。

## 7. 能力包 D：授权、人工专属输入与拒绝恢复

权限区分三层：当前用户在本次会话中给出的具体效果授权；Goal/AGENTS 的任务内容及权限线索（**不能自授权**）；已由用户配置的机器层受边界约束预授权及平台真实沙盒/审批。执行器不能从“repo 文件写了 authorized”推断当前用户已授权；当前用户已经对同一 repo、工作树、分支、路径、来源、用途、外部副作用明确授权后，也不得在后续同一效果内部把一次授权拆成多个 `HUMAN_ONLY` 请求。命令运行被平台拒绝不等于用户不存在授权；要分别报告平台能力/权限边界。

必须 `HUMAN_ONLY` 时，一次说明：**拟执行什么**、**当前已授什么**、**新增或缺失的确切效果/范围**、**为何原授权不能覆盖**；若四项对比后没有新增权限或效果，禁止重复问“是否授权”来掩盖执行路径缺陷。真正必须用户参与的凭据、账号、付费、外部发布、不可逆效果继续使用原审批。

每次拒绝归为 `OPTIONAL_NOT_REQUIRED` / `SANDBOX_CAPABLE_BUT_ESCALATED` / `BOUNDED_NORMAL_ENTRY_BLOCKER` / `TRUE_AUTHORITY_OR_SAFETY_BOUNDARY`。可选诊断被拒继续必须工作；普通沙盒操作误升级则回正常沙盒；受限入口失败只报告该精确 effect 并保留局部成功，不能继续 raw `git push`、任意 `git worktree` 或追加更大升级；真实权限边界进入合法人工/Planner/STOP。相同拒绝未改变来源/效果/运行时信息前只允许一次分类及受限重路由，不能串行请求不同高权限变体。build、render、QA、commit 等已经完成的效果按准确阶段保留，发布失败不使前面实际通过的事实失效，也不代表总体完成。

安全性实质要求：新受限 helper 的形状和默认 preauthorization **不能**让恶意仓库 Goal 单凭文本授予分支拓扑权限。对用户明确要求的工作树搬迁等更高影响效果，只有实际经过一次当前用户指令/受限机器层权限及真实命令安全检查的路径才可执行；不得仅增加一个 `--authorized` 布尔参数当伪授权，不能设 `approval_policy=never` 或关闭沙盒。运行时若既没有可合法执行的受限路径也没有现有平台许可，必须按真正阻断报告，而非使用扩大权限的另一命令。

## 8. 原生机制 vs 受限 Bridge 入口：最小化决定表

| 功能 | 首选成熟原生方案 | 何时需要 Bridge 受限入口 | 明确禁止 |
|---|---|---|---|
| 两个不同 branch 的长期 worktree | 原生 `git worktree` 列表/已有定位；不动 | **不需要**：任务级既有 Goal 绑定 | 自动迁移/合并不同分支 |
| 双脏且目标分支被别处占用 | 支持范围内 `worktree move` + `repair`，或安全的已有目录重绑定 | 仅动态核验、可回退的同一任务**双端**无损恢复，且原生路径不能满足 | reset/clean/stash/force、任意新分支、自动 /tmp |
| 部分克隆缺控制 blob | Git 临时对象库 + 只读候补对象库 | 仅固定仓库/来源提交/必读路径，隔离 Git 写和可执行配置 | 任意 `git show` 放权、受保护对象库写入循环 |
| 当前非 main 同名快进 | 受限 `git merge --ff-only` / 原生 Git 语义 | **需要**：动态核实 repo/branch/upstream/clean/OID/transport | 全局 `git pull`、rebase/autostash、换 upstream |
| 安全本地观察 | 严格检验的原生只读子命令 + 窄 prefix_rule | 一般**不需要**，特殊控制文件读取归上行 | 通用 diff/log/show、外部 textconv/helper |
| 启动规则与身份检查 | 既有 `validate --strict`、`host validate`、Codex 原生发现 | 仅薄聚合读取入口（必要时） | 定时控制器、自动改用户机器 |
| 策略恢复 | 外部一次现有 `host install`，新鲜 Codex 会话 | 不首选自刷新；若需要必须单独证明安全 | 热重载假承诺、越权编辑 CODEX_HOME |
| 运行进度 | 已有 Persistent Run 标准化、本机 latest/history、Notifier | 仅现有任务进程/调度器驱动的**受限发送适配** | 新 watch daemon、假百分比/假 ETA |

取舍：彻底不增加 helper 的原生路线对不同分支并行及部分安全只读完全成立，应优先采用；但对于**同分支动态归属、两个脏工作树无损置换、精确远端来源、当前分支 fast-forward**，静态前缀规则无法同时表达所有判断。批准额外 helper 的必要条件是它减少真实重复授权并可从可信普通入口消费，且其内部真正比 raw Git 窄；否则退回原生或诊断阻断。绝不把所有 Git 命令纳入一个新的“大包装器”。

G01/G02区分“不同分支应保持原样”和“同分支真实冲突需受限变更”；G03/G04区分“取到源的可靠性”和“未取到不能执行的顺序性”；G07/G08区分静态预算和真实会话消费；G09关乎配置和恢复；G10/G11区分权限来源和拒绝后的实际轨迹。G13 是发行集成证据而非重复功能测试。若实施表明某 Gate 无法通过且属于已承诺核心行为，返回 Planner/Critic 改设计，不换假样本降低门槛。

## 11. 安全、失败恢复与角色/权限边界

- **当前阶段**：Planner 只写此文档；Critic 独立核实并对 v0.1 给 `PASS` 或 `REVISE`。PASS 仅批准设计，不批准 implementation、Machine Policy、CODEX_HOME、消费者修改或移动 release。
- **后续若 PASS**：Planner 按角色合同另备一致版本的完整执行 Plan、Canonical Goal、Kickoff Draft 给 Critic 做 execution-ready review；这不是本轮已授权的实现动作。本次不提前写高权限 Codex 执行提示词。
- **本机权限**：裸 Git 危险变更、机器策略写入、发布 ref、外部/付费/凭据、跨 repo 消费者更改，均需所适用的用户实际授权/平台准许；不生成通用 allow、`danger-full-access`、`approval_policy=never`、脚本/R/Python/shell 任意执行预授权。
- **可恢复但不虚假完成**：一次外部更新 + fresh session 是被接受的安全路线；工作树重绑定失败时保留两个 dirty 集合及恢复证据；partial clone 读不到强制文件则停依赖操作；发行未完成则不可宣称全面交付。
- **不新增**：权限数据库、程序级任务控制面、新工作流/状态机、无穷重试、每个拒绝一层包装、repo-specific STAT5060/Lucerna 判断；AI Skills 领域 QA 不归 Bridge。
- **进度残余**：不把 Persistent Run 的本机报告器变成自动控制器；来源任务应提供真实进度，交给既有可用通知器；没有已授权投递表面时不宣称用户会自动收到消息。
- **应中止和回 Planner 的条件**：受限双脏恢复不可能实现而核心 Gate 要求不变；字节规则与目标运行时发现行为无法核实；新 helper 需要更大 Git 权限/新的平台授权方案；Host Policy 执行前验证不能接入真实任务入口；已有发布能力产生安全回归。实现中的局部修复不改变方案时不为每条 bug 重新发起审查。

## 12. 0.11.0 如何既不过重也不过简

只改常见开发时必经的四个接缝：工作地点和强制资料、已有分支与安全诊断、有效规则与环境、拒绝后的相同效果恢复。所有“更大更好的长期运行”想法都没有自动成为新能力，第三方原生 Git 优先复用；候选新增受限入口总数保持非常少，每一个都须说明静态规则无法核验的动态安全条件。现有 Reviewed 和持久运行语义不被升级成统一控制器。

反过来，只写“注意遵守 AGENTS，不要申请权限”又太简：39,688 字节根文件在默认预算下可能先被截断，partial clone 对象写受沙盒限制、Git 分支持有人与 dirty 状态不能靠自然语言安全检查、当前实际安装身份可能不同于仓库版本。这些需要真实正常入口与受限代码逻辑。**以真实用户行动次数减少、任务不漂移、控制源真正消费、危险邻近行为仍拦截，以及一次失败后成果保存作为成败标准；不以新增规则/包装器/回执数量作为成就。**

## 13. Critic 特别需要独立反证的六点

1. 双脏工作树恢复：主工作树不可 `worktree move`，受限置换能否在实际受支持文件系统安全实现并自动回滚？是否应按路径/工作树类型收窄支持，而不是为了“无损”发明更危险的通用 Git 事务？
2. `GIT_OBJECT_DIRECTORY` + 只读候补对象库能否在当前 Git/partial clone/沙盒中真正完成缺 blob 读取，是否隐含 `.git/FETCH_HEAD`、配置 helper 或新权限写入？有无不增加 wrapper 的更成熟路径？
3. `prefix_rule` 对尾随参数与环境的匹配是否足以直接放行所选 Git/gh 命令；尤其 `status` 的 fsmonitor、`show/diff/log` 的可执行扩展和 `ls-remote origin` 传输重写？
4. 有效项目指令预算是否忠实于**实际受影响安装版本**，而不是照抄 2026-10-12 官方 main 的源代码；32,768 字节截断、空 override、配置可信度、工作目录和跨环境累计的关键条件是否准确？
5. `host task-preflight` 的真正消费点能否防止规则截断后继续进行实质工作；当前 CLI 组合是否足够，还是“新命令存在≠运行前必调用”？
6. 已经直接授权的效果与平台 sandbox/Auto-review 拒绝如何在**不建立授权数据库、不信任仓库自称授权、不加 broad allow**前提下形成合法一次执行路径；0.10.0 启动器层拒绝不能冒充新鲜 child 的真实拒绝证据。
