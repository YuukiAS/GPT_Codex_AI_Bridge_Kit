## 2. 正面完成标准：普通用户从零到可用

最终 0.11.0 必须让普通用户完成以下旅程，而不理解 Bridge 内部 object store、journal、execpolicy 或状态 JSON：

1. **新机器**：安装 Bridge，`host status/install/validate` 明确当前 executable/import/source/CODEX_HOME/Host Policy；未做远端读取时 remote release freshness 明示 `UNKNOWN/UNVERIFIED`。
2. **新项目**：`ai-bridge init` + 一次 `ai-bridge validate --strict` 完成 setup/诊断；日常任务不要求每次先手敲 strict validator。
3. **Lite 日常任务**：`ai-bridge task run --target <repo> --task-key <task_key>` 自动 preflight mandatory sources/instruction budget/Host/worktree，然后才启动真实 Codex；失败直接给用户可读原因和最小恢复。
4. **Reviewed/Control**：继续使用既有正式入口；只在真实产品风险需要时选择，不因为运行时间长而升级工作流。
5. **branch/worktree recovery**：现有 non-main strict FF保持；受支持 reciprocal linked-worktree conflict由正常 Reviewed recovery自动识别 A/B/T，用户只收到一条准确自然语言授权请求，不手工拼 `exchange-worktrees` 参数。
6. **Persistent Run**：Task Writer先判断live/scheduler/service/terminal-owned四种lifetime；只有terminal-owned survive-disconnect使用 `persistent-run start`。启动新primary前必须证明当前Codex UI与Bridge reporter都能连接同一个官方shared app-server；否则 `PROGRESS_THREAD_SHARED_APP_SERVER_UNAVAILABLE`。
7. **Notifications**：machine配置仍用 `ai-bridge notifier configure`；project override唯一入口为 `notifier configure --scope project --target <repo>`，支持partial inheritance；legacy无scope `private sync --profile notifier` 仍保持project-local。
8. **状态诊断**：Host、task readiness、Persistent Run、Notifier、Reviewed均有正常 status/validate入口；用户不读内部 JSON。
9. **正式身份**：产品版本始终 0.11.0；冻结候选按 `0.11.0-rc.N @ SHA`；正式 `release` 只有用户另批 exact old SHA -> exact candidate SHA 后才推进并远端读回。

## 3. Lite / readiness / partial clone

### 3.1 Lite normal entry

README 必须正式说明：

`ai-bridge task run --target <repo> --task-key <task_key>`

它不是新 workflow，只是已有 Lite task 的受检启动器。它必须：

- 在 child 启动前重新读取当前 frozen task和 mandatory source；
- 核 Host/CODEX_HOME/Bridge identity、worktree/branch、instruction byte budget；
- 对 partial clone 缺 blob 自动使用现有 isolated mandatory-source reader；
- preflight失败时 child process=0，并说明 exact失败项、没有启动 Codex、最小恢复和“修复后重试同一 task”。

用户不得被要求手工设置 `GIT_OBJECT_DIRECTORY`、alternate objects、blob OID。

### 3.2 `validate --strict`

定位为：
- 新项目 setup；
- Bridge/项目升级后检查；
- readiness问题诊断。

日常 `task run` / Reviewed launch 必须自己消费同一 preflight；单独 validator PASS不能代 normal-entry Gate。

## 4. G02 reciprocal worktree recovery

`exchange-worktrees` 保持 narrow recovery helper，不成为普通用户每日命令。

当 Reviewed materialize/bootstrap发现：
- desired path A被 branch B占用；
- branch A又恰在 linked worktree B；
- 两树同 common-dir、非main、同filesystem、无submodule/symlink/lock/活跃进程等禁止项；

Bridge/Codex自动：
- 从 registry + frozen task确定 A/B/expected branches；
- 选同 filesystem空闲 sibling T；
- 生成 exact三步 move和最终归属；
- 向用户只问一次是否授权这一次位置交换；
- 获准后调用现有 helper。

失败/不支持必须保留原数据并说明；禁止 reset/stash/clean或要求用户自己拼复杂参数。

## 5. Persistent Run 完整产品合同

### 5.1 execution lifetime

Task Writer冻结任务时必须明确：
- ordinary live；
- scheduler-owned；
- existing service/job-owned；
- terminal-owned survive-disconnect。

只有最后一类进入 Bridge tmux Persistent Run；scheduler/service继续由原owner管理，不因为多小时运行就再套tmux。

### 5.2 normal entry

用户发送由：

`ai-bridge persistent-run prompt kickoff --target <repo> --goal <goal>`

生成并绑定 frozen Goal/hash/run key/资源边界的 kickoff 后，Codex使用：

`ai-bridge persistent-run start --target <repo> --goal <goal> --expected-goal-sha256 <hash>`

`start` 是受限、幂等start-or-resume helper：

1. 只解析frozen Persistent Run contract；
2. 使用frozen `Launch argv JSON` / `Resume argv JSON`；
3. **新primary之前先证明shared app-server topology可用**；
4. 只有shared server成立才create/reuse Progress thread并机械验证isolation；
5. 无active run时由run-scoped supervisor启动primary child + reporter child；
6. 有同hash/run key兼容run时只resume，不重复primary；
7. reporter损坏但primary仍活着时只恢复reporter；
8. primary terminal后最后runtime snapshot + reporter cleanup；
9. 不申请scheduler资源、不改data/model/budget/scope；
10. 不成为Bridge daemon/controller。

### 5.3 shared app-server ownership

正式Progress thread必须由**当前用户Codex UI正在使用的同一个官方shared app-server**承载。

合法拓扑只有：

- **local shared daemon**：同一 `CODEX_HOME` 当前正常Codex实际连接的local daemon；
- **exact explicit remote**：当前Codex已绑定的exact remote app-server，Bridge取得可信current-session endpoint/backend binding。

Bridge只discover/connect，不调用Codex `daemon start/restart/update/bootstrap`，也不创建自己的app-server daemon。

正式生产路径禁止为了Progress thread另起独立embedded app-server。

以下情况在新primary之前失败：

`PROGRESS_THREAD_SHARED_APP_SERVER_UNAVAILABLE`

包括：
- `--no-daemon` 且无exact remote；
- embedded-only；
- workload-identity/incompatible override导致UI没有共享server；
- remote endpoint不能从trusted current-session binding取得；
- server version/protocol不兼容；
- 无法证明viewer/reporter同server。

恢复提示只要求用户通过同一 `CODEX_HOME` 的普通Codex入口，或原来同一个explicit remote normal entry重新打开/恢复任务；不要求手工找socket/path。

### 5.4 shared-server run binding

Machine-local binding至少保存非secret：

- codex_home identity；
- app_server_kind；
- sanitized endpoint fingerprint；
- backend identity；
- running app-server version；
- progress_thread_id；
- thread safety/config fingerprint；
- exact run/task/Goal identity。

不保存remote auth token。每次reporter reconnect重新discover shared server并比对binding；不能只凭thread ID跨server/CODEX_HOME/store。

### 5.5 progress truth / cadence

项目原生launcher/task/scheduler/service是truth owner，Bridge只规范化。completed/total、ETA、heartbeat/checkpoint规则和v0.4完全保持；无依据就`UNKNOWN`，tmux/PID不推断领域progress。

cadence保持：
- start/resume、meaningful stage、stalled/blocked/failed、runtime completion、material ETA可立即；
- active默认约60min；
- 无任务特定理由不得低于15min；
- known↔UNKNOWN永远material；
- material ETA公式保持；
- observation与last logical delivery分离；
- fraction/count普通变化不刷屏；
- 高频observation不饿死cadence。

### 5.6 Progress thread safety

每run一个non-ephemeral dedicated Progress thread；exact thread ID为identity，name只用于发现；不写原Executor/task thread；不做Planner/Reviewer/Executor；不拥有semantic completion authority；canonical snapshot先由Bridge确定。

复用official temporary structured helper deny-config，但 `ephemeral=false`。任何render前机械关闭execution/external tool surface；无法证明则0 render turn。

### 5.7 0.160.1 persistence + viewer/reporter canary

顺序固定：

1. 确认current UI shared app-server topology。
2. reporter client连同一server。
3. `thread/start` non-ephemeral Progress thread。
4. 首turn前机械isolation。
5. 第一个bounded render。
6. 首turn完成后验证materialized/history。
7. 第二个viewer/UI client连**同一个shared server**并打开exact thread。
8. viewer看见history时，reporter执行第二个且最后一个development render。
9. viewer看见第二条更新；不得出现 `active writer` conflict。
10. disconnect后按同server binding + exact thread ID cold resume。
11. 原Executor/task thread前后不变。
12. canary结束无新消息。

不要求首turn前cold resume。

### 5.8 bounded render / status

每logical delivery最多一个turn；开发canary最多1 thread + isolation PASS后2 turns；frozen contract有render-turn ceiling；pending coalesce；foreign/business input污染后停止。

`persistent-run status` 额外显示shared app-server kind、nonsecret endpoint/backend fingerprint、running version、binding state，并继续显示run/reporter/progress/ETA/thread/runtime/isolation等v0.4字段。

## 6. Notifications / Gmail 产品合同

Gmail-only、App Password、machine profile、task intent、Lite automatic completion=UNSUPPORTED、manual/automatic authority分离全部保持。

### 6.1 provider

0.11正式provider仍为：

`smtp.gmail.com:587 + STARTTLS + App Password`

不新增generic SMTP/OAuth/Workspace relay。

### 6.2 machine / project configure唯一语法

Machine：

`ai-bridge notifier configure`  
等价 `--scope machine`。

Machine clear：

`ai-bridge notifier configure --clear`  
等价 `--clear --scope machine`。

Project override：

`ai-bridge notifier configure --scope project --target <repo>`

Project clear：

`ai-bridge notifier configure --clear --scope project --target <repo>`

Project override支持**partial inheritance**：

- field未写 = 继承machine；
- 只改recipient/from/prefix不复制、不提示machine App Password；
- project Gmail account不覆盖时credential继续继承machine；
- 只有用户明确选择project account override时才输入对应project App Password。

### 6.3 clear / revoke

`configure --clear` 只删除Bridge本地profile，不撤销Google账号端App Password。

README/help/status必须告诉用户：若要provider-side失效，需要到Google Account App Password设置撤销。Bridge 0.11不修改Google账号安全设置。

### 6.4 config layering / private sync compatibility

字段级优先级：

`machine < project < process env`

`notifier status --target <repo>` 按字段显示nonsecret source；password只显示configured/inherited/missing。

Legacy行为必须保留：

`ai-bridge private sync --profile notifier`

无 `--scope` 时仍是**current project local**，写 `.ai-bridge/private/notifier.env`。

新增显式同义：

`ai-bridge private sync --profile notifier --scope project --target <repo>`

Machine rclone恢复只有：

`ai-bridge private sync --profile notifier --scope machine`

绝不把已有project secret静默迁到machine。

### 6.5 task intent / Control authority

Project defaults与Lite/Reviewed行为保持v0.4。

Control必须按既有authority：

- Planner读取project default/override后，只在 `PLANNER_DRAFT.md` 提议resolved Notification Intent；
- Critic独立审查，并由Critic写/冻结 `FROZEN_CONTRACT.md`；
- automatic Control notifier只消费Critic frozen contract；
- runtime不读取Planner draft重新授权。

Lite automatic semantic completion仍`UNSUPPORTED`。

### 6.6 manual / automatic / semantic authority

Manual `send/send-test` one-shot保持。

Automatic Persistent/once/run/Reviewed/Control必须读frozen intent。

Reviewed与Control automatic semantic completion仍验证现有真实decision artifact，不能信brief里伪造的 `decision_authority`。

### 6.7 status / progress mail

Notifier status继续显示Gmail provider、ready/config source、sender/recipient、last test/send/failure/suppression且不显示secret；现在还必须显示project partial inheritance与clear后“provider credential revocation not performed”。

Progress邮件完整字段和UNKNOWN语义不变。
