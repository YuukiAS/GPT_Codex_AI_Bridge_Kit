## 2. Current upstream reality rechecked

### 2.1 Execpolicy `prompt` is a routing decision, not a stored authorization

Current Codex source distinguishes:

```text
Decision::Allow
Decision::Prompt
Decision::Forbidden
```

A `prompt` result becomes an approval request only when the effective approval policy permits surfacing it. It is not a receipt that says a previous user message has already approved the effect.

Current source also distinguishes policy-rule prompts from sandbox prompts and can reject either according to the effective approval policy.

### 2.2 Auto-review is a reviewer, not a deterministic Kickoff authorization consumer

Current Codex config exposes:

```text
approvals_reviewer = user | auto_review
```

and documents `auto_review` as a risk-based subagent that gathers context and independently approves/denies an approval request.

Current execpolicy rule syntax has no supported per-rule field that says:

```text
this prompt is already authorized by message X
```

or:

```text
reviewer = current-user-kickoff
```

Public upstream issues also reproduce the same class of reality: explicit user authorization can still be rejected by automatic approval review, and prompt rules cannot currently force or encode a different reviewer per rule.

Therefore the prior assumption:

```text
current-user Kickoff
+ decision=prompt
+ approvals_reviewer=auto_review
=> automatic consumption of the Kickoff
```

is unsupported and has now failed in the real target environment.

### 2.3 Sandbox is an independent boundary

Current official permission instructions state that `workspace-write` allows writes to:

- cwd;
- configured writable roots.

Writes to other paths require extra permission/escalation.

The real sibling path:

```text
/home/yuukias/AI_Skills_Collection-workflow-core--reviewed-first-bootstrap-normal-entry
```

is outside the Bridge execution cwd and is not proven by current evidence to be a baseline writable root.

Therefore the real run stopped too early to prove whether sandbox would also reject sibling creation after approval. That second blocker remains **UNRESOLVED**, not disproven.

### 2.4 Execpolicy `allow` has a materially different execution effect

Current Codex source explicitly treats an execpolicy `allow` match as an auto-approved command and, when every command segment is explicitly allowed, reports:

```text
bypass_sandbox = true
```

The current permission instructions likewise state that an execpolicy allow can take precedence over normal sandbox approval behavior.

This means a genuinely safe allowlisted Bridge executable can solve **both** layers:

- approval reviewer no longer decides the command;
- workspace-write sibling-path restriction is bypassed for that trusted executable.

But this is safe only if every possible invocation under the allow rule is itself bounded enough to be trusted.

### 2.5 Current upstream has no mature task-scoped permission profile for this use case

Current Codex supports project/user `.rules` layers and supports sandbox `additional_permissions`, but neither is a drop-in mechanical transport for the already-sent Kickoff:

- prefix rules are token-prefix rules, not end-of-command rules;
- project/user rule files are configuration state, not authenticated projections of a chat message;
- automatic approval of a permission request is still routed through the approval reviewer;
- there is no current supported execpolicy primitive that grants an exact task-scoped filesystem capability to one matching command while independently binding that grant to a previous chat authorization;
- a public upstream proposal for command-matched bounded permission profiles is still a proposal, not current production functionality.

## 3. Failure attribution

### A. Execpolicy layer

**Working as configured.**

The installed rule matched the intended command and correctly produced `prompt`.

The failure is not “prefix rule missing”.

### B. Approval / Auto-review layer

**Primary observed rejection layer.**

The `prompt` created an approval request. With `approvals_reviewer=auto_review`, that request is reviewed by the automatic risk reviewer.

There is no mechanical guarantee that the reviewer treats a prior Kickoff as an already-consumed approval. The real reviewer denied the request.

### C. Sandbox layer

**Potential second blocker; not yet observed to completion.**

Because approval rejected before execution, the real sibling write never reached the sandbox execution phase.

Under baseline `workspace-write`, the sibling path is outside cwd and therefore cannot be assumed writable.

Any repair that only changes `prompt -> approved` without proving the sibling write path is executable is incomplete.

### D. Bridge helper

**Functional exact-effect checks are present, but its trust class is currently mismatched.**

The helper already:

- derives branch from task key;
- checks repo;
- checks exact worktree assertion;
- checks base ref/commit;
- rejects existing local/remote task branch;
- checks symlink/path conflicts;
- creates only local branch/worktree/control files;
- has bounded rollback.

However the current CLI still lets the caller select target/worktree/base assertions. That is appropriate when a human approval layer authorizes an exact instance, but not sufficient by itself for a broad permanent `allow`.

### E. User/Kickoff

**Not missing.**

The current user had already explicitly authorized the exact AI_Skills effect.

The failure is transport/enforcement between that authorization and Codex's executable permission layers.

## 5. Alternatives

### Option A — keep `prompt + auto_review`, improve wording

**REJECT.**

Reason:

- the real target run already rejected;
- current upstream defines auto-review as a risk-based reviewer, not a deterministic parser of the user's Kickoff;
- execpolicy prompt rules cannot bind themselves to a specific prior authorization message;
- better justification text may change reviewer behavior but does not create a mechanical authorization contract.

This would repeat the failed assumption.

### Option B — temporary exact task-scoped execpolicy allow

**NOT SELECTED as the product mechanism.**

This is attractive in principle because an allow would bypass both approval and sandbox for the exact command.

However current execpolicy only supports token-prefix matching.

A static “full command” rule is not automatically exact because suffix tokens can be appended. The present argparse command also accepts repeatable option occurrences in the ordinary Python argparse sense, so a suffix could potentially override a previously matched safety-critical option unless the CLI is additionally hardened.

A literal `--` terminator plus duplicate-option rejection could make an individual command shape end-safe, but a second problem remains: **provisioning the temporary rule itself**.

Current Codex has no supported mechanism that mechanically converts the current user Kickoff into a same-session temporary execpolicy allow without another approval/configuration transition. Project-local rules are loaded from project config layers; user/global rules are Machine Policy state; approval-driven in-memory amendments require an approval decision.

Therefore B moves the unsolved authorization problem from “bootstrap” to “install the temporary allow”. It is suitable only if a separate trusted provisioning channel already exists. The current product does not have one, and adding one here would become Option C/framework creep.

### Option C — one-shot local authorization artifact / helper-consumed receipt

**REJECT for this recovery.**

A plain local artifact written by Codex is not evidence of user provenance: the same Codex process could manufacture it.

Making it trustworthy would require one of:

- user-created secret/token;
- signature/key;
- trusted writer;
- approval-backed provisioning;
- persistent authorization service/state.

Those are exactly the token/receipt/auth-framework mechanisms this recovery must avoid.

### Option D — permanent allow for the current arbitrary bootstrap command

**REJECT AS-IS.**

The current helper accepts caller-selected target/worktree/base assertions.

Permanently allowing that current shape would let any Codex invocation choose a new local Reviewed topology in another repo/path, subject only to helper checks. It would also bypass the sandbox.

That is broader than the intended product permission.

### Option D' — permanent allow for an intrinsically safe canonical bootstrap profile

**SELECTED.**

The key change is not “trust arbitrary bootstrap”. It is:

> narrow the executable behavior of `task bootstrap` so any invocation that reaches Git mutation is already inside one canonical, reversible, local-only Reviewed bootstrap class.

Then permanent Machine Policy `allow` authorizes a **safe capability class**, while the Kickoff still chooses the workflow task instance and supplies equality assertions.

This is the same architectural principle already used by other Bridge trusted helpers: Machine Policy trusts a Bridge executable only after the executable itself mechanically prevents scope expansion.

### Option E — project rules / additional permissions / other official scoped mechanism

**NOT SELECTED.**

Current project-local rules can scope configuration to a trusted project, and current permission requests can ask for exact additional filesystem paths.

Neither gives a zero-interaction binding from a previous Kickoff to this exact task:

- project rules still need to be provisioned/loaded;
- additional filesystem permissions still pass through approval routing;
- there is no current rule-level reviewer/authorization-message binding;
- current upstream's command-matched bounded permission-profile proposal is not yet a released mechanism.

If OpenAI later ships a mature task/command-scoped permission grant, Bridge should prefer it over custom policy logic.

## 6. Selected repair: canonical safe first-bootstrap capability

### 6.1 Machine Policy

Change 0.9.1 first-bootstrap rule from:

```text
task bootstrap -> prompt
```

to:

```text
task bootstrap -> allow
```

**only after** the helper is hardened so mutation cannot escape the canonical safe profile below.

This is not permission for arbitrary raw Git or arbitrary bootstrap topology.

Raw `git worktree add` remains prompt.

`materialize-worktree` remains its existing artifact-bound allow.

### 6.2 Canonical safe profile

Before any branch/worktree mutation, the allowlisted bootstrap must require all of the following.

#### Target repo

- target resolves to a real Git repository with Reviewed Handoff installed;
- target top-level identity equals the current command's intended target repo;
- `--expected-repo` equals the repository's actual origin identity;
- no remote mutation occurs.

Implementation should prefer running the command with cwd at the target repo and must not silently redirect to another repo.

#### Task / branch

- task key passes the existing semantic new-task validator;
- branch is only `reviewed/<task_key>`;
- no caller branch argument exists;
- local task metadata absent;
- local task branch absent;
- remote same-name task branch absent.

#### Canonical worktree path

For the permanently trusted path, the only executable worktree locator is the deterministic sibling:

```text
<target-parent>/<target-repo-name>-<task_key>
```

The existing `--expected-worktree` becomes an equality assertion against this derived path.

Any other path returns before Git mutation with a result equivalent to:

```text
NONCANONICAL_BOOTSTRAP_REQUIRES_SEPARATE_AUTHORIZATION
```

It must not run a different raw Git fallback.

For the real target:

```text
target:
/home/yuukias/AI_Skills_Collection

task:
workflow-core--reviewed-first-bootstrap-normal-entry

derived canonical sibling:
/home/yuukias/AI_Skills_Collection-workflow-core--reviewed-first-bootstrap-normal-entry
```

which is exactly the user-authorized worktree.

#### Base

The trusted profile is limited to:

```text
expected-base-ref = origin/main
```

and:

```text
expected-base-commit == current local refs/remotes/origin/main OID
```

The helper itself does not perform network fetch under this allow.

The normal workflow performs the already-low-risk `git fetch origin main` before bootstrap, freezes the OID in the Kickoff/effect, and the bootstrap only verifies equality.

A stale/different commit fails before topology mutation.

This prevents a caller from using the permanently allowed helper to choose an arbitrary historical/local commit as the bootstrap source.

#### Path safety

Retain:

- lexical absolute comparison;
- symlink/path-redirection rejection;
- occupied/registered/unrelated worktree rejection;
- no force;
- no alternate path.

### 6.3 Checkout executable fence

Because an execpolicy `allow` can bypass the outer sandbox, the helper must not let repository-controlled checkout execution become an arbitrary-code escape.

Before `git worktree add`, fail closed if the effective checkout can execute repository/config-provided programs through at least:

- active `post-checkout` hook, including effective `core.hooksPath`;
- configured external smudge/process filter drivers relevant to checkout.

The simplest safe 0.9.1 recovery is conservative:

```text
active checkout hook/filter executable
-> BOOTSTRAP_CHECKOUT_EXECUTABLE_REQUIRES_SEPARATE_AUTHORIZATION
-> no branch/worktree mutation
```

Do not silently disable a repo's legitimate hook/filter merely to pass the gate.

This fence is required specifically because Git documents that `git worktree add` performs checkout and runs the `post-checkout` hook, and checkout filters may invoke external smudge/process commands.

The real AI_Skills FB-G1 must demonstrate this fence is clear on the target repo.

### 6.4 No network / no remote publication inside bootstrap

The trusted bootstrap helper must not:

- fetch;
- push;
- create a remote branch;
- change upstream;
- modify remote;
- access a provider API.

It only uses the already-fetched local `origin/main` tracking OID and creates local branch/worktree/control files.

This sharply limits the effect of permanent allow.

## 7. What “current-user Kickoff = authorization” means after this amendment

Current Codex does not expose a trustworthy local primitive that lets Bridge cryptographically or mechanically prove:

```text
this CLI invocation came from user message X
```

The recovery must stop pretending otherwise.

The revised split is:

```text
current-user Kickoff
= workflow authority selecting the exact task/effect Codex is allowed to attempt

CLI assertions
= equality checks against the derived canonical effect

Machine Policy allow
= standing permission for the intrinsically bounded canonical bootstrap capability

Bridge helper
= mechanical enforcement that the attempted effect cannot leave that safe class
```

The Kickoff is still required by workflow policy. A Codex invocation that invents an unrequested task violates workflow authority.

But machine safety no longer depends on Auto-review correctly understanding conversation history. It depends on the helper being safe for every accepted invocation.

This is the only current-platform route found that satisfies:

- one Kickoff;
- no second user action;
- real sibling write;
- no broad shell/danger-full-access;
- no auth framework.

## 9. CLI hardening for prefix-rule safety

The permanent rule remains a prefix rule, so the helper/CLI must be robust against suffix manipulation.

Required regression:

- unknown trailing args -> parse failure before mutation;
- duplicate safety-critical options must not permit last-value override:
  - `--target`;
  - `--task-key`;
  - `--expected-repo`;
  - `--expected-worktree`;
  - `--expected-base-ref`;
  - `--expected-base-commit`;
- option abbreviation must not create alternate spellings for safety-critical fields;
- branch cannot be supplied anywhere;
- metadata-only options may not affect repo/path/base/branch selection.

Implementation may use a custom argparse action / pre-parse duplicate scan / `allow_abbrev=False`; do not add a new schema or parser framework.

This is mandatory because execpolicy has prefix semantics and no end-of-command predicate.

## 10. Threat model after hardening

An arbitrary Codex process matching the permanent allow can at most request:

- a semantic Reviewed task key;
- in the intended target Reviewed repo;
- from the current local `origin/main` OID;
- into the deterministic sibling `<repo>-<task_key>`;
- only when no conflicting task/branch/worktree exists;
- with no checkout hooks/external filters;
- with no remote mutation/network inside helper;
- with bounded rollback.

It cannot choose:

- arbitrary branch;
- arbitrary path;
- arbitrary base/ref;
- remote mutation;
- force overwrite;
- symlink redirect;
- raw shell command;
- another checkout executable path.

Residual risk:

- it could create an unwanted local Reviewed task/worktree with a new semantic key in the current repo.

Planner judges this residual effect to be bounded, reversible, local-only and materially smaller than granting generic `git worktree add` or arbitrary filesystem write. The workflow layer still forbids doing so without a Kickoff.

Critic must independently decide whether that residual local-topology capability is acceptable for permanent Machine Policy allow.

If Critic judges even this residual risk too broad, the current platform requirement set is incompatible: no-second-user-action + no persistent safe-class permission + no trusted authorization store cannot all be satisfied by current Codex primitives.
