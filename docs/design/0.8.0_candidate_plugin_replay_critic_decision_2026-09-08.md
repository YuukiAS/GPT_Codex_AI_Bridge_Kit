# Bridge Kit 0.8.0 Candidate Plugin Replay — Critic Decision

Date: 2026-09-08

Reviewed plan: `docs/design/0.8.0_candidate_plugin_replay_plan_v0.2_2026-09-07.md`

Decision: **PASS FOR PHASE 0**

This decision does **not** authorize production implementation of `candidate-plugin-replay`.

The accepted execution boundary is limited to the bounded runtime-selection probe already frozen in Plan v0.2:

```text
A. cwd/repo marketplace only
   if real runtime candidate loading + identity proof succeeds
       -> stop and return to Critic
   else
       -> B0

B0. process-local marketplace + plugin add
    + child --ignore-user-config
    + candidate-only Bridge config
   if real generic runtime smoke succeeds
       -> select B0 and stop Phase 0
   else
       -> B1

B1. persistent temporary marketplace + plugin add
    + explicit same-name process-local disables
   if real generic runtime smoke succeeds
       -> select B1 and stop Phase 0
   else
       -> NOT READY FOR IMPLEMENTATION
```

No B2/B3 path is authorized. No production candidate-replay code may be written before Phase 0 selects the supported native runtime path.

## Frozen Critic conclusions

The following v0.2 decisions are accepted and should not be reopened during Phase 0 unless real runtime evidence directly invalidates them:

- target release remains `0.8.0`;
- public command remains `candidate-plugin-replay`;
- existing `plugin-replay` semantics remain unchanged;
- candidate identity remains bound to a real Git commit;
- candidate source is resolved from the committed `.agents/plugins/marketplace.json` rather than a hard-coded generated directory;
- Bridge remains consumer-generic and does not parse 051 heavy-route/domain receipts;
- state/cleanup remains keyed by the current resolved `CODEX_HOME` identity;
- crash recovery uses one OS-backed per-identity lock and a tiny `active.json` journal;
- `active.json` must be atomically present before the first persistent mutation;
- cleanup owns only candidate resources created by the selected mode;
- child-period `$CODEX_HOME/config.toml` hashes must match before-child vs after-child/pre-cleanup;
- provenance remains minimal: candidate commit/source, staged and installed identity/path/digests, effective-plugin preflight, exact child selection config, and output locator;
- 051 remains the first real consumer, but Bridge success proves only exact candidate runtime consumption, not 051 Product PASS.

## Narrow implementation note about local marketplace source syntax

Current AI_Skills uses the object form:

```json
{
  "source": {
    "source": "local",
    "path": "./plugins/codex/plugins/writing-style"
  }
}
```

Phase 0 does not need a generic source adapter. When later implementing the committed manifest locator, reuse Codex's narrow canonical local-source semantics. Supporting another currently accepted simple local-path form is acceptable only if it is trivial; otherwise `0.8.0` may honestly document the object-local boundary. Do not add `--plugin-path` or an adapter framework.

## Phase 0 authorization boundary

The research probe happens before the permanent `candidate-plugin-replay` Host Policy capability exists.

Therefore Phase 0 may invoke the exact raw Codex commands necessary for A/B0/B1 only as a **one-time explicit research probe authorized by this task**. If the current Host Policy/Codex runtime requests confirmation, use the normal confirmation path.

Do not pre-authorize broad raw commands such as:

```text
codex plugin add ...
codex plugin remove ...
codex plugin marketplace add ...
codex plugin marketplace remove ...
raw codex exec ...
```

Do not loosen Host Policy merely to make the probe unattended.

## Evidence required from Phase 0

Phase 0 must produce a concise evidence report that records:

- installed Codex version/commit locator if observable;
- exact current `CODEX_HOME` identity locator without secrets;
- Smoke A result and why it passed or failed;
- B0 commands/config shape and result;
- whether B1 was required; if so, why B0 failed and B1 result;
- candidate commit, committed marketplace entry/source path, staged digest, installed plugin ID/path/digest;
- effective-plugin preflight;
- exact child selection configuration;
- unique harmless candidate behavior proving fresh runtime consumption;
- child-period `config.toml` before/after hashes;
- cleanup result and proof that the pre-existing same-name production/test plugin remained unchanged;
- the selected production mode: `A`, `B0`, `B1`, or `NOT_READY`.

Do not create new schemas, ledgers, transaction frameworks, adapters, or production wrapper code for this evidence.

## Stop conditions

Phase 0 must stop immediately when one of these occurs:

- A unexpectedly succeeds with real runtime identity proof -> return to Critic before any implementation;
- B0 succeeds -> record `SELECTED_MODE=B0`, stop;
- B0 genuinely fails and B1 succeeds -> record `SELECTED_MODE=B1`, stop;
- B1 fails -> record `SELECTED_MODE=NOT_READY`, stop;
- any probe would require copying auth, switching `CODEX_HOME`, persistent disabling/overwriting of production plugin, broad Host Policy relaxation, arbitrary user-config copy/minimization, or another new architecture -> stop and return for review.

## Final Critic interpretation

**Plan v0.2 is accepted for Phase 0 only. No v0.3 design revision is required before that probe. Production implementation remains gated on Phase 0 selecting the supported runtime path.**
