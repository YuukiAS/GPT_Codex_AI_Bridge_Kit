## 先验证 BR-NAC-ER-R2-01 是否真正关闭

原根因：正式 Host 模板 `host_executable.paths` 绑定实际已安装的可信 `ai-bridge` 绝对路径，不自动信任 `candidate-venv/bin/ai-bridge`。候选 `no_match` 不能误作已自动 allow，也不应单凭不匹配就判候选功能失败。

本包现明确**三个不同证据和一个实际审批边界**：

1. **候选动态安全行为**：固定候选虚拟环境与绝对 CLI 不变，在隔离仓库先从候选实际 CLI 进行 Git 安全正反测试，证明危险 URL/分支/上游/钩子/dirty/diverged/环境等 fail-before-effect；真实正向 HTTPS 同名快进仅对已经批准的 `YuukiAS/AI_Skills_Collection:work/bridge-core--normal-entry-acceptance-text-transform`，在现有最多三次远端结果写入后、pre-final Critic 放行及用户原有外部授权下由候选 CLI 直接执行，核对真实 OID。不经旧受信程序代理，也不增加远端写。
2. **机器当前权限实况**：正式 0.11.1 的现有 Host CLI、`CODEX_HOME` 和规则不变。用原已安装程序、真实文件和当前 Codex `execpolicy check` **只读**核实 `host_executable` 实际受信路径、原合法 Git 低打扰与原始危险 Git 仍受审批；`--rules` 是指定规则的静态判定，不可假装是运行时已加载/已真实授权。候选通过当前真实 Codex 会话执行时，实际审批结果另行记录。候选自己的 `host validate` 因代码模板/可执行路径不同出现 expected drift 时，不应立即触发 `host install`。
3. **未来候选安装之后**：如需要，仅在任务隔离临时规则中模拟替换 `host_executable.paths`，其判定一律标记 `WOULD_MATCH_AFTER_INSTALL`，绝不冒充 `CURRENT_LOADED_ALLOW`，不升级正式机器或移动 `release`。
4. **现有授权与平台审批**：用户发送经 Critic PASS 的有界 Kickoff 后才形成当前任务执行授权；候选 CLI 由既有 `workspace-write` 加 `on-request / auto_review` 正常执行。若 Codex 对此候选绝对路径给出 `no_match`、`prompt`，必须使用当前平台本来提供的精确动作审批；未获批准就保持待审批，不换 PATH、软链接、shell/Python 宽授权或机器 Host 配置绕过。机器既有已绑定正式程序的 allow 仍有效，但不能继承给候选路径。

独立判断该方式是否真实保留了「候选 Host 动态安全验证」与「机器危险 Git 不被错误自动放行」两种义务，同时避免了上一轮要求候选提前成为机器正式受信程序的自相矛盾。
