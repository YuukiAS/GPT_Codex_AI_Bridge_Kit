本轮只审 transport executable fence。

--------------------------------------------------
2A. SSH transport
--------------------------------------------------

请复核 v0.3 是否充分处理：

- GIT_SSH；
- GIT_SSH_COMMAND；
- GIT_SSH_VARIANT；
- effective core.sshCommand；
- inherited command-scope Git config。

v0.3 选择：
- non-empty GIT_SSH / GIT_SSH_COMMAND -> trusted helper fail closed；
- any effective core.sshCommand -> trusted helper fail closed for 0.9.0；
- caller GIT_SSH_VARIANT 不进入 mutation env；
- normal ~/.ssh/config + SSH_AUTH_SOCK 仍是允许的 host/user transport path；
- custom SSH transport 仍可走 ordinary raw git push approval。

判断：
1. 这是否关闭了 repo/caller 通过 trusted ai-bridge 执行自定义 SSH program/shell 的路径；
2. 是否仍保留正常 GitHub SSH 使用能力；
3. 是否不需要第二个 wrapper/auth DB/transport registry。

--------------------------------------------------
2B. HTTPS credential helper
--------------------------------------------------

v0.3 要求枚举 effective credential helper 的 origin/scope，覆盖：

credential.helper
credential.<url>.helper

选择的 trust boundary：

- system/global -> 可保留，属于 host/user credential manager；
- local/worktree -> fail closed；
- inherited command scope -> fail closed；
- empty reset、named helper、absolute executable、!shell 都属于该 scope 判定；
- helper 不读取/复制/打印/保存 credential。

请复核：
1. Git 当前 config scope/origin 是否能支持这一判定；
2. local/worktree/command injection 是否被挡住；
3. normal system/global Git Credential Manager / keychain helper 是否保持可用；
4. 是否遗漏一个明显同类 repo/caller-controlled credential executable path。

不要因为“global helper 也可能是自定义程序”重新扩大 blocker：
本设计 threat boundary 明确把 system/global 视为 host/user-controlled configuration，
与用户要求一致。
