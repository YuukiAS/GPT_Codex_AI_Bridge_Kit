## 6. Phase 0：只验证 dedicated Progress thread 的持久隔离，不再研究原 Executor thread 注入

### 6.1 原 thread 路线正式退出

本版明确记录：

`P0_A=UNSUPPORTED_ATOMIC_IDLE_GUARD`

只表示 0.160.1 下“从外部向原 active task thread 安全注入”没有被证明；**这不是 0.11 release blocker**。实现和 Gate 禁止：

- `thread/inject_items` 向原 Executor/task thread 投递 progress；
- 原 thread atomic idle-only guard；
- 原 thread two-client race；
- 原 thread same-thread `turn/start`；
- 原 thread tool-confinement probe。

原 Executor/task thread 的内容、turn 和业务执行完全不受 Persistent Run progress 修改。

### 6.2 唯一产品路线：自动创建 dedicated Progress thread

Persistent Run normal entry 在 run binding 不存在时自动通过官方 app-server `thread/start` 创建一个**非 ephemeral、持久化**的 Progress thread；用户不手工创建。

必须：

- `ephemeral=false`；不能照搬官方 temporary helper 的 `ephemeral=true`，因为产品要求 reconnect/history；
- thread start 后验证 response/thread 为 non-ephemeral 且存在可持久 resume/read 的 thread id/history；
- 使用 0.160.1 已有 `thread/name/set` 设置可读且确定性的名称，例如 `Progress · <repo> · <task-key> · <run-short-id>`，名称只用于用户发现，不作为 identity authority；
- machine-local binding 保存 exact `progress_thread_id`，后续永远按 ID resume/reuse，不按名称、cwd、mtime 猜；
- 同一 run 若已有合法 binding，resume exact thread，不再创建第二个；
- binding 指向的持久 thread 丢失/不可 resume 时标 `PROGRESS_THREAD_UNAVAILABLE`，不静默新建重复线程冒充历史连续性。

新 run（新的 run locator）创建新的 Progress thread；同一 run 的 process reconnect/resume 复用原 thread。

### 6.3 机械无副作用隔离：复用官方 temporary/structured **安全配置模式**，不复用 ephemeral 生命周期

0.160.1 官方 `temporary_structured_request.rs` 已提供成熟的“先读 effective config，再明确禁用工具/环境”的安全配置模式。本任务只选择性复用这套**能力关闭配置**。

Progress thread 创建时至少：

- thread-local read-only sandbox；
- thread-local approval policy no-approval（只在这个无工具 Progress thread 生效，绝不修改 Host-wide policy）；
- `runtime_workspace_roots=[]`；
- `environments=[]`；
- `dynamic_tools=[]`；
- `selected_capability_roots=[]`；
- 关闭 apps/plugins、code mode、shell tool、unified exec、web/search、hooks、image generation、memories、multi-agent、request-permissions、update-plan、skills/instruction loading 等官方 temporary structured helper 已关闭的执行/外部能力；
- 先通过 `config/read` 枚举 effective MCP server names，再在 thread config 中逐个 `enabled=false`；
- 不暴露外部 connector / plugin / MCP / environment / shell / Git / filesystem mutation surface。

**关键差异**：官方 helper 创建 ephemeral thread；本产品需要持久进度历史，所以只复制其 deny configuration recipe，并创建 non-ephemeral Progress thread。不得因为“复用 temporary helper”而让 Progress thread 变成断线后消失的 hidden helper。

Phase 0 必须在模型 render turn **之前**机械证明实际 Progress thread 的 effective capability surface符合上述合同；如果实际 Codex 版本无法证明 execution/external tools 已被关闭：

`PROGRESS_THREAD_ISOLATION=UNVERIFIED_BLOCKER`

停止，不运行 render turn，不回原 Executor thread路线。

### 6.4 bounded render turn

每个 user-facing logical delivery 对 dedicated Progress thread最多产生一个 bounded render turn：

1. Bridge 先完成 canonical snapshot；model 不计算 completed/fraction/ETA/status；
2. Bridge 先生成确定性的 progress payload/人类可读字段；
3. render turn 只要求把这些**既定值**呈现为简短中文消息，不规划、不评审、不调用工具、不修改任何对象；
4. Progress thread 的 base/developer instructions 固定为“只呈现 snapshot，不推断、不改变值、无 semantic completion authority”；
5. 记录 turn id、snapshot digest、token usage、开始/完成时间；
6. turn 输出若改变数字、阶段、ETA/UNKNOWN 或引入业务判断，判 render fidelity FAIL；
7. 前一个 render turn 未完成时不并发启动下一个；coalesce 为最新待发 snapshot，避免 progress thread 自身刷屏；
8. thread 中出现非 Bridge 绑定的外来业务 turn/input 时标记 `PROGRESS_THREAD_CONTAMINATED` 并停止自动发送，不能把它当任务控制入口。

因为该 thread 没有 execution/external tools，即使 render turn本身是模型调用，也没有代码/Git/文件/资源/外部系统副作用能力。

### 6.5 Phase 0 开发 canary

获批准 Kickoff 后只允许一个开发 Progress thread canary，验证：

- normal adapter能自动创建并命名 persistent Progress thread；
- actual effective config/tool surface机械满足 `6.3；
- 最多两个 bounded render turns：一个 start/resume snapshot + 一个更新 snapshot；
- UI 中可见，数值/ETA与 canonical snapshot一致；
- app-server/client断开后按 exact thread id resume，历史仍在且不重复；
- 原 Executor/task thread 的 history/turn count/content hash均未变化；
- canary结束后不再产生新消息。

这只是开发机制证据，不能 grandfather final C' G14-C。

## 7. Progress thread identity 与 run binding

### 7.1 exact binding

每个 Persistent Run 的 machine-local binding 至少保存：

- repo identity / resolved root；
- task_key；
- run_locator；
- frozen Goal source + content hash；
- `progress_thread_id`；
- deterministic human-readable thread name；
- Codex executable/version；
- CODEX_HOME；
- model/provider identity；
- thread creation config/safety fingerprint（不含 credential/token）；
- created_at / last_resumed_at。

它只是 observation/routing binding，不是授权数据库。

### 7.2 create-or-reuse

- binding不存在：创建一个 non-ephemeral Progress thread，验证隔离，命名并持久化 exact ID；
- binding存在：`thread/read/resume` exact ID，验证 task/run/Goal hash 与 safety fingerprint，再复用；
- 不按名称/cwd/最近时间搜索后“收养”另一 thread；
- 同 run 并发第二个 reporter发现已有 binding/owner 时 fail closed，不创建第二 Progress thread；
- 用户查看/重连不需要运行 `ai-bridge persistent-run latest`。

### 7.3 Executor thread完全独立

Progress binding不保存、不需要、不修改 Executor/task thread id。Lite/Reviewed/Control 的业务 thread/session identity继续由各自现有 workflow拥有；Persistent Run 不把任何 progress item写入这些 thread。

## 8. observation 与 last logical delivery 分离

保留 `latest.json` / bounded history 作为 observation。另存最小 logical-delivery state：

- last delivered snapshot/time/reason
- last successful thread projection identity
- progress email result（若启用）

普通 count/fraction 只更新 observation。

Immediate：

- start/resume
- meaningful stage transition
- first stalled/blocked/failed/runtime completion
- material ETA

material ETA：

`abs(expected_finish_delta) >= max(15 minutes, 25% of prior remaining time)`

known ↔ UNKNOWN 永远 material。

普通 active progress 只有距**last delivered**达到 interval 才投递。默认 3600 秒；任务可给有理由的 bounded cadence；无任务理由不得低于 900 秒。

每 5 分钟 observation 不能把 60 分钟 cadence 永久饿死。

Progress thread/email/local 使用同一个 canonical snapshot；email 失败不影响 Progress thread/run，Progress thread 失败也不能自动用 email/manual latest 冒充 G14-C。

## 9. lifecycle-bound report loop

正常入口可为：

`ai-bridge persistent-run report-loop --target <repo> --goal <goal> --progress <source>`

语义固定：

- foreground；
- 不 daemonize；
- 不发现下一任务；
- 不改资源/scope；
- tick 只读 progress、normalize、decision、projection；
- runtime terminal 后向 Progress thread投递一次 runtime-completion snapshot（不是 semantic Goal PASS），然后退出；
- SIGTERM/INT 正常清理；
- reporter退出后 Progress thread本身保留为可查看历史，但没有任何后台 Bridge进程继续发消息。

### tmux owner

同一 canonical launch script 启 actual work + reporter child，记录 PID，trap 在 owner/work exit/failure/signal 时 kill/wait reporter。Reporter 不单独保持 tmux session。

### scheduler owner

job script/native orchestrator 持有 reporter child；job/cgroup + cleanup trap 收尾。已有 heartbeat 若保证 interval 调 one-shot reporter，可不用 loop。Bridge 不套 tmux。

### existing service owner

只有现有 supervisor 能管理 sidecar child 才支持；不为 Bridge 新建 system service。不能证明 cleanup -> 该 topology 不 claim proactive PASS。

Observation frequency 与用户 report cadence 分离。

## 10. ER11-03：Notification Intent、manual one-shot 与真实 semantic authority 分离

Frozen Goal/task 继续明确：

`Progress email: ENABLED | DISABLED`  
`Semantic completion email: ENABLED | DISABLED`

缺失/非法 -> automatic path DISABLED/no-send。SMTP profile存在绝不推导 task intent。

### 10.1 A — automatic / derived live send

以下属于 **automatic**：

- Persistent Run progress projection；
- `ai-bridge notifier once` / `run` 自动扫描；
- 当前或未来 workflow 在没有用户当场手敲 send 命令时触发的 semantic completion。

automatic path 必须走独立的内部 authorization mode（例如 `authorization_source=automatic`），不得 shell out 到 manual `notifier send` 来绕过检查。

映射：

- `operational_progress`、`operational_blocked`、现有 milestone/awaiting-human/非成功 terminal 等“不是成功语义完成”的自动邮件，要求当前 task frozen source 的 `Progress email=ENABLED`；
- 成功 semantic completion 自动邮件要求 `Semantic completion email=ENABLED` **并且** `10.3 的真实 semantic decision locator 验证通过。

`notifier once/run` 在 intent 缺失、source 无法 mandatory-bind、decision locator不合法时必须 no-send 并给明确 suppressed reason；不能仅验证 brief 中字符串。

Persistent Run progress JSON 中历史 `notification_authorized` / repo 自称 authorized 不再提供 live automatic authority。

### 10.2 B — current user explicit one-shot compatibility

保留现有人工正常入口：

`ai-bridge notifier send <brief>`  
`ai-bridge notifier send-test`

当前用户**亲自在终端执行**该 one-shot command，本身就是该次 SMTP effect 的 current authorization；不要求历史 Goal 为这一次人工 send 补 Progress/Semantic intent 字段。

为机械区分 automatic 与 manual：

- live CLI `send` / `send-test` 进入 `authorization_source=explicit_user_cli`；
- live manual path 必须确认是交互式当前用户终端调用，并拒绝已知 Bridge/Codex 自动执行上下文（包括 Bridge-managed executor guard / `CODEX_THREAD_ID` 等自动 agent 环境）；非交互/自动上下文返回 `EXPLICIT_USER_ONE_SHOT_REQUIRED`；
- dry-run/render 可非交互执行，因为没有外部 send effect；
- `once/run`、Persistent Run、Control/Reviewed automation 永远使用 automatic mode，不能借 manual flag/function；
- repo script/Codex Executor 调用 `ai-bridge notifier send` 不得因为命令名称叫 manual 就绕过 automatic contract。

该限制只区分 effect authority，不新增 auth DB/state machine，也不改变用户直接在普通终端输入原命令的语法。

### 10.3 C — automatic semantic completion 必须绑定真实 workflow decision artifact

`decision_authority: Critic/Reviewer/...` **只是展示字段，不是 authority**。Automatic semantic completion 必须先解析当前 task 的现有 workflow 类型，并验证真实、canonical decision locator。

**Reviewed Handoff**：只接受由 task_key 推导的既有 canonical paths，并复用当前 validators。最低同时要求：

- `automation/reviewed_handoff/tasks/<task_key>/CURRENT.json` task_key匹配；
- state=`AWAIT_HUMAN_DECISION`、`human_gate_reason=PASS`、`last_review_decision=PASS`；
