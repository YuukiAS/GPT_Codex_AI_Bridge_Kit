## 1. 用户真正要解决的问题

不是“所有长任务都必须 tmux”。

真正问题是：

> 用户睡觉或离开电脑后，长任务不要因为一个开始前已经可以预见的 approval / Auto-review / user question，在执行数小时后才停住。

同一个 frozen scope 内已经明确授权的同一个 effect，不应因为进入后续阶段而重复询问。

真正的新 scope 仍必须停，例如：

- 新 GPU / resource；
- 换数据、模型、方法、split、endpoint；
- 新 external upload/provider/recipient；
- 费用扩大；
- destructive action；
- 新 deployment；
- Goal 外副作用。

## 2. Planner v0.1 的核心结论

Proposal 推荐：

```text
RECOMMENDATION=OPTION_B_MINIMAL_SEMANTIC_REFINEMENT
PERSISTENT_RUN_KEEP=YES
TMUX_DEFAULT_FOR_ALL_LONG_TASKS=NO
UPFRONT_UNATTENDED_PREFLIGHT_CHANGE=YES
PROGRESS_REPORTING_DECOUPLE=YES
PROPOSED_VERSION=0.9.2
```

具体主张：

1. 0.8.1 已经实现了真正关键的 upfront authorization preflight；
2. 当前缺口主要是 authoring / product semantics：
   “overnight / unattended / multi-hour” 被过度映射成 `Persistent execution: REQUIRED / Backend: tmux`；
3. Persistent Run 保留，但只负责真正需要 terminal-independent process/session persistence 的拓扑；
4. `sbatch` 等 scheduler-native persistence 不应因为运行时间长再套 tmux；
5. interactive allocation + foreground long orchestrator 仍是 tmux 的有效场景；
6. progress reporting 的真实 source 是 project-native JSON，语义应独立于 tmux，但 0.9.2 不重命名现有 `persistent-run report/latest` CLI/schema；
7. 不新增 `UNATTENDED_READY`、authorization DB、daemon、watcher、controller、state machine；
8. 不扩大 Host execpolicy，不放开 generic shell/Python/tmux mutation/sbatch/srun；
9. Persistent Run kickoff 保留为 tmux-specific bounded helper；更一般的 foreseeable gated effects 由当前 user-visible execution kickoff / existing upfront preflight 一次性处理；
10. 当前 Machine Policy / Default-mode HUMAN_ONLY 机制原则上足够，不需要新 Host Policy 机制。

## 3. 你必须独立攻击的关键点

不要只确认 Planner 的叙述。至少独立回答：

### A. Failure attribution 是否正确？

重点核实：

- 0.8.1 的 upfront preflight 是否真的已经进入当前正常 source / tests / consumer guidance；
- 当前真实问题到底是 implementation 没落实、consumer 没使用、还是 authoring 把 duration 和 persistence topology 混在一起；
- 是否存在 Planner 漏掉的真实 late-approval failure，必须用 runtime mechanism 才能解决。

### B. 是否真的应该保留 Persistent Run？

检查：

- interactive allocation + long foreground orchestrator；
- foreground process；
- multi-stage resume；
- 当前 DII 真实用法。

如果 tmux 的独立价值已被 scheduler/service 完全覆盖，可以提出删除；但必须给直接证据，不能因为“更简单”而删除真实能力。

### C. tmux eligibility 是否过宽或过窄？

特别攻击：

- overnight != tmux；
- scheduler-owned `sbatch` 是否确实无需 tmux；
- `salloc` / interactive allocation 的 holder 是否仍有 terminal lifetime 风险；
- 已 detached service/job 是否应保持原 owner；
- bounded single eval/inference 是否不应自动升级；
- 是否存在需要 tmux 但 Proposal 条件会错误排除的普通场景。

### D. authorization semantics 是否安全？

重点攻击：

- “current user-visible authorization” 的边界；
- same frozen effect 的去重是否可能错误覆盖新 resource/provider/artifact/purpose；
- 是否错误把 repo Goal/receipt 当 current-user authorization；
- 是否需要新 schema/state 才能跨 reconnect 正确恢复，还是现有 transcript/Goal 足够；
- kickoff 是否被偷偷扩大成万能授权；
- unknown future side effect 是否可能被预授权。

### E. progress decoupling 是否真的可以不改 runtime code？

核实 `ai_bridge_kit/persistent_run.py`：

- report/latest 是否只依赖 project-native progress evidence；
- 是否存在隐含 tmux dependency；
- 仅改 semantics/docs/tests 是否足以支持 scheduler-native progress；
- 保留旧 CLI/schema 名是否会造成真实产品错误，还是只是命名不完美。

### F. Machine Policy 是否真的无需改变？

重点检查：

- current `approval_policy=on-request` + Auto-review + execpolicy；
- `default_mode_request_user_input=false` + durable plain-text HUMAN_ONLY gate；
- 当前 read-only Slurm/tmux diagnostic rules；
- tmux mutation / sbatch / srun / shell / Python 保持 gated 是否足够。

除非有直接证据，否则不要用“更保险”为理由增加 broad allowlist、wrapper framework、approval store。

## 6. Capability Gate Matrix 审查

Proposal 定义了 G1–G9。逐项检查：

- G1 foreseeable approval early preflight；
- G2 same frozen effect 不重复问；
- G3 scheduler-native overnight 不自动 tmux；
- G4 terminal-owned orchestrator 仍保留 tmux；
- G5 progress without tmux；
- G6 新 scope/resource/provider/cost/destructive effect 必须重新问；
- G7 no broad permission expansion；
- G8 backward compatibility / existing consumers；
- G9 README / normal-entry truth。

如果 Gate 有重复、缺关键失败模式、只测关键词/schema、或无法通过 normal entry 证明真实能力，应要求修改。

不要仅因为“再多一个 gate 更保险”而阻塞。
