# Bridge Kit 0.8.0 Candidate Plugin Replay Design Plan

Plan version: **0.1**

Target Bridge Kit release: **0.8.0**

Status: **DRAFT / READY FOR CRITIC REVIEW / NOT EXECUTION AUTHORIZATION**

Current source baseline: Bridge Kit `0.7.1` at `3b061167794d593b113ca8f4a8a43c4c8000fc01`.

Primary real consumer trigger: `YuukiAS/AI_Skills_Collection` task `051_writing_style_rebuild`. Its frozen Plan requires an ordinary installed-plugin black-box replay of the candidate `writing-style` build, while Bridge Kit `0.7.1` can replay only plugins already installed in the current Codex identity.

This document is versioned because it may receive further Critic revisions. Future revisions must use a new file/version such as `..._v0.2_...md`; do not silently overwrite this design history.

---

## 0. Why this plan exists

Bridge Kit `0.7.1` solved a different lifecycle problem:

```text
already-installed production plugin
-> bounded fresh Codex replay
```

A real AI_Skills production task has now exposed the missing next lifecycle step:

```text
candidate Git commit
-> temporary real plugin installation
-> fresh Codex black-box replay
-> cleanup
```

This distinction matters. A consumer plugin cannot honestly prove its ordinary production entrypoint merely by reading source `SKILL.md`, calling a helper, or forcing a hidden subskill. It must run the candidate through the actual Codex plugin runtime before release.

The 051 failure is therefore not evidence that its writing architecture is wrong. It is evidence that Bridge Kit lacks a reusable way to test a not-yet-released plugin candidate without permanently replacing the user's installed production plugin.

The goal of 0.8.0 is to add exactly that missing capability and no larger deployment system.

---

## 1. Verified reality

### 1.1 Bridge Kit 0.7.1 boundary

`ai_bridge_kit/plugin_replay.py` deliberately:

- resolves the current Codex identity from the current `CODEX_HOME`;
- rejects selection of another Codex identity;
- requires the requested plugin to already be installed/enabled in that identity;
- stages only explicit task/input files;
- launches a fresh Codex child in a write-isolated replay workspace;
- does not allow arbitrary Codex flag passthrough.

This is correct behavior for `plugin-replay` and must remain unchanged.

### 1.2 AI_Skills 051 requirement

The frozen 051 Plan requires a normal installed `writing-style` replay where the user-facing prompt does not name internal heavy-route components. A forced `scientific-rewrite` invocation is diagnostic only.

Therefore replaying the current production `writing-style@yuukias-ai-skills` cannot prove the candidate branch works. The exact candidate build must enter the real Codex plugin runtime first.

### 1.3 Current Codex plugin primitives

Official Codex source inspected for this design at public source commit `d70044072c05e8a5c8b16cac76c75368a860c454` shows the required primitives already exist:

- `codex plugin marketplace add <local-path>`;
- `codex plugin marketplace remove <name>`;
- `codex plugin add PLUGIN@MARKETPLACE --json`;
- `codex plugin remove PLUGIN@MARKETPLACE --json`;
- plugin identity includes plugin name + marketplace;
- plugin add reports the concrete `installedPath`;
- plugin config uses entries such as `[plugins."sample@test"] enabled = true`;
- installing a plugin enables that plugin in user configuration.

Codex runtime plugin loading is configuration/store based. Merely placing a `.agents/plugins/marketplace.json` under a replay cwd is not currently enough evidence that an uninstalled candidate becomes an effective runtime plugin.

### 1.4 One unresolved runtime detail

The selected design intends the replay child to use wrapper-generated **process-local config overrides** so that, during the child process only:

- all pre-existing installed plugins with the same plugin name are disabled;
- the unique candidate plugin identity is enabled.

Codex already supports `-c` process-local config overrides and plugin enablement is represented in config. However, this exact same-name candidate-selection combination must be proven with a bounded real smoke before the design may claim it works in production.

Do not silently fall back to persistently disabling the production plugin if this process-local selection fails.

## 2. Product target

After 0.8.0, a trusted local developer/repository workflow should be able to say, in effect:

> Test plugin `writing-style` exactly as built at candidate commit `abc123`, through a fresh Codex runtime, while leaving the installed production `writing-style` intact after the run.

The stable Bridge Kit product boundary is a new command, tentatively:

```text
ai-bridge candidate-plugin-replay ...
```

This is a sibling of `plugin-replay`, not an extension of it.

Expected normal shape:

```bash
ai-bridge candidate-plugin-replay \
  --target /path/to/repo \
  --plugin writing-style \
  --candidate-commit <sha> \
  --task <explicit-task-file> \
  --input <explicit-input-file>
```

The caller does **not** get to provide:

- another `CODEX_HOME`;
- arbitrary Codex `-c` overrides;
- arbitrary candidate marketplace names;
- arbitrary additional writable roots;
- raw `codex plugin add/remove` command fragments;
- an arbitrary plugin directory outside the candidate Git commit.

---

## 3. Version decision

Target release: **0.8.0**, not `0.7.2`.

Reason: this adds a distinct user capability that 0.7.x does not have:

```text
0.7.x: replay an already-installed plugin
0.8.0: replay a not-yet-released candidate plugin commit through the real plugin runtime
```

This is a new Bridge Kit lifecycle capability, not a compatibility patch to Goal Fidelity or Review Plan validation.

No new Review/Lite/Control role, workflow state, task schema, queue, controller, or ledger is justified by this feature.

---

## 4. Alternatives

### A. Repo-workspace marketplace discovery without install

Idea:

```text
replay workspace
├── .agents/plugins/marketplace.json
└── plugins/<candidate>/
```

and hope fresh `codex exec` automatically treats the candidate as an effective plugin.

Decision: **bounded research smoke only; not the selected production architecture today**.

Current official Codex source indicates effective runtime plugin loading is driven by configured/installed plugins, not merely cwd marketplace presence. Therefore do not build infrastructure around A.

One real smoke of A is allowed before implementation, capped at roughly ten minutes and requiring no new Bridge Kit subsystem. If A unexpectedly proves, on the actual installed Codex runtime, that an uninstalled candidate is loaded as the selected effective plugin and the tested identity can be proven, stop and return to Planner/Critic for a v0.2 design. Do not silently switch architectures inside implementation.

### B. Unique temporary marketplace + candidate plugin in current identity

Decision: **selected design**.

Use Codex's supported plugin primitives to install a candidate beside the production plugin under a unique marketplace identity, run one fresh child with process-local plugin selection, then remove only resources created by this replay.

### C. Switch to another `CODEX_HOME`

Rejected.

It reopens identity/authentication copying, credential-scope, and cross-identity Host Policy problems that existing `plugin-replay` intentionally avoids.

### D. Temporarily overwrite the production plugin/cache

Rejected.

It makes the production plugin itself unavailable or ambiguous during replay, creates a much more dangerous rollback problem, and can affect unrelated sessions.

### E. Full environment snapshot/restore transaction

Rejected.

Bridge Kit must not snapshot and restore every marketplace, plugin, config file, or cache. Unrelated concurrent user changes must remain out of scope. Cleanup owns only resources this run created.

## 5. Selected runtime flow

```text
candidate commit
    ↓
validate commit + candidate plugin path
    ↓
stage one-plugin local marketplace under Bridge machine state
    ↓
create unique marketplace: ai-bridge-candidate-<run-id>
    ↓
codex plugin marketplace add <staging-root>
    ↓
codex plugin add <plugin>@ai-bridge-candidate-<run-id>
    ↓
verify staged tree == installed candidate tree
    ↓
fresh Codex child
    - same current CODEX_HOME
    - production same-name plugin(s) disabled process-locally
    - candidate enabled process-locally
    - natural consumer task unchanged
    ↓
local replay outputs / downstream domain receipt
    ↓
remove candidate plugin
    ↓
remove candidate marketplace
    ↓
verify owned cleanup + production plugin unchanged
```

The user's normal production plugin remains installed throughout. The candidate is a second plugin identity because the marketplace differs.

## 6. Candidate identity and staging

### 6.1 Candidate must be a Git commit

Require `--candidate-commit <sha>` to resolve to a real commit inside the target Git repository:

```text
git cat-file -e <sha>^{commit}
```

The candidate plugin is staged from the Git tree, not the working tree. Dirty/untracked files must not affect the candidate.

The expected source path is:

```text
plugins/codex/plugins/<plugin>/
```

for repositories using the Codex generated plugin layout. A future generalized source adapter may be designed only if a real consumer needs a different committed plugin layout; 0.8.0 should not invent one pre-emptively.

### 6.2 Staged marketplace

Bridge Kit constructs a machine-local staging root under its own state directory, for example:

```text
${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/candidate-replay/<identity-id>/<run-id>/marketplace/
```

The staging root contains only:

- the candidate plugin tree from the frozen commit;
- a minimal `.agents/plugins/marketplace.json` pointing to that local plugin;
- no unrelated repository source.

The marketplace name is generated by Bridge Kit:

```text
ai-bridge-candidate-<run-id>
```

The caller cannot choose or reuse it.

### 6.3 Minimal provenance

Bridge Kit records only the evidence needed to prove which build ran:

```text
candidate_commit
staged_plugin_tree_digest
installed_plugin_id
installed_path
installed_plugin_tree_digest
child selected plugin identity
replay run/output locator
```

It must not understand or validate consumer-domain receipts such as `SCIENTIFIC_REWRITE_HEAVY_ROUTE_RECEIPT_V2`. Those remain owned by the consumer workflow.

## 7. Same-name plugin selection in the fresh child

Candidate installation temporarily leaves two or more same-name identities in the current Codex identity, for example:

```text
writing-style@yuukias-ai-skills
writing-style@ai-bridge-candidate-<run-id>
```

This is expected.

Before candidate installation, inspect the current installed plugin list and record all installed identities whose plugin name equals the candidate plugin name.

The replay child command is generated by Bridge Kit. The caller cannot control it. For that child process only, add config overrides equivalent to:

```text
plugins."<existing-same-name-id>".enabled = false
plugins."<candidate-id>".enabled = true
```

All unrelated plugins remain untouched.

The harness selecting **which plugin build** is under test is legitimate test infrastructure. The user task itself must remain natural and must not force a hidden internal skill/stage. For AI_Skills 051, selecting the candidate `writing-style` build is allowed; writing `scientific-rewrite`, `REALIZE_MEANING`, or a heavy-route stage into the user task would still invalidate its black-box routing gate.

### Hard pre-implementation proof

Before relying on this contract, a real bounded smoke must prove that the installed Codex runtime honors these process-local same-name plugin overrides without persisting changes to user config.

If that smoke fails:

- do not persistently disable the production plugin;
- do not mutate user `config.toml` as a fallback;
- do not weaken the consumer black-box gate;
- stop and return to Planner/Critic.

---

## 8. Reuse existing replay isolation without changing `plugin-replay`

`plugin-replay` remains semantically unchanged:

```text
installed production plugin
-> bounded fresh replay
```

`candidate-plugin-replay` may internally reuse/refactor common lower-level helpers for:

- explicit task/input staging;
- replay workspace creation;
- fixed child sandbox/approval settings;
- read-scope diagnostic;
- write-isolation canary;
- child-output/run metadata.

But public `plugin-replay` arguments, authorization semantics, identity rules, output semantics, and behavior must not gain candidate-install side effects.

A regression test must prove the existing command still behaves as 0.7.1 documents.

---

## 9. Registry mutation boundary

The selected design does temporarily mutate the current Codex plugin registry. This limitation must be stated honestly.

During the short transaction:

- production plugin identity remains installed and unchanged;
- the candidate marketplace/plugin temporarily exists in current `CODEX_HOME`;
- another Codex session started at exactly that time may be able to observe the candidate registry entry;
- the replay child itself is constrained to select the candidate via process-local config.

0.8.0 does **not** claim invisibility to all concurrent Codex processes.

If the product requirement later becomes “no other process can even observe candidate registry state,” this architecture is insufficient. Achieving that would require a mature alternative identity/registry isolation mechanism and should be a different design problem.

---

## 10. Lock and minimal crash journal

### 10.1 One lock per Codex identity

Keep one candidate-replay lock for the resolved current `CODEX_HOME` so two candidate replays cannot concurrently mutate the same plugin registry.

A narrow correction to the Critic proposal: Bridge Kit already treats different `CODEX_HOME` values as different identities. Therefore the lock/journal should be **logically keyed by resolved current Codex identity**, not one machine-global file that could mix two identities.

A simple state layout is enough:

```text
${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/candidate-replay/<identity-id>/
├── candidate-replay.lock
└── active.json
```

`identity-id` may be a stable non-secret digest of the resolved `CODEX_HOME` path. This does not authorize the caller to select another identity; it only prevents state collisions when different shell environments legitimately use different current identities.

### 10.2 Minimal `active.json`

Record only what is required to recover an interrupted run:

```text
run_id
candidate_plugin_id
candidate_marketplace_name
staging_path
phase
```

Optional safety fields may include candidate commit and current identity digest, but this must not grow into a workflow state machine.

### 10.3 Stale recovery

On next candidate replay under the same current identity:

1. acquire the lock;
2. if `active.json` exists, validate that all names/paths belong to Bridge's candidate namespace/state root;
3. remove only the exact candidate plugin and marketplace named by that journal;
4. remove only that run's staging directory;
5. verify they are gone;
6. clear the journal;
7. start the new run.

Never “restore” unrelated marketplaces/plugins/config from a snapshot.

If stale cleanup cannot be completed safely:

```text
CANDIDATE_REPLAY_CLEANUP_FAILED
```

and stop.

---

## 11. Cleanup contract

Normal cleanup belongs in `finally`, but `finally` is not considered sufficient for crash safety; the journal above covers hard process termination/reboot recovery.

Cleanup owns only:

```text
candidate plugin created by this run
candidate marketplace created by this run
candidate staging directory created by this run
```

After cleanup, verify:

1. candidate plugin identity is absent;
2. candidate marketplace is absent;
3. the pre-existing same-name production plugin identity/path/tree digest still matches its pre-run observation.

Do not compare or restore the whole Codex environment.

A cleanup command failure is a hard failure even if the child replay itself succeeded.

---

## 12. Host Policy

This must be a new Host Policy capability, separate from existing `plugin-replay` authorization.

Host Policy should allow only the trusted Bridge executable prefix for:

```text
ai-bridge candidate-plugin-replay ...
```

It must **not** broadly allow:

```text
codex plugin add ...
codex plugin remove ...
codex plugin marketplace add ...
codex plugin marketplace remove ...
raw codex exec ...
```

Existing `ai-bridge plugin-replay ...` authorization and behavior remain unchanged.

`ai-bridge host validate` for 0.8.0 must verify both facts:

- the candidate wrapper has its intended narrow allow;
- raw plugin-registry mutation commands did not gain a broad allow rule.

Installing/upgrading Host Policy to 0.8.0 is the explicit machine-level authorization step for this new capability.

---

## 13. Failure behavior

Use explicit errors rather than broad fallback:

```text
CANDIDATE_COMMIT_INVALID
CANDIDATE_PLUGIN_NOT_FOUND
CANDIDATE_MARKETPLACE_ADD_FAILED
CANDIDATE_PLUGIN_ADD_FAILED
CANDIDATE_INSTALL_IDENTITY_MISMATCH
CANDIDATE_CHILD_SELECTION_NOT_PROVEN
CANDIDATE_REPLAY_FAILED
CANDIDATE_REPLAY_LOCKED
CANDIDATE_REPLAY_CLEANUP_FAILED
```

Names may be refined during implementation, but failure classes should remain small.

A consumer-specific test failure is not converted into a Bridge infrastructure failure. For example, Bridge may prove it ran the correct 051 candidate while `writing-style` itself returns a failed heavy-route receipt; that is a 051 product result, not `CANDIDATE_PLUGIN_ADD_FAILED`.

## 14. Tests and real evidence

### 14.1 Deterministic tests

At minimum:

- invalid/nonexistent candidate commit rejected;
- candidate plugin path missing at commit rejected;
- working-tree dirty content cannot change staged candidate tree;
- generated marketplace identity is unique and caller cannot override it;
- install result ID/path is parsed and tree digest matches staged candidate;
- same-name production identities are discovered without mutating them;
- wrapper generates process-local candidate-only selection overrides;
- existing `plugin-replay` behavior remains unchanged;
- marketplace-add followed by replay exception executes owned cleanup;
- child failure executes owned cleanup;
- cleanup command failure reports `CANDIDATE_REPLAY_CLEANUP_FAILED` and retains recovery journal;
- stale journal is recovered on the next run;
- concurrent candidate replay for the same current identity refuses the second run;
- stale recovery never deletes a marketplace/plugin outside the Bridge candidate namespace.

Do not build a chaos-testing subsystem or a large transaction ledger.

### 14.2 Required real smokes

#### Smoke A — bounded workspace-only discovery probe

One short probe only. No infrastructure investment.

If an uninstalled candidate unexpectedly becomes the effective plugin from a repo-local marketplace alone, stop for design revision before implementation.

#### Smoke B — candidate install and process-local selection

Using a harmless generic local candidate:

- add unique marketplace;
- install candidate beside same-name production/test identity;
- prove child process-local config selects candidate and disables the other same-name identity for that child;
- run a natural task;
- verify installed candidate identity/path/tree digest;
- cleanup;
- verify production identity unchanged.

#### Smoke C — interrupted-run recovery

A controlled failure after marketplace/plugin installation must leave the minimal journal and the next run must remove only its owned candidate resources before proceeding.

No multi-stage chaos matrix is required.

### 14.3 First real consumer

After the generic smoke passes, the first real consumer is AI_Skills task `051_writing_style_rebuild`.

The evidence chain is:

```text
051 candidate commit
-> candidate-plugin-replay
-> exact temporary candidate plugin identity
-> fresh Codex
-> natural writing-style user task
-> consumer-owned heavy-route receipt/artifact
```

Bridge proves the exact candidate plugin ran. 051 decides whether its internal routing, fidelity, language quality, rendering, and human artifact gates pass.

## 15. Security / non-substitutable semantics

0.8.0 must not weaken these boundaries:

- no caller-selected alternate `CODEX_HOME`;
- no copying `auth.json` or credential files;
- no raw arbitrary Codex flag passthrough;
- no broad allow for plugin add/remove or marketplace add/remove;
- no overwrite/removal/disable persistence of the user's production plugin;
- no full-environment snapshot restoration;
- no candidate sourced from dirty worktree state;
- no arbitrary external candidate directory;
- no candidate output auto-publication;
- no destructive Git/branch/remote/release authority;
- no claim of strict filesystem read isolation that current Codex does not provide;
- no claim that other concurrent Codex sessions cannot observe the temporary registry entry;
- no consumer-specific receipt/parser embedded into Bridge Kit;
- no change to existing `plugin-replay` semantics.

If the implementation cannot satisfy these without a weaker substitute, stop and return to Planner/Critic.

## 16. Red-team paths

Before release, actively test for these fake-PASS paths:

1. candidate marketplace added, but child still used production plugin;
2. candidate installed from a stale cache rather than the requested commit;
3. tree digest was calculated on staging but not checked at installed path;
4. production plugin was persistently disabled to make candidate selection easy;
5. candidate cleanup succeeded but marketplace entry remained;
6. cleanup restored an old global snapshot and overwrote an unrelated user plugin change;
7. SIGKILL/restart left candidate resources with no recovery path;
8. two candidate replays raced in one current identity;
9. caller escaped candidate namespace through a custom marketplace name/path;
10. current `plugin-replay` gained registry mutation as an accidental refactor side effect;
11. Bridge declared 051 Product PASS merely because the correct candidate plugin ran;
12. documentation claimed “isolated/no global effect” even though candidate registry visibility is temporarily global to the current identity.

Any of these blocks 0.8.0 release.

## 17. Proposed implementation phases

### Phase 0 — bounded runtime proof

User-visible capability gained: none yet; this is a go/no-go research gate preventing implementation on a false Codex assumption.

- run Smoke A, capped and disposable;
- prove process-local same-name plugin selection is supported by the actual installed Codex runtime;
- if either finding invalidates selected architecture B, stop and produce design v0.2 rather than coding around it.

### Phase 1 — candidate staging + registry transaction core

User-visible capability gained: Bridge can bind a real candidate Git commit to a temporary installed plugin identity and clean it up safely.

Implement:

- commit/tree staging;
- minimal marketplace construction;
- one lock per current identity;
- minimal active journal;
- add/remove candidate marketplace/plugin;
- minimal provenance/digest checks;
- owned-resource cleanup and stale recovery.

No replay PASS claim yet.

### Phase 2 — fresh child replay + Host Policy

User-visible capability gained: a candidate plugin can be exercised by a fresh Codex runtime through a separately authorized Bridge command.

Implement:

- fixed child candidate selection overrides;
- reuse common replay isolation helpers;
- new CLI route;
- separate Host Policy allow + validation;
- regression proving old `plugin-replay` unchanged.

### Phase 3 — generic production smoke

User-visible capability gained: real proof that the end-to-end candidate lifecycle works on the machine/runtime rather than only in unit tests.

Run Smoke B/C and inspect actual plugin registry before/during/after.

### Phase 4 — AI_Skills 051 consumer replay

User-visible capability gained: 051 can resume its previously blocked ordinary-user routing Gate without overwriting live production `writing-style`.

Bridge Kit should only report the candidate replay identity/result. 051 owns its domain receipt and artifact judgment.

### Phase 5 — 0.8.0 release closure

User-visible capability gained: reusable candidate-plugin black-box replay is a supported Bridge Kit capability for future `presentations`, `research-writing`, statistical plugins, and other repositories.

Release only after:

- old `plugin-replay` regression passes;
- Host Policy validation passes;
- generic real smoke passes;
- 051 consumes the capability successfully enough to prove it solves the original infrastructure blocker (051 itself need not already achieve final Product PASS);
- package/version/README/CHANGELOG are updated consistently to `0.8.0`.

## 18. Deliberately not built in 0.8.0

- no alternate Codex identity manager;
- no strict read-isolation container/sandbox subsystem;
- no global plugin-registry snapshot/restore service;
- no multi-candidate parallel test farm;
- no generic deployment manager;
- no plugin release publisher;
- no candidate branch/PR manager;
- no new Reviewed Handoff state/role/schema;
- no consumer-specific routing/receipt parser;
- no automatic holdout/test orchestration;
- no chaos-testing framework;
- no promise that concurrent unrelated Codex sessions cannot observe the temporary candidate registry entry.

## 19. Critic questions for v0.2 review

1. Is `candidate-plugin-replay` the right public command name, or should the shorter `candidate-replay` be preferred without losing clarity?
2. Is process-local same-name plugin selection sufficiently bounded once real smoke proves the Codex `-c` override behavior, or is there a safer existing Codex selection primitive we should use instead?
3. Is staging specifically from `plugins/codex/plugins/<plugin>/` appropriately narrow for 0.8.0, or is there already a mature generic committed-plugin locator Bridge should reuse?
4. Is one lock + one minimal crash journal per current Codex identity sufficient, or is any field still unnecessary?
5. Does the cleanup contract correctly avoid owning unrelated registry state while still proving the production same-name plugin was not changed?
6. Are the required tests/smokes enough to prove crash recovery without overbuilding a transaction framework?
7. Does release `0.8.0` accurately reflect the new product capability without implying candidate replay is fully invisible to other concurrent Codex sessions?
8. Is there any path by which the wrapper-generated process-local plugin selection could accidentally persist into user config, and what is the smallest observable regression that should prove it does not?

---

## 20. Readiness decision

**READY FOR CRITIC REVIEW; NOT READY FOR IMPLEMENTATION.**

The product need and selected minimal architecture are now specific. Before implementation, Phase 0 must verify the two runtime assumptions that cannot be proven from repository structure alone:

1. repo-workspace-only candidate discovery is not a better supported path on the installed runtime;
2. process-local config can reliably select the unique candidate while suppressing other same-name plugins for only the fresh replay child.

If either assumption fails, revise this design rather than weakening the consumer production gate or mutating the production plugin persistently.
