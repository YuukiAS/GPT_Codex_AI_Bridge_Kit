## 1. v4 的产品判断

总体方向不变。Bridge Kit 仍然不是中央编排系统：工作模式只有 Lite、Review、Control；Persistent Run 只负责终端拥有的前台任务断线存活和运行观察；Notifier 是每个 OS 用户的一份机器级公共邮件能力；Clear Writing 只是自动邮件发送前的一次表达适配。0.11.0 不新增 daemon、数据库、跨工作流事件总线、持久 Codex thread、WebSocket/app-server reader、自动 worktree exchange 或第二套状态机。

v4 不是新的范围重置。v3 已关闭并冻结的七个 blocker 保持不变；本版只关闭 execution-ready Critic 对原 F05 指出的最后一个残余矛盾：生产自动 Notifier 的 transport 配置必须只有机器级单一真值，不能再允许 process-level SMTP credential/config override。关闭后，六项正式能力仍是：

A. 低打扰机器策略。  
B. 精确执行位置与必读源。  
C. Bridge 管理的根 AGENTS.md 安全写入。  
D. Persistent Run 生命周期、进度与主动 ETA。  
E. 机器级共享 Notifier 与四类直接消费者。  
F. 自动通知的一次性 Clear Writing。

## 3. 能力 A：低打扰机器策略

保持 v2，不重新设计。Host Policy 继续让窄的安全 Git/GitHub/Slurm/process/tmux 读取和已经批准的 bounded 当前分支快进同步低打扰；危险 Git、凭据、资源申请/取消、部署、外部发送和其他真实副作用继续由现有权限层拦截。

0.11 不新增通用 Git controller，也不扩大 shell/Python 权限。

## 4. 能力 B：精确执行位置与必读源

保持 v2。Bridge 管理的 Executor 真正 spawn 之前，冻结并验证 exact repo、worktree、branch、expected commit 和 mandatory source paths。source authority 是 exact commit blob；无关 dirty 文件不阻断，mandatory path 与冻结提交冲突则 child=0。

正常路径先读本地 exact Git object；只有 exact blob 确实缺失才进入隔离 object fallback。不得自动切分支、搬 worktree、使用旧聊天摘要或另一个“差不多”的候选替代冻结 source。

C2 必须覆盖 Lite、Review、Control 和适用的 Persistent foreground launch boundary。

## 5. 能力 C：AGENTS.md 安全写入事务

### 5.1 为什么 v2 不够

当前三个 writer 都是“先读并计算，再检查，再单独 write_bytes”。即使 replace 是原子的，也不能防两个 Bridge writer 同时基于同一个旧文件构造不同新文件，后写者覆盖前写者。

### 5.2 v4 的唯一写入模型

Lite/core、Persistent、Overleaf 不再各自实现“读取后直接写”。三者调用同一个目标级事务 helper。

每个 canonical repo root 对应一个 machine-local lock identity，例如：

~/.ai-bridge/locks/agents/<sha256(canonical-repo-root)>.lock

事务固定顺序：

1. 获取该 target 的独占 Bridge 写锁；锁必须由操作系统在进程退出时释放。
2. 在持锁状态下重新读取当前 AGENTS.md。
3. 在内存中只替换当前 writer 自己的 managed block，保留其他 Bridge block 和 user-owned bytes。
4. 在同一锁内读取实际 instruction 配置并执行 projected byte budget 和当前 block cap 检查。
5. 任一检查失败，零 AGENTS.md mutation。
6. 写同目录临时文件，flush/fsync 后使用 os.replace 原子替换。
7. 必要时 fsync 父目录，然后释放锁。

这保证 Bridge↔Bridge writer 真正串行。实现可以按平台使用成熟的 OS advisory lock；不得创建 daemon 或锁数据库。

对于不合作、完全不读取 Bridge lock 的外部编辑器/进程，v4 不宣称存在 portable conditional replace/CAS。实现可以在 replace 前再次比较持锁后读取的 digest 来发现已发生的外部改变，但不能宣传为消除最后一个微小 race window。产品保证准确收窄为：Bridge 管理的 writer 不互相覆盖；用户区域在 Bridge 写事务中 byte-for-byte 保留；检测到的外部竞争会 fail closed。

### 5.3 安装顺序

任何会写根 AGENTS.md 的安装入口必须先完成上述事务中的预算检查，AGENTS.md mutation 是该入口的第一个项目写动作；通过后再写该功能自己的 Bridge-owned 模板/config。这样不会出现“预算失败但已经写了一半项目文件”。

## 6. 能力 D：Persistent Run 生命周期、进度、ETA 与恢复

### 6.1 运行拓扑不变

每个 run 仍只有：

- 一个 exact tmux session；
- 一个 run-scoped supervisor；
- 一个 primary child；
- 一个 machine-local binding。

scheduler-owned batch 或 already-detached service 不因为时间长再套 tmux。Review watcher、Control controller 也不因自身长期存在而自动再套 Persistent。

### 6.2 进度合同必须在启动前冻结

Persistent Goal 必须声明：

- Progress mode: count | fraction | stage | none
- Progress owner: bridge-child | project-native | none
- Progress source locator: bridge-state | repo-relative-path | NONE
- Expected progress update seconds: integer | UNKNOWN
- Notify: OFF | ON
- Recipient override: NONE | explicit address
- Notification cadence minutes: integer，默认 60，普通进度通知不得低于 15

约束：

- count/fraction 不允许 owner=none。
- bridge-child 模式使用 Bridge 标准 progress update 入口和 machine-local progress file。
- project-native 模式由项目已有进度生产者写指定 repo-relative JSON；Bridge 只读。
- stage/none 可以没有可辩护 ETA。
- 不能证明量化进度来源时，不得把任务声明为 count/fraction 以换取一个好看的 ETA。

### 6.3 supervisor 给 child 的标准环境

启动 primary child 时注入：

AI_BRIDGE_RUN_KEY  
AI_BRIDGE_PROGRESS_PATH  
AI_BRIDGE_PROGRESS_MODE  
AI_BRIDGE_PROGRESS_OWNER  
AI_BRIDGE_PROGRESS_EXPECTED_UPDATE_SECONDS  
AI_BRIDGE_RUNTIME_OWNER=persistent  
AI_BRIDGE_RUNTIME_ID=<launch_id>

这些值不包含 SMTP secret。AI_BRIDGE_RUNTIME_OWNER/ID 同时用于防止被包住的 Lite/Executor 再重复发送同一 runtime terminal 邮件。

bridge-child 的标准命令为：

ai-bridge persistent-run progress update ...

它从上述环境定位当前 run，不要求 child 自己拼 state path。update 先验证字段，再用同目录临时文件 + fsync + os.replace 原子写。count 要满足 0 <= completed <= total；fraction 要满足 0 <= fraction <= 1。

### 6.4 主动 ETA

supervisor 每 60 秒进行一次非阻塞 observation。对于 count/fraction，只有真实量化观测进入估计器。

冷启动条件：至少 3 个有效量化点，并跨越至少 10 分钟。满足后，从最近最多 60 分钟、最多 12 个同一连续阶段的有效点计算近期推进率。默认使用相邻有效区间推进率的中位数作为稳健速度；只有正速度用于 ETA。剩余量除以稳健速度得到中心 ETA；速度分布的四分位范围换算成一个 ETA 区间，区间不足时只给中心 ETA 并标记低置信。

以下情况立即使旧 ETA 失效并重新 warm-up：

- stage 改变；
- total 改变；
- fraction/count 回退；
- 长时间观测中断超过 max(15 分钟, 3 × expected update cadence)；
- 近期有效速度为零或波动大到无法形成有意义区间。

所以 UNKNOWN 是冷启动或真实证据不足状态，不是永久默认。一个 count/fraction child 按冻结 cadence 持续写真实进度，C4 必须证明 warm-up 后出现 ETA；如果仍一直 UNKNOWN，C4 失败。

通知默认约 60 分钟一次。阶段变化、stalled/blocked/failed、运行结束或 ETA 的实质变化可以提前通知。小进度波动只更新本地 latest/history，不刷邮件。

### 6.5 progress 文件故障不能杀任务

一次读取出现 missing file、半写 JSON、坏 JSON、schema 错误、permission/OSError 或读竞争，只产生 progress_observation=UNAVAILABLE：

- primary child 继续；
- supervisor 继续；
- last-good progress/ETA 不被伪造覆盖，但对外注明当前 observation 不可用；
- 下一轮继续读取；
- 后续恢复合法进度后继续积累并重新形成 ETA。

supervisor 自己的生命周期只由 primary child 和自身致命错误决定，不能由一次 progress 解析失败决定。

### 6.6 正式恢复入口

新增：

ai-bridge persistent-run recover --target ... --goal ... --expected-goal-sha256 ...

recover 只读检查当前 exact binding/session/process identity，并返回一个分类和唯一安全下一动作。

需要时再由用户显式执行：

ai-bridge persistent-run resolve --target ... --goal ... --expected-goal-sha256 ... --expected-launch-id ... --close-stale

状态真值：

| 观察 | recover 结论 | 允许动作 |
| --- | --- | --- |
| exact session + matching binding | ACTIVE | 继续 status；禁止 close/relaunch |
| session 缺失，但可证明同一旧 child 仍活着 | ORPHAN_CHILD_ALIVE | 等待并再次 recover；若用户需要终止，必须另行授权破坏性终止 |
| session 缺失，且 host/process identity 能证明旧 child 已不可能存活 | SAFE_TO_CLOSE_STALE | 允许显式 resolve --close-stale |
| 无法证明旧 child 活着或已死 | DUPLICATE_RISK_UNRESOLVED | 禁止 close/relaunch；下一动作是取得能证明进程已结束的主机证据，或另行授权终止疑似旧进程，然后重新 recover |
| session/binding 身份冲突 | IDENTITY_CONFLICT | 禁止 takeover；先处理冲突 session 的独立授权，再 recover |

process/PID identity 只用于判断“会不会重复跑”，永远不能产生 Goal completion。实现应在支持的 host 记录 boot identity、child PID、child start identity 和 argv digest；若平台无法可靠证明 process identity，就保留 DUPLICATE_RISK_UNRESOLVED，不猜测。

resolve --close-stale 只有在最新可证明分类为 SAFE_TO_CLOSE_STALE、exact session 不存在、launch_id 完全匹配时才允许。它写入 resolved_at 和 STALE_CLOSED_WITHOUT_COMPLETION，不删除 binding、不写 exit_code、不产生 semantic completion。再次运行必须使用新的 run identity/run_key。

机器重启和 supervisor loss 都必须走这套入口，不让用户手工删除 ~/.ai-bridge state。

## 7. 能力 E：机器级共享 Notifier

### 7.1 唯一配置和状态

运行时唯一 secret authority：

~/.ai-bridge/private/notifier.env

唯一正式 transport：

Gmail SMTP 587 + STARTTLS + App Password

所有 state 留在：

~/.ai-bridge/state/notifier/

repo 内旧 .ai-bridge/private/notifier.env 永远不参与 runtime precedence，也不自动合并。

生产自动 Notifier 的 SMTP user、SMTP password、FROM、默认 TO、subject prefix 以及其他 transport 配置，只能来自 ~/.ai-bridge/private/notifier.env。AI_BRIDGE_NOTIFY_SMTP_USER、AI_BRIDGE_NOTIFY_SMTP_PASSWORD、AI_BRIDGE_NOTIFY_FROM、AI_BRIDGE_NOTIFY_TO、AI_BRIDGE_NOTIFY_SUBJECT_PREFIX 等 AI_BRIDGE_NOTIFY_* 进程环境变量在 production normal entry 中不得覆盖或参与合并；即使进程环境存在这些变量，也不能改变 effective transport config。

逐任务唯一允许改变的收件人是冻结任务合同里的 recipient_override。它只是一次 logical delivery 的已授权收件人覆盖，不是第二套 Notifier config，更不能覆盖 SMTP credential、FROM、subject prefix 或其他机器 transport 配置。

AI_BRIDGE_PRIVATE_RCLONE_SOURCE 等只服务 private sync 的导入定位，不属于 Notifier runtime transport authority。测试可以通过显式函数参数、dependency injection、temporary state/config root 注入测试配置，但测试注入不得成为 production normal entry 的配置来源。

notify 默认 OFF。

### 7.2 配置与 readiness

机器正常入口：

ai-bridge private sync --profile notifier  
ai-bridge notifier validate  
ai-bridge notifier send-test  
ai-bridge notifier status

private sync 把 rclone source 复制到 machine path 的临时文件，先校验必需字段，再 chmod 0600 并原子替换。不得把 secret 打印到 stdout/log/state。

validate 只验证配置形状和安全性，不发送邮件。

send-test 是真实 Gmail 外部效果；SMTP server 接受消息后，记录 transport_test_accepted_at 和当前 redacted config digest。不得声称 inbox 已经 delivered。machine config 变化后旧 readiness 失效。

当一个冻结任务明确 Notify: ON 时，首次业务执行前检查当前 config digest 是否已有 transport-ready 证据；不满足就 fail before first business child/model launch。任务已经开始之后的 DNS/SMTP/Clear Writing 故障不得改变业务状态或杀 child。

### 7.3 唯一 legacy migration

唯一旧项目配置迁移命令：

ai-bridge notifier migrate-legacy --project /path/to/repo

只读取该项目的：

/path/to/repo/.ai-bridge/private/notifier.env

规则：

- 先验证旧配置完整性，不打印 secret；
- machine config 不存在：复制到 machine path、chmod 0600、原子写；
- machine config 已存在且 digest 完全相同：NOOP_ALREADY_MIGRATED；
- machine config 已存在但 digest 不同：MACHINE_CONFIG_CONFLICT，零覆盖；
- 不自动删除、重命名或提交旧项目文件；
- 迁移完成后 runtime 仍只读取 machine config；
- 新旧同时存在时 machine config 是唯一 runtime authority，旧文件只是一份等待用户自行处理的 legacy secret。

如果用户要主动替换 machine config，走 private sync 的明确配置入口，不让 migrate-legacy 带 --force 偷偷覆盖。

### 7.4 自动通知使用严格 NotificationRequest

自动消费者不能再把任意 notification brief dict 直接送模型/transport。自动请求只允许以下事实族：

- project、task_key、consumer
- fact_class
- status、decision_authority
- 固定/受控 summary、next_action
- stage、completed、total、fraction
- ETA 中心/区间或 UNKNOWN
- duration_seconds
- branch、version
- run_id、runtime_id
- recipient_override（只给 transport，不进入模型）

所有字符串有上限，并拒绝 CR/LF header injection。details、stdout/stderr、环境变量、凭据、任意日志、任意私有正文、任意 reviewer body、任意 evidence_paths 默认都不属于自动 NotificationRequest。

manual notifier send 作为 0.10 兼容入口可以继续消费旧 brief，但默认不经过自动 Clear Writing，也不是 C5 四消费者的正式自动路径。

### 7.5 并发、去重与 DELIVERY_UNKNOWN

每个 logical event 在 machine state 下使用独立 event directory/receipt，event identity 至少绑定 canonical repo identity、task key、consumer、fact class、源事件 identity/runtime_id 和 resolved recipient。不同 repo 即使 task_key 同名也不会碰撞。

发送前原子 claim。两个进程竞争同一 event 时最多一个获得发送权。

attempt 至少记录：

CLAIMED → EXPRESSION → TRANSPORT_STARTED → SMTP_ACCEPTED

或明确 FAILED。

SMTP_ACCEPTED 只表示 Gmail SMTP 接受，不表示 inbox delivered。

如果 transport 已开始但进程/网络在是否被 SMTP 接受这一边界上无法证明结果，状态必须是 DELIVERY_UNKNOWN，并禁止自动重发。

### 7.6 显式 retry

新增：

ai-bridge notifier retry --event-key <event-key>

只允许已有 FAILED 或 DELIVERY_UNKNOWN event。

FAILED 可以显式 retry。DELIVERY_UNKNOWN 必须额外要求：

--confirm-possible-duplicate

因为上一封可能已经被 SMTP 接受。

retry 复用 machine state 中已经冻结的安全 NotificationRequest、原 resolved recipient 和 attempt lineage；不重新读取一个后来可能已经改变的 repo brief。每次 retry 记录 parent attempt、新 attempt、当前 redacted config digest。没有自动无限重试。

status 必须给出：

- 当前 machine config 是否完整；
- 当前 config digest 是否通过真实 send-test；
- 最近失败/DELIVERY_UNKNOWN；
- exact event key；
- 对每个可恢复项给出下一条明确命令。

## 8. 能力 E 的四个直接消费者

Notifier 是 transport owner，不是 workflow decision owner。

### 8.1 Lite

任务策略写在现有 Lite task frontmatter：

notify: false  
recipient_override: ""

run_lite_task 完成真实 codex process 后是 Lite 的 transport caller。它只有 runtime exit 事实，因此自动邮件只能说：进程已退出、exit code、duration 等运行事实。exit code 0 不能变成 task PASS、Goal completion 或 release readiness。

如果 Lite 本身运行在 Persistent primary child 内，AI_BRIDGE_RUNTIME_OWNER=persistent 时 Lite 不发送 runtime terminal；由 Persistent supervisor 统一发送，避免重复。

### 8.2 Review

通知策略写入现有 REQUEST.md 的 Notification 小节，不新建中央 config。

Reviewer 决定仍由 reviewed_handoff.record_review 记录到 REVIEW_n.md/CURRENT。现有 reviewed_runner watcher 在 validate_task 确认该 Reviewer 事实有效之后，才作为本机 transport caller 调用共享 Notifier。

watcher 不生成 Reviewer 决定，不把 Codex exit code 变成 Reviewer PASS，也不获得 Reviewer authority。

Review watcher 本身已有长期 watcher 生命周期，0.11 不因为它运行久就再套 Persistent。若未来某一个前台 Executor 明确需要 Persistent，那是该 Executor 的 run contract；Review watcher仍然拥有 Review workflow 生命周期和语义决定。

### 8.3 Control

通知策略写入现有 task REQUEST.json 的 notification_policy，不新建第二套 config。

现有 agent_flow.apply_transition 是 transport caller。只有 transition predicate、对应角色 artifact、state write 和 post-validation 全部通过后，才从已经存在的 authoritative role fact 构造 NotificationRequest。

Planner/Critic/Final Critic 的语义决定仍由其 artifact 决定；Controller 只搬运已验证事实。Notifier 失败不能回滚已经合法完成的 Control transition。

Control controller 自己不因长期运行自动套 Persistent。只有一个明确 foreground runtime 另行满足 Persistent 选择条件时才使用 Persistent，并且 Persistent 仍只拥有 runtime facts。

### 8.4 Persistent

run-scoped supervisor 是 transport caller，只允许发送：

- run start；
- periodic/material progress；
- stalled/blocked/failed runtime fact；
- runtime terminal。

它永远不能发送 semantic PASS/READY/RELEASE_READY。

任务策略存在 Persistent Goal contract：Notify、Recipient override、Notification cadence minutes。

### 8.5 recipient authorization

使用 machine default recipient 时，用户批准 Notify: ON 的当前 task/Goal 即构成本任务向该默认 recipient 发送上述安全事实的 bounded 授权。

recipient_override 只有在同一用户批准的 task/Goal 中显式冻结时才允许；运行中临时改变 recipient 需要新的用户授权。Notifier 不因 repo 文本自行扩大 recipient。

## 9. 能力 F：one-shot Clear Writing

### 9.1 真实依赖

AI_Skills_Collection main@23f51b0... 的 writing-style v0.4 正式 profile/plugin 当前包含 writing-fidelity、scientific-prose、scientific-rewrite、chinese-prose，没有正式 response-clarity 依赖。

因此 0.11 只要求 installed/enabled writing-style@yuukias-ai-skills 实际提供并消费：

writing-fidelity + chinese-prose

不修改 AI_Skills，不等待新 skill，不把本地/未来可能出现的 response-clarity 变成 Bridge 发布依赖。

### 9.2 输入和一次调用

自动 NotificationRequest 先转成 Clear Writing safe facts；recipient、SMTP config、credentials、日志、details、review body、raw source、任意 evidence paths 不进入模型。

每个 logical auto delivery：

- 最多一次 codex exec --ephemeral --json；
- read-only sandbox；
- 最多一个 turn；
- model retry = 0；
- Clear Writing 墙钟预算最多 90 秒；
- 输出字节有界；
- 必须有 installed skill 的真实消费证据；
- 数字、状态、UNKNOWN、版本、runtime/task identity 和结论强度做确定性保真检查；
- 任一失败立即使用 deterministic fallback。

## 10. 自动 deliver 的端到端墙钟

自动 deliver 总墙钟 deadline 固定 120 秒，从消费者提交请求开始计时，不是只给模型的 timeout。

发送由一个一次性的、可终止 helper/subprocess 承担；它只活这一封 logical delivery，不是 daemon、worker pool 或 watcher。父进程用 monotonic deadline 等待。到 120 秒仍未结束时必须 terminate，必要时 kill，并返回状态给 caller。

阶段预算：

- Clear Writing 最多 90 秒，或剩余 deadline，取更小；
- 表达失败后若仍有剩余时间，立即走 deterministic fallback；
- SMTP/DNS/TLS/login/send 使用剩余时间，单 socket timeout 不能超过剩余 deadline；
- 父进程 deadline 是最终上限。

超时归类：

- 尚未进入 TRANSPORT_STARTED：FAILED_TIMEOUT_BEFORE_TRANSPORT，可显式 retry；
- 已进入 TRANSPORT_STARTED，但没有可证明 SMTP_ACCEPTED 或明确失败：DELIVERY_UNKNOWN，不自动重发；
- 已写入 SMTP_ACCEPTED：按 SMTP accepted 恢复/完成 receipt，即使高层 receipt 尚未落盘。

任何通知失败、超时或 DELIVERY_UNKNOWN 都不能改变业务状态、杀 primary child、回滚 Review/Control transition 或制造 semantic failure。

## 11. 用户正常体验

### 新机器

配置一次 machine Notifier，validate，再做一次真实 send-test。以后新 clone 的 repo 不再重复放 Gmail/App Password。

### 新 repo

继续按原 Lite/Review/Control 使用。只有任务显式 notify=ON 才通知；默认 OFF。需要 Persistent 的前台长任务再安装/选择 Persistent，不因为“很久”自动套 tmux。

### 长任务

count/fraction 模式由真实 child/project owner持续生产进度。前 10 分钟可能没有 ETA；达到 3 个有效点后开始主动 ETA。坏一次 progress JSON 不会杀任务。断线后 status；异常丢失 supervisor/session 后先 recover，只有能证明没有重复执行风险才 resolve stale，然后以新 run identity 重启。

### 邮件

所有消费者调用同一个 machine Notifier。自动邮件只含冻结的安全事实，最多一次 Clear Writing。Gmail 卡死最多占用一个 bounded deliver deadline，不会把 primary runtime 永久卡住。
