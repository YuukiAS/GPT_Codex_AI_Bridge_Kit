## 1. Remaining defect

Recovery Plan v0.3 said:

```text
git fetch --all --prune
-> inspect refs/remotes/origin/reviewed/<task_key>
-> absence is authoritative
```

That is incomplete for a noncanonical remote configuration.

Official Git behavior establishes:

1. `git fetch --all` skips any remote whose `remote.<name>.skipFetchAll` is true;
2. when fetch has no explicit command-line refspec, the refs fetched are controlled by `remote.<name>.fetch`;
3. pruning also follows the remote's configured refspec;
4. negative refspecs can exclude refs even when a positive glob would otherwise include them.

Therefore:

```text
fetch --all --prune
+ local reviewed ref absent
```

proves remote absence only when the effective origin fetch configuration is known to mirror **all remote heads** into the normal `refs/remotes/origin/*` namespace.

A repo configured to fetch only `main` could otherwise produce a false “task branch absent” result.

---

## 2. External reality rechecked

Targeted official Git documentation rechecked:

- `git fetch --all` fetches all configured remotes **except** those with `remote.<name>.skipFetchAll`;
- with no command-line refspec, `remote.<name>.fetch` determines which refs are fetched and which remote-tracking refs are updated;
- the normal clone-style mapping is:
  `+refs/heads/*:refs/remotes/origin/*`;
- negative refspecs beginning with `^` exclude matching refs;
- pruning removes remote-tracking refs according to the configured refspec, rather than proving arbitrary remote namespaces by itself.

Adopted consequence:

> 0.9.1 trusted repo-local bootstrap supports only the ordinary clone-style `origin` fetch configuration. Exotic/custom fetch layouts remain outside the low-friction safe class.

No new network mechanism is needed.

---

## 3. Selected closure: canonical origin fetch profile

Before the workflow relies on:

```text
git fetch --all --prune
```

as authoritative remote-branch synchronization for first bootstrap, mechanically verify that the **effective origin fetch configuration** is canonical.

### 3.1 Required origin participation

Require:

```text
remote.origin.skipFetchAll
```

to be:

- unset; or
- explicitly false.

If effective value is true:

```text
NONCANONICAL_ORIGIN_FETCH_CONFIGURATION
```

and trusted first bootstrap must not continue.

Do not temporarily override it.

### 3.2 Required origin fetch refspec

Require the effective `remote.origin.fetch` values to be exactly the ordinary full-heads mapping:

```text
+refs/heads/*:refs/remotes/origin/*
```

For the 0.9.1 trusted safe class, the simplest rule is:

- exactly one effective `remote.origin.fetch` value;
- it equals the canonical mapping above.

Reject:

- main-only refspecs;
- custom destination namespaces;
- multiple custom refspecs;
- mirror-style refspecs;
- any negative refspec;
- any configuration that cannot prove every `refs/heads/*` remote branch maps into `refs/remotes/origin/*`.

This is intentionally strict.

0.9.1 does not need to normalize, rewrite, infer equivalence, or support exotic remote layouts. Those repos can use ordinary approval/manual handling.

### 3.3 No config mutation

The trusted path only validates configuration.

It does not:

- edit `.git/config`;
- add/replace refspecs;
- clear `skipFetchAll`;
- rename remotes;
- add remotes;
- change fetch behavior.

A noncanonical repo simply falls outside the trusted first-bootstrap safe class.

## 4. Canonical sync sequence

Only after the canonical origin fetch profile passes:

### Step 1 — sync configured remotes

Run the already-existing low-friction command:

```text
git fetch --all --prune
```

No new wrapper or Machine Policy rule is introduced.

### Step 2 — capture authoritative local state

Record:

```text
refs/remotes/origin/main
refs/remotes/origin/reviewed/<task_key>
```

Because origin participated and its canonical refspec maps all remote heads, these local remote-tracking refs are now authoritative for the relevant branch namespace.

### Step 3 — branch-existence decision

If:

```text
refs/remotes/origin/reviewed/<task_key>
```

exists:

```text
REMOTE_TASK_BRANCH_ALREADY_EXISTS
```

and first bootstrap does not run.

If absent, the helper may proceed, subject to all other frozen fences.

### Step 4 — exact base binding

The current:

```text
refs/remotes/origin/main
```

OID is recorded after sync.

The first-bootstrap command receives:

```text
--expected-base-commit <post-sync origin/main OID>
```

and requires exact equality before mutation.

A stale or different expected commit fails closed.

## 5. Bootstrap remains network-free

The standing-allow `task bootstrap` helper must not perform any remote query.

Specifically it must not run:

- `git fetch`;
- `git ls-remote`;
- provider APIs;
- remote branch queries;
- push/publication.

It relies only on:

1. validated canonical origin fetch configuration;
2. the immediately preceding allowed `git fetch --all --prune`;
3. local remote-tracking refs.

This preserves the v0.3 security model: the unsandboxed standing-allow helper itself is local-only.

---

## 6. Where the configuration check belongs

The canonical fetch-profile check must be mechanically enforced **before first-bootstrap mutation**.

Preferred minimal implementation:

- implement a small Bridge validation helper in the existing Reviewed Handoff source;
- call it from the trusted bootstrap preflight immediately before relying on local remote-tracking refs;
- expose no new CLI command;
- create no new policy object/schema.

The workflow may also preflight the same condition before running `git fetch --all --prune` so the user gets an earlier clear failure, but the bootstrap helper must still re-check the effective config before mutation.

This avoids a TOCTOU gap between a workflow-level preflight and the permanently allowed helper.

---

## 7. Effective-config reading requirements

The implementation should read effective Git configuration narrowly and explicitly.

Required facts:

- effective `remote.origin.skipFetchAll`;
- all effective `remote.origin.fetch` values.

Do not build a generic Git-config security subsystem.

The check only answers:

```text
Does origin participate in fetch --all?
Does origin fetch every remote head into refs/remotes/origin/* with the standard mapping?
```

If the answer cannot be proven exactly, fail closed.

A suitable failure result is:

```text
NONCANONICAL_ORIGIN_FETCH_CONFIGURATION_REQUIRES_ORDINARY_APPROVAL
```

Exact string is an implementation detail; the semantics are frozen.

## 9. Direct regression bank for RL-B2

### Case 1 — canonical full-heads refspec + remote reviewed branch exists

Fixture origin config:

```text
remote.origin.skipFetchAll = unset/false
remote.origin.fetch = +refs/heads/*:refs/remotes/origin/*
```

Remote contains:

```text
refs/heads/reviewed/<task_key>
```

After:

```text
git fetch --all --prune
```

local must contain:

```text
refs/remotes/origin/reviewed/<task_key>
```

Bootstrap rejects before mutation.

### Case 2 — reviewed branch deleted remotely

With the same canonical config:

- establish the reviewed remote-tracking branch;
- delete the remote fixture branch;
- run `git fetch --all --prune`;
- verify local `refs/remotes/origin/reviewed/<task_key>` is pruned;
- bootstrap may continue if all other conditions pass.

This proves both positive freshness and deletion freshness.

### Case 3 — main-only/custom fetch refspec

Examples:

```text
+refs/heads/main:refs/remotes/origin/main
```

or any noncanonical/multiple/negative fetch configuration.

Expected:

```text
NONCANONICAL_ORIGIN_FETCH_CONFIGURATION...
```

before trusted bootstrap mutation.

Do not claim remote reviewed-branch absence.

### Case 4 — skipFetchAll origin

Effective:

```text
remote.origin.skipFetchAll = true
```

Expected:

- trusted preflight fails closed;
- do not rely on `git fetch --all --prune`;
- no bootstrap mutation.

### Case 5 — stale base commit

After canonical fetch:

- current local `origin/main` = OID B;
- caller passes expected base OID A.

Bootstrap rejects before mutation.

### Case 6 — zero network inside bootstrap

Instrument/canary the bootstrap implementation.

Expected:

- no fetch;
- no ls-remote;
- no provider/network operation;
- only local config/ref/worktree operations.
