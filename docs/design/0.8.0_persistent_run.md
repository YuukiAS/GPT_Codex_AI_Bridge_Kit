# Bridge Kit 0.8.0 — Persistent Run

Status: frozen implementation plan for the next minor release. This document defines the intended product boundary; it does not itself install or enable Persistent Run in any consumer repository.

Baseline used for this plan:

- Bridge Kit `main`: `761d3388ecbec4e7d1ebf6dae9a68e9be75979f3` (`0.7.3`)
- production reference: `YuukiAS/Distributed_Imaging_Inference` `main` at `2f3ceb823168a55814bca677fa9587869a128459`

## 1. Decision: this is `0.8.0`, not `0.7.4`

Bridge Kit currently treats a new independently usable capability as a new `0.x` minor line, while patch releases mainly correct safety, compatibility, or default behavior. Persistent Run is a new project-level capability that can be installed and used independently of Lite / Review / Control, so the correct release target is `0.8.0`.

Persistent Run is **not a fourth workflow**.

The workflow axis remains:

```text
Lite
Review
Control
```

Persistent Run belongs to the optional project-capability axis:

```text
Machine layer
└── Host Policy

Project workflow
├── Lite
├── Review
└── Control

Optional project capabilities
├── Persistent Run
├── Generic Notifier
├── Overleaf Bridge
├── Visual Review
└── other existing optional capabilities
```

Therefore valid combinations include:

```text
Host Policy + Lite + Persistent Run
Host Policy + Review + Persistent Run
Host Policy + Control + Persistent Run
```

Long runtime, GPU runtime, many stages, or overnight execution must not by itself force a task from Lite into Review or Control. Review / Control remain about planning, independent review, authority and risk; Persistent Run is about execution surviving the interactive Codex / SSH session.

## 2. Product problem

The production failure is not primarily “Codex cannot write a training script”. The failure is that a correctly specified long-running goal can still be interrupted by the lifecycle of the interactive agent session or by Codex inventing a different background mechanism when a launch or diagnostic is inconvenient.

`Distributed_Imaging_Inference` demonstrates the required behavior in a real research task:

- a long multi-stage goal reuses an existing interactive Slurm allocation;
- the actual experiment must survive Codex / SSH disconnect;
- a persistent tmux master/orchestrator owns the run;
- lock, heartbeat, stage-state, atomic outputs and resume semantics provide observable recovery state;
- `squeue`, `ps` and tmux session inspection are diagnostics, not completion evidence;
- an optional diagnostic or secondary arm must not terminate the whole scientific goal;
- “job/session is still running” is not equivalent to scientific completion.

0.7.2/0.7.3 Host Policy already reduces approval friction for the read-only observation side (`squeue`, `scontrol show`, `ps`, `tmux ls` / `has-session`, routine Git synchronization). Persistent Run solves the different project-level problem: how an explicitly authorized long task is represented, launched, resumed and completed without inventing a new workflow role system.

## 3. Product outcome

After a repository installs Persistent Run, a normal user should be able to:

1. keep using the repository's existing Lite, Review, Control, custom Goal, or plain task entry point;
2. mark a particular task / Goal as requiring persistent execution;
3. send one explicit user-visible kickoff authorization for that task;
4. have Codex use the canonical tmux persistence route instead of `setsid`, `nohup`, background `&`, or ad-hoc process-manager fallbacks;
5. reconnect later and recover from the existing tmux/session + lock/heartbeat/stage-state/resume evidence;
6. avoid duplicate launch when the same persistent run already exists;
7. continue ordinary in-scope engineering recovery without treating an optional diagnostic failure as a terminal blocker;
8. still judge completion by the original Goal's observable completion criteria, not by process/session existence.

Persistent Run does not decide the scientific task, resource budget, model, dataset, deployment semantics, or review policy. Those remain owned by the original Goal / task / workflow.

## 4. Alternatives considered

### A. Only patch each research repository's `AGENTS.md`

This is appropriate for immediate incident repair but not for the reusable solution. The same tmux / explicit-kickoff / resume / no-fallback behavior would be copied across DII, future HPC projects, long data-processing repositories and other server work.

Decision: keep repository-specific scientific/resource rules in each repo, but move the reusable persistence contract into Bridge Kit.

### B. Fold Persistent Run into Lite

Rejected. Many Lite repositories do not run long-lived work and should not receive tmux/HPC-style execution rules. Lite must remain the default low-friction handoff layer.

### C. Create a fourth workflow beside Lite / Review / Control

Rejected. Persistent execution introduces no Planner, Reviewer, Critic, authority transfer, review round or new decision owner. Calling it a workflow would conflate runtime lifetime with governance.

### D. Build a custom daemon / process manager

Rejected for `0.8.0`. Mature runtime mechanisms already exist. The first production backend is tmux. Bridge Kit should standardize the contract around tmux rather than reimplement a weaker process manager.

### E. Globally allow `tmux new-session`, `setsid`, generic shell, `sbatch` or `salloc`

Rejected. Those are materially broader execution capabilities than the read-only Host Policy introduced in `0.7.2/0.7.3`. Persistent Run should first use explicit current-user authorization plus a canonical project contract. Do not expand global execpolicy merely to avoid designing the project execution contract correctly.

## 5. `0.8.0` implementation surface

Add one new Bridge Kit CLI family:

```text
ai-bridge persistent-run install --target /path/to/repo
ai-bridge persistent-run validate --target /path/to/repo
ai-bridge persistent-run prompt kickoff --target /path/to/repo --goal <repo-relative-goal-path>
```

The first release deliberately has **no** `start`, `stop`, `kill`, `submit`, `allocate`, `cancel`, daemon, watcher, scheduler or background-service command.

### Installed project files

The installer owns only:

```text
automation/persistent_run/README.md
automation/persistent_run/CONTRACT_TEMPLATE.md
automation/persistent_run/KICKOFF_TEMPLATE.md
```

and one managed block in the repository root `AGENTS.md`:

```text
<!-- ai-bridge-kit:persistent-run:start -->
...
<!-- ai-bridge-kit:persistent-run:end -->
```

Source templates live under:

```text
templates/persistent_run/
```

The installer must be idempotent and must preserve all user-owned `AGENTS.md` content outside the managed block. It must not modify `$CODEX_HOME`, Host Policy, `.codex/rules`, Lite, Review or Control installation state.

Persistent Run must be installable into a Git repository that does not have Lite installed.

## 6. Contract template: no new state machine

`CONTRACT_TEMPLATE.md` is a small section intended to be copied or referenced by an existing Goal/task. It is not a second Plan and not a state machine.

It should cover only the execution facts needed for persistence, with placeholders such as:

```text
Persistent execution: REQUIRED
Backend: tmux
Goal source: <repo-relative path>
Run/session key: <project-owned stable key>

Authorized effects:
- execute the already-frozen task / Goal;
- use only resources already authorized by that Goal;
- write the Goal's logs/checkpoints/results/state artifacts;
- continue after Codex / SSH disconnect.

Forbidden expansion:
- changing scientific/product scope;
- silently changing data/split/model/budget/resource semantics;
- requesting/cancelling resources unless the Goal explicitly allows it;
- switching to `setsid`, `nohup`, background `&`, screen, sudo or another persistence backend just because tmux launch/inspection failed.

Recovery evidence:
- tmux session identity;
- project-native lock / heartbeat / stage-state / checkpoint / resume evidence, or equivalent observable state.

Completion:
- session/job existence is not completion;
- the original Goal's completion criteria remain authoritative.
```

Do not define a universal JSON schema for heartbeat/stage-state in `0.8.0`. Consumer repositories may already have valid state formats. Persistent Run standardizes the semantics, not a new storage format.

## 7. Kickoff template: explicit current-user authorization

A repository Goal file may describe persistent execution, but production evidence shows that runtime approval can still interpret a long unattended launch as lacking current user authorization. Therefore Persistent Run must include an explicit **user-visible kickoff template**.

`KICKOFF_TEMPLATE.md` and `ai-bridge persistent-run prompt kickoff ...` must render a concise prompt equivalent to:

> I explicitly authorize execution of the referenced frozen Goal using its Persistent Run contract. Start or resume the required persistent tmux session, execute the already-authorized work, use only the resources authorized by that Goal, write its declared artifacts, and allow the run to continue after Codex/SSH disconnect. Do not ask again merely because the task is long-running or unattended. This authorization does not permit scope expansion, different compute resources, cancellation, sudo, or fallback to another persistence backend unless the Goal explicitly permits it.

The command only prints text. It does **not** create a session or claim that a generated file is equivalent to current-user approval. The user must actually send/submit the kickoff prompt through the active task interface.

Once this explicit kickoff is present, Codex should not repeatedly ask for approval merely because later stages remain part of the same frozen persistent Goal. A genuinely new side effect outside the Goal still follows normal approval rules.

## 8. Managed AGENTS behavior

The Persistent Run AGENTS block must establish a single canonical execution path for tasks whose Goal/contract says persistent execution is required.

### Before launch

1. read the current Goal/task and its persistent execution contract;
2. confirm that the current user-visible request contains the explicit persistent kickoff authorization;
3. inspect the canonical tmux session name with `tmux has-session` / `tmux ls`;
4. inspect project-native lock/heartbeat/stage-state/resume evidence when present;
5. use scheduler/process diagnostics only as supporting evidence;
6. do not require host-wide process inventory as perfect proof that no stale run exists.

### Launch

- use tmux as the `0.8.0` persistence backend;
- use the repo/Goal-owned launcher or command rather than inventing a generic Bridge-owned scientific orchestrator;
- create at most one canonical session for the run key;
- after launch, verify session existence and the strongest available project-native progress evidence;
- the launching Codex session may then disconnect without terminating the run.

### Resume

- reconnect to the same run identity rather than creating a duplicate;
- inspect stage-state / heartbeat / checkpoint / output evidence before deciding what is incomplete;
- resume only work allowed by the original Goal;
- stale session or lock evidence must be reconciled against stronger observable state rather than blindly trusted.

### Failure behavior

- no automatic fallback from tmux to `setsid`, `nohup`, bare `&`, screen, sudo, new resource allocation or job cancellation;
- optional diagnostic failure is not a terminal task failure when stronger state exists;
- ordinary in-scope engineering faults may be repaired/resumed as allowed by the Goal;
- only the original Goal/workflow may define scientific/product hard blockers;
- if the canonical tmux launch is still denied after explicit current-user kickoff, report the exact rejected command and reason. Do not bypass the denial by switching persistence mechanisms.

### Completion

A live tmux session, live Slurm job, PID, heartbeat or checkpoint proves activity/state, not task completion. Persistent Run never weakens the Goal Fidelity / completion requirements of Lite, Review, Control or a custom research Goal.

## 9. Host Policy relationship

`0.8.0` must keep the `0.7.3` Host Policy boundary unless new direct production evidence from implementation testing proves a specific change is required.

Already-low-friction observation stays available:

```text
squeue / sinfo / sacct / sstat / sprio
scontrol show / ping
ps
tmux ls / list-sessions / has-session
git fetch origin main
git fetch --all --prune
```

Persistent Run does not globally preauthorize:

```text
tmux new-session / send-keys / kill-*
setsid / nohup
sbatch / salloc / srun / scancel
kill / pkill
sudo
generic shell / generic Python
```

Do not add a DII-specific job ID or other transient allocation identifier to Bridge Kit policy.

## 10. Integration with Lite / Review / Control

Persistent Run owns **execution lifetime only**.

- Lite remains the default task handoff and completion-report structure.
- Review keeps Planner / Executor / Reviewer ownership exactly as before.
- Control keeps its role authority/state machine exactly as before.
- Persistent Run must not add Planner, Reviewer, Critic, review rounds, new workflow terminal states or independent completion authority.
- Existing Notifier/Overleaf/Visual/Text capabilities remain orthogonal.

When a Review/Control task uses Persistent Run, the Codex Executor may keep the approved implementation/execution alive through tmux, but it still cannot self-promote workflow state or perform Planner/Reviewer work.

## 11. Tests

Add focused unit tests, preferably `tests/test_persistent_run.py`, covering at least:

- install into a real temporary Git repository;
- installation does not require Lite;
- existing user `AGENTS.md` content is preserved;
- managed block is appended/updated idempotently;
- Bridge-owned Persistent Run files are installed at the expected paths;
- repeated install is stable;
- validate passes for a correct install;
- validate fails clearly when a required managed file/block is missing or malformed;
- kickoff prompt requires a repo-relative existing Goal file and rejects path escape;
- rendered kickoff includes the exact Goal path and explicit persistent authorization semantics;
- installer/validator do not write `$CODEX_HOME` or `.codex/rules`;
- CLI dispatch works through `ai-bridge persistent-run ...`;
- existing Lite / Review / Control / Host Policy tests remain green.

Run the repository's full existing test suite, not only the new tests.

## 12. Real/runtime acceptance

Mechanical tests are insufficient. Before calling `0.8.0` complete:

1. install Persistent Run into a temporary worktree/copy of a real consumer repository such as `Distributed_Imaging_Inference` and validate the actual resulting files/AGENTS composition;
2. if tmux is available on the implementation host, perform one harmless real detached-session smoke using the standard explicit kickoff authorization: start a bounded task-owned session, verify it is observable through the canonical read-only tmux queries, verify its output/progress evidence, and clean up only that task-owned smoke session;
3. confirm that no `setsid` / `nohup` / bare `&` fallback is used;
4. confirm that the Persistent Run install path did not modify Host Policy or workflow state;
5. treat the current DII incident as the production reference for wording and failure modes, but do not modify or launch DII scientific experiments from the Bridge Kit implementation task unless separately authorized.

If the canonical tmux launch is still rejected by Auto-review even though the current user-visible implementation prompt explicitly authorizes the bounded Persistent Run smoke, do **not** broaden Host Policy or silently add a generic launcher. Return `REVISE` with the exact rejected command/reason so the architecture can be reconsidered from real evidence.

## 13. Red-team conditions

`0.8.0` is not complete if any of these are true even when unit tests pass:

- normal user installation does not cause the target repository's AGENTS to route persistent tasks through the new contract;
- kickoff text exists only in documentation but there is no clear user-facing way to obtain/send it;
- Codex still treats a live tmux session as task completion;
- a stale tmux session or stale lock can silently suppress a new run without checking stronger state;
- the implementation quietly falls back to `setsid`, `nohup`, bare `&` or another backend;
- Persistent Run changes scientific/resource scope or scheduler semantics that belong to the Goal;
- installing Persistent Run silently installs Lite, Review, Control, Host Policy or project-local execpolicy;
- a synthetic fixture is used as the only evidence that the real tmux lifecycle works;
- the capability becomes a new Planner/Reviewer workflow under another name.

## 14. Release changes

If implementation and acceptance pass:

- bump `0.7.3 -> 0.8.0` in `pyproject.toml` and `ai_bridge_kit/__init__.py`;
- add `ai_bridge_kit/persistent_run.py` and dispatch in `ai_bridge_kit/bridge_cli.py`;
- add `templates/persistent_run/` sources;
- add tests;
- update `README.md`, `QUICKSTART.md`, `AGENTS.md`, and `CHANGELOG.md` to show Persistent Run as an optional project capability rather than a fourth workflow;
- keep the three workflow display names unchanged: Lite / Review / Control;
- do not modify Host Policy rules unless a new reproduced blocker from the real acceptance step is returned to the user for a separate decision.

## 15. Release claim

The allowed release claim is narrow:

> Bridge Kit 0.8.0 adds Persistent Run, an optional project capability for explicitly authorized long-running tasks to use a canonical tmux persistence contract, survive Codex/SSH disconnect, resume from project-native observable state, and preserve the original workflow's completion and authority semantics.

Do not claim that `0.8.0` makes every long command approval-free, manages Slurm automatically, replaces scheduler batch jobs, or guarantees recovery from arbitrary machine/node failure.
