## 4. P1 implementation contract — sandbox-first without authority regression

Managed Host guidance must state, in executable behavior terms:

- ordinary repo/workspace-contained build, test, lint, render, QA, deterministic
  scripts and task-owned generated output use normal `workspace-write` first;
- Python, TeX, shell-script or compiler identity alone is not a reason to request
  escalation;
- writing inside the allowed workspace is not itself an authority boundary;
- do not pre-emptively request `require_escalated` for ordinary workspace work.

Preserve existing upfront authorization semantics:

- current-user bounded authorization;
- frozen Goal/Plan/contract;
- existing authority contracts;
- trustworthy static effect analysis

may establish a real future authority boundary before command execution.

Known private transfer, paid/external call, deployment, migration,
scheduler/resource allocation, Persistent Run launch, destructive action, or changed
provider/artifact/recipient/purpose/resource/cost/backend scope still uses the
existing approval/HUMAN_ONLY route.

Do not intentionally trigger a forbidden effect just to prove it is forbidden.

## 5. P2 implementation contract — refusal classification

Managed Host guidance must require classification before another authority route is
attempted:

```text
OPTIONAL_NOT_REQUIRED
-> skip and continue required work

SANDBOX_CAPABLE_BUT_ESCALATED
-> if the effect has not already happened, return only to ordinary sandbox execution

BOUNDED_NORMAL_ENTRY_BLOCKER
-> preserve completed work
-> do not widen to raw operation
-> use only an already-defined legal recovery or report the exact unresolved effect

TRUE_AUTHORITY_OR_SAFETY_BOUNDARY
-> existing approval / HUMAN_ONLY / Planner route
```

These labels are explanatory vocabulary only; do not add repository/runtime state
enums or schemas.

A refusal does not create authorization for another, broader
`require_escalated` attempt.

One Goal must not chase refusals through multiple fallback command shapes without new
evidence that the required effect or authority actually changed.

## 7. P4 implementation contract — Git config/credential safety

### 7.1 Process-level config/transport fence

Before any security-sensitive Git inspection, reject caller-controlled process
overrides on this approved list:

```text
GIT_CONFIG
GIT_CONFIG_GLOBAL
GIT_CONFIG_SYSTEM
GIT_CONFIG_NOSYSTEM
GIT_CONFIG_COUNT
GIT_CONFIG_KEY_*
GIT_CONFIG_VALUE_*
GIT_CONFIG_PARAMETERS
GIT_SSH
GIT_SSH_COMMAND
GIT_ASKPASS
GIT_PUSH_OPTION*
```

Do not turn this into a generic `GIT_*` deny sweep.

Before final candidate freeze, record the exact Git version used for the real gates
and perform the approved bounded compatibility check for additional formal
config-source/command-scope inputs on the same causal chain. A newly discovered
equivalent input returns Planner/Critic unless it is a direct same-mechanism omission
that the execution-ready Critic explicitly allowed to be incorporated.

### 7.2 Stable security-inspection environment

Add one internal, auditable security-inspection environment construction path.

Before any security-sensitive `git config`, effective remote URL, hook/config, or
related safety read:

- start from the current process environment;
- remove every rejected config-source/command-scope override above;
- remove rejected transport/askpass/push-option overrides;
- ensure caller `GIT_CONFIG_PARAMETERS` cannot reappear;
- inspect the repository's actual normal config stack.

All helpers used by the publisher for security decisions must accept/use that same
stable view. This includes current equivalents of:

- config value lookup;
- config key existence lookup;
- config entries with scope/origin;
- effective fetch/push URL resolution;
- hooks-path resolution when config-backed.

A safety decision from one config view may not be followed by a network operation
under another view.

### 7.3 Repository config fences

Retain fail-closed behavior for at least:

- effective `core.askPass`;
- local/worktree/command-scope executable `credential.helper`;
- effective custom SSH transport;
- active pre-push hook;
- mirror/follow-tags/submodule recursion/push options/signed-push expansion;
- wrong/multiple/effectively rewritten fetch/push URLs;
- wrong repo/branch/upstream;
- unsupported transport.

Existing accepted system/global GitHub HTTPS credential-manager behavior remains a
required positive neighbor.

### 7.4 Ambient SSH_ASKPASS positive path

An inherited `SSH_ASKPASS` value is no longer an automatic rejection on the
approved GitHub HTTPS positive path.

Safety is established by non-execution, not by trusting its value.

Before the first remote/network Git operation capable of authentication:

- build one sanitized network/push environment;
- remove `SSH_ASKPASS`, `GIT_ASKPASS`, every approved config-source/command-scope
  override including `GIT_CONFIG_PARAMETERS`, and rejected transport overrides;
- set `GIT_TERMINAL_PROMPT=0`;
- use that environment for remote read and final push.

If implementation discovers a required remote/network operation before this sanitized
environment can be established, stop and return Planner/Critic.

### 7.5 Required config canaries

ER-G4 must include both approved bypass shapes.

`GIT_CONFIG` canary:

```text
process GIT_CONFIG = clean substitute
real repo config = malicious core.askPass or credential.helper=!canary
-> fail closed before network/mutation
-> executable canary count = 0
```

`GIT_CONFIG_PARAMETERS` canary:

```text
process GIT_CONFIG_PARAMETERS injects executable credential.helper
-> fail closed before network/mutation
-> executable canary count = 0
-> stable inspection env does not inherit the variable
-> sanitized remote/push env does not inherit the variable
```

No raw push fallback is permitted in either case.

### 8.1 Formal release reference

Do not compare runtime health to latest `main`.

When a local canonical release ref is available, use the locally known
`release` target as formal-release identity and state explicitly whether freshness
has been proven.

No `git fetch` is performed merely by `host validate`.

### 8.2 Severity contract

Hard incompatible/failure:

- trusted executable and imported package resolve to different active Bridge
  installations/sources in a way that can change executed behavior;
- imported/package/source version identity is internally contradictory;
- a runtime claiming the same locally known formal release version resolves to a
  different source commit than that release target;
- required Machine Policy capability/support is missing.

Warning, not automatic incompatible:

- stale duplicate distribution metadata exists but does not win executable/import
  resolution;
- active editable source is dirty while otherwise pointing at the intended source;
- local release ref is absent or freshness is unknown because no fetch was authorized;
- an intentionally activated pre-release candidate has a version ahead of the current
  formal release, provided an external exact-candidate gate separately binds its
  expected SHA/version.

Dirty editable source must clearly warn that current bytes may differ from committed
HEAD. Normal `host validate` does not claim byte-exact release in that state.

The exact-candidate Stage B gate is stricter than ordinary `host validate`: it must
bind the candidate SHA/version and reject dirty candidate source.

### 8.3 Duplicate metadata

Use installed distribution metadata only as diagnosis.

If multiple historical metadata records exist but actual executable/import resolution
is unambiguous, warn and record them. Do not fail simply because stale metadata
exists.

If metadata ambiguity corresponds to different active executable/import resolution,
fail.
