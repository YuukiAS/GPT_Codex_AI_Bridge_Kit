## 7. C4 — Persistent Run 必须进 release Gate

**结论：需要测，而且必须是真实 Persistent Run 正常入口；但只需要一个短、有界、本地 canary，不需要跑长时间真实业务任务。**

原因很简单：Persistent Run lifecycle/status 是当前 0.11.0 五项正式用户能力之一。如果 release Gate 只跑 unit test / JSON schema，而没有真实 `persistent-run start/status` + tmux lifecycle，最终只能证明代码结构存在，不能证明用户断线后仍能看到真实 run 状态。

当前 C4 设计是合适的，Gate 至少直接证明：

1. 从正式 `persistent-run start` 启动一个安全、短时、无外部副作用 child；
2. tmux detached 后，从另一个 fresh CLI invocation 重新 `status`，仍看到同一 run；
3. 同一 active run 再次 `start` 返回 existing，不能创建第二个 child；
4. child 真正退出后，只有 supervisor 的 `child.wait()` observation 产生 exit code；
5. 无 progress source 时诚实返回 `UNKNOWN`；
6. nonterminal binding + missing session 不自动 relaunch；
7. session/binding mismatch 不 takeover；
8. partial start / supervisor loss 不猜 terminal。

其中 1–5 应走真实 production entry；6–8 可用预先冻结的本地异常构造验证，不需要另跑长任务。

**不需要**：

- app-server；
- Progress display thread；
- Gmail；
- Clear Writing；
- overnight duration；
- 多轮反复 canary；
- 用户人工盯着 tmux。

所以 C4 Gate 是必要的，但已经是本次 reset 后应有的最小测试，不是旧 G14 那种大而耦合的验收。
