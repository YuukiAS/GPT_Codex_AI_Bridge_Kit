## 2. v0.2 的核心产品判断

当前 0.11.0 仍应整体重置，而不是继续修 v0.8。正式 0.10.0 到旧实验 main 的问题不是“最后一个 canary 没过”，而是将低打扰执行、控制源读取、长期运行、显示线程、通知、Clear Writing、app-server 和工作树交换绑成一个候选，使可选表达层和内部线程拓扑获得了不应有的发布否决权。

v0.2 保留版本号 `0.11.0`，但最终最小产品范围调整为五项彼此独立的能力：

1. 低打扰 Host Policy；
2. execution context + mandatory source 的 exact truth；
3. Bridge 管理指令的写入前预算；
4. 本地 Persistent Run 生命周期与状态；
5. 自动通知的一次性 Clear Writing 表达层。

第五项是 v0.2 相对 v0.1 唯一新增回产品范围的能力。它恢复用户已经明确要求的结果，但不恢复任何旧 app-server、持久 reader、Progress display thread、共享 server、跨 workflow event bus 或 G14 拓扑。

## 3. 如果今天从正式 0.10.0 重新开始，还会这样设计 0.11.0 吗？

不会采用旧 v0.8。

从 `release@9db19b0409816c22042a246b35a33e1d34fedd0a` 重新开始，今天会选择：

```text
Host 精确低风险规则
+ 一个启动前 execution/source preflight
+ 一个 managed-writer projected-byte preflight
+ 一个 run-scoped tmux supervisor / binding / status
+ 一个 one-shot Clear Writing notification adapter
```

而不会选择：

```text
shared app-server
+ dedicated Progress display thread
+ fresh app-server reader thread
+ thread injection / reconnect
+ multi-agent / instructionSources readback
+ production worktree exchange transaction
+ cross-workflow event bus / intent propagation
```

旧实现可以作为“为什么不能这样设计”的证据，但不因沉没成本获得保留资格。

## 4. 五遍预检的更新

### 4.1 产品

用户正常使用仍通过现有 `ai-bridge`、Lite/Reviewed/Control 正常入口和 `persistent-run` 命令。新增价值不是新的控制台或新工作流，而是：

- 安全高频操作少被打断；
- Executor 在正确位置、读到冻结控制源之后才启动；
- Bridge 不会通过自己写入的 `AGENTS.md` 块制造截断；
- 长任务断线后仍可用本地命令查到可证明的运行事实；
- 自动通知在真正发送前最多做一次 Clear Writing，自然中文失败时仍有确定性通知，不影响业务任务。

### 4.2 现实

当前仓库的旧 canary 已证明 app-server reader isolation 依赖并不成立，因此该路径不应继续作为发布基础。相反，以下能力已有直接现实基础：

- Host Policy / execpolicy；
- Git 当前仓库、worktree、commit 和 object database；
- `tmux`；
- 本地 JSON；
- 0.10 的 progress normalize/report/latest；
- 正式 `writing-style@yuukias-ai-skills`。

AI Skills 当前正式插件 `writing-style` 版本为 0.4，包含 `chinese-prose` 与 `writing-fidelity`。历史 release closure 已有 fresh normal `codex exec` smoke：实际安装的生产插件被加载，两个 skill 均进入运行，并产出正常中文改写。该历史证据只证明路线现实可行，不替代本次 0.11 final candidate 的 Gate。

OpenAI 当前官方 non-interactive 文档把 `codex exec` 定位为脚本、流水线和一次性 CLI 任务入口；`--ephemeral` 可避免持久化 session rollout，`--json` 可观察 `turn.started` / `turn.completed` 等事件。因此 one-shot Clear Writing 可直接建立在普通 `codex exec` 上，不需要 app-server client。

### 4.3 替代

- 继续 v0.8：拒绝，发布耦合和运行机制都过重。
- 删除 Clear Writing：拒绝，会删掉用户已明确要求的产品结果。
- 为 Clear Writing 恢复 app-server reader：拒绝，真实 runtime 已反证其 release-critical 隔离前提。
- 使用一次 fresh `codex exec --ephemeral`：采用；这是已有正式 skill 与平台一次性运行入口的最薄连接方式。
- 为 Persistent 建 daemon / watcher / database：拒绝。
- 为 mandatory source 建通用 Git controller：拒绝。

### 4.4 反证

本提案接受这些诚实结果：

- skill 或模型不可用时自动通知使用确定性 fallback；
- transport 失败时邮件可能发送失败，但业务状态不改变；
- progress 无依据时显示 `UNKNOWN`；
- stale Persistent Run 不自动复活；
- supervisor 丢失后 child 生死不可证明时显示 `UNKNOWN/UNAVAILABLE`；
- mandatory source 无法证明 exact content 时 child 数保持 0；
- session approval 不能证明跨会话延续时允许平台重新审批；
- 无排他 quiescence primitive 时不自动交换 worktree。

这些都优于通过更多控制层“推断成功”。

### 4.5 执行

本轮仍只冻结 Proposal 语义。Critic PASS 后，Planner 才形成同一范围的简短 Execution Plan、Canonical Goal 和 Kickoff Draft，再进入 execution-ready review。

## 5. 能力 A：低打扰 Host Policy

### 用户价值

可信开发仓库中的高频安全读取与窄的当前非 main 分支快进同步不再反复打断；真正危险的 Git、凭据、外部写入和高影响动作仍由 Codex/Host 的真实权限边界处理。

### 最小机制

继续使用 Host Policy / execpolicy 的精确命令形状。保留当前有独立价值的安全读取规则和 `ai-bridge host sync-current-branch`。不新增通用 Git parser、wrapper registry 或 controller。

### 正常入口

Codex 正常运行安全 Git/Slurm/process/tmux 读取；需要 clean、same-name、fast-forward-only 的当前非 main 分支同步时调用现有 bounded helper。

### 失败

dirty、diverged、错误 upstream、错误 repo、危险 transport/config/hook 等返回明确原因；不自动 stash、merge、rebase、force 或改变 branch topology。

### 发布地位

release-critical。

## 6. 能力 B：execution context 与 mandatory source exact truth

本节关闭 `BR11-RESET-R0-F02_SOURCE_BINDING_TRUTH_UNDERSPECIFIED`。

### 6.1 task locator 的唯一真值

每次 Bridge-managed Executor launch 必须在启动前冻结并消费：

```text
repo_root
worktree_path
branch
expected_commit
mandatory_source_paths
```

其中 `expected_commit` 必须是 exact commit OID，不允许用“当前 branch 大概是对的”、远端 branch 名或旧聊天摘要代替。

当前 worktree 的 `HEAD` 必须等于该 `expected_commit`。如果不等，返回 context mismatch；不得切换 branch、搬 worktree 或寻找旧候选来“修正”。

### 6.2 mandatory source authority

每个 mandatory source 的唯一 authority 是：

```text
exact repository
+ exact expected_commit
+ exact repo-relative path
→ exact Git blob content
```

worktree 文件本身不是 frozen authority。

因此：

- unrelated dirty worktree 不构成全局 blocker；
- 不再使用整个 worktree 的 `require_clean=True` 作为启动条件；
- 只有 task locator、mandatory paths 和已有 workflow 自己明确拥有的冲突才可阻断；
- mandatory path 的 worktree copy 若与 `expected_commit` 对应内容不一致，绝不能静默作为 frozen source；
- 0.11 的默认语义是对此 path 返回 `MANDATORY_SOURCE_WORKTREE_MISMATCH` 并停止 launch；不在本版本增加“同时信任 commit blob、忽略冲突 worktree copy”的例外；
- 若仓库存在合法文本归一化，比较应使用 Git 能证明内容等价的窄路径语义；无法证明等价时仍 fail closed。无论如何，交给 Executor 的 frozen text 始终来自 exact commit blob，而不是未经证明的 worktree bytes。

### 6.3 本地 object 优先

读取顺序固定：

1. 在禁止 lazy fetch 的条件下解析 `expected_commit:path` 的 tree entry/blob OID；
2. exact blob 已存在本地时，直接使用普通 Git object read；
3. 不因为“已有 isolated helper”就把所有 source read 都改成 isolated path；
4. 只有确认 exact blob 本地缺失时才允许进入 isolated-object fallback。

这使 partial clone 成为 fallback 情形，而不是正常路径的默认复杂度。

### 6.4 isolated-object fallback

fallback 只接受：

```text
exact repo identity
exact 40-hex commit
exact repo-relative path
```

并满足：

- 临时 object directory 只位于 Bridge machine state；
- 原仓库 object store 只读；
- 不 checkout；
- 不改 branch/ref/upstream/remote/config/index/FETCH_HEAD；
- 不把 arbitrary URL/refspec 暴露给 caller；
- 读取后重新验证 protected Git state 与原 object store 未变化；
- 返回 exact blob OID、size、digest 和文本；
- 任一身份、路径、Git 安全边界或内容校验失败即停止。

它不是通用 `git show` wrapper，也不拥有 task lifecycle。

### 6.5 launch-before-read 禁止

所有 mandatory source 必须在模型和 Executor child 创建之前完成绑定和验证。

验收必须能直接证明：

```text
mandatory_source_failure
→ codex/model child count = 0
→ executor child count = 0
```

不能先启动 Codex 再让模型自己尝试补读，也不能在读取失败后用 prompt 摘要或旧缓存代替。

### 6.6 正常入口

只有真正拥有 Executor launch 的 Lite、Reviewed、Control 入口在最终 spawn boundary 前调用这一窄 preflight。没有 mandatory source 的普通操作不经过它。

## 7. 能力 C：Bridge-managed instruction 写入前预算

能力 C 保持 v0.1 方向，并补充 F04 对 Overleaf 的归属。

所有真正写 root `AGENTS.md` managed block 的 Bridge writer，在任何项目 mutation 前：

1. 内存构造更新后的文件；
2. 读取当前支持的 `project_doc_max_bytes` 与实际指令链；
3. 计算 projected UTF-8 bytes；
4. 检查对应 Bridge-owned block cap；
5. 超限时返回 `BRIDGE_MANAGED_INSTRUCTION_PROJECTED_OVERFLOW`；
6. 原文件 byte-for-byte 不变。

当前真实消费者至少包括：

- Lite/core writer；
- Persistent Run writer；
- Overleaf writer。

`ai_bridge_kit/overleaf.py` 当前接入的 projected preflight 属于本能力，应 `KEEP/SIMPLIFY`，不能在 reset 时机械恢复到 0.10 而删除。

用户自有 instructions 超限只诊断，不自动删、摘要、改写或提高 limit。本能力不扩成通用 runtime instruction auditor。

## 8. 能力 D：Persistent local lifecycle / status

本节关闭 `BR11-RESET-R0-F03_PERSISTENT_STALE_RUN_RECOVERY_UNDERSPECIFIED`。

### 8.1 最小运行对象

仅允许：

- 一个 exact run-scoped tmux session；
- 一个与该 run 同寿命的 supervisor；
- 一个 machine-local binding JSON；
- 一个 child process；
- 复用既有 `progress/report/latest`。

supervisor 只拥有这一个 child 的生命周期；child 结束后 supervisor 退出。它不是 daemon、watcher、中央 controller 或跨 run 调度器。

binding 记录观察到的事实，不建立新的全局 state machine。至少记录：

```text
repo
run_key
goal_sha256
session_name
launch_id
start_requested_at
child_started_at (optional)
child_pid (optional)
child_exit_observed_at (optional)
exit_code (optional)
```

`running/terminal/unknown/conflict` 等用户状态由这些事实与 exact tmux session 的当前存在性派生，不靠单独数据库宣告。

### 8.2 start / status 的 fail-closed 表

| binding | exact session | 可证明事实 | `start` 行为 | `status` 行为 |
|---|---|---|---|---|
| 不存在 | 不存在 | 尚无该 run 的本地启动证据 | 允许 new start | `NOT_STARTED` |
| compatible binding | exact active session 存在 | 已有同一 run owner | 返回 existing，绝不再建 child | `RUNNING` 或 `STARTING`，取决于是否已有 `child_started_at` |
| nonterminal binding | session 不存在 | 旧 run 曾启动/准备，但当前 lifecycle 无法证明 | `STALE_OR_UNAVAILABLE`，禁止自动 relaunch | `UNKNOWN/UNAVAILABLE` |
| binding 不存在或 identity 不匹配 | session 存在 | session ownership 不可证明 | `RUN_IDENTITY_CONFLICT`，禁止接管 | `CONFLICT` |
| terminal binding | session 不存在 | supervisor 已真实观察 child terminal | 返回 `ALREADY_TERMINAL`，同 run key 不自动再次运行 | 只报告已记录 terminal facts |
| terminal binding | session 仍存在 | terminal 记录与 runtime surface 不一致 | 禁止新启动 | `CONFLICT`，不修改旧 terminal facts |

再次运行必须使用新的明确 run identity / run key 或新的冻结任务决定；`start` 不是“再跑一次”按钮。

### 8.3 partial start

启动顺序应使不确定性可见，而不是自动补救：

1. 先原子写入只包含 frozen identity 与 `start_requested_at` 的 binding；
2. 尝试创建 exact tmux session；
3. supervisor 真正创建 child 后写 `child_started_at` 与 `child_pid`；
4. supervisor 亲自观察 `child.wait()` 返回后，才写 `child_exit_observed_at` 和 `exit_code`。

若调用方在任一步崩溃：

- binding 已存在但未看到 `child_started_at`：状态为 `UNKNOWN/UNAVAILABLE` 或 `STARTING`，取决于 exact session 是否仍存在；
- 不得因重试 `start` 自动 relaunch；
- 不以 PID 扫描、tmux 缺失或“没有观察到进程”推断 terminal；
- 不自动清理、接管或 restart。

### 8.4 supervisor 异常消失

如果 supervisor 异常消失而 child lifecycle 不能由 supervisor 的已记录 terminal observation 证明：

- 不自动 restart；
- 不把 session 消失等价为 child 完成；
- 不把旧 PID 是否存在升级成 completion authority；
- `status` 返回 `UNKNOWN/UNAVAILABLE`，并保留最后可证明事实。

exit code 只有 supervisor 真实观察 child 退出时才成为 terminal fact。

### 8.5 progress

项目原生 progress file 存在时继续使用 0.10 的 normalize/report/latest；无证据时 `UNKNOWN`。progress、Notifier、Clear Writing 或其他显示表面的失败均不得杀 child。

## 9. 能力 E：一次性 Clear Writing 自动通知表达

本节关闭 `BR11-RESET-R0-F01_CLEAR_WRITING_SCOPE_REGRESSION`。

### 9.1 产品语义

只要某个既有自动通知入口已经决定“这一封邮件应该发送”，它先形成一份 immutable canonical facts，然后进行一次表达转换：

```text
immutable canonical facts
→ 最多一次 fresh codex exec --ephemeral
→ 正式 writing-style@yuukias-ai-skills
→ writing-fidelity + chinese-prose
→ mechanical fidelity check
→ existing notifier transport
```

Clear Writing 只拥有用户可见措辞，不拥有 runtime、semantic completion、权限、recipient、transport 或业务状态。

### 9.2 不引入的机制

明确禁止：

- app-server client；
- WebSocket / JSON-RPC；
- persistent reader/session；
- dedicated Progress thread；
- shared app-server；
- `instructionSources=[]` Gate；
- multi-agent readback Gate；
- second model / second repair turn；
- cross-workflow event bus；
- 为所有 Lite/Reviewed/Control/Persistent 强制引入新 schema 或 intent；
- 让 Persistent Run start/status 等待该表达层。

### 9.3 输入

调用方必须先拥有发送 authority，并提供不可变事实包。它可以沿用该入口已有 brief/facts 结构，不建立新的全局事件协议。至少保护：

- task/run identity；
- notification purpose；
- status；
- 数字、比例、时间；
- `UNKNOWN`；
- 路径/版本/错误码等必须逐字保留的 token；
- 当前结论强度；
- next action（若事实源已有）。

adapter 不自行推断“任务完成”“发布就绪”或根因。

### 9.4 fresh `codex exec` 约束

每个 logical delivery：

- 最多启动一个 fresh `codex exec --ephemeral`；
- 使用当前选定 `CODEX_HOME` 中正式安装的 `writing-style@yuukias-ai-skills`；
- 明确要求使用 `writing-fidelity` 与 `chinese-prose`；
- 使用 read-only sandbox；
- 不 `resume`；
- 不在失败后再次调用模型；
- 使用 `--json` 或等价正式可观察入口验证本 logical delivery 的 `turn.started` 不超过 1；
- 正常路径必须有实际消费正式 installed skill 的证据，不能接受模型自称“用了 Clear Writing”；
- 若无法证明正式 plugin/skill 被消费，本次表达视为失败并 fallback。

当前 proposal 不冻结内部 plugin-cache 路径或 app-server discovery；Execution Plan 只可采用 Codex 正常 plugin/skill 入口与 AI Skills 已验证的 production invocation，不得重新造 discovery runtime。

### 9.5 mechanical fidelity

模型输出发送前执行确定性检查。至少验证：

- 所有受保护数字、比例、时间与 exact token 未改变；
- `UNKNOWN` 不得变成猜测；
- runtime-only 文本不得升级为 semantic completion；
- blocked/failed/pending 等极性不得被“润色”为成功；
- recipient、provider、路径、版本、任务 identity 不得被模型改写。

检查失败不进行第二次模型修复，直接 fallback。

### 9.6 fallback 与 transport

以下任一条件立即 deterministic fallback：

- plugin/skill 不可用；
- `codex exec` 启动或 turn 失败；
- 超过 one-turn 边界；
- 无法证明正式 skill 消费；
- 输出为空/无法解析；
- mechanical fidelity 失败。

fallback 仍进入现有 Notifier 发送流程，不 suppression。

如果随后 Gmail/transport 自身失败：

- 记录 transport failure；

### 13.1 回归归属

- 高频 Git 误打断与危险邻近绕过 → C1；
- `/tmp` 漂移、wrong worktree/HEAD、mandatory source 未读、partial clone → C2；
- Bridge-managed `AGENTS.md` overflow → C3；
- disconnect、stale binding、partial start、supervisor loss、terminal truth → C4；
- 自动通知的自然中文、one-shot、保真与 fallback → C5。

旧 G14 reader canary 只保留为删除旧路线的反证，不迁移到 C5。current fake app-server tests 也不能作为 C5 production evidence。

### 13.2 Gate 执行顺序

1. cheap deterministic regression bank 与 should-not-change；
2. C1 真实 Host execpolicy 正负例；
3. C2 真实 worktree + exact local blob + partial clone fallback；
4. C3 三类真实 writer under/overflow；
5. C4 真实 tmux lifecycle、stale/partial negative；
6. C5 一次真实 installed writing-style automatic delivery 与预先冻结的 failure/fallback negative；
7. 同一候选的完整测试、CI、README/CHANGELOG/安装身份核对。

C5 的正常路径需要真实模型调用，但只能在 C1–C4 和 cheap regressions 已通过、final candidate 已稳定后运行；开发期可先用 deterministic harness 验证 fallback/fidelity/one-call admission，不用反复消费真实模型。

## 14. normal user workflow

相较旧 v0.8，普通路径从一条跨多个 runtime 的链条缩为五个互不强耦合的薄点。

### 普通开发

```text
用户在已经选定的 repo/worktree 工作
→ Host Policy 自动放行窄的安全读取
→ launcher 做一次 exact context/source preflight
→ 通过后启动原本的 Executor
```

用户不需要理解 reader、display thread、shared app-server、event owner 或 Gate topology。

### 长任务

```text
persistent-run start
→ 一个 tmux session
→ 一个 run-scoped supervisor
→ child
→ binding/status + existing project-native progress
```

断开后只运行 `persistent-run status`。没有 app-server、Progress thread 或邮件前置条件。

### 自动邮件

```text
原 owner 已决定需要发送
→ immutable facts
→ 最多一次 fresh codex exec --ephemeral + Clear Writing
→ mechanical fidelity
→ 正常文本或 deterministic fallback
→ existing Notifier transport
```

Clear Writing 或 Gmail 失败都不会改变业务任务状态。

## 17. 风险与恢复

- **Clear Writing 再次膨胀：** C5 只允许一个 fresh `codex exec --ephemeral`、一个 turn、无模型重试；任何需要 app-server/session 的方案直接越界。
- **mandatory source 重新变成全局 clean Gate：** C2 明确只检查 task locator 与 mandatory paths；unrelated dirty 不阻断。
- **mandatory path 与 frozen source 冲突：** 不使用 worktree copy 冒充 authority；无法证明等价则 child=0。
- **Persistent 重复执行：** stale/partial/identity conflict 一律不自动 relaunch；terminal run 同 key 不自动再跑。
- **status 过度推断：** exit code 只来自 supervisor 的真实 child terminal observation；其余不确定性保持 UNKNOWN/UNAVAILABLE。
- **reset 误删有价值改动：** migration matrix 明确保留 Host rules/sync、compact AGENTS 与 writer projection。
- **reset 留下旧通知架构：** machine notifier profile、DEFAULTS、three-intent/canonical-event bus 明确删除。
- **Gate 再次耦合：** C1–C5 失败只说明对应能力失败；不通过把 unrelated runtime topology 塞入同一个 Gate 来“统一”。
- **行数压力导致偷工减料：** 行数只触发架构复审，不是通过标准。

## 18. 阶段价值

Proposal v0.2 若获得 design PASS，新增的是一个可以进入执行包设计的稳定产品决定：

- 旧 v0.8 明确退出 authority；
- 0.11.0 由五个独立、可正常入口验证的能力构成；
- Clear Writing 用户需求被恢复，但实现降到一次 fresh `codex exec`；
- source truth、Persistent stale recovery 和 reset migration 都不再留给 Executor 临场决定；
- Gate 按能力而非固定数量形成。

这仍不表示代码已实现、候选已冻结、真实 Gate 已通过或 release 已获授权。
