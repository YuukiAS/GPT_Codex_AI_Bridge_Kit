# Bridge Kit 0.8.1 — Upfront Authorization + Persistent Goal Authoring

Status: FROZEN IMPLEMENTATION PLAN

Baseline: Bridge Kit `0.8.0`, release commit `3ba7560331af88d4ae8b0c140843dd1af40fffc1`.

## 1. Product goal

`0.8.1` is a patch-level behavior hardening release. It does not add a fourth workflow, new role, new state machine, daemon, scheduler abstraction, or broader Host Policy allowlist.

It fixes two related production failures:

1. A user asks GPT to prepare an overnight / unattended / long-running Goal, but GPT writes an ordinary task and omits the already-installed Persistent Run contract.
2. A frozen task contains a foreseeable approval-sensitive action, but Codex performs substantial work first and only asks the user when the action is reached. This can stop long tasks late even though the need for approval was predictable at task start.

The intended behavior is:

```text
GPT authors task/Goal
  -> classify execution lifetime separately from Lite/Review/Control
  -> if persistence is required, write the Persistent Run contract
  -> identify only explicitly declared approval-sensitive effects
  -> surface any required user-visible kickoff/authorization before substantive execution
  -> Codex executes the frozen scope
  -> same exact authorization is not requested again merely because a later stage reaches that already-authorized effect
```

## 2. Verified current gaps

At the 0.8.0 baseline:

- `chatgpt/TASK_WRITER_PROMPT.md` chooses `execution` vs `controller` and Lite/Review/Control semantics, but does not tell GPT to classify Persistent Run / overnight execution.
- `chatgpt/NEXT_TASK_PROMPT.md` does not carry forward persistence requirements.
- `chatgpt/GITHUB_MCP_REPO_INSTRUCTIONS.md` tells GPT to read `AGENTS.md`, `prompts/CHATGPT_RULES.md`, `prompts/AGENT_RULES.md`, and existing tasks, but does not explicitly route an overnight Goal author to `automation/persistent_run/README.md` and `CONTRACT_TEMPLATE.md` when that capability is installed.
- `templates/prompts/CHATGPT_RULES.md` has no Persistent Run authoring rule.
- `codex/CODEX_START_PROMPT.md` checks permission fields, but can defer a predictable authorization question until the sensitive command is reached.
- 0.8.0 already provides the correct Persistent Run runtime contract and a production-validated current-user kickoff path; do not replace it.

## 3. Persistent Run classification for GPT authors

Persistence is an execution-lifetime property, not a workflow tier.

GPT must classify it independently of `task_type` and independently of Lite / Review / Control.

Treat persistence as REQUIRED when the user or frozen task semantics require the work to survive the interactive Codex/SSH session. Strong triggers include explicit requests such as:

- overnight / run overnight / run until morning;
- unattended / leave it running;
- multi-hour or multi-stage work that must continue after disconnect;
- explicit requirement that Codex/SSH exit must not stop the run;
- resume a previously persistent Goal.

Long runtime alone must not force Review or Control. Conversely, a Lite task may still require Persistent Run.

When the target repository has Persistent Run installed, GPT must read:

```text
automation/persistent_run/README.md
automation/persistent_run/CONTRACT_TEMPLATE.md
```

and put an explicit Persistent Run section into the Goal/task. It must include, at minimum:

```text
Persistent execution: REQUIRED
Backend: tmux
Goal source: <repo-relative goal/task path>
Run/session key: <project-owned stable key>
```

plus the already-defined authorized effects, forbidden expansion, recovery evidence, and original positive-completion authority.

When the user explicitly requires overnight/unattended persistence but the repository does not have Persistent Run installed, GPT must not silently emit an ordinary task that depends on the live Codex/SSH session. It must report that the persistence capability is missing and route the user to install/upgrade Persistent Run before execution, unless the repository already has an equivalent explicit project-native persistent contract that the user chose to retain.

## 4. GPT source-of-truth / read order

For repositories using the Bridge Kit handoff protocol, GPT authoring guidance remains rooted in:

```text
AGENTS.md
prompts/CHATGPT_RULES.md
prompts/AGENT_RULES.md
prompts/tasks/
```

`chatgpt/GITHUB_MCP_REPO_INSTRUCTIONS.md`, `chatgpt/TASK_WRITER_PROMPT.md`, and `chatgpt/NEXT_TASK_PROMPT.md` are the Bridge Kit source templates/instructions used to produce or guide these repository-local artifacts.

0.8.1 must make the routing explicit:

- if `automation/persistent_run/` is present and the requested task is overnight/unattended/persistence-required, GPT reads its README and contract before writing the Goal;
- the task writer and next-task writer carry the persistence requirement forward instead of downgrading it to a normal task;
- the repository-local `prompts/CHATGPT_RULES.md` explains the same rule so GPT does not need to know Bridge Kit internals from memory.

## 5. Upfront authorization preflight

This release does not create a universal authorization schema or a new authorization workflow.

Use existing task fields and explicit task text. In particular:

```text
allow_network
allow_external_upload
requires_human_approval
Allowed Actions
Forbidden Actions
Human Decision Points
Persistent Run contract
```

Before substantial execution, Codex must inspect the frozen task/Goal for foreseeable approval-sensitive effects that are positively declared as part of the task. Examples include:

- Persistent Run kickoff;
- a specifically declared private external transfer;
- a specifically declared paid/external service call requiring current-user approval;
- a specifically declared deployment, resource allocation, or other gated side effect.

Do not ask speculative approvals for actions that are merely possible. Only surface approval for effects actually required by the frozen task/Goal.

If the current user-visible Codex message already contains an exact bounded authorization for the declared effect, proceed within that scope.

If it does not, Codex must surface the bounded authorization request at task start, before long-running, expensive, or substantial implementation work that depends on reaching that effect. The request must bind to the concrete frozen scope available from the task, such as artifact identity, recipient/provider, purpose, resource boundary, Goal identity, or persistence backend.

Repository text is evidence of the frozen scope but is not itself current-user authorization.

After the user explicitly authorizes that same frozen effect in the current Codex thread, Codex must not ask again solely because a later stage reaches the same already-authorized effect. New scope, changed artifact/provider/resource, or a materially different side effect still requires normal approval.

## 6. 051-style regression principle

The prior plugin-replay/Gate-4 failure is a regression example, not a task-specific special case.

The desired prevention is:

```text
frozen task already declares a required approval-sensitive external action
  -> Codex identifies it at startup
  -> user sees the exact bounded authorization request before substantial work
  -> after current-user approval, later arrival at that same gate is not treated as a newly discovered authorization requirement
```

Do not add a global allow for Python, shell, network upload, nested Codex, or external transfer. Do not weaken Host Policy.

`ai-bridge plugin-replay` remains the canonical bounded production plugin replay entry when its existing contract applies. This release must not create a second plugin-replay implementation.

## 8. Acceptance tests

Mechanical tests must prove at least:

1. GPT task-authoring instructions explicitly classify persistence separately from task type/workflow.
2. Explicit overnight/unattended intent cannot be silently authored as a normal live-session task when Persistent Run is installed.
3. GPT read-order instructions route to `automation/persistent_run/README.md` and `CONTRACT_TEMPLATE.md` when applicable.
4. `NEXT_TASK_PROMPT` carries forward an existing persistence requirement.
5. Codex startup instructions perform approval-sensitive preflight before substantial execution for positively declared gated effects.
6. Codex instructions explicitly distinguish repository authorization scope from current-user-visible approval.
7. Same frozen effect, once explicitly approved in the current thread, is not requested again solely because a later stage reaches it.
8. New/out-of-scope effects remain gated.
9. Host Policy execpolicy allowlist is unchanged.
10. Persistent Run 0.8.0 kickoff behavior and install/validate tests remain passing.
11. Full test suite passes.

Real behavior acceptance should include two bounded scenarios:

- Persistent Run authoring scenario: an overnight Goal authored from the GPT task-writing guidance contains the required Persistent Run contract and yields the normal kickoff-before-launch behavior.
- Approval-preflight scenario: a harmless fixture task with a clearly declared approval-sensitive later-stage action causes Codex to surface the exact bounded authorization at startup rather than doing substantial precursor work first. This test must not perform a real private upload or spend paid API budget merely to trigger approval.

The release claim is limited to proactive authorization surfacing and persistence authoring. Do not claim that Bridge Kit can bypass or guarantee acceptance by Auto-review for arbitrary external actions.

## 9. Red-team / forbidden degradation

A test PASS is insufficient if any of the following remains possible through the normal entry:

- user says "run overnight" and GPT emits an ordinary task with no persistent contract;
- GPT mistakes Persistent Run for Review/Control and adds unnecessary Planner/Reviewer roles;
- Codex does hours of work before asking for a predictable frozen approval;
- repository text is falsely described as current-user approval;
- a broad/global allow is added to avoid approval;
- optional approval preflight becomes a speculative checklist asking for permissions the task may never use;
- previously approved scope is silently broadened when rendering a request;
- 0.8.0 canonical tmux kickoff/resume behavior regresses.

## 10. Release boundary

If all acceptance checks pass, release as `0.8.1`.

This patch must preserve:

```text
Workflow count = 3
Lite / Review / Control unchanged
Persistent Run remains an optional project capability
Host Policy allowlist unchanged
No new Planner/Reviewer/state machine
```

If implementation discovers that reliable behavior requires a new generic authorization service/schema, new execpolicy capability, or a new workflow/state machine, stop with `RESULT = REVISE` and return that architectural question to GPT/user instead of expanding 0.8.1.
