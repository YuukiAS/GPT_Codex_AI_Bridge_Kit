https://github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md

**OpenAI plugin/Marketplace**

Current official plugin guidance still supports repo/personal marketplaces and local plugin authoring/testing. Nothing in this amendment changes the v0.2 conclusion that ordinary plugin development belongs on the official route:

https://developers.openai.com/plugins/build/plugins

**Git SSH transport**

Current Git documentation states that:

- `GIT_SSH_COMMAND` / `GIT_SSH` replace the SSH program used by fetch/push;
- `GIT_SSH_COMMAND` is interpreted by the shell;
- `core.sshCommand` likewise replaces SSH and is overridden by the environment form.

Sources:

https://git-scm.com/docs/git  
https://git-scm.com/docs/git-config

**Git credential helpers**

Current Git credential documentation states that `credential.helper` invokes an external helper; a helper beginning with `!` is a shell snippet, an absolute-path helper is executed directly, and other helper names are transformed into `git credential-<name>`. The resulting command is executed through the shell.

Source:

https://git-scm.com/docs/gitcredentials

Git config exposes configuration scopes including `system`, `global`, `local`, `worktree`, and `command`. The current design treats system/global as host/user-controlled for HTTPS credential-manager compatibility, while local/worktree/command injection is outside the trusted low-friction publication boundary.

Source:

https://git-scm.com/docs/git-config

**Git askpass**

Current Git credentials documentation gives the prompt order:

```text
GIT_ASKPASS
-> core.askPass
-> SSH_ASKPASS
-> terminal
```

Any of the first three can name a local executable. The trusted low-friction publisher must not inherit a repository/caller-injected askpass executable.

Source:

https://git-scm.com/docs/gitcredentials

These facts are the complete new external basis for v0.3. No unrelated architecture research was reopened.

## 5. B — bounded publisher with transport-execution fence

### 5.1 Public shape and wrapper count remain unchanged

There is still exactly one bounded publication operation:

```text
ai-bridge host publish-current-branch   --expected-repo <canonical-repo-identity>   --expected-branch <branch>
```

`--expected-repo` and `--expected-branch` remain equality assertions only.

They cannot select:

- another remote;
- another branch;
- refspec;
- URL;
- upstream;
- force mode;
- delete mode;
- tags;
- transport executable;
- credential helper;
- askpass program.

The helper still derives repo/current branch/origin/same-name destination from actual current Git state.

No second wrapper is added.

### 5.2 All v0.2 exact-effect checks remain required

Before mutation the helper still must prove:

- canonical repository identity;
- exactly one effective fetch URL and one effective push URL;
- fetch/push repository identity equality;
- expected repo equality;
- symbolic current branch equals expected branch;
- upstream remote is exactly `origin`;
- upstream merge is exactly `refs/heads/<current>`;
- same-name remote branch already exists;
- remote is ancestor of the captured local HEAD;
- behind count is zero;
- no `remote.origin.mirror=true`;
- follow-tags disabled for this invocation;
- recursive submodule push disabled;
- inherited push options neutralized;
- signing/external signing program not part of the bounded push;
- no active effective pre-push hook;
- Review Executor process-local push guard remains authoritative;
- branch/HEAD/effective destination are rechecked immediately before mutation.

The internally generated mutation remains exactly one non-force ref update:

```text
<captured-local-oid>:refs/heads/<expected-branch>
```

### 5.3 New v0.3 transport trust boundary

The trusted publisher distinguishes **host/user transport configuration** from **repository/caller/process transport injection**.

The low-friction path may rely on:

- the ordinary installed Git client;
- standard HTTPS or standard SSH/scp-style Git remote transport;
- host/user-managed SSH configuration;
- system/global HTTPS credential managers;
- existing SSH agent state such as `SSH_AUTH_SOCK`.

The low-friction path must not execute a transport/auth program selected by:

- repository-local Git config;
- worktree Git config;
- inherited command-scope Git config;
- caller environment overrides.

Unsupported/custom transport cases fail closed to the ordinary raw `git push` approval path. They do not receive a new helper.

### 5.4 SSH publication fence

For an SSH/scp-style effective push URL, the low-friction helper requires the ordinary SSH transport path.

Before mutation:

1. inspect the inherited environment for:
   - `GIT_SSH`;
   - `GIT_SSH_COMMAND`;
   - `GIT_SSH_VARIANT`;
2. inspect the effective Git config, including origin and scope, for `core.sshCommand`;
3. inspect inherited command-scope Git config for transport-sensitive overrides.

Selected v0.3 rule:

- any non-empty inherited `GIT_SSH` or `GIT_SSH_COMMAND` -> **fail closed to ordinary approval**;
- any effective `core.sshCommand`, regardless of scope -> **fail closed to ordinary approval** for v0.9.0;
- `GIT_SSH_VARIANT` is removed from the trusted mutation environment after preflight so it cannot alter a caller-selected executable path;
- standard user `~/.ssh/config` and SSH agent use remain compatible because they are host/user transport configuration, not repository/caller Git executable injection.

This is intentionally conservative. A user who deliberately depends on `core.sshCommand` still has a legal path: ordinary raw `git push` with normal approval. v0.9.0 does not need to make custom SSH transports low-friction.

### 5.5 HTTPS credential-helper fence

For HTTPS publication, preserve normal system/global credential managers, including OS/keychain/Git Credential Manager style helpers.

Before mutation, enumerate effective credential-helper entries with origin/scope, covering both generic and URL-scoped forms:

```text
credential.helper
credential.<url>.helper
```

Selected trust rule:

- `system` / `global` helpers -> allowed as host/user-controlled credential infrastructure;
- `local` / `worktree` helper entry -> fail closed;
- inherited `command`-scope helper entry -> fail closed;
- this applies even when the value is empty/resetting, an absolute executable, a named helper, or a `!shell` snippet.

This prevents a repository/worktree from causing the trusted Bridge process to execute arbitrary credential code while preserving normal machine/user credential-manager setups.

The helper does not copy, store, inspect, print, or persist credentials.

### 5.6 Askpass fence

The trusted mutation path must not execute an arbitrary askpass program.

Before mutation:

- non-empty inherited `GIT_ASKPASS` -> fail closed;
- non-empty inherited `SSH_ASKPASS` -> fail closed;
- any effective `core.askPass` -> fail closed for the low-friction publisher.

The sanitized mutation environment sets:

```text
GIT_TERMINAL_PROMPT=0
```

so the bounded publisher either obtains authentication from already-configured allowed credential infrastructure or fails. It does not open an interactive password/token prompt from inside the trusted Host helper.

This does not remove the user’s ability to authenticate. If the repository needs askpass, use ordinary raw `git push` approval or configure a normal host/user credential manager.

### 5.7 Command/config environment fence

Because Git command-scope config can be supplied through process environment, the helper must examine the inherited process before sanitizing it.

If inherited command/config-source environment can alter safety-critical transport, hook, credential, destination, or push behavior, the low-friction helper fails closed.

At minimum the implementation must account for command-scope mechanisms such as:

```text
GIT_CONFIG_COUNT
GIT_CONFIG_KEY_*
GIT_CONFIG_VALUE_*
```

and config-source overrides that would prevent the preflight from meaningfully establishing the expected system/global/local/worktree scopes.

The implementation may choose either of these equivalent bounded approaches:

1. reject such inherited custom config environment wholesale for the low-friction publisher; or
2. prove that every inherited entry is non-safety-critical, then omit the command-scope/config-source overrides from the mutation subprocess.

The preferred minimal implementation is **reject when present in a way that changes the safety-critical effective config**, because custom cases may use ordinary approval.

### 5.8 Captured/sanitized mutation environment

After all inherited-state checks pass, construct a mutation environment from a captured baseline rather than passing the caller environment through unchanged.

For the Git push subprocess:

- do not pass `GIT_SSH`;
- do not pass `GIT_SSH_COMMAND`;
- do not pass caller `GIT_SSH_VARIANT`;
- do not pass `GIT_ASKPASS`;
- do not pass `SSH_ASKPASS`;
- do not pass unapproved command-scope Git config overrides;
- set `GIT_TERMINAL_PROMPT=0`;
- retain legitimate host/user mechanisms required by standard transport, including `SSH_AUTH_SOCK` and system/global credential-manager access;
- retain the v0.2 push-effect overrides that suppress tags, recursive submodule publication, push options, signing side effects, and hooks after the no-active-hook precondition has passed.

Immediately before spawning the push, re-evaluate the safety-critical facts:

- current branch;
- current HEAD;
- effective destination;
- mirror/follow-tags/submodule/push-option/signing state;
- effective pre-push hook;
- `GIT_SSH` / `GIT_SSH_COMMAND`;
- effective `core.sshCommand`;
- credential-helper scopes;
- askpass executable sources.

If any differs from the captured safe state, abort before mutation.

This is a TOCTOU fence, not a new state machine.

### 5.9 Review watcher ownership remains unchanged

The generic publisher remains prohibited as a Review Executor bypass.

Current `reviewed_runner.push_guard_environment()` uses process-local Git configuration to install a pre-push guard. That environment is intentionally outside the low-friction publisher’s accepted transport/config boundary.

Therefore a Review Executor that inherits the guard must cause the generic publisher to fail closed. Only the existing `reviewed_runner` publication path may publish validated Review progress.

No change to Reviewed watcher authority is proposed.

## 12. Recovery / rollback / should-not-change

### Publisher transport fence

Any unsafe/custom transport case performs no trusted-helper push.

It returns a precise reason such as:

```text
CUSTOM_SSH_TRANSPORT_REQUIRES_APPROVAL
REPO_CREDENTIAL_HELPER_REQUIRES_APPROVAL
ASKPASS_REQUIRES_APPROVAL
CUSTOM_GIT_CONFIG_REQUIRES_APPROVAL
```

Exact error names may be refined in implementation, but the semantics are:

```text
fail closed
-> ordinary raw git push approval remains available
-> no fallback wrapper
-> no auth/config mutation
```

The helper never edits the user’s Git config, credential configuration, SSH configuration, or environment to “repair” a custom transport.

### Reviewed worktree

Unchanged v0.2 bounded local rollback only.

### Persistent Run / Notifications

Unchanged v0.2.

### Naming

- Lite / Reviewed Mode / Controlled Mode are display labels for the same three existing workflow classes.
- `reviewed-handoff` and `agent-flow` compatibility identities remain.
- Machine Policy is still implemented by `ai-bridge host`.
- Notifications is still implemented by `ai-bridge notifier`.
- Review watcher authority remains.
- candidate-plugin-replay remains removed.
