## 4. B1 — publish preflight transport fence

### 4.1 Root cause to repair

Current `host.py` performs the first remote/network operation:

```text
git ls-remote --heads origin refs/heads/<branch>
```

before `_reject_transport_injection(...)`.

That violates the approved trusted-helper boundary because Git may invoke repo/caller-controlled SSH, credential, or askpass executable paths before the helper rejects them.

### 4.2 Required ordering

No remote/network Git command may occur until the transport/config/credential/askpass fence has been established.

Allowed local preflight before the fence includes only local repository/config inspection needed to decide whether the transport is safe.

The implementation must use one of these equivalent approved routes:

1. **preferred:** complete all rejection checks before the first remote/network Git command; then construct the sanitized environment and use that environment for every subsequent remote/network preflight and push;
2. **equivalent:** if a remote/network preflight is needed earlier, it must already run under the exact sanitized/captured environment whose executable/config boundary has been proven safe.

Do not use unsanitized `ls-remote`, `fetch`, or `push`.

### 4.3 Executable-canary regressions

For each case below, install a harmless executable canary that would write a marker if invoked. Invoke the normal bounded publisher path and prove:

```text
expected rejection occurs
canary marker remains absent
no remote ref changes
```

Required canaries:

- inherited `GIT_SSH_COMMAND`;
- inherited `GIT_SSH` when it can select an executable;
- inherited `GIT_ASKPASS`;
- inherited `SSH_ASKPASS`;
- repo-local `core.sshCommand`;
- worktree-local `core.sshCommand` where supported;
- local `credential.helper=!<canary shell>`;
- worktree `credential.helper=!<canary shell>` where supported;
- command-scope `credential.helper=!<canary shell>`.

Also keep deterministic regressions for:

- `GIT_CONFIG_COUNT / GIT_CONFIG_KEY_* / GIT_CONFIG_VALUE_*`;
- `GIT_CONFIG_GLOBAL`;
- `GIT_CONFIG_SYSTEM`;
- `GIT_CONFIG_NOSYSTEM`.

These config-source overrides must not cause a remote/network command to run under a different executable/config boundary before rejection.

### 4.4 Positive transport paths

The repair must not break the approved normal paths:

- standard HTTPS publication with existing system/global credential manager;
- standard SSH/scp-style publication with normal SSH agent / user SSH config and no custom Git SSH executable override.

Custom transports continue to fail closed to ordinary raw `git push` approval. Do not add a compatibility wrapper.

### 4.5 Final recheck

Immediately before the push, recheck all already-approved facts:

- branch;
- HEAD;
- effective destination;
- hook;
- mirror/followTags/submodule/push-option/signing state;
- SSH executable overrides;
- effective `core.sshCommand`;
- credential-helper scopes;
- askpass sources;
- config-source override environment.

## 5. B2 — complete Persistent Run reporter

### 5.1 Keep the current normalizer, add the missing product behavior

The existing `persistent-run progress --evidence` normalization may remain as a diagnostic/compatibility surface, but it is not sufficient for the approved 0.9.0 product.

Persistent Run must provide an event-driven reporter inside the existing product. Prefer the approved shape:

```text
ai-bridge persistent-run report --progress <project-native-progress-json>
```

Equivalent naming is acceptable only if it preserves the approved semantics and does not create a second workflow.

### 5.2 Contract fields

Extend the existing Persistent Run contract with explicit observational fields:

```text
Progress source locator:
Report interval:
Delivery mode:
Stall threshold:
```

These are project/run configuration, not workflow state.

The reporter reads the project-native source named by the contract. It must not infer domain progress from tmux/PID existence.

### 5.3 Normalized report

Every accepted progress event must normalize/render at least:

- task/run locator;
- observed timestamp;
- current stage;
- human-readable progress since previous real event;
- last real progress timestamp;
- completed/total/unit only when real;
- fraction only when a valid real denominator exists;
- ETA/expected finish only with defensible basis;
- ETA uncertainty;
- status: normal / slow / stalled / blocked / complete / failed;
- semantic completion claim remains false.

No fake percentage or ETA.

### 5.4 Machine-local latest + bounded history

Persist observational state under the existing Bridge machine-state home, in a Persistent Run namespace keyed by repository/run identity.

Required behavior:

- one queryable latest normalized report;
- bounded recent history sufficient for reconnect;
- history is observation only, not authorization/workflow state;
- bounded retention must be explicit/tested and cannot grow without limit;
- reconnect query does not require attaching tmux.

Do not add a new ledger/state-machine framework.

### 5.5 Event comparison, dedupe, cadence

Compare the new normalized event with the previous delivered/recorded event.

The approved semantics remain:

- start/resume -> report;
- meaningful stage transition -> report;
- blocked/stalled/failure/runtime completion -> prompt report;
- active long stage -> periodic report at the contract interval;
- default guidance approximately 60 minutes;
- do not default below 15 minutes without a task-specific reason;
- material ETA change:
  `abs(expected_finish_delta) >= max(15 minutes, 25% of prior remaining time)`;
- known <-> UNKNOWN ETA is always material;
- unchanged/non-material events may update latest/history but must be deduplicated/rate-limited for user delivery.

Reporter execution is event-driven by the project’s existing heartbeat/checkpoint/progress boundary. It does not become a timer daemon or watcher.

### 5.6 Optional Notifications projection

If contract `Delivery mode` requests Notifications and an already-authorized Notifications configuration exists:

- produce the existing one-shot `operational_progress` brief;
- use current recipient/provider only;
- preserve transport-only authority;
- delivery failure is recorded but does not kill/restart the underlying run.

If Notifications is unavailable/not authorized:

- persist local latest/history;
- report delivery unavailable;
- do not silently install/configure a provider.

### 5.7 Required B2 normal-entry evidence

Use a real bounded local multi-event process, not a single static JSON normalization call.

Case A — multi-event progress:

- process emits at least three real events across multiple stages;
- reporter consumes events through normal CLI entry;
- latest changes;
- history contains bounded ordered events;
- progress comparison is real;
- duplicate/non-material event is suppressed for delivery;
- material stage/ETA/progress event is surfaced;
- defensible ETA includes basis + uncertainty;
- optional Notifications projection is exercised only if the existing authorized configuration is available.

Case B — UNKNOWN/stall:

- separate run has no defensible ETA -> `UNKNOWN`;
- no real progress beyond task-declared test stall threshold -> `stalled`;
- last real progress timestamp is preserved;
- no automatic restart/cancel/resource mutation.

A bounded test-specific cadence/stall threshold may be shortened to make the gate practical; this must be explicit and must not change the production default guidance.

## 6. B3 — Reviewed frozen-scope fidelity

### 6.1 Stable frozen path identity

Current code calls `.resolve()` on both the stored REQUEST locator and caller assertion at use time. A changed symlink target can therefore move both identities together.

Repair this without adding a new authorization store/schema family.

Preferred bounded approach:

- the frozen REQUEST locator remains an absolute locator in the existing `User constraints` section;
- treat its stored lexical absolute value as the task identity instead of redefining it through current `.resolve()`;
- reject locator paths whose existing parent/path components introduce symlink redirection at freeze/use, or otherwise record/check an equally stable resolved-parent identity within the same existing REQUEST constraint surface;
- caller `--expected-worktree` remains equality assertion only;
- a symlink target change after freeze must fail before branch/worktree mutation.

Do not silently update the frozen locator to the new symlink target.

### 6.2 Base lineage for bootstrap

Before bootstrap creates a branch/worktree:

1. fetch/inspect the frozen `origin/<base_branch>` under the ordinary approved Git path;
2. require `base_commit` exists;
3. require `base_commit` has the required frozen lineage against `origin/<base_branch>` — at minimum `base_commit` must be an ancestor of the fetched frozen base branch reference;
4. only then create `reviewed/<task_key>` exactly at `base_commit`.

Commit existence alone is insufficient.

### 6.3 Preserve normal cases

Must continue to pass:

- exact sibling worktree bootstrap;
- exact `/tmp` worktree rematerialization;
- existing remote reviewed branch metadata/lineage checks;
- current-user kickoff remains authorization;
- REQUEST/CURRENT remain frozen scope evidence only.

### 6.4 Partial-failure rollback/evidence

Track which local objects were created by the current invocation:

- local reviewed branch;
- worktree registration/directory.

If a later step fails:

- remove only invocation-created local objects whose identity is still exactly the expected task identity and whose worktree has no user/task modifications;
- never delete remote refs;
- never reset/clean user work;
- never remove a pre-existing local branch/worktree;
- if safe cleanup cannot be proven, leave the partial local state intact and return precise recovery evidence identifying created objects and failure point.

Add tests for:

- bootstrap creation failure after local branch creation;
- resume worktree-add failure after invocation-created branch;
- cleanup refusal when ownership/cleanliness changes;
- no remote deletion.
