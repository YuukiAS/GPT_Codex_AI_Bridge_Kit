## 2. Frozen semantics

The following architecture is fixed and must not be re-decided by Executor.

### 2.1 Three independent questions

Before long or unattended work:

```text
A. Authorization readiness:
   Are all foreseeable, required HUMAN_ONLY effects in the frozen scope
   already covered by exact current-user authorization?

B. Process persistence:
   Who owns the lifetime if Codex/SSH/terminal disappears?

C. Progress reporting:
   What project-native evidence truthfully reports stage/progress/ETA/status?
```

Do not infer B or C from A.

### 2.2 tmux eligibility

Use Persistent Run/tmux only when:

1. the Goal must survive loss of the active Codex/SSH/terminal;
2. the required process/orchestrator would otherwise die with that session;
3. no scheduler/service/project-native owner already provides the needed lifetime;
4. the frozen Goal selects tmux and current-user authorization covers the bounded mutation.

Representative tmux-valid cases:

- terminal-owned foreground process;
- interactive environment plus a long terminal-owned orchestrator;
- multi-stage coordinator whose lifetime/resume identity would otherwise be bound to the current shell.

Representative tmux-not-required cases:

- scheduler-owned `sbatch` job after accepted submission;
- already-detached service/job;
- bounded single evaluation/inference with no survive-disconnect requirement;
- progress observation by itself.

### 2.3 DII 922349 reference must be described accurately

DII job `922349` is **reference evidence only** and must not be modified.

The current DII `resource_receipt.json` shows:

- `BatchFlag=1`;
- `SubmitLine=sbatch ... --wrap=... sleep ...`;
- job `922349` is therefore a **scheduler-owned batch holder**;
- formal GPU work enters the already-running allocation through:
  `srun --jobid=922349 --overlap ...`.

Therefore:

- Slurm owns the holder lifetime;
- tmux does **not** make job 922349 persistent;
- tmux's useful role is only where the orchestrator / repeated `srun` lifecycle is terminal-owned and must survive Codex/SSH disconnect.

Do not rewrite the existing DII Goal to retrofit this terminology.

## 4. Authoring behavior to implement

### 4.1 Replace duration-based persistence selection

Current guidance that treats these phrases as direct tmux/Persistent Run triggers must be corrected:

- overnight;
- unattended;
- multi-hour;
- multi-stage;
- leave it running;
- run until morning;
- survive disconnect.

New guidance must first ask what owns execution lifetime.

The authoring decision should be conceptually:

```text
unattended/long intent
-> perform upfront authorization readiness analysis
-> determine execution-lifetime owner
   -> scheduler/service/native detached owner exists:
      no tmux solely for duration
   -> terminal-owned process must survive disconnect:
      Persistent Run/tmux eligible
   -> no survive-disconnect requirement:
      ordinary execution
```

A user explicitly requesting tmux may still select tmux if it is compatible with the frozen Goal and authorization boundary.

### 4.2 Preserve explicit existing Persistent Run Goals

A previous task/Goal that already contains:

```text
Persistent execution: REQUIRED
Backend: tmux
```

must carry that explicit requirement forward unless the user/Planner changes it.

Do not reinterpret an existing explicit contract merely because 0.9.2 has better selection semantics.

### 4.3 Scheduler-native authoring

A scheduler-owned batch task may still be unattended and approval-sensitive.

Its authoring semantics are:

```text
upfront authorization readiness
-> exact scheduler/resource submission effect if required
-> scheduler owns lifetime after accepted submission
-> scheduler/project-native progress
-> no tmux solely because runtime is long
```

Do not globally authorize `sbatch`, `srun`, `salloc`, cancellation or resource mutation.
