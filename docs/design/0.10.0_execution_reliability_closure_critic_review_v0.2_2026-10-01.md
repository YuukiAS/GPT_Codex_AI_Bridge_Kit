## Only new blocker

```text
BR-ER-F04-GIT-CONFIG-PARAMETERS-COMMAND-SCOPE
```

The Critic independently verified that current Git source still defines
`GIT_CONFIG_PARAMETERS` as a command-config environment entry and that Git's own
tests exercise it. The Critic also verified that current OpenAI Codex safe Git command
construction explicitly removes `GIT_CONFIG_PARAMETERS`.

Proposal v0.2 explicitly fences `GIT_CONFIG`,
`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`,
and `GIT_CONFIG_COUNT/KEY/VALUE`, but does not name
`GIT_CONFIG_PARAMETERS`. Therefore the proposal has not yet proven that
caller-controlled command config is fully closed on the same security chain.

### Minimum closure required by Critic

1. Add `GIT_CONFIG_PARAMETERS` explicitly to the P4.1 process-level config fence.
2. State that both the stable security-inspection environment and the sanitized
   remote/push environment do not inherit `GIT_CONFIG_PARAMETERS`.
3. Add an ER-G4 `GIT_CONFIG_PARAMETERS` command-scope canary, for example an
   executable `credential.helper`, requiring fail-closed behavior before
   network/mutation and canary execution count = 0.
4. Do not broaden the work into an audit of every `GIT_*` environment variable;
   close only this verified command/config-view entry on the same security causal
   chain.
