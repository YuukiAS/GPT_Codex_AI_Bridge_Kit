## 1. Executive decision

**Recommend Option B, but keep it deliberately small.**

Persistent Run should be retained, but narrowed to one job: **provide process/session persistence when the execution topology actually needs a terminal-independent owner**. It should no longer be inferred merely from “overnight”, “multi-hour”, or “unattended”.

The user's original problem — “do not run for hours and only then discover a foreseeable approval/user question” — is already substantially implemented by the 0.8.1 **upfront authorization preflight**, current Host/Machine Policy, and the Default-mode `HUMAN_ONLY` transcript gate. The missing piece is not a new authorization state machine. The residual defect is that current authoring guidance still maps long/unattended wording too directly to:

```text
Persistent execution: REQUIRED
Backend: tmux
```

That conflates three different concerns:

1. **authorization readiness** — are all foreseeable frozen-scope `HUMAN_ONLY` effects covered before expensive/long work begins?
2. **process persistence** — will the actual process/orchestrator die when the interactive shell/Codex/SSH session ends?
3. **progress reporting** — can the user later observe project-native progress truthfully?

0.9.2 should separate those semantics without adding a new workflow, state, database, watcher, daemon, controller, or generalized launcher.

## 2. Required reading and reality findings

The planning round used the latest AI Skills Planner/Critic contracts and Capability Gate policy, then Bridge current main, and the current DII consumer.

### 2.1 Existing Bridge capability that already solves most of the approval problem

The current `templates/host/GLOBAL_AGENTS_SNIPPET.md` and `codex/CODEX_START_PROMPT.md` already require:

- before substantive execution, inspect the frozen Goal/task for **foreseeable approval-sensitive effects**;
- repository Goal/Plan/contract text is frozen scope evidence, not current-user authorization;
- if the current user message already contains exact bounded authorization for the same frozen effect, do not ask again merely because a later stage reaches it;
- if authorization is missing, ask **before** substantial, expensive, long-running, or precursor work;
- a new artifact/provider/resource/purpose/out-of-scope effect still requires fresh authorization.

0.8.5 also already classifies dependencies into the existing categories:

```text
HUMAN_ONLY
AGENT_RESOLVABLE
UNSUPPORTED_WITH_EVIDENCE
OPTIONAL_NOT_REQUIRED_FOR_CURRENT_CLOSURE
SAFETY_OR_AUTHORITY_BLOCKER
```

and deliberately avoids a parallel waiting state machine.

Therefore the core approval-readiness mechanism is **present in production source**. The correct refinement is to make task authoring and Persistent Run consume it correctly, not to invent `UNATTENDED_READY`, an authorization ledger, or a second approval engine.

### 2.2 Current over-coupling

Current authoring surfaces still teach that these are “strong persistent-execution triggers”:

- overnight / run until morning;
- unattended / leave it running;
- long-running / multi-hour / multi-stage;
- survive disconnect;
- resume persistent Goal.

When Persistent Run is installed, that path forces `Backend: tmux`.

That is too broad. “The work must continue while the user sleeps” and “the process needs tmux to stay alive” are not equivalent statements.

### 2.3 Real DII consumer evidence

The current DII Goal `GOAL_MMS_COMMON_REFERENCE_RISK_GRADIENT_PERSISTENT_2026-09-24.md` is a valid tmux case:

- it uses a user-supplied interactive Slurm allocation;
- it has a long multi-stage orchestrator;
- it must survive Codex/SSH disconnect;
- its Goal freezes resource/data/model/scope;
- it has project-native lock/heartbeat/stage-state/checkpoint/progress evidence;
- it already records a single user kickoff authorization and does not reinterpret session existence as scientific completion.

DII's own `AGENTS.md` also makes the opposite case explicit: short/independent training, evaluation or inference should normally use `sbatch`. Scheduler-owned batch execution does not gain useful persistence merely by wrapping submission or monitoring inside tmux.

This means Persistent Run still has genuine value, but only for the topology where the shell/interactive session is part of the lifetime boundary.

## 3. Failure attribution

### 3.1 Primary failure

**Category: Bridge authoring / product semantics, not missing authorization infrastructure.**

0.8.1 correctly introduced upfront authorization preflight, but its task-authoring rule simultaneously retained the assumption that long/unattended execution implies Persistent Run with tmux. The first half solves the user's original approval-timing problem; the second half overgeneralizes process persistence.

### 3.2 Secondary coupling

**Progress reporting is semantically independent already, but its naming/documentation is coupled to Persistent Run.**

`ai_bridge_kit/persistent_run.py` normalizes a project-native JSON progress source and stores local latest/history. It does not infer progress from tmux and does not require a live tmux session. No code-level redesign is necessary to make this distinction truthful.

### 3.3 What is not currently supported by evidence

There is no evidence that the problem requires:

- a new authorization database;
- a new `UNATTENDED_READY` schema/state;
- a watcher/daemon/controller;
- broad `tmux new-session`, shell, Python, `srun`, `sbatch` or host mutation allowlists;
- `approval_policy=never`;
- a DII-specific Bridge mechanism.

Those would add security and recovery complexity without addressing the actual failure.

## 4. Alternatives

### Option A — keep 0.9.1 unchanged

Advantages: zero compatibility risk and zero implementation cost.

Failure: task authoring can still equate “overnight/unattended/multi-hour” with `Backend: tmux`, so scheduler-native or already-detached work may acquire a redundant process layer. It also leaves the product story focused on “long task = Persistent Run” rather than “foreseeable approval readiness + topology-appropriate persistence”.

**Decision: not recommended.**

### Option B — small semantic refinement

Make upfront unattended readiness the general startup rule already enforced by Host/Codex instructions; apply Persistent Run only when topology needs process persistence; explicitly decouple progress reporting semantics.

Advantages:

- fixes the real mismatch;
- reuses existing 0.8.1/0.8.5 mechanisms;
- preserves current security boundary;
- preserves existing Persistent Run consumers;
- no state migration;
- no new backend or daemon;
- no broad Host Policy rule.

**Decision: recommended.**

### Option C — docs/authoring wording only, leaving installed Persistent Run semantics unchanged

This would reduce some new-task misclassification, but the installed `automation/persistent_run/README.md`, managed AGENTS block and contract still teach that persistent/long execution is tmux-centered. Different entry surfaces would then disagree.

**Decision: insufficient as the final fix.** The runtime implementation can remain mostly unchanged, but the installed contract/guidance must be brought into the same semantics.

## 5. Proposed product semantics

### 5.1 Persistent Run stays, but owns only persistence topology

Persistent Run remains an optional project capability.

It owns:

- canonical tmux session identity when tmux is actually required;
- start/resume/no-duplicate semantics for that session;
- relation to project-native recovery evidence;
- no fallback to ad-hoc `setsid` / `nohup` / `screen` / bare `&`;
- preservation of original Goal completion authority.

It does **not** own:

- generic unattended authorization readiness;
- scheduler job lifetime;
- scientific/product scope;
- resource allocation decisions;
- paid/external service authorization;
- progress truth;
- a universal long-job state machine.

### 5.2 “overnight / unattended / multi-hour” does not automatically mean tmux

These phrases should trigger **unattended-readiness preflight** first, not a backend selection.

The persistence question is separate:

> If the active Codex/SSH/terminal disappears, is there already a stronger native owner that keeps the required execution alive?

If yes, do not add tmux merely for duration.

### 5.3 tmux eligibility rule

Use tmux when all of the following are true:

1. the Goal requires survival beyond the active interactive session, **and**
2. the actual process/orchestrator is otherwise owned by that terminal/session, **and**
3. no scheduler/service/project-native persistence owner already provides the required lifetime, **and**
4. the frozen Goal chooses Persistent Run/tmux and current-user authorization covers the bounded tmux mutation.

Typical **tmux-required** cases:

- interactive allocation + long foreground orchestrator;
- local/remote foreground process that must survive SSH/Codex disconnect;
- multi-stage coordinator whose resume identity and lifetime would otherwise be tied to the current shell.

Typical **tmux-not-required** cases:

- `sbatch` after successful submission, because Slurm owns queued/running lifetime;
- an already detached service/job with an existing owner;
- a bounded single evaluation/inference that can finish in the current session and has no survive-disconnect requirement;
- progress observation of any of the above.

If a scheduler-native job requires **submission** approval, that effect still belongs in upfront authorization. The fact that tmux is unnecessary does not make `sbatch` or resource allocation automatically authorized.

### 5.4 Scheduler-native persistence rule

For a frozen Goal whose execution is submitted as a scheduler-owned job:

```text
authorization readiness -> authorize exact submission/resource effect up front
process persistence      -> scheduler owns it after accepted submission
progress/reporting       -> scheduler/project-native evidence
tmux                      -> absent unless a separate foreground coordinator truly needs it
```

Do not wrap `sbatch` merely to make the task “persistent”.

For interactive `salloc`-style workflows, the allocation holder may itself be terminal-sensitive; there tmux can still be the correct durable owner.

## 6. Unattended-readiness preflight: minimal algorithm, no new schema

Do not add an `UNATTENDED_READY` field.

Before substantive/expensive/long-running work, Codex should perform this existing-contract check:

1. **Read the frozen authority surfaces.** Use existing frontmatter and sections such as Allowed Actions, Forbidden Actions, Human Decision Points, Persistent Run Contract, resource/data/provider/budget/cleanup boundaries.
2. **Enumerate only required foreseeable effects.** Do not speculate about every imaginable future action.
3. **Classify each dependency** with the existing five-way dependency classification.
4. **Compare genuine `HUMAN_ONLY` effects with the current user-visible instruction.** Match the concrete Goal/task identity and, where relevant, artifact/hash, provider/recipient, purpose, resource, backend and cost/scope boundary.
5. **If any required effect is missing authorization, ask once before precursor work.** Consolidate the known bounded effects into one concise request where doing so does not blur separate risk boundaries.
6. **If the exact effect is already authorized, continue.** Do not ask again solely because a later stage reaches the same effect.
7. **Re-open the gate only on a materially new effect or scope.**

This is an execution-start decision procedure, not persisted workflow state.

### 6.1 Effects that require a fresh user decision

Fresh authorization is required for facts such as:

- new or different GPU/compute resource, allocation or cancellation;
- changed data, model, method, split, endpoint or scientific/product scope;
- new artifact, external upload, provider, recipient or purpose;
- higher paid-call/cost/budget ceiling;
- destructive delete/reset/kill/cancel/force operation;
- new production deployment or live-global mutation;
- changed persistence backend or new persistence side effect not in the frozen Goal;
- a Goal amendment that broadens authority.

An unknown future side effect cannot be “pre-approved without bounds” merely because the user wants an overnight run.

### 6.2 Same-scope authorization reuse

No authorization DB should be introduced.

Within the current user-visible execution thread, exact bounded authorization for the same frozen effect is reused. Repository text or a historical receipt alone does not create fresh current-user authorization in a new independent thread. A new thread/session may need the bounded kickoff again if the platform cannot carry the prior current-user instruction as active authority.

This is intentionally narrower than “authorization forever”.

## 7. Kickoff semantics

**Keep kickoff authorization, but stop treating “kickoff” as synonymous with “permission to create tmux”.**

There are two levels:

1. **General execution kickoff / current user instruction** — the place to include the foreseeable bounded `HUMAN_ONLY` effects for the frozen Goal before long work starts.
2. **`ai-bridge persistent-run prompt kickoff`** — retain as the specialized helper for a Goal that actually uses Persistent Run/tmux.

Do not turn the Persistent Run CLI into a universal Goal parser or authorization generator. That would be a new authority engine and would require much more validation.

For tmux Goals, the Persistent Run kickoff should continue to say that it authorizes the exact frozen Goal's canonical tmux start/resume and no broader scope. For non-tmux scheduler-native Goals, no fake Persistent Run kickoff is required; the user's normal execution kickoff must instead authorize the exact scheduler/resource effect if one is required.

## 8. Progress reporting ownership

Progress truth belongs to the consumer project's native source.

The existing `progress/report/latest` code already works from project-native JSON and correctly avoids treating tmux/PID/session existence as semantic completion.

0.9.2 should therefore:

- declare progress reporting **orthogonal to tmux**;
- permit report/latest use for scheduler-native and already-detached jobs;
- keep the existing `ai-bridge persistent-run report/latest` command names and schema identifiers for backward compatibility in 0.9.2;
- avoid a rename/migration merely for taxonomy cleanliness;
- avoid adding a progress daemon or watcher.

A future rename is not justified unless the compatibility namespace itself causes a real user-facing failure.

## 9. Machine Policy / Default-mode judgement

Current Machine Policy is sufficient for this refinement.

Keep:

```text
approval_policy = "on-request"
approvals_reviewer = "auto_review"
default_mode_request_user_input = false
```

Keep low-friction read-only diagnostics and keep mutation paths gated.

No new Host execpolicy allow rules are proposed.

The current Default-mode durable plain-text `HUMAN_ONLY` question + same-Goal resume semantics already provide the needed fail-closed behavior. The required change is to ask at the correct time and not create unnecessary tmux effects, not to weaken the gate.

Observed: OpenAI's current model is bounded sandbox + approvals, with low-risk routine actions kept frictionless, higher-risk actions explicit, Auto-review able to use user authorization, and scoped rules preferred over broad prefixes.

**ADOPTED:** bounded upfront authorization and narrow rules.  
**NOT ADOPTED:** host-wide `approval_policy=never`, broad shell/Python/tmux mutation allowlists, or bypassing approval by alternate tools.

### tmux

Checked current tmux project documentation:

- https://github.com/tmux/tmux/wiki/Getting-Started
- https://github.com/tmux/tmux/blob/master/tmux.1

tmux explicitly provides detach/reattach and session survival across terminal/SSH disconnect.

**ADOPTED:** tmux as the mature backend for terminal-owned foreground/orchestrator persistence.  
**NOT ADOPTED:** tmux as a universal wrapper for all long work.

### Slurm

Checked current SchedMD documentation:

- https://slurm.schedmd.com/sbatch.html
- https://slurm.schedmd.com/salloc.html
- https://slurm.schedmd.com/srun.html

`sbatch` transfers the script to the controller, gets a job ID and exits; the job can remain queued and execute later. `salloc`, in contrast, is designed around an allocation plus a foreground command/shell and has terminal/signal lifetime considerations.

**ADOPTED:** scheduler-native batch lifetime is already persistence; interactive allocation holders may still need a terminal-independent owner.  
**NOT ADOPTED:** a Bridge-owned process manager, scheduler wrapper, or universal tmux layer.

## 12. Normal user entry

### Case A — overnight scheduler-native batch

User gives a frozen Goal and asks it to run overnight.

Codex/GPT:

1. runs upfront authorization preflight;
2. asks once at the beginning for the exact scheduler/resource submission effect if not already authorized;
3. submits through the Goal-authorized scheduler path;
4. lets the scheduler own lifetime;
5. uses scheduler/project-native progress evidence;
6. does not install/create tmux solely because the run is long.

### Case B — interactive GPU allocation + long orchestrator

User gives/reuses the frozen interactive allocation and authorizes the frozen Goal.

Codex/GPT:

1. preflights all foreseeable gated effects before expensive work;
2. uses the Goal's Persistent Run contract;
3. starts/resumes the canonical tmux session;
4. runs the orchestrator within the authorized allocation;
5. reports progress from project-native state;
6. does not re-ask merely because Codex reconnects.

### Case C — short bounded eval/inference

If no survive-disconnect requirement exists, run normally. “Could take a while” alone is not a Persistent Run trigger.

## 15. Red-team checks

The candidate must fail review if any of these remain possible by design:

- user says “run tonight” and a foreseeable approval is deferred until hour 4;
- all overnight tasks still become tmux tasks;
- a successful scheduler-native `sbatch` gets wrapped in tmux merely for longevity;
- kickoff becomes a blanket authorization for unknown future actions;
- an authorization for one resource/provider/artifact is reused for a different one;
- Host Policy is broadened to solve an authoring problem;
- a watcher/daemon/controller/authorization DB is added without a new failure requiring it;
- tmux session alive is treated as healthy/complete;
- progress reporter requires tmux;
- repository Goal text is accepted as current-user authorization;
- a same frozen effect is re-asked solely because a later stage reaches it;
- “unattended” becomes a reason to pre-approve broad shell/Python/srun/tmux mutation.

## 19. Rollback

Because the proposal adds no data/schema migration, rollback is straightforward:

- before release: revert the implementation/refinement commits;
- after release: ship a follow-up patch that restores the last known-good authoring/template behavior while retaining existing Goal compatibility;
- do not rewrite active consumer Goals or delete machine-local progress state;
- do not force-update `release`, reset user repos, or kill active sessions/jobs as rollback.

## 20. Proposed implementation boundary after Critic PASS

A future Executor may only:

1. correct the authoring/topology rules;
2. align installed Persistent Run templates;
3. clarify progress orthogonality without renaming/migrating its CLI/schema;
4. update focused tests and user-facing docs;
5. preserve Host Policy and existing consumers.

It may not add a backend, wrapper framework, authorization store, daemon, scheduler integration, or generalized orchestration layer.
