==================================================
1. USER PROBLEM TO PRESERVE
==================================================

Real production regression:

The user already authorized one exact Reviewed effect:

- exact repo;
- semantic task_key;
- branch reviewed/<task_key>;
- exact worktree;
- base/scope.

But a brand-new task has no CURRENT.json / REQUEST.md.

Current Bridge materialize-worktree requires those files before Git mutation.
Current task init creates them in the target checkout and leaves the worktree locator unresolved.

The current Project Thread Handoff recovery therefore still contains:

NEEDS_HUMAN_WORKTREE_BOOTSTRAP
+ one raw git worktree add command.

The target product behavior is:

one approved Kickoff
-> normal bounded Reviewed first bootstrap
-> exact branch/worktree
-> REQUEST/CURRENT created in reviewed worktree
-> continue normal lifecycle

without asking the user to manually create Git/workflow state.

3. ALTERNATIVES / OVERENGINEERING CHECK
==================================================

Planner rejected:

A. turning task init into the Git bootstrap command;
B. adding a new reviewed-handoff task bootstrap command;
C. consumer-only orchestration with current primitives unchanged;
D. task init -> manually patch REQUEST -> materialize choreography;
E. permanent manual raw git worktree fallback.

Selected architecture:

extend the existing:

ai-bridge reviewed-handoff materialize-worktree --mode bootstrap

so task-missing is a real first-bootstrap transaction.

No new top-level command.
No new Machine Policy allow prefix.

Please attack both sides:

- Is this unnecessarily complex compared with a safe composition?
- Is it too simple to solve the actual chicken-and-egg?

If you believe another existing-command composition is strictly simpler and actually eliminates main pollution/manual assembly, give direct source evidence.

==================================================
4. FIRST-BOOTSTRAP TRANSACTION
==================================================

Selected first-bootstrap lifecycle:

1. task metadata absent;
2. derive branch only as reviewed/<task_key>;
3. validate expected repo;
4. validate exact absolute worktree path;
5. reject symlink/path redirection;
6. reject local/remote task branch conflicts;
7. require frozen expected base ref + expected base commit;
8. verify base lineage;
9. create exact local branch/worktree;
10. only inside the newly-created reviewed worktree, initialize REQUEST/CURRENT/results;
11. REQUEST freezes exact worktree locator;
12. CURRENT freezes source base_branch/base_commit;
13. canonical main never receives temporary task control files.

Review whether this actually resolves the chicken-and-egg without weakening scope.

Critical question:

Is it correct that the FIRST tracked REQUEST/CURRENT should live only in the new reviewed worktree, not canonical main?

==================================================
7. PARTIAL FAILURE / RECOVERY
==================================================

Planner proposes invocation-local ownership only, no durable ownership ledger.

Required:

- failure before branch -> no cleanup;
- branch created / worktree fails -> remove only exact invocation-created branch if identity still proves ownership;
- worktree created / control initialization fails -> remove only exact known invocation-created control paths/worktree/branch if no unexpected user work exists;
- ambiguous/dirty/unowned partial state -> preserve + recovery evidence;
- later invocation cannot infer ownership only from name match;
- no git clean/reset-hard/arbitrary destructive cleanup.

Compare against official Git worktree behavior.

Check whether this recovery is actually implementable without relying on unsafe forced cleanup.

8. BOOTSTRAP / RESUME TABLE
==================================================

Review this lifecycle table:

A:
task absent / branch absent / worktree absent
-> first bootstrap

B:
task exists / remote reviewed branch exists / local branch/worktree missing
-> existing resume/rematerialize

D:

-> fail closed

-> fail closed

F:

-> bounded rollback

G:
ambiguous/dirty partial state
-> preserve + recovery evidence

Do not convert this into a new workflow/state machine.
