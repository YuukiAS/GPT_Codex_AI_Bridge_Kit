# 0.7.5 — Project override / Git escalation guardrail

日期：2026-09-10
状态：IMPLEMENTATION SPEC

## 1. 触发事件

Asteria 在 Codex Desktop 中出现了一个会让普通开发完全停摆的配置组合：

```text
workspace root                         writable
<repo>/.git                            sandbox read-only child mount
<repo>/.codex/config.toml              approval_policy = "never"
```

Linux 文件权限本身正常；失败来自 sandbox mount：

```text
touch .git/<probe>
Read-only file system
```

这不是要求把 `.git` 改成 sandbox 内可写。当前 Codex 的 `workspace-write` 可以保护 Git metadata；普通 Git 写操作应通过 Host Policy 已授权的 host/escalation 路径执行。

真正的问题是 repo-local `.codex/config.toml` 把 `approval_policy` 改成 `never`，从而关闭了该 escalation/auto-review 通道。结果是：源码能写，`.git` 不能写，而且 agent 没有合法的方式离开 sandbox 完成 `git add/commit/push`。

Asteria 的该 `.codex/config.toml` 是本机 project override，不在 Git 历史中；Asteria `.gitignore` 本身忽略 `.codex/`。这类本地 drift 因而可以长期存在，并跨新 thread/task 复现。

## 2. 当前 Host Policy 为什么没有提前阻止

Bridge Kit 的全局 Host Policy 已经选择了正确组合：

```toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"
approvals_reviewer = "auto_review"
```

并通过 execpolicy 对当前 `main` 的常规 Git 工作流提供低打扰授权：

```text
git fetch origin main
git pull --ff-only origin main
git add ...
git commit ...
git push origin main
```

因此不要把全局 Host Policy 改成 `never`，也不要把 sandbox 改成 `danger-full-access`。

当前缺口在 `ai_bridge_kit/host.py`：`detect_project_overrides()` 只报告 `<cwd>/.codex/config.toml` / rules 是否存在；`inspect_host_policy()` 的 `overall_state` 只由 `$CODEX_HOME` 全局 config、global AGENTS 和 rules 决定。也就是说，一个 project override 即使明确写着 `approval_policy = "never"`，`ai-bridge host validate` 仍可能把全局 Host Policy 报成 configured。

`ai-bridge validate --target ...` 目前也没有把这种 project-level Codex 配置冲突纳入 workspace compatibility gate。

这是 0.7.5 要修的 bug。

## 3. 产品原则

目标不是“让 Git 永远不受 sandbox 保护”，而是保证：

> 普通 repository 不会因为 repo-local Codex override 静默关闭 Host Policy 的低打扰 Git escalation，从而形成 `repo rw + .git ro + approval never` 的死锁。

`on-request + auto_review + narrow execpolicy` 是正常 unattended development 的目标状态。`on-request` 不等于要求用户手动盯每一条命令；自动审阅器和明确的 execpolicy 规则负责让已授权、低风险动作低打扰通过。

## 4. 0.7.5 必须实现的行为

### 4.1 解析 project-level override，而不是只报告路径

新增 project override inspection，例如：

```python
@dataclass(frozen=True)
class ProjectCodexOverrideStatus:
    config_path: Path | None
    approval_policy: str | None
    sandbox_mode: str | None
    approvals_reviewer: str | None
    state: str
    issues: list[str]
```

状态至少区分：

```text
none
compatible
redundant
incompatible
unreadable
```

只读取当前 target/cwd 的 `.codex/config.toml`；不要扫描用户整个 home 或其他 repository。

### 4.2 将 `approval_policy = "never"` 视为普通开发 repository 的 hard incompatibility

当 project override 显式设置：

```toml
approval_policy = "never"
```

`ai-bridge host validate`（在该 repo cwd 下）必须：

- 明确输出 project override path；
- 输出 effective conflict：project override shadows Host Policy `on-request`；
- 解释 `workspace-write` 下 Git metadata 可能需要 host/escalation；
- 将 overall compatibility 标记为 `incompatible`；
- exit non-zero；
- 给出精确 repair command；
- 不建议 chmod/chown/remount `.git`；
- 不建议 `danger-full-access`。

如果未来确有一个 bounded child runtime 需要 `approval_policy=never`（例如 production `plugin-replay`），应继续通过 wrapper 的 explicit child Codex CLI overrides 实现，而不是在普通 source repository 的 `.codex/config.toml` 中永久设置 `never`。

### 4.3 `ai-bridge validate --target` 也要检查

对已经安装 Lite/Review/Control 的 repository，`ai-bridge validate --target <repo>` 应调用同一 project override compatibility helper。

默认模式至少 warning + 明确 `INCOMPATIBLE project Codex override`；`--strict` 必须作为 error。考虑到 `approval_policy=never` 已能阻止 task-owned commit/push，推荐即使非 strict 也直接 error。

这样新 repo 初始化/升级后，在真正启动长 Goal 之前就能发现配置死锁。

### 4.4 增加显式、窄范围的 project repair 命令

建议增加：

```bash
ai-bridge host repair-project --target /path/to/repo
```

它不是 `host install` 的静默副作用。只有用户或任务显式调用时才修改 project-local config。

安全规则：

1. 只允许修改 `<target>/.codex/config.toml`；
2. 修改前建立带时间戳 backup；
3. 非破坏式保留其他 TOML section / comments / project-specific settings；
4. 优先移除与 Host Policy 冲突的 host-owned root override，让 `$CODEX_HOME/config.toml` 继续作为真值：
   - `approval_policy`；
   - 若与 Host Policy 冲突，再处理 `approvals_reviewer`；
   - `sandbox_mode` 只有明确冲突时才处理；
5. 不写 `danger-full-access`；
6. 不把 `approval_policy` 改成 `never`；
7. repair 后立即重新 inspect/validate；
8. 重复执行必须幂等。

若实现者认为“删除 root override 继承全局值”在当前 Codex config precedence 下不可可靠验证，则退而求其次把 project values 显式规范化为：

```toml
approval_policy = "on-request"
approvals_reviewer = "auto_review"
sandbox_mode = "workspace-write"
```

但仍必须保留 unrelated project config。

### 4.5 启动前提示必须说清楚 restart boundary

project config 已经被当前 Codex Desktop task/profile 读取时，修改文件通常不能重写本次已建立的 sandbox mount/profile。因此 repair 命令成功后应明确输出：

```text
PROJECT_CONFIG_REPAIRED = YES
CURRENT_SESSION_RESTART_REQUIRED = YES
SAFE_NEXT_STEP = reopen/restart the repository task, then run host/target validation before development
```

不要让用户误以为当前已经启动的 `approval_policy=never` session 可以原地恢复 escalation。

## 5. Asteria 本次事故的推荐恢复方式

对当前机器上的：

```text
/home/yuukias/code/Asteria/.codex/config.toml
```

不要改 `.git` mount，也不要 chmod/chown `.git`。

应在 sandbox 外的正常 host context，或另一个具有正常 `on-request + auto_review` escalation 的 Codex context 中：

1. 备份该 project config；
2. 删除/修正 `approval_policy = "never"` project override；
3. 验证全局 Host Policy 仍为 `on-request + workspace-write + auto_review`；
4. 关闭旧 Asteria task/context；
5. 重新打开 Asteria workspace；
6. 先验证：

```bash
ai-bridge host validate
git status --short --branch
```

7. 然后恢复原 Asteria autonomous goal。

即使新的 Asteria sandbox 仍把 `.git` 显示为 read-only child mount，也不必视为失败；真正的 acceptance criterion 是：普通、已授权的 `git add/commit/push origin main` 能通过 Host Policy 的 sanctioned host/escalation path 完成，而不要求用户逐条人工批准。

## 6. 不能采用的“修复”

禁止：

- 把 `.git` 永久 bind/remount 为 sandbox writable；
- `chmod -R` / `chown -R` 当成修复；
- 全局 `approval_policy = "never"`；
- 全局 `sandbox_mode = "danger-full-access"`；
- 泛化 allow `bash` / `sh` / `python`；
- 泛化允许所有 `git push`、force push、branch/remote mutation；
- 为 Asteria 单独写一个特殊 Git 绕过器；
- 使用临时 clone 或 GitHub contents API 代替 active worktree 的正常本地 Git 历史。

## 7. 测试要求

至少新增：

1. no project override → compatible；
2. unrelated project config only → compatible；
3. `approval_policy="on-request"` → compatible/redundant；
4. `approval_policy="never"` → incompatible + non-zero validate；
5. global config correct + project `never` 仍必须 fail（本次核心 regression）；
6. repair only removes/normalizes Host Policy-owned conflicting keys；
7. repair preserves unrelated TOML content；
8. repair creates backup；
9. repair is idempotent；
10. `ai-bridge validate --target` detects the same conflict；
11. existing host execpolicy tests for ordinary Git remain unchanged；
12. plugin-replay child `approval_policy=never` tests continue passing，并确认不会被误判成 source-repo project override。

建议给本事故加入一个 fixture 名称，例如：

```text
project_override_never_git_escalation_deadlock
```

避免未来再次退化。

## 10. 完成门槛

只有以下全部满足才能称为修复：

- Host Policy validator 能发现 project-level `approval_policy=never`；
- target validator 能发现同一问题；
- 有显式、安全、幂等的 repair path；
- repair 不碰 Git mount / Git 权限；
- ordinary main-branch Git policy 仍保持低打扰；
- dangerous Git 仍 gated；
- plugin-replay 的 bounded child `never` 不受影响；
- tests 全部通过；
- docs/version/changelog 同步；
- 用一个临时 fixture repo 复现“global host correct + project never”，确认修复前会漏报、修复后能阻止。
