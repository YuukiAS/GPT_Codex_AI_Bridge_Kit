## 1. 本轮实际核查事实与外部依据

### 1.1 Bridge 当前实现

实际读取当前 `main@a03742ed07d00d36e3436f64a17e92c40a51064e` 的 AGENTS、README、CHANGELOG、`pyproject.toml`、Lite/Reviewed/readiness/Persistent Run/Host/Notifier/private/plugin-replay 源码及相关模板；a03742 只新增 v0.4 设计包，生产源码仍与上一实现基线一致。关键事实：

- `ai-bridge task run --target <repo> --task-key <key>` 是现有 Lite 正常入口。它在启动 `codex exec` 前调用 `readiness.preflight_lite_task()`，绑定 `AGENTS.md`、`prompts/AGENT_RULES.md`、`prompts/tasks/<task_key>.md`；失败时不启动子 Codex。

- `host sync-current-branch` 已有严格 non-main、clean、same-name origin、fast-forward-only 语义，README 已有真实用法，本轮不重设计。
- 当前 `persistent_run.py` 没有启动/恢复/supervisor/status 入口，周期 reporter 只有“被调用时”才工作。
- 当前 `notifier.py` 只支持 Gmail 主机、587、STARTTLS；配置只合并项目 `.ai-bridge/private/notifier.env` + process env；`status` 不报告 readiness/source/sender/recipient/suppression。

### 1.2 Git 官方机制

本轮核对 Git 官方文档：

- partial clone 明确允许省略对象并在真正需要时 demand-fetch；`git clone --filter=blob:none` 会让 blobs 在 Git 需要时才取得。
- `GIT_OBJECT_DIRECTORY` 指定新对象存储位置；`GIT_ALTERNATE_OBJECT_DIRECTORIES` 只作为搜索旧对象的 alternate，不向其写新对象。这与 Bridge 当前 isolated mandatory-source reader 的方向一致。
- `git worktree move` 是官方 linked-worktree 移动机制；主工作树和带 submodule 的 linked worktree不能直接用该命令移动，`repair` 用于已移动后重连。这支持当前 G02 “严格准入、原生 move、不能泛化所有拓扑”的设计。

因此 G02/G03 不需要重造 Git abstraction；需要修的是正常入口与错误/恢复呈现。

### 1.3 Codex 0.160.1 Progress thread 与 shared app-server writer ownership

目标稳定运行身份仍以实施时实测为准；本轮重新核对 `openai/codex rust-v0.160.1@d27764b82f7118f674371e6d6e76271d9d606edb`：

- `thread/start` 支持 non-ephemeral thread、config、sandbox、approval、runtime workspace roots、environments、dynamic tools、selected capability roots、base/developer instructions 等。
- 官方 `temporary_structured_request.rs` 在 model turn 前读取 effective config，关闭 shell/unified exec、web、apps/plugins、MCP、environment、dynamic tools、multi-agent 等，并使用空 runtime roots；这是 Progress thread 的安全配置参考。
- 官方 helper 自身 `ephemeral=true`，不能直接代替需要 reconnect/history 的 Progress thread。
- 官方文档明确 unused thread 不保证跨 restart 保存；真实 canary 已证明首 turn 前 cold resume 不能当成 persistence前提，所以仍使用 `start -> isolation -> first turn -> materialize -> disconnect -> cold resume`。
- `thread/name/set` 可提供 human-readable name；exact thread ID 才是运行 identity。

**v0.5 新增 writer ownership直接证据：**

1. 官方 `codex-rs/app-server/tests/suite/v2/thread_resume.rs` 的 `thread_resume_rejects_legacy_writer_owned_by_another_process` 与 `thread_resume_rejects_paginated_writer_owned_by_another_process` 均验证：当 primary app-server process仍持有 thread writer时，secondary app-server process resume 同一 thread会返回 `thread <id> already has an active writer`；primary退出后 secondary才可resume。
2. 官方 `codex-rs/tui/src/session_queue_commands.rs` 在 `--no-daemon` 且无显式remote时直接拒绝 queue，并在发现 local daemon正在运行但当前路径变成 embedded server时拒绝写入，错误理由就是避免通过 separate server writer。
3. `codex-rs/features/src/lib.rs`：`daemon_auto_start` 是 Stable，`default_enabled=true`。
4. TUI官方启动逻辑把可复用shared server分为 `AppServerTarget::LocalDaemon` 或 `AppServerTarget::Remote`；local normal entry会探测当前 `CODEX_HOME` 对应daemon控制端点，显式 `--remote` 则使用exact remote endpoint。`--no-daemon`、workload identity、某些 config override或executor override会导致embedded路径。
5. 官方 `codex-app-server-daemon` 是多client共享server；本任务**不调用 start/restart/update/bootstrap**。Bridge只连接已经被当前正常Codex使用的shared server。

因此“Progress thread本身是dedicated”不等于“可以另开dedicated app-server”。正式产品必须保证UI viewer与reporter client连到**同一个app-server writer owner**。

### 1.4 Gmail 官方事实

当前 Google 官方帮助支持以下产品事实：

- Gmail 外发服务器为 `smtp.gmail.com`，要求认证，TLS/STARTTLS 端口为 587。
- Google App Password 是用于不能走“Sign in with Google”的应用的一次性 16 位应用密码；创建 App Password 需要先启用两步验证。
- App Password 可能因安全密钥专用两步验证、组织账号策略或 Advanced Protection 等原因不可用；Bridge 不能假装一定能生成。
- Google 更推荐支持 OAuth/“Sign in with Google”的客户端，但当前 Bridge 实现没有 OAuth。0.11 不为“通用”而顺手加 OAuth/provider framework。

因此 0.11 的诚实产品范围是：**Gmail SMTP + App Password**。任意 SMTP provider、Google OAuth、Workspace SMTP relay 都不属于本版正式承诺。

## 3. 普通用户从零到可用

### 3.1 新机器：一次性机器设置

正常入口：

`pip install -e /path/to/GPT_Codex_AI_Bridge_Kit`  
`ai-bridge host status`  
`ai-bridge host install`  
`ai-bridge host validate`

用户提供：目标 `CODEX_HOME` 身份（显式参数、环境变量或默认路径）以及现有 Bridge 源码安装。

Bridge 自动：
- 确认实际 `codex`、`ai-bridge`、import source/version；
- 安装/验证 Host Policy；
- 只报告本地可验证的 source HEAD/dirty、local formal release ref、distribution metadata；
- **不做远端 fetch/readback 时，remote formal release freshness 明确显示 `UNKNOWN/UNVERIFIED`**，不得假装知道 GitHub 最新 release。

成功时用户看到“本机 Host ready + 当前本地身份”；远端新鲜度另列 UNKNOWN。失败时直接给最小动作，例如重新 `host install`、换正确 `CODEX_HOME`、开启 fresh Codex session。

### 3.2 新项目：一次性项目设置

正常入口：

`ai-bridge init --target <repo>`  
`ai-bridge validate --strict --target <repo>`

`validate --strict` 定位为**安装/升级后与诊断时**使用，不要求用户每次任务手敲。日常 Lite/Reviewed launch 自己重新做受检 preflight。

如果项目选择 Reviewed、Control、Persistent Run 或 Notifications，再安装/配置对应可选层；不因为“装 Bridge”静默全装。

### 3.3 Lite 普通任务：日常最小路径

1. GPT 按 Task Writer 写 `prompts/tasks/<task_key>.md`，把用户目标、授权范围、通知最终 intent 和必要 source 冻结进去。
2. 用户/Codex 从正常入口运行：
   `ai-bridge task run --target <repo> --task-key <task_key>`
3. Bridge 自动检查 Host/工作树/指令预算/mandatory source；partial clone 缺 blob 时内部通过 isolated reader 安全取得。
4. preflight PASS 后才启动真实 `codex exec`。

用户不需要知道 object OID、`GIT_OBJECT_DIRECTORY`、alternate object dir 或 mandatory-source helper。

失败时只显示：哪一项必读来源/Host/预算不满足、为什么不能安全启动、怎样恢复同一任务。例如：
“必读来源 `prompts/tasks/x.md` 未冻结到 HEAD；先提交该任务文件再重试。”
或：
“必读文件在 partial clone 中缺失且无法从已验证 GitHub HTTPS origin 取得；恢复网络/凭据/remote identity 后重试。”
不得把低层 object-dir 命令甩给用户。

### 3.4 Reviewed / Control 选择

- Lite 默认。
- 需要 GPT 先规划并由独立 GPT 复核时选择 Reviewed；继续使用现有 `task bootstrap / publish-first / watcher`。
- 只有高风险、已经明确需要严格角色隔离与 Final Critic 时才选择 Control。
- 长运行不自动升级 Reviewed/Control；execution lifetime 与 workflow type 分开决定。

### 3.5 分支与 worktree 异常恢复

普通 non-main 同名分支严格落后：继续使用 `ai-bridge host sync-current-branch`。

只有当 Reviewed/materialize 正常入口发现**两个普通 linked worktree 正好形成可支持的 reciprocal placement conflict**时，才进入 G02 恢复：

- desired path A 当前是 branch B；
- expected branch A 当前登记在 path B；
- 两端均同 common-dir、非主工作树、同一文件系统、无 submodule/symlink/lock/活动进程等禁止条件；
- Codex 从 `git worktree list --porcelain` 与 frozen task locator 自动确定 A/B/expected branches；
- T 由 Bridge 确定为 A 所在文件系统上的唯一空闲 sibling 临时路径；
- Codex 只向用户展示一次自然语言请求：将 A→T、B→A、T→B，最终两分支位置怎样变化；询问是否授权这一次准确搬迁 effect；
- 用户只回答同意/拒绝，不拼 CLI 参数；
- 同意后 Codex 调已有 `exchange-worktrees` helper；
- helper失败则按 journal 回滚；不能证明恢复时保留全部证据并停止，不做 reset/stash/clean。

其他拓扑不强行“智能恢复”。

### 3.6 判断 execution lifetime

GPT Task Writer 在冻结任务前依次判断：

1. 普通 live：断开即允许停止，不使用 Persistent Run。
2. scheduler-owned：提交后由 scheduler 管寿命，不套 tmux。
3. existing service/job-owned：由既有 supervisor 管寿命，不新建 Bridge service。
4. terminal-owned 且必须 survive disconnect：选择 Persistent Run。

只有第 4 类使用 `persistent-run start`。这个选择与 Lite/Reviewed/Control 正交。

### 3.7 Persistent Run：一次授权后自动运行与自动进度

正常链条：

`GPT 冻结 execution lifetime + Persistent Run contract`  
→ `ai-bridge persistent-run prompt kickoff ...` 生成绑定 Goal hash 的一次授权文本  
→ 用户发送该 kickoff  
→ Codex 调 `ai-bridge persistent-run start --target <repo> --goal <goal> --expected-goal-sha256 <hash>`  
→ Bridge先确认**当前Codex UI/会话实际使用的同一个官方shared app-server**可安全连接：同 `CODEX_HOME` local daemon，或当前会话已经绑定的exact explicit remote app-server  
→ 无shared binding则在新primary启动前返回 `PROGRESS_THREAD_SHARED_APP_SERVER_UNAVAILABLE`，不另起embedded writer  
→ shared server内create/reuse dedicated Progress thread并验证机械隔离  
→ Bridge幂等start-or-resume canonical tmux run  
→ 同一个run supervisor保证reporter同生命周期启动  
→ reporter client继续连接同一shared server  
→ project-native progress source → canonical snapshot → dedicated Progress thread  
→ cadence/event主动更新  
→ 用户UI作为第二client随时打开同一Progress thread  
→ reporter在viewer存在时仍可继续后续bounded render  
→ disconnect/reconnect仍按exact server binding + thread ID恢复  
→ runtime terminal最后一条运行状态  
→ reporter cleanup  
→ semantic completion仍归原Lite/Reviewed/Control合法owner。

用户不用手工找daemon socket、remote endpoint、attach tmux、调用 `latest`、创建Progress thread或每小时问status。

### 3.8 Notifications：一次机器配置，多项目复用

0.11 正式邮件 provider：**Gmail SMTP only**。

首次机器配置：

`ai-bridge notifier configure`

等价于 `--scope machine`；交互式读取 Gmail账号、Google App Password（不回显）、发件地址、默认收件地址和可选prefix，写 machine profile：

`${AI_BRIDGE_STATE_HOME:-~/.ai-bridge}/private/notifier.env`

**project override唯一正式入口：**

`ai-bridge notifier configure --scope project --target <repo>`

project scope默认只建立覆盖层：每个字段可留空表示继承machine。只有用户明确输入project Gmail account override时才提示输入project App Password；仅改recipient/from/prefix时不复制也不要求重新输入machine credential。

删除本地配置：

`ai-bridge notifier configure --clear`  
= 清machine profile。

`ai-bridge notifier configure --clear --scope project --target <repo>`  
= 删除project override并立刻回落machine profile。

`--clear` 只删除Bridge本地保存的credential/override，**不会撤销Google账号端已经创建的App Password**；provider-side revoke必须由用户在Google Account中完成，Bridge 0.11不修改Google账号安全设置。

配置优先级仍为：

`machine < project < process env`

rclone保留兼容但不再是首次配置必修课：

- 旧命令 `ai-bridge private sync --profile notifier` **原样保持project-local current-directory语义**；
- 显式project形式：`ai-bridge private sync --profile notifier --scope project --target <repo>`；
- 只有 `--scope machine` 才恢复machine canonical profile；
- 绝不把旧项目私密recipient/credential静默提升为machine default。

项目通知偏好继续使用非secret project defaults。Task Writer/Reviewed Planner/Control Planner在freeze前解析默认和task override；但Control中Planner**只能把resolved intent提议写入 `PLANNER_DRAFT.md`**，既有Control Critic才有authority写/冻结 `FROZEN_CONTRACT.md`。Automatic notifier只消费Critic冻结后的Control contract。

### 3.9 disconnect / reconnect

- 普通 live task：按原 workflow 处理。
- Persistent Run：`persistent-run status` 显示 run owner/reporter/progress thread；用户在 Codex UI 直接打开同名 Progress thread看历史。
- Reviewed：现有 watcher/status + GitHub state。
- Progress thread exact ID 才是恢复 authority；名字只帮助用户发现。

### 3.10 blocked / failed / runtime completion / semantic completion

- runtime failed/blocked/stalled：Progress thread立即显示；若 frozen Progress email=ENABLED，可自动发运行层邮件。
- runtime completion：立即显示“运行已结束”，但**绝不等于 Goal PASS**。
- Reviewed semantic completion：只有 current Reviewed PASS artifact + frozen Semantic completion email=ENABLED 才自动发完成邮件。
- Control：只有 current Final Critic PASS artifact + frozen intent 才自动发。
- Lite：0.11 没有 canonical semantic-owner PASS artifact，因此 **automatic semantic completion = UNSUPPORTED**；用户可明确执行一次 `notifier send`，或选择 Reviewed/Control。不能给 Lite 一个看似可开的自动完成邮件开关却永远不发生。

## 5. ER11-05 — Persistent Run 端到端正常入口

### 5.1 两个启动方案比较

**方案 A：继续由 Codex 按 kickoff 手工拼 canonical tmux launch**

优点：不新增 CLI。  
缺点：每个任务都要重做 session/run/reporter/thread 绑定逻辑；最关键的是 reporter 可以被忘记，已经直接违反“没有 caller 不能 periodic reporting PASS”；恢复语义也容易因 Codex 当次实现漂移。

**方案 B：新增受边界约束的 `persistent-run start`，语义固定为 start-or-resume**

优点：
- 用户只有一次 kickoff；
- helper 统一核 frozen contract、Goal hash、run/session、primary process、reporter 和 Progress thread；
- reporter 必然随真实 run owner启动；
- reconnect/status有统一 machine-local binding；
- 不重复实现领域 launcher。

代价：增加一个小型生命周期 supervisor，但只属于**这个 run 的前台/tmux 子进程**，不是机器 daemon、controller 或下一任务决策者。

**决定：采用 B。**

### 5.2 Frozen Persistent Run contract 增补

现有 Markdown contract继续使用，不建新数据库。至少新增/冻结：

`Persistent execution: REQUIRED`  
`Backend: tmux`  
`Goal source: <repo-relative path>`  
`Run/session key: <stable key>`  
`Working directory: <repo-relative path>`  
`Launch argv JSON: ["executable", "..."]`  
`Resume argv JSON: SAME_AS_LAUNCH | ["..."]`  
`Progress producer: project-native | lifecycle-only`  
`Progress source locator: <path or NONE>`  
`Stage/status evidence: <source>`  
`Completed/total evidence: <source or UNKNOWN>`  
`ETA basis source: <source or UNKNOWN>`  
`Heartbeat/checkpoint evidence: <source or NONE>`  
`Report interval: 60 minutes ...`  
`Stall threshold: <value or UNSUPPORTED>`  
`Progress thread: AUTO`  
`Progress render max turns: <bounded integer derived from run time/cadence>`  
`Progress email: ENABLED | DISABLED`  
`Semantic completion email: ENABLED | DISABLED | UNSUPPORTED`

复杂 shell 激活逻辑应放进已经冻结、受 Git 追踪的 project-owned launcher script；Bridge helper执行 JSON argv，不接受随意 shell 字符串作为新的通用 orchestrator。

### 5.3 Kickoff 与 Goal hash

`persistent-run prompt kickoff` 升级为：

- 读取/验证 frozen Goal + Persistent Run contract；
- 要求 Goal/contract已冻结且没有相关 dirty drift；
- 计算 Goal/contract content SHA-256；
- 生成包含 exact goal path、hash、run key、资源/时间边界、Progress render turn 上限和已授权外部 effects 的自然语言 kickoff；
- 给 Codex明确的 `persistent-run start ... --expected-goal-sha256 <hash>` 调用参数。

Repo 文件本身仍不能自授权。只有用户把该 prompt 发回当前会话，Codex才执行 `start`。

### 5.4 `persistent-run start` 的幂等 start-or-resume 语义

入口只支持 terminal-owned + tmux contract：

1. 重读 Goal/contract并核 expected hash。
2. 检查 repo、branch/worktree、已授权资源/launch argv、canonical tmux session、现有 machine run binding。
3. 在启动长任务前创建/恢复 Progress thread并机械验证 tool isolation；无法验证则**不启动新 primary run**。
4. 若已有同 hash/run key 的兼容 primary run：不重复启动，修复/确认 reporter lifecycle后返回 `RESUMED_EXISTING_RUN`。
5. 若无 active run：
   - 使用 exact JSON argv，不经通用 shell拼接；
   - 在 canonical tmux中启动一个 run-scoped supervisor；
   - supervisor启动 primary child + reporter child；
   - supervisor等待 primary，primary结束后触发最后 runtime snapshot、停止 reporter并退出；
   - 不维持额外机器服务。
6. helper不提交 scheduler job、不申请资源、不改数据/model/budget；这些 effect若由 launcher需要，必须已在 Goal/kickoff明确授权，否则停止。
7. checkpoint resume只按 frozen `Resume rule/Resume argv`；Bridge不自行猜恢复命令。

### 5.5 scheduler/service topology

scheduler-owned 与 existing service/job-owned任务继续使用原 owner，不调用 tmux `persistent-run start`。

若用户仍要求 Bridge 主动 progress，现有 scheduler/service lifecycle hook必须显式启动同一个 reporter primitive并在 owner结束时清理。不能保证 hook/caller，就不能 claim proactive reporting。Bridge不为此新建 systemd/daemon。

### 5.6 Progress source 的 truth owner

Progress source由**项目原生 launcher/任务代码/调度器/既有服务**产生；Bridge只规范化。

有真实量化证据：
- completed/total 合法时才算 fraction；
- ETA必须带真实 basis；
- heartbeat/checkpoint可用于 last real progress / stall。

没有量化证据但任务仍合法长期：
- stage只从直接证据给出；
- completed/total/fraction = UNKNOWN；
- ETA = UNKNOWN；
- 不因为 tmux/PID活着猜 30%、80% 或预计完成时间；
- 若没有可靠 heartbeat，也不能仅因一段时间没新日志自动宣称 stalled。

lifecycle-only source可以报告 starting/running/runtime-failed/runtime-complete，但不冒充领域 progress。

### 5.7 reporter cadence

继续使用已批准规则：

- start/resume：立即；
- meaningful stage transition：立即；
- stalled/blocked/failed：立即；
- runtime completion：立即；
- material ETA：提前；
- normal active：默认约 60 分钟；
- 无任务特定理由不得低于 15 分钟；
- known ↔ UNKNOWN 永远 material；
- material ETA阈值：`abs(expected_finish_delta) >= max(15 minutes, 25% of prior remaining time)`；
- observation 与 last logical delivery分开；
- 普通 fraction/count变化只更新观察态；
- 高频观察不能重置 last-delivered 导致 cadence starvation。

### 5.8 dedicated Progress thread

每个 run 自动 create-or-reuse：

- non-ephemeral；
- exact `progress_thread_id` 是 identity；
- `thread/name/set` 的人类可读名字只用于发现；
- Bridge-owned display thread，不执行业务、不做 Planner/Reviewer/Executor；
- 不写原 Executor/task thread；
- Bridge先计算 canonical snapshot，render turn只呈现；
- 无 semantic completion authority。

### 5.9 Progress thread app-server ownership / connection topology

这是 v0.5 对 ER11-05 的唯一新增产品接缝。

**正式 Progress thread 必须由用户当前 Codex 所使用的同一个官方 shared app-server承载。**

支持两种且仅两种拓扑：

1. **Local shared daemon**：当前用户 Codex使用同一 `CODEX_HOME` 的官方 local app-server daemon。
2. **Exact explicit remote**：当前用户 Codex已经连接一个显式 remote app-server，Bridge得到同一当前会话的可信endpoint/backend binding并连接它。

Bridge不得把“thread ID正确”与“server owner正确”混为一谈。

#### Local daemon discovery

Bridge复用Codex官方session-command/TUI发现原则：

- 解析当前实际 `CODEX_HOME`；
- 使用官方daemon control endpoint derivation/probe与正常initialize handshake；
- 核当前Codex normal entry确实不是 `--no-daemon` / embedded-only / workload-identity / incompatible override；
- 核running app-server version与当前Codex兼容；
- 连接已存在daemon，不调用 `daemon start/restart/update/bootstrap`；
- 不要求用户手工找socket路径。

如果当前正常Codex没有可证明的shared local daemon：

`PROGRESS_THREAD_SHARED_APP_SERVER_UNAVAILABLE`

在**新primary run启动前**失败。Bridge不能为了满足Progress thread自行启动/重启官方daemon，也不能另起embedded writer。

#### Exact explicit remote

如果当前用户Codex已经通过正式 `--remote` /对应正常入口连接 remote app-server，Bridge只接受**current-session trusted binding**：

- exact sanitized endpoint identity；
- backend/transport kind；
- running server version；
- current CODEX_HOME / remote execution identity关联；
- remote auth token value绝不写入binding，最多保留当前会话已经选择的auth-token environment name/credential locator；
- 不从repo文本、thread标题、cwd、最近连接、端口扫描或猜测得到remote endpoint。

实现必须使用官方RemoteAppServerClient/等价正式connect+initialize路线。若当前0.160.1正常执行上下文不能把“当前UI正在使用的 exact remote endpoint”以可信machine-readable方式交给Bridge，则当前run直接：

`PROGRESS_THREAD_SHARED_APP_SERVER_UNAVAILABLE`

并提示用户恢复到支持shared-server的正常Codex入口；**不得要求用户手工搜索socket/path，也不得猜endpoint**。这不授权Bridge修改Codex本体或创建新的remote-control服务。

#### Binding

machine-local run binding至少增加：

- `codex_home_identity`；
- `app_server_kind=local_daemon|explicit_remote`；
- `app_server_endpoint_fingerprint`（必要时只保存hash/非secret locator，不保存auth token）；
- `app_server_backend_identity`；
- `app_server_version`；
- `progress_thread_id`；
- thread safety/config fingerprint；
- run/task/Goal identity。

每次reporter reconnect先重新discover current shared server并比对binding，再resume exact Progress thread。server合法重启后可以由新process接管持久thread，但必须先确认旧writer已经退出且新的shared server身份/CODEX_HOME/remote binding仍匹配；不能因thread ID相同跨到另一个server/store。

#### Unsupported normal entries与恢复

以下情况在新primary启动前fail closed：

- current Codex `--no-daemon` 且没有exact remote；
- embedded-only；
- workload identity导致shared local daemon不可复用；
- config/profile/executor override使UI实际走embedded；
- remote endpoint无法从可信current-session binding取得；
- running shared server版本/protocol不兼容；
- viewer与reporter无法证明同server。

用户恢复提示必须是正常产品动作，例如：

“请从当前任务退出后，用同一 `CODEX_HOME` 的普通Codex入口重新打开/恢复该任务（不要使用 `--no-daemon` 或会强制embedded的override）；若该任务原本使用显式remote，请用原来同一个remote normal entry恢复。Bridge会重新自动检查shared server。”

不要求用户复制socket/path或自行管理daemon。

### 5.10 0.160.1 正确 persistence + shared-server canary 顺序

开发 canary 与 final G14 都使用：

1. current Codex/UI normal entry先确认shared app-server topology。
2. Bridge reporter client连接**同一**shared app-server。
3. `thread/start` 创建 non-ephemeral Progress thread。
4. 在任何 model turn前机械核 effective config/tool surface。
5. isolation无法证明 → 0 render turn。
6. isolation PASS → 第一个 bounded render turn。
7. 第一个turn完成后验证 rollout/history materialize/persist。
8. 第二个viewer/UI client连接**同一个shared app-server**并打开 exact Progress thread；历史可见。
9. reporter client在viewer仍连接/可查看时执行第二个且最后一个development bounded render；不得出现 `active writer` conflict。
10. viewer看到第二条更新，reporter仍active。
11. 断开reporter/client，再按同一server binding + exact thread ID cold resume；历史仍在且不新建第二thread。
12. 原 Executor/task thread前后完全未变化。
13. canary结束停止自动消息。

**不再要求首turn以前 cold resume**。开发canary仍只有1个Progress thread、isolation PASS后最多2个render turns。

### 5.11 Progress thread tool isolation

复用官方 temporary structured helper 的 deny configuration recipe，但 `ephemeral=false`。

至少：
- read-only sandbox；
- thread-local no-approval，仅作用于这个无工具 thread，不改 Host-wide policy；
- `runtime_workspace_roots=[]`；
- `environments=[]`；
- `dynamic_tools=[]`；
- `selected_capability_roots=[]`；
- 禁用 shell/unified exec/code mode；
- web/search；
- apps/plugins；
- MCP（先 `config/read` 枚举 effective servers，再逐一 disabled）；
- environment；
- multi-agent；
- image generation；
- hooks；
- skills/instruction loading；
- permission request/tool；
- 其他 actual runtime 出现的 execution/external capability。

无法机械证明全部关闭则不发 render turn，也不退回原 Executor thread。

### 5.12 bounded render 与成本

每个 logical delivery最多一个 render turn：
- 输入是已冻结 canonical snapshot；
- model不得重估 stage/status/fraction/ETA；
- 输出值与 snapshot不一致 = fidelity FAIL；
- 上一 render未完成时 coalesce成最新待发 snapshot，不并发；
- foreign/business input出现 → `PROGRESS_THREAD_CONTAMINATED`，停止自动投递；
- 每次记录 snapshot digest/turn id/token/time。

Frozen contract必须有 `Progress render max turns`，由任务时间边界、60min cadence和有限 immediate-event余量预先确定；超过上限停止自动 render并要求用户决定，不无限消耗模型。

### 5.13 `persistent-run status`

用户至少看到：
- active / terminal / unavailable；
- run locator / session key；
- lifecycle owner；
- Goal/hash；
- stage/status；
- completed/total/fraction 或 UNKNOWN；
- ETA/basis/uncertainty 或 UNKNOWN；
- last real progress；
- reporter active/last heartbeat；
- Progress thread human name + exact ID；
- shared app-server kind / nonsecret endpoint/backend fingerprint / running version；
- shared-server binding state；
- latest logical delivery time/reason；
- primary runtime exit code/terminal state；
- Progress thread isolation status；
- 不显示 remote auth token、Gmail secret或其他credential。

`report/latest` 保留兼容/诊断，不再是用户获得主动进度的必要步骤。

## 8. G01–G14 正常入口与最终验收矩阵

所有 release-critical Gate 必须由**同一个人类可读 release candidate + 同一个 exact Git SHA**直接通过。开发期测试只进入 regression bank，不能拼接为正式 PASS。

### G01 — 不同分支长期 worktree 并行

- **用户能力声明**：两个独立任务在不同分支/linked worktree长期运行时互不覆盖。
- **普通入口**：Lite在当前已选 worktree用 `task run`；Reviewed用现有 `task bootstrap/materialize` 生成/恢复确定性 sibling worktree。
- **内部自动机制**：每个入口核 repo/common-dir/current branch/worktree identity；不要求用户管理 common-dir。
- **用户成功结果**：两个任务各自在自己的 cwd/branch运行、原脏内容不被另一任务接管，产物留在各自树。
- **失败结果**：路径/branch占用时出现明确 readiness/recovery分类，而不是静默切目录。
- **最小恢复**：正确现有 worktree直接继续；只有 reciprocal dirty conflict才进入 G02。
- **分类/消费**：日常；Lite CLI、Reviewed runtime、README工作流说明。
- **最终真实证据**：同一 0.11.0 release candidate 上两个真实 worktree任务并行；记录 cwd/branch/原脏状态/产物。
- **最终候选要求**：必须由同一 candidate exact SHA直接通过。

### G02 — 双脏关联 worktree 冲突恢复

- **用户能力声明**：受支持的 reciprocal linked-worktree位置冲突可以一次授权、无损交换，用户不拼 A/B/T CLI。
- **普通入口**：Reviewed materialize/bootstrap正常恢复路径检测冲突后提出一条自然语言授权请求；`exchange-worktrees` 保持 recovery helper。
- **内部自动机制**：从 worktree registry + frozen task locator确定 A/B/branches；确定同文件系统空 sibling T；准入检查；journal；三次 `git worktree move`；postcheck/rollback。
- **用户成功结果**：用户只看到最终 branch→path 归属和“原 staged/unstaged/untracked保持”。
- **失败结果**：不支持条件或 rollback状态，明确原数据是否已经恢复。
- **最小恢复**：拒绝/不支持时保持两边原状；支持但需移动时只索一次 exact effect授权。
- **分类/消费**：recovery；Reviewed runtime/README高级恢复。
- **最终真实证据**：真实支持平台的双脏 linked worktree，含 staged/unstaged/untracked，中断/回滚；不包含主 worktree/submodule/cross-fs。
- **最终候选要求**：同一 candidate exact SHA。Git官方 `worktree move` 限制保持。

### G03 — partial clone mandatory blob

- **用户能力声明**：受检任务即使本地缺必读 blob，也能安全取得并读取，不污染原 Git 状态。
- **普通入口**：`task run` / Reviewed watcher自动消费；没有独立用户命令。
- **内部自动机制**：isolated object dir + original alternate + verified GitHub HTTPS promisor fetch + exact blob read + protected state前后比对。
- **用户成功结果**：任务正常启动；用户不用知道 object dir/OID。
- **失败结果**：明确缺哪个 mandatory source、remote/network/credential/identity哪个前提失败。
- **最小恢复**：恢复网络/凭据/remote identity或冻结 source，再重试同一任务；不让用户手工操作 objects。
- **分类/消费**：daily内部；readiness。
- **最终真实证据**：真实 GitHub HTTPS `--filter=blob:none` 缺 blob正常入口读取，原 refs/index/config/FETCH_HEAD/object store保护不变。
- **最终候选要求**：同一 candidate exact SHA。

### G04 — mandatory source 真消费

- **用户能力声明**：Bridge-managed Lite/Reviewed在 Codex执行前真正读入 frozen mandatory sources；缺源不启动。
- **普通入口**：`ai-bridge task run`；Reviewed watcher/run_codex_event。
- **内部自动机制**：每次 launch边界重新 preflight/bind bytes/hash/content，source明确标成 repo材料不是用户授权。
- **用户成功结果**：真实 child启动且初始上下文包含当前 source。
- **失败结果**：`PRELAUNCH_NOT_READY` + source +恢复动作；attempt不消耗。
- **最小恢复**：提交/恢复/同步正确 frozen source后重试。
- **分类/消费**：daily；README必须正式教 Lite `task run`。
- **最终真实证据**：两个入口都做真实 child canary，source内容改变可观察地影响 child初始行为；路径/grep不算。
- **最终候选要求**：同一 candidate exact SHA。

### G05 — 当前 non-main 同名安全快进

- **用户能力声明**：已有非 main分支严格落后同名 origin时低打扰 FF，不产生 merge/rebase/stash。
- **普通入口**：现有 `ai-bridge host sync-current-branch --expected-repo ... --expected-branch ...`。
- **内部自动机制**：clean/current/tracked/same-origin/same-name/HTTPS/fast-forward检查。
- **用户成功结果**：already-current 或 fast-forward old→new OID。
- **失败结果**：dirty/diverged/wrong upstream/repo/transport具体原因。
- **最小恢复**：用户/Codex处理真实 dirty/divergence；helper不 reset/rebase/autostash。
- **分类/消费**：daily/recovery；README现有说明保留。
- **最终真实证据**：真实 existing branch fast-forward +负例。
- **最终候选要求**：同一 candidate exact SHA。

### G06 — 安全低打扰读取与 wrapper 审计

- **用户能力声明**：常见安全诊断不反复误拦，危险邻近形状仍受保护；用户不用理解 execpolicy规则。
- **普通入口**：Host Policy在 Codex normal use自动消费；`host validate` setup/diagnostic。
- **内部自动机制**：current Codex `execpolicy check` + malicious config probes；只 allow已证明安全的 native shapes。
- **用户成功结果**：安全 branch/worktree/repo identity读取顺畅。
- **失败结果**：危险 `diff/log/show/ls-remote` 邻近仍提示/拒绝，不自动 wrapper。
- **最小恢复**：走普通审批或已有 bounded helper。
- **分类/消费**：内部/setup；Host rules。
- **wrapper审计**：`plugin-replay` 保持 `KEEP_NARROW`；当前 AI Skills maintenance/Reviewed production evidence仍有真实消费者；不扩为通用 Reviewer。
- **最终真实证据**：实际当前 Codex execpolicy + malicious pager/ext-diff/textconv/fsmonitor/transport/helper负例。
- **最终候选要求**：同一 candidate exact SHA。

### G07 — effective instruction byte budget

- **用户能力声明**：Bridge-managed任务不会在规则已经超当前 runtime有效字节预算时仍启动并假装规则完整。
- **普通入口**：Lite/Reviewed preflight自动；`validate --strict` 只用于 setup/diagnostic。
- **内部自动机制**：按当前 runtime discovery/cumulative bytes计算有效规则，UTF-8 raw bytes。
- **用户成功结果**：task正常启动；诊断显示总量/limit。
- **失败结果**：启动前指出总量、limit、主要超量来源，child=0。
- **最小恢复**：精简/移动非必要项目指令，再 `validate --strict`，然后重试同一 task。
- **分类/消费**：daily自动 + setup诊断；readiness/README。
- **最终真实证据**：真实入口超限阻断 + 合法边界 PASS；单独 validator PASS不能代 task run。
- **最终候选要求**：同一 candidate exact SHA。

### G08 — fresh Codex 真消费规则

- **用户能力声明**：最终 Host/项目规则不只存在于文件，而在新的真实 Codex identity/session中实际影响行为。
- **普通入口**：发行验收，不要求日常用户手工跑。
- **内部自动机制**：安装目标 candidate后启动 frozen fresh canary。
- **用户成功结果**：预先定义的规则行为在 fresh session发生。
- **失败结果**：规则未加载、加载错 CODEX_HOME、身份不一致。
- **最小恢复**：回开发；不能用 grep、文件存在或模型自报替代。
- **分类/消费**：final acceptance。
- **最终真实证据**：fresh real Codex。
- **最终候选要求**：同一 candidate exact SHA。

### G09 — stale Host / CODEX_HOME 恢复

- **用户能力声明**：用错/过时 Host时任务先阻断，并给最小恢复；普通 status不会伪造远端新鲜度。
- **普通入口**：task preflight自动；`host status/validate` 诊断。
- **内部自动机制**：核 actual executable/import/source/Host/CODEX_HOME；remote freshness未联网时显示 UNKNOWN。
- **用户成功结果**：ready；local identity和remote unknown分栏。
- **失败结果**：stale/wrong identity + exact目标path。
- **最小恢复**：经用户批准对 exact CODEX_HOME做一次 `host install`，开启 fresh Codex后同 Goal恢复。
- **分类/消费**：daily guard + setup/recovery。
- **最终真实证据**：真实 stale Host阻断、获授权更新、fresh session恢复；final release另做remote exact SHA readback。
- **最终候选要求**：同一 candidate exact SHA。

### G10 — 授权连续性

- **用户能力声明**：用户已经授权的 exact effect不重复问；repo文件不能自授权；scope/provider/data/cost/target改变才重新问。
- **普通入口**：Task Writer/approved Kickoff + Lite/Reviewed/Control/Persistent normal entry。
- **内部自动机制**：task source只定义scope，不把 `authorized=true`/repo字段当用户授权；Host规则读取当前会话授权。
- **用户成功结果**：同一 exact branch/run/publication effect只问一次。
- **失败结果**：真正新 effect时一条最小问题，不权限瀑布。
- **最小恢复**：用户只批准新增差异，不重批整个任务。
- **分类/消费**：daily；task templates/AGENTS/runtime。
- **最终真实证据**：同一任务重复进入与scope变化对照。
- **最终候选要求**：同一 candidate exact SHA。

### G11 — 真实 refusal recovery

- **用户能力声明**：某个 child/Host effect被拒绝后，Bridge不扩大权限、不丢已完成成果，仍完成不依赖该 effect的部分。
- **普通入口**：真实 Lite/Reviewed/Host操作。
- **内部自动机制**：refusal分类，optional vs bounded blocker vs true authority。
- **用户成功结果**：build/QA/commit成果保留；合法路径继续。
- **失败结果**：exact rejected effect +原因；不 raw broad fallback。
- **最小恢复**：仅对真正必要 effect请求一次 bounded授权，或保持 partial/blocked。
- **分类/消费**：recovery。
- **最终真实证据**：真实 Codex/Host refusal，不用 launcher fixture冒充。
- **最终候选要求**：同一 candidate exact SHA。

### G12 — 0.9/0.10 should-not-change

- **用户能力声明**：0.11正常入口收口不破坏已交付 Reviewed bootstrap/resume/publish-first、安全 publisher、Host、安全边界、Persistent基础观察与Notifier旧项目配置/私密同步路径。
- **普通入口**：各自既有命令；Notifier特别包含 legacy `ai-bridge private sync --profile notifier`。
- **内部自动机制**：全回归 +代表性正常任务。
- **用户成功结果**：旧用户工作流不需要迁移到新控制层；旧project notifier config仍是project-local，不会突然提升为machine default。
- **失败结果**：任何旧入口语义漂移阻止发布。
- **最小恢复**：修同一开发分支并重新冻结新版 release candidate。
- **分类/消费**：release regression。
- **最终真实证据**：同一 release candidate直接跑关键旧入口，尤其验证：
  - no-scope `private sync --profile notifier` 仍写current project；
  - existing `.ai-bridge/private/notifier.env` 仍是字段级project override；
  - `send/send-test`、milestone、blocked/awaiting-human、dedupe/retry不退化。
- **最终候选要求**：同一 candidate exact SHA。

### G13 — 0.11.0 release candidate identity

- **用户能力声明**：最终看到的人类版本名、源码 SHA、真实安装、Gate和正式 release一致，不拼多个候选。
- **普通入口**：release流程。
- **内部自动机制**：所有 production source/templates/README/CHANGELOG/version/tests稳定后冻结 `0.11.0-rc.1 @ <exact SHA>`。
- **用户成功结果**：pre-final与 G01–G14/CI都明确写同一个 label+SHA；正式 release推进后remote readback等于该 SHA。
- **失败结果**：任何 production/user-facing contract变化使旧候选失效。
- **最小恢复**：冻结 `0.11.0-rc.2 @ <new SHA>`，按影响重跑 release-critical Gate；不跨 SHA拼证据。
- **分类/消费**：release。
- **最终真实证据**：remote `refs/heads/release` exact readback。
- **最终候选要求**：同一 candidate exact SHA。

### G14 — Persistent Run + Progress thread + Notifications

- **用户能力声明**：一次 Persistent kickoff后真实run、reporter、Progress thread和可选邮件形成完整主动路径；用户不用手工status获取进展。
- **普通入口**：`prompt kickoff -> 用户发送 -> persistent-run start`；查看Codex Progress thread；诊断时 `persistent-run status`。
- **内部自动机制**：
  A. run lifecycle owner启动reporter；
  B. canonical source/cadence/last-delivered；
  C. reporter与用户viewer连接**同一个官方shared app-server**，在其上承载dedicated non-ephemeral tool-free Progress thread；
  D. frozen notification intents；
  E. progress renderer + existing semantic authority验证。
- **用户成功结果**：
  - 至少一次纯cadence主动进度；
  - Progress thread内容与canonical snapshot一致，ETA/UNKNOWN正确；
  - 用户UI在reporter仍active时能打开同一Progress thread/history；
  - viewer连接后reporter还能继续下一次bounded render，不出现active-writer conflict；

  - 原Executor/task thread完全未写；
  - reporter随run结束；
  - Gmail automatic路径仅在intent/authority满足时发送。

- **分类/消费**：daily Persistent + setup Notification + recovery status。
- **最终真实证据**：同一release candidate完整Persistent生命周期；reporter+viewer两个client在同一shared server并发使用同一Progress thread；final Gmail transport与G12 compatibility路径。
- **最终候选要求**：同一 candidate exact SHA。

## 9. 跨 Gate 端到端真实旅程

最终评估不能只把每个 Gate拆成 unit test。至少固定以下真实旅程；能共享同一受控环境就共享，但不能让一个 proxy PASS替另一能力：

1. **fresh-machine-like Bridge/Host setup**：干净/受控 CODEX_HOME identity → install/status/validate → fresh Codex规则消费。
2. **fresh Lite task**：`init -> validate --strict -> task run -> mandatory source -> real Codex`。
3. **existing non-main branch safe sync**：strict FF。
4. **supported worktree conflict recovery**：normal Reviewed/materialize发现 reciprocal conflict → 一次自然语言授权 → helper交换/恢复。
5. **stale Host recovery**：prelaunch阻断 → 获授权修 exact CODEX_HOME → fresh session同任务恢复。
6. **Persistent Run完整生命周期 + shared server topology**：task lifetime分类 → frozen contract → kickoff → discover当前Codex shared server → reporter client → dedicated Progress thread → `start` primary+reporter → cadence；第二viewer/UI client同时打开同一thread → reporter继续后续render → disconnect/reconnect exact binding → runtime terminal → cleanup；另有no-daemon/embedded/remote-binding-unavailable负例。
7. **fresh Gmail setup**：`notifier configure -> status -> send-test`；用户真实输入App Password，不回显。
8. **第二个项目复用machine notifier profile**：不重新填Gmail credential，status按字段显示machine source。
9. **project partial override -> remove -> machine default**：`configure --scope project --target` 只改recipient/from/prefix且继承machine credential；clear project后回machine。
10. **private-sync backward compatibility**：旧无scope `private sync --profile notifier` 仍写current project；只有显式 `--scope machine` 才恢复machine profile。
11. **task notification default/override真实冻结**：project default → Lite/Reviewed freeze；Control Planner draft → Control Critic frozen contract；随后改project default，旧任务intent不变。
12. **Reviewed semantic completion notification**：current Reviewed PASS artifact + frozen intent → automatic notifier → Gmail正例。
13. **Lite对应语义**：Lite frozen semantic field明确 `UNSUPPORTED`；automatic不会假发完成邮件，explicit one-shot仍可用。
14. **same exact 0.11.0 release candidate identity + final release readback**：所有release-critical Gate、CI、安装身份指向同一个 `0.11.0-rc.N @ SHA`；用户随后另批 old release SHA → exact candidate SHA，推进后远端readback确认。

这些旅程的真实 production entry/CLI/render/remote效果是能力证据。unit tests、schema、JSON存在、receipt、fixture只能作为开发回归，不能替代上述旅程。

## 13. 最终外部预算与不换样本

### Fresh Codex

最终不可继续调优的fresh campaign仍最多4个session，exact mapping必须在pre-final冻结为S9的F1–F4：

- F1 = worktree-A；
- F2 = worktree-B，与F1真实并行证明G01；
- F3 = Persistent shared-server G14；
- F4 = Host/authority/refusal/recovery。

development Progress-thread canary仍只有1个Progress thread、isolation PASS后最多2个render turns，是开发机制额度，不是final fresh session evidence，也不因本轮v0.5增加。

第5个session只有存在真正独立失败模式、pre-final Critic同意且用户明确授权才可增加。创建新task/thread编号不能重置预算。

### GitHub

用户另批一个 exact disposable/test repo或分支集合。最多1次 ordinary non-force positive publication；read-only partial clone/fetch可复用。不得 force/delete remote branch/修改消费者repo。

### Gmail

最多2封真实邮件，见 `6.13。账号/recipient/App Password使用必须在真正发送前另获当前用户 exact authorization；本 execution package和未来开发 Kickoff都不预授权真实 Gmail。

### CODEX_HOME / Machine Policy

真实安装只在 pre-final PASS后对 exact路径另获授权；必须有backup/restore。开发回归使用 disposable身份。

### 最终样本

一旦 final 输入产生结果：
- 不因失败换 thread/repo/task；
- 不拼最好一次；
- 只能分类为产品失败、基础设施失败或评审错误；
- 产品修复后形成新的 release candidate label+SHA并重跑受影响 Gate。

## 14. 失败与恢复边界

- Lite mandatory source失败：child不启动，保留同task，修source后重试。
- G02不支持拓扑：两边原数据不动，返回 `UNSUPPORTED_WITH_EVIDENCE`，不尝试 reset/stash。
- isolated blob fetch失败：不污染原 object store；用户只修网络/credential/remote/source。
- Host remote freshness未知：显示 UNKNOWN，不把它当stale；只有实际remote evidence才能判 freshness。
- Persistent contract缺真实 launch/progress evidence：不启动长run。
- shared app-server无法证明或current UI实际走embedded/no-daemon/incompatible override：新primary启动前返回 `PROGRESS_THREAD_SHARED_APP_SERVER_UNAVAILABLE`；不启动daemon/embedded second writer，不用email/latest替代。
- reporter/viewer落在不同app-server或出现 `active writer` conflict：G14-C FAIL；保留primary事实，不自动cancel，停止新的Progress render并要求恢复到同一shared normal entry。
- Progress thread isolation无法机械证明：不启动新 Persistent primary run；已有运行若后续投递隔离失败，不自动cancel primary，标 progress blocker并停止新 render。
- first Progress render后无法materialize/cold resume：G14-C失败，不创建第二thread冒充历史。
- reporter崩溃但primary仍active：`persistent-run start` 同一run可按现有授权边界恢复reporter；不得重复primary。
- progress source不足：显示 UNKNOWN，不推断。
- Gmail未配置/ACL不安全/App Password不可用：自动邮件suppressed + status原因；不改用普通Google密码或另一个provider。
- project notifier clear只移除本地override；status提醒Google端App Password未被撤销。legacy no-scope private-sync若行为漂移到machine scope，视为G12 regression并阻止发布。
- automatic intent缺失：no-send。
- semantic artifact不合法：no semantic completion mail。
- explicit manual send继续只在current-user one-shot路径。
- final release candidate生产字节改变：新 `0.11.0-rc.N`，旧 final evidence不拼。
- 四个 final sessions用尽仍缺证据：停止并请求新预算。
